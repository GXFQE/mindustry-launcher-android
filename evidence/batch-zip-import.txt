批量导入：整包 zip（第 127 轮之二 · 2026-10-10）
================================================

用户原话：「先让导入支持 zip 形式的吧（批量选择依旧麻烦）」
⇒ 这一批做的**不是**"从零加一个 zip 导入"（上一轮已经有了），而是把这条路易用、好用：
   ① 界面上说清"可以选一个 zip"；② 补上真机上**真的会失败**的那两种包；③ 一条都没命中时给句人话。

★ 全部走**真机 + 真选择器**（不是 dev 口）：`adb shell input tap` 点开各页的导入行 →
  在系统 DocumentsUI 里搜 `ziptest` → 点中夹具 zip。夹具放 `/sdcard/Download/`（用户真会放的地方）。


## 一、先确认"已经能用的那部分"（免得修一个不存在的问题）

| 场景 | 夹具 | 结果 |
|---|---|---|
| 地图页选一个装了 2 张 `.msav` 的 zip | `mdt-ziptest-maps.zip` | ✅「批量导入结果 / 共处理 2 份 / 导入成功：2 / 从 mdt-ziptest-maps.zip 里解出 2 份」 |
| 模组页选一个装了 2 个模组包的 zip | `mdt-ziptest-mods.zip` | ✅ 2 份落位（`betterMiniMap.jar` / `dep-base.zip`） |
| zip 能不能在系统选择器里被选中 | —— | ✅ 能（`*/*`，选择器里列得出来、点得中） |

⇒ 也就是说：**"导入支持 zip"本身上一轮就通了**，缺的是下面两条 + 发现性。


## 二、真机上真的会失败的那两条（本轮修的）

### 1. 「一个模组一个文件夹」打成的 zip（模组页）

夹具 `mdt-ziptest-modfolders.zip`（424 B）= `foldA/mod.hjson` + `foldA/scripts/main.js` + `foldB/mod.hjson`。

* **改前**（真机原话）：点下去 ⇒ 「导入失败 / ❌ 没做：这个包不是游戏能加载的模组」
  —— 用户明明是想批量导入，却被按"**一个**模组包"去验，验不过就报这么一句。
* **改后**：✅「批量导入结果 / 共处理 2 份 / 导入成功：2 /
  从 mdt-ziptest-modfolders.zip 里认出 2 个模组文件夹，各自打成了一个 zip」，
  槽里落位 `foldA.zip`（295 B）/ `foldB.zip`（163 B）—— 每个都是"根上有 mod.hjson"的包形状。

判据：`BatchIo.modFolderNames`（**只认一级**：`<目录>/mod.hjson`；`foldB/deep/inner/mod.hjson`
不算 —— 那是模组内部的资源）+ `BatchIo.extractModFolders`（各自 `Exporter.zipDirFlat` 打成一个 zip）。

### 2. 是 `.zip`、可一条都没命中 ⇒ 旧代码给不出人话

夹具 `mdt-ziptest-nohit.zip`（230 B）= `readme.txt` + `data/thing.bin`。

* **改前**：这种包只能按普通文件丢给单份导入 ⇒ 地图页报的是「不是有效的地图」那种话
  （用户看不懂：我明明选的是个 zip）。
* **改后**：✅「批量导入结果 / 共处理 1 份 / 跳过：1 /
  mdt-ziptest-nohit.zip — 这个 zip 里没有能导入的东西（找的是 .msav）」

根因：旧的 `bundleNames` 只有两态（命中条目 / `null`），而 `null` 同时代表
「**根本不是 zip**」（真存档 / 真地图就是 zlib 流，必须走单份那条老路）与
「**是 zip 但没命中**」⇒ 后者没法单独说话。现在改成三态 `BatchIo.Probe`
（`zip` / `selfPack` / `hits`）。


## 三、为什么"改前"会漏掉模组夹：**判据写了两份**

界面那条路（`runImport`）与 dev 口 / 自检那条路（`importSync`）各写了一遍"选回来的文件怎么摊成条目"，
于是 dev 口验过的（上一轮的整包往返）与界面能做的**不是同一套**。
⇒ 本轮把这段收进 `BatchIo.expand`，两条路共用一份 —— 模组夹这条也因此一改两通。


## 四、本轮的坑（都进了自检）

🔴 **同一个 `InputStream` 不许读两遍**：`extractModFolders` 第一遍认模组夹、第二遍才解包，
最初把**同一条流**传了两次 ⇒ zip 是顺序流，第二遍读到 0 个条目 ⇒ 自检当场报
「每个模组夹各自打成一个 zip（**0 个**）」。修法 = 传"再开一条流"的钩子 `BatchIo.Reopen`。


## 五、验收数字

* 自检 **1052 → 1062 通过 / 0 失败**（新增 10 条：第三态、模组夹识别 / 打包形状 / 端到端落位、
  路径穿越 `safeRel`、`.zip` 与 `.jar` 的区分、两种"没有内容"的报告，另加两条反向）。
* 界面文案：四个导入行 + 两个导出行的副标题都写清"可多选，也可选一个 zip 整包"。
* 真机证据截图：`evidence/batch-zip-modfolders.png`、`evidence/batch-zip-nohit.png`。

## 六、没做的

* **多选那个系统选择器本身**（长按勾选）改不了 —— 那是系统 DocumentsUI 的交互，
  我们能做的就是把"一个 zip"这条替代路写清楚、并且真的能用（本批做的就是这个）。
* 整包里再套整包（`mods.zip` 里放 `inner.zip`，`inner.zip` 里才是模组）：**没做**
  （`extractBundle` 只解一层）。
