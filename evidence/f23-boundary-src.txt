F23 收尾批（2026-10-08，第七批）—— 三条尾巴的定案证据
=====================================================

设备：HONOR ELP-AN00 / Android 16 (API 36)
产物：本地构建的 **dev 变体**（`DEBUGGABLE=true SUFFIX=-dev`），自检 1022 通过 / 0 失败
实验槽：新建的 `datalab2`（**不碰用户槽**；收尾已删、配置与槽指针已还原 —— 见 §4）
源码：`Mindustry-master.zip`（`素材/Mindustry本体/`）、`Arc-159.7.zip`（`素材/Arc/`）

本文件回答三件事：
  ① 行星 / 渲染 / 环境类崩溃 —— 要不要做归因？
  ② 蓝图 / 地图 / 存档"数据损坏"族 —— 要不要做"非模组原因"？
  ③ `Patches:` 段能不能当"谁打了数据补丁"的旁证？


§1 结论先行（每一条都有下面的逐字证据）
----------------------------------------
1. **地图 / 存档 / 蓝图损坏：结构上不可能产生崩溃报告** ⇒ 不需要 CAUSE_DATA。
   游戏自己用 `catch(Throwable)` 把整条读档链路包住了（连 `OutOfMemoryError` 一起收），
   然后弹一句人话、回主菜单。⇒ 归因器在这条路上**永远没有输入**。
   ★ 所以"把地图尺寸字段改成极大"这种 OOM 型坏法**也不必再试** —— 它抛出的 OOM 同样在
   `SaveIO.load` 里被包成 `SaveException`、再被 `World.loadMap` 的 `catch(Throwable)` 收掉。
2. **图形 / 显存类（`Frame buffer couldn't be constructed` / GL 1285）：不做。**
   语料里只有**桌面**样本；用户 2026-10-07 已把它定为**本机显卡驱动/环境问题**、
   明确"不建议为此设计归因"；安卓 12 份真机报告里图形类签名 0 处。
3. **行星渲染类：不做。** 语料里 `Planet` 一份都没有（连桌面样本都没有）。
4. **`Patches:` 段：不做归因**（结构上不能点名）、**也不加展示**（安卓侧 0 真实输入）。
   理由见 §3 —— 报告里打印的是**补丁正文**，`PatchAsset` 没有任何 mod 归属字段。
5. **内存不足（`OutOfMemoryError`）例外，要做** —— 它有安卓真机输入
   （`docs/crash-corpus/03-蓝图.md` §3.1，`Android API level: 31`），而且**逃逸路径清楚**：
   它崩在界面构建（`SchematicsDialog.setup`）而不是读档链路里 ⇒ 没人接 ⇒ 走到默认
   未捕获处理器 ⇒ 真的写了报告。⇒ 已实现为 `CrashAnalysis.CAUSE_OOM`（只给"认不出"补一句原因，
   **不参与点名**）。

§3 `Patches:` 段为什么不能当旁证（源码级）
-----------------------------------------
3.1 它打印的是**补丁正文**，不是来源
    `Mindustry-master/core/src/mindustry/net/CrashHandler.java:45`
        + (state != null && state.data != null && state.data.getPatches().size > 0
             ? "\n\nPatches: \n" + state.data.getPatches().toString("\n---\n", p -> p.patch) + "\n" : "");
    ⇒ 逐份打印 `PatchAsset.patch`（**原始文本**），`\n---\n` 分隔。

3.2 `PatchAsset` **没有**任何 mod 归属字段
    `Mindustry-master/core/src/mindustry/mod/data/PatchAsset.java`
        public String patch = "";        // 原始文本
        public JsonValue json;           // 解析后的值
        public boolean error;
        public Seq<String> warnings;
        （加上基类 `DataAsset` 的 `path` / `name` —— **但报告里不打印它们**）
    ⚠️ 连 `path` 都不可靠：`PatchAsset(String patch)` 的构造注释写着
       "patches don't have a path by default, so make it something random when reading."

3.3 正文里那个 `name:"…"` **不是模组名**
    `Mindustry-master/core/src/mindustry/mod/DataPatcher.java:251~252`
        set.name = value.getString("name", "");
        value.remove("name"); //patchsets can have a name, ignore it if present
    ⇒ 它是**补丁集自己起的名字**（作者随手写的），不参与打补丁逻辑、也不含 internalName。
    语料里的实例（`docs/crash-corpus/08-其它游戏侧异常.md` §8.14）：
        Patches:
        name:"世处ipt提高上限"block.world-processor.maxInstructionsPerTick:100000
        ---
3.4 真实输入有多薄：120 份语料里 **4 份**带 `Patches:` 行，其中 **3 份是空段**，
    唯一非空的那份是**桌面 Windows + MindustryX** ⇒ **安卓侧 0 份**。
    ⇒ 按本项目的老规矩（别给没有真实输入的地方加判据）**不加展示**。

§5 这一轮**没做**的（诚实清单）
-------------------------------
1. **没有真的在 GUI 里点进「自定义游戏 → 选 oomtest → 开始游戏」那一步**。
   原因是搜索框没吃进 `adb shell input text`（libGDX 的文本输入要 IME 连接），而地图列表
   有 114 张内置图 + 2 张夹具，滚动定位代价高。
   ⇒ 但"开局那条路不会产生报告"这一点由 §2.3 的 `catch(Throwable)` **源码级**定案，
     并且**上一轮**已经在真机上点过一条同族的路（`crash-corpus/15` §2 的 `4cutinner`：
     开局 ⇒ 弹「加载地图时出错。地图文件损坏或无效。」⇒ 无报告）。
2. 蓝图的"`Too many blocks` / `Too large`"这两种**校验型**失败没造（要摸块数/尺寸字段的偏移）。
   本轮用的是"改头"与"截断"，都落在 `Schematics.read` 的同一条 catch 上。
3. 没有试"世界数据里数值合法但语义荒谬"的坏法（上一轮也列着，未做）。
