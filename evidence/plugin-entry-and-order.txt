# 第 135 轮证据：插件自述（入口类一插件一份）+ 注入顺序（第三方优先）

用户 2026-10-12 定的两条口径：
- **「让第三方肯定可以覆盖官方」** ⇒ 同名类冲突时第三方赢（`injectOrder`：官方先注入、第三方后注入）；
- **保持"插件能盖宿主未加载的类"**（不收紧）——`[插件们][宿主自己 dex]` 这个既有事实不变；
- 入口类**一插件一份**（从插件自述读：`assets/plugin.json` → 清单 `meta-data` → 默认 FQN）。

## 1) 注入顺序：两遍对调，规则不吃安装顺序

```
A: 官方(o1) 先装 → 第三方(t1) 后装      active.txt = o1=1 t1=1
   启动报告  order  = o1=1(official) t1=1(third)
   host tag PluginProbe = PLUGIN-tp        ← 同名类归**第三方**
B: 第三方(t2) 先装 → 官方(o2) 后装      active.txt = t2=1 o2=1
   启动报告  order  = o2=1(official) t2=1(third)     ← 顺序被规则重排了（不是文件顺序）
   host tag PluginProbe = PLUGIN-tp        ← **仍然**归第三方
```
★ `order` 那一行就是判据（报告里直接打出来，不靠猜）；两遍结论相同 ⇒ 规则由"来源 + 登记表"决定，
**跟安装顺序无关**（这正是用户要的"第三方肯定能盖官方"）。
★ 判据怎么读：`PluginProbe` 是**同名宿主类**（壳里也有一份），`dev_pluginstatus` 读的是
**宿主 CL 里真正解析到的那个类**的 tag ⇒ 它归谁就是谁赢了。

## 2) 自述入口类：一插件一份（真机）

```
启动报告:
  order  = o1=1(official) t1=1(third)
  - o1=1 file=1.apk entry=v1.PlugPage         INJECTED … entry=OK api=1
  - t1=1 file=1.apk entry=thirdparty.PlugPage INJECTED … entry=OK api=1     ← 两行入口**不同**
```
★ 报告里打的是"**包名尾段 + 类名**"（只打简单名两行会一模一样 —— 夹具正是"同名类、不同包"）。

## 3) 界面「点谁开谁」（第 134 轮那个 bug 的修复验收）

```
★ 点 o1（官方那行）⇒ 页面 = 来自插件的字符串  [PLUGIN-v1]     ← 它自己的类
★ 点 t1（第三方那行）⇒ 页面 = 来自插件的字符串  [PLUGIN-tp]   ← 它自己的类
```
（第 134 轮同样场景下，点文件里靠后的那个插件渲染的是**第一个**插件的类；现在各是各的。）
判据 = 夹具入口页把编译期 tag 打进页面文字（`PlugPage.tag()`，第 134 轮加的）。

## 4) 诚实报告：入口类被人先定义过要**说破**

两个**没有自述**的插件（都回落默认入口 `io.mdt.plugtest.PlugPage`）：
```
  - k1=1 file=1.apk entry=plugtest.PlugPage INJECTED … entry=OK api=1
  - k2=1 file=1.apk entry=plugtest.PlugPage INJECTED … entry=OK api=1 SHARED(entry class already defined by k1)
```
★ 没有这行标注的话，第二条的 `entry=OK api=1` 是**骗人的**（它命中的是 k1 的类）。
★ 老插件（没写自述）照旧能加载 —— 这是**向后兼容**那条判据。
