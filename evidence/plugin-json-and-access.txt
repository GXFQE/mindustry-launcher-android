# 第 148 轮证据：扩展点声明搬到 JSON + 权限与数据目录的约定（C 的前半）

用户 2026-10-14 定：「**真的不如使用 json，后面还好扩展**」＋「**现在地基以及交互还差什么**，
实际拆启动器功能估计挺麻烦先不急」⇒ 本轮做 **A（JSON）+ C（权限与数据目录）**。

## 1) A：声明格式搬回 JSON（承认上一轮的理由站不住脚）

第 139 轮我把扩展点声明做成了"每行一条"的 `assets/extensions.txt`，理由是"极简 JSON 解析器只吃平铺对象"。
**查证后这条理由当时就不成立**：`org.json` 是**框架自带**的（android.jar 里就有），
本工程 `Config.java` 早就在 `import org.json.JSONObject/JSONArray` 解析嵌套数组。

⇒ 改法：声明回到自述 `assets/plugin.json` 里，用 `org.json` 解：

```json
{
  "entry": "io.mdt.plugtest.v1.PlugPage", "name": "plugtest-v1", "version": "1",
  "author": "mdt-fixture", "description": "plugtest-v1 fixture",
  "access": ["slots", "telepathy"],
  "extensions": [
    { "id": "plugtest-v1-tool", "title": "plugtest-v1 tool",
      "subtitle": "opens a page from plugtest-v1", "entry": "io.mdt.plugtest.v1.PlugPage" },
    { "id": "broken", "title": "missing entry" },
    { "id": "later", "title": "future slot", "entry": "io.mdt.plugtest.v1.PlugPage", "slot": "tomorrow" }
  ]
}
```

- **删掉 `extensions.txt`**，不留双格式（两套格式并存 = 判据两处必漂，本工程的老账）；
  `grep extensions.txt` 在 `app/src`、`app/src-dev`、`tools/plugtest` 里 **0 处残留**。
- 夹具里**故意混两条坏样本**：`broken` 没有 `entry`（该被丢掉）、`later` 用宿主不认识的插槽（该被跳过）
  ⇒ 两者都不许影响那条好条目。

## 3) C 定了什么（以及**它不是什么**）

- **C2 已完成（读取 + 告知）**：自述里的 `access` 数组 ⇒ 插件信息弹窗**永远显示一行**
  （没有声明就明说「没有额外声明」）：安全相关的字段**留白是歧义的**（用户分不清"没声明"和"我们没看见"）。
  名字**原样列出**（含宿主不认识的，比如 `telepathy`）——用户有权知道插件要什么。
- **C2 的另一半是"构造上就成立"**：宿主**从来不主动**把槽 / 存档 / 模组的路径交给插件；
  插件拿到的只有一个 `Context`（见下）⇒ "未声明就不给现成入口"目前是**没有入口可给**。
- **C1-a 已完成（代码）**：插件拿到的 `Context`（`PluginHost.PContext`）把
  `getFilesDir()` / `getCacheDir()` 指到 **`<插件>/data`**、**`<插件>/cache`**
  （与它的 APK 同住 `<plugins>/<id>/` ⇒ 将来"卸载连数据一起收拾"只需要动一个目录）。
  ⚠️ **懒创建**：插件不调 `getFilesDir()` 就不会有那个目录。
- 🔴 **必须说清楚（口径）**：宿主与插件**同进程、同 ClassLoader** ⇒ 上面这些是**约定 + 告知**，
  **不是沙箱** —— 插件真要自己拼 `/data/data/io.mdt.launcher/...` 我们拦不住。
  想真隔离只有两条路：独立进程（像 `:game`）或 Android 的 isolatedProcess（那样插件就拿不到我们的 Context）。
  **拿它当沙箱用会出事。**

## 4) C1-b（收官补做）：插件数据目录 + **卸载搬进中转站**（真机验过）

```
① 插件写"自己的数据"落到哪（夹具 createView 里调 ctx.getFilesDir() 写一个文件）：
   app_hub/plugins/probe/            →  2ed851ab.apk   data
   app_hub/plugins/probe/data/       →  plug-test.txt        ← ✅ 落在**插件自己的目录**里
   （上一轮这条"没验到"，原因是懒创建 + 夹具还没调用过 getFilesDir()）

② 卸载（外部夹具 x2，tab 内点「删除」）：
   app_hub/plugins/x2                →  **没了**
   hub/plugins-trash/20261014-223003-886__plugins__x2/   →  1.apk      ← ✅ 整台进了中转站
   （内部 → 外部是**跨卷**：靠 `Trash.move` 的"renameTo 失败 ⇒ 复制 + 校验长度 + 才删源"）
```
⚠️ **我第一遍点错了行**：夹具自述名都叫 `plugtest-v1`，内置那条与外部那条**同名** ⇒ 我点到内置
（它本来就不给删，"弹窗里没有删除"是**正确行为**），于是什么都没发生。换名字唯一的夹具才是有效实验
—— 与 §85.16.3「测试辅助别按界面文案定位」同族：**同名两行时，按键要按位置/唯一特征**。

## 4b) 还没做的（如实说）

- **一键恢复没做**：`plugins-trash` 里的件被归成 `Kind.OTHER`，而 `Trash.restore*` 对 `OTHER` 会
  直接返回 `T_NO_KIND`（"unknown kind"）⇒ 用户目前**看得见、能手动取回**，但**不能一键恢复**。
  做它要新增 `Kind.PLUGIN` + `kindIn` 映射 + 恢复目标（`Plugins.dir`）+ 中转站文案。
- **卸载失败界面没说话**：`uninstall` 搬不动时返回 `false`（**刻意不退化成删除** —— 删了就真没了），
  但插件页还没把这个 `false` 说给用户听。


1. ✅ **私有目录那条已在收官时验到**（见上面 §4）：夹具写 `getFilesDir()` ⇒ `<插件>/data/plug-test.txt` 出现。
2. ✅ **那条"写错 API"的教训仍然成立，但结论已经补全**：真正的搬运是 **`Trash.move(src, dst)`**
   （renameTo 失败 ⇒ 复制 + 校验长度 + 才删源）；`Trash.remove` 是"从中转站彻底删"。**收官时已改用 `Trash.move`**，
   并刻意让"搬不动"**返回 false、保持还装着**（绝不退化成删除）。
