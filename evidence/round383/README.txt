第 383 轮证据：所有缓存类数据合并给一个自动清理开关
====================================================

用户原话（四句，前两句是起点、后两句是最终口径）：
  「最底下那个可以清理的残留是什么鬼啊」
  「还有我们是不是应该把自动清理残留和这个合并」
  「反正这些都是可以自动清理的，不如合并到一起」
  「不如把所有缓存类的东西都合并给一个自动清理的开关」

结论
----
1. **存储占用卡**：原来的「清理游戏缓存」「清理分享缓存」两个按钮 + 底部「可以清理的残留」段
   → **一个「清理」**（`Cleanup` = 游戏缓存 + 分享缓存 + 旧版本重复文件），立即清一次、不受时限。
2. **设置页**：那一行从「自动清理残留」→「**自动清理缓存**」，一个开关管三样：
   - 游戏缓存（`getCacheDir` + `getCodeCacheDir`）
   - 分享缓存（**只清超过 1 小时**的，接收方可能还在读）
   - 旧版本重复文件（`Data.autoCleanRedundant`，只删有正证据的）
3. **自动触发**：主进程**冷启动**时检查一次；开关开、游戏没在跑、距上次 ≥ **24 小时**才清
   （时间戳 `app_hub/auto-clean.txt`）。不是每次启动都清 —— 否则每次拉起游戏前都把音乐/模组
   缓存删掉，下次启动更慢。进存档页不再清（`SlotsActivity.autoHealth` 已删）。
4. **安全边界**：`CacheClean` 现在把"启动占位"也算作"游戏要跑了"（更严于
   `CacheEpoch.otherInstanceRunning`）；拿不准时拒绝清理。存档 / 模组 / 地图 / 蓝图 / 导入包 /
   启动器数据一律不动。

改动文件
--------
- 新增 `Cleanup`：三样清理的编排 + 24h 调度 + 时间戳；`Cleanup.run`（手动，分享全清）/
  `runAuto`（自动，分享 1h 宽限）/ `autoDue` / `markAuto`。
- `CacheClean`：`anyGameStarting` = 运行实例 + 启动占位，拿不准也拒绝。
- `LauncherApp`：Config.load 之后调 `Cleanup.autoCleanInBackground`（自己起后台线程）。
- `SlotsActivity`：删掉 `autoHealth`（不再进页面就清）。
- `Storage`：不再 `healthScan`、不再列「可以清理的残留」（存储页只回答"空间被什么占了"）。
- `SettingsActivity`：存储卡一个「清理」；设置行改成「自动清理缓存」+ 解释弹窗，只留开关。
- `PluginData.storage()`：插件 API 的 `redundant` 键保留、按需现算（`storage()` 本来就是重接口）。
- 删掉 19 个只服务于旧两个按钮 / 旧残留行的字符串；新增 9 个。

自检
----
`selftest-383.txt` = **2308 项通过 / 0 失败**（第 382 轮基线 2304；+4 = 统一清理 3 + 确认文案 1 +
自动清理 2，另删掉旧的分享按钮断言 / 残留行断言各 1）。新增：
  ✅ ① 一个动作跑完三样（缓存 / 分享 / 重复文件），并合计释放量
  ✅ ② 游戏在跑 ⇒ 只跳过游戏缓存，分享 / 重复文件照清
  ✅ ③ 没东西可清时 any()=false
  ✅ ④ 自动清理只清超过 1 小时的分享件（新的那份留着）
  ✅ ⑤ 自动清理每 24h 最多一次；没记录算到期、时钟回拨也算到期
  ✅ ★一个「清理」的确认文案说清三样 + 不动的数据

真机验收（详见 `cleanup.txt`）
-----------------------------
- 第一次冷启动（无时间戳）：`auto cleanup: cache=cleared 9 entr(ies) / 152 B share=1/3B dup=1/21B`；
  旧分享件 / 假 config.json / cache 探针全消失，**新分享件保留**，时间戳落盘。
- 第二次冷启动（1 分钟内）：cache 探针**保留**，没有新的 auto cleanup 日志（24h 节流生效）。
- 设置行「自动清理缓存 / 自动清理：开」，点开解释包含"每天最多一次 / 超过 1 小时 / 不动存档模组"。
