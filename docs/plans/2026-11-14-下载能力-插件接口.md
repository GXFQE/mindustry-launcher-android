## 3. 下载核心（宿主侧）—— 研究结论，不重复论证

只列要落进代码的定案（细节与实测数字见研究文档）：

1. **续传协议**：`Range: bytes=<offset>-` + **手动跟 302（≤5 跳，每跳重带）** + `Accept-Encoding: identity`；
   200 ⇒ 截断重下；206 ⇒ 校验 `Content-Range` 的起点与总长；416 ⇒ 总长反推，满了就校验、不满就重来。
2. **不信任 206**：镜像会回 `206` 却是错误页（实测 `Content-Range: bytes 0-1023/1901`）⇒ 总长对不上就换源。
3. **`If-Range` 只当优化**：实测服务端会忽略过期 ETag，照样回 206 ⇒ 唯一信任根是**长度 + sha256**。
4. **取消 ≠ 失败**：`CANCELED` / `NETWORK` 保留 `.part`，`SIZE` / `SHA` 才删。
5. **限速用虚拟时钟**（不是每个任务各自 sleep）：所有下载共用一个额度，`reserve(n)` 返回该睡多久；
   单任务时等价于研究稿的 Pacer（256 KB/s 实测 255.2 KB/s、取消 7 ms）。
6. **签名 URL 不落盘**：GitHub 302 的目标带 `se=`（一小时过期）⇒ `.meta` 只存**原始 URL**。

## 4. v43 接口草案

### 4.1 下载

```java
// ① 旧签名保持**今天的行为**：一次性子目录、失败 / 取消删半截、不续传
Task download(String url, String expectedSha256, Download callback);

// ② v43：插件显式决定续不续。key 是稳定身份（落点 = downloads/<key>/），resume 是开关
Task download(String url, String expectedSha256, String key, boolean resume, Download callback);

// ③ 进度：default 方法 —— 老插件（只实现 onDownload）照跑，不会 AbstractMethodError
interface Download {
    void onDownload(Result result, File file, String sha256);

    /** v43：主线程回调，宿主节流到 ≥250 ms 一次；total = 0 表示不知道。 */
    default void onProgress(long done, long total, long bytesPerSec) { }
}

// ④ 跨页面 / 跨进程恢复 UI（列表行显示"继续下载 45%"）。null = 没有这份记录
//    只 stat + 读小文件，可以直接在 UI 线程调
DownloadState downloadState(String key);

public final class DownloadState {
    public final String key;
    public final long done;        // 已落盘（含续传偏移）
    public final long total;       // 0 = 不知道
    public final boolean complete; // 成品在且 sha 对得上
    public final File file;        // complete 时非 null
}
```

语义（全部要写进 `docs/PLUGIN-API.md`）：

| 项 | 规则 |
|---|---|
| `key` | 仅 ② 用：`[A-Za-z0-9._-]{1,64}`，不许 `.` 开头、不许路径分隔符；非法 ⇒ `invalid`；同一 key 已有任务在跑 ⇒ 第二个 `busy` |
| 落点 | ②：`<插件 cache>/downloads/<key>/<清洗过的文件名>`；①：一次性子目录（**不变**）。都不出插件 cache |
| `resume=true` | 同 key 已有 `.part`（且 meta 的 sha / size 与本次一致）⇒ 接着下；取消 / 网络断 ⇒ **保留** `.part` |
| `resume=true` 的缓存命中 | 成品已在且 sha 匹配 ⇒ 直接 `ok`，**一个请求都不发** |
| `resume=true` 的前提 | **必须给 sha256**（空 ⇒ `invalid`）：没有内容锚，续出来的文件无法证伪。来源见 §4.1.1 |
| `resume=false` | 忽略已有半截（从 0 写）与成品（**不**命中）；失败 / 取消删半截；**新文件校验通过后才替换旧成品**（重下失败不丢旧的） |
| 服务端不支持 Range | 自动整包重下（`resume` 是"允许续"，不是"保证续"），不报错 |
| 进度 | `done` 含续传偏移；`bytesPerSec` 宿主算好（别让每个插件自己算）；页面关掉后回调仍可能到达 |
| 限速 | 吃用户设置（`download_limit`，0 = 不限），插件**不可覆盖**；`settings()` 加只读键 `download_limit` |
| 并发 | 宿主全局并发 2（含宿主自己的下载，见 §8-1）；超了 ⇒ `busy`（插件自己排队重试） |
| 体积 | 1 GB 上限不变（边下边查）；`size` 码不变；**开下前新增磁盘余量检查**（`getUsableSpace`，现在全工程零调用） |
| 清理 | `.part` 超 7 天且无活动任务 ⇒ 宿主删；成品不自动删（插件装完自己清） |
| 安全 | https only（本机回环除外）；`.meta` 不存 token；key 防 `../` |

### 4.1.1 清单里的 sha256 从哪来（GitHub 现在自带）

| 源 | 有没有 sha256 | 说明 |
|---|---|---|
| **GitHub release 资产** | ✅ `assets[].digest` = `sha256:<64 hex>` | 2026-11-14 实测本仓库 5 个 release / **11 个 asset 全有**（含更早的 v0.5）；同一个列表响应里就有，**不额外花 API 配额** |
| mdtbbs 资源 | ✅ `content_hash` | V1 manifest 与 legacy 列表都带 |
| 自定义清单 / 插件自建索引 | 看清单自己 | 没有就只能 `resume=false` |
| 裸 URL（`raw.githubusercontent.com`、任意直链） | ❌ | 同上 |

⚠️ 边界：

- `digest` **只覆盖 release 资产**：GitHub 自动生成的源码包（`zipball_url` / `tarball_url`）没有；
- 下载响应头里的 `X-Ms-Blob-Content-Md5` 是 **MD5**，别当 sha256 用；
- 老资产可能没有 `digest`（本仓库实测都补了，但别许诺所有仓库都有）⇒ 解析层按"可选"处理。

⇒ 需要动的只有解析层：`GitHubReleases.parseStrict` 读 `digest`（去掉 `sha256:` 前缀、校验 64 位 hex、
其它算法 / 认不出 ⇒ 空），`PluginApi.GitHubRelease.Asset` 加 `sha256` 字段
（**3 参构造器保留**，老插件不受影响）。

### 4.2 装进槽：`modsInstall`

```java
/**
 * v43：把一个模组包装进某个槽的 mods/（**走宿主自己的导入链**）。
 *
 * @param slot      槽；null / 空 = 当前槽
 * @param name      完整文件名（必须 .jar / .zip；规则与宿主 checkPackName 同一份）
 * @param content   包字节（宿主读完关闭）
 * @param overwrite false 时同名 ⇒ exists；true 时旧件**挪进中转站**（不是裸删）
 *
 * 异步：拷贝 + 校验在后台线程，回调回主线程（88 MB 的包不能占着 UI 线程）。
 * 宿主做：WriteGate（这个槽有实例在跑 ⇒ game-running）→ checkPackName →
 *         Mods.importPackage（readOne 游戏判据）→ 旧件进 trash → 原子改名
 * 失败码：not-found / invalid / exists / not-a-mod / game-running / io
 */
void modsInstall(String slot, String name, InputStream content, boolean overwrite, Done done);
```

**为什么不让插件用 `addItem` + `writeItem` 自己拼**（这是本设计最重要的一条）：

- `addItem` 明写「宿主只做路径 / 后缀 / 槽名 / 原子写，**不做内容校验**」⇒ 插件装进去一个
  `mod.hjson` 都没有的包，游戏不认，用户只会觉得"下载完没反应"；
- 覆盖已有模组要走 `writeItem`，它**不把旧件进中转站**——宿主的"挪不删"红线在插件这条路上就断了；
- 游戏自己的判据是 `Mods.readOne`（含 `parts()` / `willFailJavaLoad`），插件没有这个类；
- 现有 `writeItem` 是**同步**的（拷贝 + fsync 都在调用线程）——88 MB 的包走它会卡住调用方；
- 同一条规矩已经吃过一次亏：AGENTS「同一件事有两条路时，判据必须共用一份实现」（§88.11）。

### 4.3 启用 / 停用：`modsSetEnabled`

```java
/**
 * v43：改某个槽里一个模组的启用状态（游戏设置里的 `<internal>-enabled` + `-failed` 成对写）。
 * @param internalName 模组自述里的内部名（mod.hjson 的 name）——不是文件名
 * 失败码：game-running / unreadable / not-found / invalid / io
 */
void modsSetEnabled(String slot, String internalName, boolean on, Done done);
```

宿主直接转 `Mods.setEnabled`（同一份实现、同一份设置备份），**不新增判据**。
`download_count` 之类统计不归宿主。

### 4.4 认证下载（mdtbbs）—— 降到备选，本期不做

★ 2026-11-14 用户提醒「anuken 给模组列表了」⇒ **发现层已经不需要 mdtbbs**（见 §4.5）；
mdtbbs 剩下的价值只有"国内镜像 + 中文社区索引"，而它的文件下载要登录。

2026-11-14 实测：`GET /api/v1/resources/…/download` 返回
`401 RESOURCE_DOWNLOAD_AUTH_REQUIRED`（"登录后才能下载此类资源"），而 manifest 匿名可读。
所以"模组清单"能匿名拉，**文件下载要登录**。

三条路，本期只走第 1 条：

1. **v43 只做匿名源**（官方列表 + GitHub release / zipball、直链、以后公开的 CDN）——先把断点 / 限速 / 安装跑通；
2. **宿主登录态**（以后）：宿主做 OAuth PKCE，拿到 token 后由**宿主下载器**对该域名自动带
   `Authorization`；插件只给 URL，**永远拿不到 token**。跨域 302 必须丢头（签名 URL 自己带权限）。
3. ❌ 不给插件"自定义 header"——一开这个口，token、镜像前缀、Cookie 全回来了，等于没设计。

> 结论：mdtbbs 的登录是**另一条线**（宿主登录 + 账号页），和本设计解耦；本设计只保证
> "换成一个带登录态的 URL 也能用"（下载器不需要知道认证细节）。

### 4.5 模组源：Anuke 官方列表（2026-11-14 实测）

Mindustry 自己的模组浏览器就用它，**不需要登录**：

| 项 | 实测 |
|---|---|
| 地址 | `https://raw.githubusercontent.com/Anuken/MindustryMods/master/mods.json` |
| 体积 / 条数 | **725,388 B / 1,015 条** |
| 字段 | `repo` / `internalName` / `name` / `author` / `description` / `version` / `minGameVersion` / `lastUpdated` / `stars` / `hasIcon` / `hasJava` / `hasScripts` / `iconHash` |
| 下载地址 | ❌ 没有（列表只给 GitHub 仓库） |
| sha256 | ❌ 没有（要另外拿） |

**游戏自己怎么装**（`ModsDialog.githubImportMod`）：`GET /repos/<repo>` 拿默认分支 →
`GET /repos/<repo>/releases/latest` 找一个 `.jar` 资产（优先 `dexed*.jar`）→ 下载
`browser_download_url`；**没有 release 资产时退化成 `/zipball/<branch>`**。

两种下载形态实测差别很大（这条决定能不能续传）：

| 下载形态 | Range | sha256 |
|---|---|---|
| release 资产（`.jar`） | ✅ 206（`Content-Range` / `ETag` 正常） | ✅ API 的 `digest` |
| `zipball`（源码包） | ❌ **`Range: bytes=0-1023` 回 200 + 整包**（实测 292,814 B），无 `Accept-Ranges` | ❌（只有一个 ETag，不是可信哈希） |

抽样 8 个模组（每 127 条取一个）：**3 个有 `.jar` release 资产且有 digest**、2 个有 release 但没资产、
3 个没有 release ⇒ 约一半能续，另一半只能 `resume=false`。

**对 v43 的三点影响：**

1. **列表 725 KB > `fetchText` 现在的 512 KB 上限** ⇒ 加 **`fetchText(url, int maxBytes, cb)`**
   重载（宿主钳到 2 MB，默认仍 512 KB）。否则插件连官方列表都拉不下来。
   ⚠️ 725 KB JSON 解析别放 UI 线程（回调在 UI 线程，插件自己扔后台）。
2. **列表没有 sha** ⇒ 插件顺序应是：`githubReleases(repo)`（1 次 API，带 `digest`）→ 有 `.jar` 资产就
   `resume=true`；没有就 zipball + `resume=false`。配额按"选中某个模组才查"算，40 次/小时够用
   （同一 repo 10 分钟内走缓存）。
3. **图标是二进制**（`icons/<owner>_<name>`，实测 1,023 B PNG、`application/octet-stream`）⇒
   现在只有 `download` 能拿二进制，而它会起任务 + 通知 ⇒ 列表要图标就得加
   **`fetchBytes(url, maxBytes, cb)`**（上限 256 KB，同步小请求）。

⚠️ 顺带：当前 `githubReleases` 的 `Asset.url` **优先给 API 资产地址**（`/releases/assets/<id>`），
拿它下载会**再花一次 API 配额**；模组这条路应改用 `browser_download_url`（实测同样支持 Range，
不占 API 配额）。v43 在 `Asset` 上补 `browserUrl`，文档写"下载用 browserUrl"。

## 5. 兼容、版本与文档

| 项 | 改动 |
|---|---|
| `PluginHost.API` | 42 → **43** |
| `PluginApi.DOC_VERSION` | 42 → **43** |
| `docs/PLUGIN-API.md` | 三处：版本一览、§网络与下载（改写下载、加 v43 两条写接口 + `fetchText` 上限 / `fetchBytes` / `Asset` 两字段）、逐版记录追加 v43 |
| `Result` 文档 | 补 `not-a-mod` / `exists`（已有码，本来在写文件那一节；这里只是让下载/安装也能引用） |
| `settings()` | 加 `download_limit`（字节/秒，0 = 不限）。**加键不抬版本** |
| `fetchText` | 加 `fetchText(String url, int maxBytes, Fetch cb)` 重载：`maxBytes` 宿主钳到 **2 MB**，默认仍是 512 KB（官方模组列表 725 KB 要用它） |
| `fetchBytes` | 新增：二进制小请求（图标等），https only、上限 **256 KB**，同步小请求、不起任务/通知 |
| `GitHubRelease.Asset` | 加 `sha256`（来自 `digest`，去前缀；没有 = 空串）与 `browserUrl`（`browser_download_url`；下载**不占 API 配额**）+ 新构造器；**3 参构造器保留**（老插件二进制兼容） |
| 老插件 | 安全：`PluginApi` 加方法是宿主实现、插件只调用；`Download` 加的是 `default` 方法 |
| 旧签名行为 | **完全不变**（一次性子目录、失败 / 取消删半截、不续传）—— 续传只走 ② 重载 |

**自检（SelfTest）必须钉的十四条**（PC 能跑的就别放真机）：

1. `download` 三参 / 五参两个签名都在，且都转到同一个实现；
2. 只实现 `onDownload` 的匿名类能跑（`default onProgress` 不炸）；
3. `resume=true` + sha 为空 ⇒ `invalid`（没有内容锚不许续）；
4. key 校验：空 / `../` / 超长 / 非法字符 ⇒ `invalid`，且**落点仍在插件 cache 下**（防穿越）；
5. 旧签名走一次性子目录，失败 / 取消删 `.part`（与 v39 行为一致）；
6. 取消两侧都钉：`resume=true` 保留 `.part`、`resume=false` 删除；
7. `downloadState` 三态：没有 / 半截 / 成品；成品但 sha 不符 ⇒ 当没有并自愈删除；
8. 缓存命中只在 `resume=true`：成品在 + sha 对 ⇒ 0 请求 `ok`；`resume=false` ⇒ 仍然发请求；
9. `modsInstall` 与宿主模组页导入**同一份夹具**：结果、中转站里的旧件、`-enabled` 记账一致；
10. `modsSetEnabled` 与宿主 `Mods.setEnabled` 同源：写坏 / 只写一半（`-enabled` 没有 `-failed`）能被抓到；
11. `GitHubReleases` 解析 `digest` 四种形态：`sha256:<64hex>` 去前缀成功 / 没有 `digest` ⇒ 空 / `sha512:…` ⇒ 空 /
    非 64 位 hex ⇒ 空；并映射进 `GitHubRelease.Asset.sha256`（老 3 参构造器得到空串）。
12. `fetchText(url, maxBytes, cb)` 的钳位：`0` ⇒ 512 KB、`10 MB` ⇒ 2 MB（两侧都要钉，别只钉一侧）；
13. `fetchBytes`：非 https ⇒ `bad-url`；超 256 KB ⇒ `size`；正常返回字节（用本机回环夹具）；
14. `Asset.browserUrl` 与 `sha256` 同时映射：有 `browser_download_url` / `digest` 就有，缺一个就空串（不互相牵连）。

真机另有三条（研究文档 §6）：302 是否保留 Range、是否自动加 gzip、force-stop 后 `.part` 长度与 fsync。

## 6. 一个模组浏览器插件的完整调用链（验收时照这个走）

```java
// 1) 官方列表（Anuke，725 KB / 1015 条，匿名）—— 用 maxBytes 重载，自己扔后台解析
api.fetchText("https://raw.githubusercontent.com/Anuken/MindustryMods/master/mods.json",
        2 * 1024 * 1024, (r, json) -> list = parse(json));

// 2) 选中某个模组：1 次 API 拿 release 资产（带 digest）；没有 release 就 zipball
api.githubReleases(mod.repo, (r, releases) -> {
    Asset jar = pickJar(releases);              // 优先 dexed*.jar
    if (jar != null) {
        // 用户点「继续下载」⇒ resume=true；点「重新下载」⇒ resume=false（同一个 key）
        api.download(jar.browserUrl, jar.sha256, key(mod), userTappedContinue, dl);
    } else {
        // zipball 不支持 Range（实测 200 整包）⇒ 只能 resume=false
        api.download("https://github.com/" + mod.repo + "/archive/refs/heads/main.zip",
                "", key(mod), false, dl);
    }
});

// 3) 下载回调：进度进自己的 UI；装进用户选的槽（宿主做游戏判据 + 旧件进中转站）
@Override public void onDownload(Result r, File file, String sha) {
    if (!r.ok) { row.fail(text(r.reason)); return; }
    api.modsInstall(slot, fileNameFor(mod), open(file), true, done -> { ... });
}
// 页面重进：api.downloadState(key) 有半截 ⇒ 行上显示「继续下载 45%」+「重新下载」
```

这条链里插件**没有**碰：Range、限速、落点、校验、写门禁、中转站 —— 正是设计目标。

## 7. 实施顺序与工作量

| 步 | 内容 | 估时 | 备注 |
|---|---|---|---|
| 1 | `ResumableDownload` 进 `app/src` + `Bandwidth` + PC 夹具移植成自检 | ~1 天 | 研究稿已是一半；先不加任何插件接口 |
| 2 | `Downloads` 编排（key / 落点 / 并发 / TTL / 磁盘余量 / 进度节流）+ 宿主自更新改走它 | ~1 天 | 行为回归靠现有 16 条 PC 夹具 + 更新链路自检 |
| 3 | v43 插件口：下载三件套 + `modsInstall` + `modsSetEnabled` + `fetchText` 重载 / `fetchBytes` + `Asset` 两字段 + 文档 + 自检十四条 | ~1.5 天 | 三处版本一起抬 |
| 4 | 真机：`adb reverse` 夹具 + 三条 Android 待确认 + 弱网 / 杀进程 | ~0.5 天 | 与第 3 步可并行准备 |

**第 1、2 步不依赖 v43**：先把宿主自己的下载做到能续、能限速，插件口再开。
反过来（先开接口后补底座）会让插件先踩一遍半成品，不划算。
