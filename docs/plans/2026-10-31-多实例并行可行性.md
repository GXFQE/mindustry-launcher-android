# 多实例并行（多开）可行性（2026-10-31）

> 状态：**可行性已验，未开工**。本文件是定案依据；动手前先读「§6 MVP 边界」。
> 触发：B 站评论区有人问「这玩意能多开吗？就是一次性打开两个。」
> 设备：HONOR ELP-AN00 / Android 16（API 36），序列号 `AJYMUT4522007370`。

## 0. 一句话

**同一台手机上同时开两个游戏、都在跑：可行，但只在分屏里。**
后台挂一个（挂机 / 开服）不可行，模组和补丁也救不了。

## 1. 现状（为什么现在不支持）

启动第二局之前，`MainActivity.startVersionConfirmed` 必然先走
`ensureGameProcessDead()` → `Data.killGame()` → `killBackgroundProcesses(包名)`：
**第一局的 `:game` 进程会被直接杀掉**，不是暂停。

其余单实例假设：

| 位置 | 事实 |
|---|---|
| `AndroidManifest.xml` | `android:process=":game"` 写死；游戏 Activity `launchMode="singleTask"` |
| `Injector` | 注入（dex / 资产链 / `System.load`）是**进程级静态** ⇒ 一个进程只能一局 |
| `Paths` | `mdt-slot.txt` 是**全局单指针**，`:game` 在 `prepareSlot` 里写它 |
| `Data` | `gameAlive` 只认 `pkg:game`；`killGame` 杀整个包 |
| `LauncherApp` | 迁移 / 回收靠 `!gameAlive` 判断，隐含"同一时刻最多一局" |
| `AutoBackup` / `LaunchMarker` / `CrashAlert` / 探针会话 | 都按"当前槽 + 单进程"记账 |

## 2. 现场证据（2026-10-31 实测）

### 2.1 用户与存储是分开的

```
pm list users: 0 机主 / 10 隐私空间 / 100 平行空间 / 128 分身应用
/storage/emulated/: 0  10  100  128  obb
```

⇒ 分身（user 128）是独立 Android 用户，**外置存储也各一套**。
`pm list packages --user 128` 当时只有 35 个包（系统组件 + 微信），启动器不在其中。

### 2.2 微信的"能开一堆"是**静态池**

```
Task #6138  A=12810240:.AppBrandUI00  cmp=com.tencent.mm/.plugin.appbrand.ui.AppBrandUI00
Task #6139  A=12810240:.AppBrandUI01  cmp=...AppBrandUI01
Task #6140  A=12810240:.AppBrandUI02  cmp=...AppBrandUI02
Task #6141  A=12810240:.AppBrandUI03  cmp=...AppBrandUI03
Task #6142  A=12810240:.AppBrandUI04  cmp=...AppBrandUI04
mRootProcess = ...:com.tencent.mm:appbrand0
```

5 个**预声明**的容器类，各自一个 `taskAffinity`、各自一个 task，跑在 `:appbrand0`。
⇒ 不是"想开多少开多少"，也不为每个小程序单独编译；池子多大就是上限。

### 2.3 同 App 两个 task 可以同屏，且两侧都在跑

- 微信两个小程序（`AppBrandUI04` + `AppBrandUI01`）分屏同屏，两个 task 都 `visible=true`。
- 操作上面那一块时，下面那一块（Mindustry）继续动；`dumpsys activity activities` 里
  两条可见 Activity 都是 `state=RESUMED`（其余是 STOPPED）⇒ **multi-resume**。
- 切换上下焦点时画面会闪一下（系统合成 / 刷新率切换），游戏没有重启、没有回主菜单。

### 2.4 游戏在半屏窗口里能正常渲染

- 官方 Mindustry 159.7（`io.anuke.mindustry`）放在约 1224×1170 的下半屏：菜单正常重排，
  按钮完整，可交互；`dumpsys display` 仍是 `1224 x 2700, rotation 0`
  ⇒ 系统没有转屏，是**游戏自己按窗口比例重排**（arc 视口）。
- ⚠️ 这是**官方独立 App**，不是我们注入的那一份（见 §7 待验第 1 条）。

### 2.5 跨用户分屏

同一屏里出现过 U=0 的 Mindustry 与 U=128 的微信并排 ⇒ **这台 ROM 的分屏跨用户可用**
（AOSP 一般不支持，Honor 放开了）。设计仍按"同一用户"做，不依赖这条。

## 3. 不可行的三条路（都别试）

### 3.1 后台挂一个

- libGDX/arc 的 `onPause` → `AndroidGraphics.onPause` 把渲染线程停在 `pausePoint`，
  游戏循环、联机逻辑一起停。这是引擎行为，不是 Mindustry 的开关。
- 系统层还有 Cached Apps Freezer / LMK；前台服务只能抬进程优先级，**保不住执行**。
- 结论：后台实例"进程活着，但游戏不在跑"。

### 3.2 模组

模组跑在内容层（`Mod.init` / `loadContent`），拿不到 Activity 生命周期，也换不了后端类；
起线程会和主循环抢 `Logic` / `Time` 的状态，且系统冻结面前一样无效。

### 3.3 补丁改 arc 后端

- 暂停点确实在游戏自带的 `arc.backend.android.AndroidApplication`（随 dex 注入），
  启动器能改（反射改 `ArcNativesLoader.loaded` 是同一类操作，见 `Injector.flagNativesLoaded`）。
- 但改掉"停线程"只是第一关：
  - 后台时 Surface 被销毁 ⇒ 渲染线程没有 EGL surface，要"只跑逻辑"就得拆
    `Mindustry.render()` 的"逻辑 / 渲染"，等于给游戏写 headless 模式；
  - headless 入口所在的 `mindustry/server/` 整包已被 R8 树摇掉
    （见 [`docs/backlog/09` 的 §7.2](../backlog/09-七-代码复核后的功能池.md#L42-L71)）；
  - arc 随游戏版本滚动 ⇒ 每个版本一份补丁 + 自测，20+ 轮量级。
- 结论：**不是"打一个补丁"，且做完也只买到"后台挂机"，买不到多开。**

## 4. 可行方案：静态池（照微信抄）

| 微信 | 我们 |
|---|---|
| `AppBrandUI00`~`04` 五个容器类 | `Game0` / `Game1` 等空壳 Activity |
| 每个容器自己的 `taskAffinity` | 每个实例自己的 `taskAffinity` |
| `:appbrand0` / `:appbrand1` 进程 | `:game0` / `:game1` 进程 |
| 池子大小 = 同时能开的上限 | 池子大小 = 同时能开的上限（MVP = 2） |

要点：

1. **空壳对桩编译**：`Game1 extends mindustry.android.AndroidLauncher`，编译期给一份
   `AndroidLauncher` 的桩（只声明"它是个 Activity"）。
   🔴 **桩绝对不能打进包**——否则 app 的 CL 先命中桩，把游戏的真身挡掉。
2. 空壳零游戏代码（初始化都在 `AndroidLauncher.onCreate`），**编一次跟所有版本走**；
   入口类名本来就是契约（`Injector.GAME_ACTIVITY`）。
3. 实例 0 保持现状（`:game` + `mindustry.android.AndroidLauncher`），只新增实例 1，
   把改动面压到最小。
4. **槽**：`prepareSlot` 收实例带来的 extra；`mdt-slot.txt` 从"当前槽"降级为
   "最近一次启动"（只给 UI 看）。
5. **杀进程**：按 pid（同 UID 内可杀）或发退出 intent；**不要**再 `killBackgroundProcesses(包名)`。
6. **记账分账**：`gameAlive` 按进程名；`AutoBackup` / `LaunchMarker` / `CrashAlert` /
   探针会话按实例 + 槽；`LauncherApp` 的迁移 / 回收只在实例 0（或"没有实例在跑"时）做。

## 5. 为什么这条路成立

- 两个实例各占一个进程、各自 `mindustry.data.dir`（属性是进程级的）⇒ 数据天然隔离；
- 分屏下两条 Activity 都是 RESUMED ⇒ **两个游戏真的都在跑**，不需要后台保活；
- 静态池是微信在这台机器上已经跑通的形态，不是新发明。

## 6. MVP 边界

- 只做 **2 个实例**；不做 N、不做负载均衡、不做后台、不做"一个按钮同时拉起两个"。
- 用户自己把两个实例拖进分屏（和刚才微信的操作一样）。
- 验收：
  1. 两个实例同屏、都在跑（`dumpsys` 两条 RESUMED）；
  2. 各自的槽数据不串（存档 / 设置 / 模组互不影响）；
  3. 杀掉一个不影响另一个（按 pid 杀）；
  4. 自检全绿。

## 7. 风险 / 待验

1. **我们注入的那一份**在半屏下的表现（官方 App ≠ 我们的 Activity：资产链、`configChanges`）。
2. 游戏 Activity 的 `configChanges` **少了 `smallestScreenSize`**
   （[`AndroidManifest.xml`](../../app/AndroidManifest.xml#L421)）：拖分屏分隔条跨过最小宽度阈值
   可能触发 `recreate()` ⇒ 游戏重开。建议补上再真机拖一次。
3. 两个 `largeHeap` 进程 + 分屏的内存 / 发热（后台那个仍是 LMK 的首选目标）。
4. 两个实例同时开服会抢 6567。
5. `singleTask` 在分屏里的行为（12L+ multi-resume 应该没事，但要真机试）。

## 8. 工作量

| 项 | 量级 |
|---|---|
| 空壳 + 对桩编译 + 桩不打包 | 一次性，小 |
| 槽绑定实例 / 指针语义 | 中 |
| 按 pid 杀 / `gameAlive` / 记账分账 | 中偏大，但每处都不深 |
| 合计 | **5~10 轮**（本工程粒度），且只在分屏里有意义 |

## 9. 对外怎么回（可直接抄）

> **现在不能一次跑两个**：槽让多个版本装得下、存档互不覆盖，但同一时刻只跑一局——
> 点开第二个版本时第一个会被关掉。
>
> **想两个同时在跑，眼下只有一条零代码的路**：手机自带的「应用分身」里再装一份启动器 + 游戏，
> 然后分屏。这台 ROM 支持同一个 App 的两块窗口、也支持跨用户同屏，两块都是 RESUMED，
> 没点的那边照样在跑。代价是两边存档、备份、插件各一套。
>
> **原生多开**：技术上可行（同一 App 两个 `:game` 进程、各一个槽、分屏并排），但**只限分屏**；
> 切后台会被游戏引擎暂停，模组 / 补丁解决不了，所以"挂后台当服务器"这种做不到。

## 11. 2026-11-05 真机实验（未采用，RC 期不动源码）

为回答「现在这个版本能不能开两个」，在 RC 分支上做过一次**临时**改动并真机验证，
验完已回退（用户：「没必要真的去改，毕竟现在还是 rc 的状态」）。结论对后续实现有效。

### 11.1 先复现的现状问题：切版本会静默失败

- 159.7 在跑时点 MindustryX：`report-starttap` 记了这次点击，`report-launch` 也跑完了整条管线，
  但 `:game` 的 **pid 没变**（23684 两次都是它），屏幕还是 159.7。
- 原因：`ensureGameProcessDead()` 用 `killBackgroundProcesses(包名)`，对**刚切走几秒**的进程不生效
  （还没落到 cached 档）⇒ 注入白做、`singleTask` 把旧实例提回前台。
- 同一条 API 在游戏真的进后台几分钟后执行 `am kill` 能杀掉 23684 ⇒ 不是 API 坏，是时机。
- 副作用：那次"白做"的注入把 MindustryX 的 dex 也塞进了同一个进程（`dexElements` 3→4），
  资产链也被换成 MindustryX 的 APK —— 一个同时含两份游戏 dex 的脏进程。

### 11.2 两处临时改动 + 验证结果

| 改动 | 结果 |
|---|---|
| 游戏 Activity 加 `taskAffinity="io.mdt.launcher.game"` | 最近任务变成两张卡（`io.mdt.launcher` / `io.mdt.launcher.game`）；Home 回启动器时 `:game` 仍活着 |
| `killGame` 改成先 `Process.killProcess(pid)`（`killBackgroundProcesses` 兜底） | 切版本 `:game` pid 27788 → 28147（新进程），`report-launch` 目标 = MindustryX，`dexElements 合并后 = 2`（干净），屏幕是 MindustryX |

### 11.3 还观察到

- 切版本后旧的 `:probe` 进程还活着（探针会话没跟着收）——多开做的时候要一起收。
- 「启动器 + 游戏」分屏没在自动化里验（adb 拖动分屏不可靠），但两张卡已经在最近任务里成立。

> ★ 这两处改动**没有保留**：RC 期源码保持干净，等真正做多开时再按上面的结论落地。
