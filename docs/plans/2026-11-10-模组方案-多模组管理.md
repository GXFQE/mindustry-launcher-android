## 0. 一句话

**对 MDT 来说，"模组方案"比"整合包"更贴需求**：
方案只记「槽里哪几个模组算一组」，动作是**开关**（只写 `settings.bin`），不搬文件、不建新槽、可逆；
整合包是**分发一个完整环境**的形态（MC 需要，因为版本断代 + 大包 + 中心 registry），
MDT 的日常痛点不是"一次装 50 个模组"，而是"槽里十来个模组，想成组开关 / 成组排查 / 换着玩"。

---

## 1. 两者不是一回事（别混）

| | **整合包**（artifact） | **模组方案**（live） |
|---|---|---|
| 本质 | 一个 zip：清单 + 模组文件 + 内容 | 槽里的一个**命名集合**（只记成员） |
| 动作 | 解包进新槽（复制文件） | 开/关成员（只写 `mod-*-enabled`） |
| 风险 | 覆盖、新槽、版本绑定、空间 | **无文件改动**，可逆 |
| 适用 | 分享 / 换机 / 开箱即玩 | 日常管理 / 切换玩法 / 排查 |
| 依赖 | `PackManifest` + `SlotZip` + `Importer` | `Mods.scan` + `stateOf` + `SettingsBin` |
| 缺什么 | 有包才能装 | 只能管理**已经在本槽**的模组 |

⇒ **方案是主对象，包是 transport**：方案可以导出成包（带成员文件），包导入后也能落成一个方案。
两者都做时，先做方案（2~3 轮），包后置（+1~2 轮）。

## 2. 数据模型：`mdt-groups.json`（槽根）

```json
{
  "schema": 1,
  "groups": [
    {
      "id": "g-1712345678-1",
      "name": "QoL",
      "note": "",
      "members": [
        { "internal": "logic-tool", "file": "logic-tool.jar", "sha256": "…可选…" }
      ],
      "created": "2026-11-10T20:00:00+08:00",
      "updated": "2026-11-10T20:00:00+08:00"
    }
  ]
}
```

- 放**槽根**（和 `mdtpack.json` 同一个位置）：`Data.contentRoots` 会带上它 ⇒ 整槽导出/备份/换机后方案还在；
  游戏忽略未知文件。
- **成员键 = `internal`（内部名）**：内容 ID、`settings.bin` 开关都认它；`file` 只用于显示/找回，
  `sha256` 可选（只用来标"被换过"）。
- 一个模组**可以属于多个方案**：方案是视图/动作，不是所有权（没有"把模组从别的方案抢过来"）。
- 不存"方案开/关"：状态每次从 `Mods.scan` 的 `Info.enabled` 算（同整合包 §3.4 那条纪律）。

## 3. 动作（全部只写开关）

| 动作 | 实现 | 注意 |
|---|---|---|
| **应用** | 把成员里"当前关着"的写成开（其余不动） | 一次 `SettingsBin.applyBools`（读 → 备份 → 原子写 → 读回） |
| **关闭** | 把成员里"当前开着"的写成关 | 同上；不动非成员 |
| **单独启用（solo）** | 成员全开 + **槽内其他模组全关** | 破坏性：确认框要写"会关掉其他 N 个"；默认不做 |
| **加/减成员** | 只改 `mdt-groups.json` | 不碰 `settings.bin` |
| **新建** | 默认取"当前已启用的模组"；也可从空开始 | 名字必填；重名拒绝 |
| **改名 / 删除方案** | 只改/删记录 | **不关模组、不删文件**（提示一句） |

- `Mods.setEnabled` / `applyBools` 在游戏运行时**拒绝**（`E_GAME_RUNNING`）⇒ 动作前判 `Data.gameAlive`。
- `Mods.scan.skipModLoading`（上次启动整槽被跳过 + `modcrashdisable`）时，应用/关闭**仍可写**，
  但要提示「下次启动仍可能整槽跳过」——与模组页现有的那道门**同一判据**（别在方案里另写一套）。
- 所有动作都**只动 `mod-<内部名>-enabled`**，成对清 `-failed`（照游戏写法）；非成员一个字节不碰。
- **不搬文件、不用 SAF、不建槽** ⇒ 这是它比整合包轻的地方。

## 4. 状态（派生）

```java
final class GroupView {
    ModGroup group;
    List<Member> members;   // present / missing / modified / Info / enabled / state
    int missing, modified, incompatible;
    boolean allOn, off, partial;
    boolean slotSkipped;    // scan.skipModLoading（全槽级，别混进"方案关了"）
}
```

- 成员匹配：先按 `internal`，找不到再按 `file`（文件名被改过时还能找回）；都没有 ⇒ `missing`。
- `modified`：`sha256` 有值且与实物不符（或按 `file` 找到但 `internal` 不一致）。
- `enabled`：`Mods.Info.enabled`（`Mods.scan` 已从 `settings.bin` 读好，缺省 true）。
- `state`：`Mods.stateOf(info, resolved, build, rev)` —— 与装包/模组页同一套游戏口径。
- `allOn / partial / off` 由成员算；**不另存**。

## 5. UI（v1）：组就是列表里的一个条目（虚拟条目）

> 用户 2026-11-10：「我就希望整到一起看起来就像是一个模组一样」
> 之前否决：合并插件（四域 + 与三插件冲突）、折叠（抢插件卡、体验不稳）。

**不做独立合集页、不做折叠、不合并插件**；在模组列表里，一个组就是**一行**，和普通模组行同构：

```
[icon] QoL 整合包          v1.0        [5/6 启用]
       5 个模组 · 缺 1 · 2 条体检结论
```

- 点这一行 = 打开**组详情**（二级页）：成员模组行（真实开关）+ 成员上的体检结论（mods-health 原样）+
  组动作（全部启用/关闭）。
- 顶层**不再显示被收进组的成员**（否则“像一个模组”不成立）；未分组的模组照常显示。
- **一个模组只能属于一个组**（v1）：否则顶层重复/归属不清；多组需求以后再说。
- 搜索/筛选/排序：组行按组名匹配；搜成员名也命中组行；“只看有问题的”把组算作有问题（任一成员）；
  排序按组名。`mShown` 从 `List<Mods.Info>` 变成 `List<Row>`（Row = group | mod）。
- 组行状态：全部启用 / 部分 / 全部关闭 / 有不兼容 / 缺成员——**聚合，不存**。
- 组开关：一次 `SettingsBin.applyBools` 写全部成员；部分状态显示“部分启用”，点开关 = 全开/全关（确认）。
- **四类内容**：v1 先做模组；存档/地图/蓝图的“合集行”同理，但各自列表里一行（Phase 2），不和模组混。
- **为什么插件做不了**：插件不能往宿主列表里插行（`PluginEntries` 只能加 section/content/action/analyzer）。
  这必须是**宿主功能**，或宿主新增“虚拟行 provider”API（本质仍是宿主）。

**收益**：

- 看起来就是“一个模组”；
- mods-health 的 findings **不用改接口**：仍按成员 `path` 注入，宿主在组行汇总、在组详情逐条显示；
- 不抢插件卡、不合并、不折叠；三个官方插件原样。

**代价**：宿主改 `ModsActivity` 列表模型（Row = group/mod）、搜索/筛选/排序、组详情、聚合 badge；
**2.5~3.5 轮**。Phase 2 三个内容页再 +1.5~2。

**v1 不做**：独立合集页、折叠、合并插件、行内展开、跨槽组。

---

## 5.1 为什么这个方案能兼容 mods-health（不用改接口）

- `mods-health` 仍然只返回 `Finding.anchorPath = 成员 mod 的 path`；
- 宿主 `mIssues` 仍按成员 path 存；
- 组行只做**聚合**（数一下成员有几条），组详情逐条显示成员上的 findings；
- 不需要 `FindingsRouter`、不需要插件互相调用、不需要合并。
- 唯一要小心：组行不是 `ItemInfo`，别把它塞进 `PluginData.pageItems()`；分析器看到的仍是**全部真实模组**
  （`Mods.scan` 不变），所以体检不会漏项。

## 6. 与现有代码的接线

| 现有 | 怎么用 |
|---|---|
| `Mods.scan(ctx, slot)` | 成员是否存在、`enabled`/`failed`、`internalName`/`fileName` |
| `Mods.resolveDependencies` | 依赖图（缺依赖/循环）→ 方案健康 |
| `Mods.stateOf` | 与目标版本/黑名单/Java 门槛的判定 |
| `SettingsBin.applyBools` | 应用/关闭 **一次写**；自带备份、读回、失败还原 |
| `Data.gameAlive` | 动作前判；游戏在跑就不写 |
| `Config`? | **不用**：方案是槽内文件，不是全局配置；随槽导出/备份 |
| `Data.contentRoots` | `mdt-groups.json` 自动进整槽导出/备份（不额外写口径） |

新增（2 个类）：

| 文件 | 职责 |
|---|---|
| `ModGroup.java` | 模型 + `mdt-groups.json` 读/写/校验（纯逻辑；`org.json`，设备侧自检） |
| `ModGroups.java` | 对账 + 状态 + 动作（apply/off/solo/加成员/删成员）；调 `Mods`/`SettingsBin` |

UI 全在 `ModsActivity`（+ 1 个 `item_group.xml` / 1 个成员勾选页，尽量复用 `CardStack`）。

## 7. 导出 / 导入：不新增按钮，走现有整槽 zip

> 用户 2026-11-10：「不想搞出一堆按钮，明明可以共用原有导入导出」

- **方案不是另一种"包"**：它只是槽里的一份 `mdt-groups.json`。
- **导入**：现有「导入整槽（zip）」把它当普通槽文件解出来；zip 里同时有 `mods/`、`saves/`、`maps/`、`schematics/` 就一起进新槽。
- **导出**：现有「导出整槽」会把它一起打进去（`Data.contentRoots` 已包含它）。
- **不新增"导入方案 / 导出方案"按钮**；插件也不做自己的导入导出。
- 下面 §7.1 的 `mdtpack.json` 是**将来**要"完整环境包/显式清单"时才用的；**v1 不需要**，以 §7.2 为准。

### 7.1 `mdtpack.json`：让 zip 自描述（可选，将来）

> 用户 2026-11-10：「导入的 zip 中包含某个 json 表示这些模组在启动器中是统一管理，甚至地图/蓝图/存档也可以」

- 这就是"包"与"方案"之间的契约：**zip 是传输，JSON 是意图**。
  没有 JSON = 普通内容导入；有 JSON = 按声明落成方案 / 环境。
- 示例：

```json
{
  "schema": 1,
  "kind": "group",
  "name": "QoL 方案",
  "version": "1.0",
  "author": "",
  "note": "",
  "group": { "name": "QoL", "note": "" },
  "game": { "version": "159.7", "build": 159, "revision": 7 },
  "mods": [
    { "file": "mods/a.jar", "internal": "a", "name": "A",
      "sha256": "…可选…", "enabled": true, "dependencies": ["b"] }
  ],
  "content": {
    "saves": ["saves/x.msav"],
    "maps": ["maps/y.msav"],
    "blueprints": ["schematics/z.msch"]
  },
  "settings": "mods-only"
}
```

| 字段 | 语义 |
|---|---|
| `kind` | `group` = 只模组（合并进当前/新建槽）；`environment` = 整槽（含 `settings.bin`/内容，新槽） |
| `group` | **有它才建方案**：成员 = `mods[]`；没有 ⇒ 只导入内容，不建方案 |
| `mods[].enabled` | 初始开关意图（可选，默认 true）；导完用 `writeGameSettings` 写一次，之后状态派生 |
| `mods[].internal` | 成员键（内部名）；`file` 只用于安装/显示 |
| `content` | `saves` / `maps` / `blueprints` 相对路径；**是槽内容，不是方案成员**（方案只管模组） |
| `settings` | `mods-only`（group）或 `full`（environment）；group 包**不碰**键位/音量 |
| `game` | 提示版本，**不锁** |

**导入规则**：

1. 读 zip 根（或唯一一层包裹目录）的 `mdtpack.json`；
2. 校验：`schema` / 路径（拒 `..`、绝对路径、控制字符）/ 重名 `internal` / 大小；
3. `kind=group`：目标 = 当前槽（或新建空槽）→ 逐份 `addItem` / `writeItem`（同名先问，一批只问一次）
   → 写 `mdt-groups.json` → 用 `writeGameSettings` 写 `enabled` 初值；
4. `kind=environment`：新槽 → `SlotZip` 整槽导入（settings/内容/模组）→ 从 `mods[]` 建方案；
5. 结果页：缺依赖 / 不兼容 / 重名 / 清单与实物不符，照 §4 / §10。

- **兼容**：没 JSON = 老的内容导入；不认识的字段忽略；`schema` 更高 ⇒ 拒绝（不猜）。
- **安全**：zip 条目**一律不按路径解**；只用 basename + `addItem`，路径校验归导入方；模组是代码，提示「只装信得过的包」。
- **插件能不能做**：`group` 可以（`pickFile` + 自己解 zip + `addItem` + `writeGameSettings` + `slotDir` 写方案）；
  `environment` 不行（没有 `SlotZip` / 新槽），归宿主。

### 7.2 最小配置 + 共用现有导入导出（v1 推荐）

> 用户 2026-11-10：「任何一个配置文件，配置本身版本号是很重要的」「不想搞出一堆按钮，明明可以共用原有导入导出」「主要是插件有没有这个能力」

**结论：只用一个槽内文件 `mdt-groups.json`；导入导出完全走现有的整槽 zip，不新增按钮。**

```json
{
  "schema": 1,
  "groups": [
    { "name": "QoL", "kind": "mods", "members": ["a", "b"] },
    { "name": "战役", "kind": "saves", "members": ["world1.msav"] },
    { "name": "常用蓝图", "kind": "blueprints", "members": ["factory.msch"] },
    { "name": "对战图", "kind": "maps", "members": ["pvp.msav"] }
  ]
}
```

- **`schema` 必须有版本号**：
  - 写的时候永远写 `1`；读的时候 `schema > 1` ⇒ **拒绝**（不猜）；
  - `schema` 缺失按 `1`（只对手写文件宽容，读到时可以提示"已按 v1 读"）；
  - **已有字段不改语义**；以后加字段只抬 `schema`，老文件照读；不认识的字段忽略。
- **`kind` 必填**，四种：`mods` / `saves` / `maps` / `blueprints`；一个组只能是一种，不混。
- **`members` 的键按 kind 不同**：
  - `mods` = **内部名**（`Mods.Info.internalName`，小写）；
  - `saves` / `maps` / `blueprints` = **文件名**（这三类目录是平的，文件名叫得准；用 path 会在换槽/换机后失效）。
- **动作按 kind 不同**（内容没有“开/关”，别硬套模组语义）：
  - `mods`：应用 / 关闭 / solo（写 `settings.bin`）；
  - `saves` / `maps` / `blueprints`：导出（打包 zip）/ 删除（走中转站）/ 只看这组（插件页内过滤）；
  - v1 **不做**宿主页的“按组过滤”（那要 filter/sort 注入，另算）。
- **不写哈希 / 依赖 / 版本**：插件用 `contents(slot, kind)` 的 `extra` 现场算（模组有 `enabled` / `depState` / `targetBuild`，内容有尺寸/时间/元数据）。
- **导入**：现有「导入整槽（zip）」把 `mdt-groups.json` 当普通槽文件解出来；zip 里同时有 `mods/`、`saves/`、`maps/`、`schematics/` 就一起进新槽。**没有新按钮。**
- **导出**：现有「导出整槽」会把它一起打进去（`Data.contentRoots` 已包含它）。**没有新按钮。**
- **插件**：不负责导入导出（`pickFile` / `addItem` / `export` 都不用），只读/写槽内 `mdt-groups.json`、
  按 kind 做动作、显示合集页。
- **唯一可能的宿主小改**：如果 zip 是"单层包裹目录"（`pack/mdt-groups.json`），`SlotZip.detectStrip` 目前只认 `settings.bin` / `saves/`；把 `mdt-groups.json` 加进"根标记"即可（**无 UI 变化**）。
- **徽标**：不是按钮，是行上状态徽标旁的一枚小文字（如「方案：QoL」）；v1 **可以不做**，插件页里看即可。要做再谈 `labels()`。

**插件能力**（最小配置，四类内容都算）：

| 动作 | 接口 | 能力 |
|---|---|---|
| 读/写 `mdt-groups.json` | `slotDir()` + `File`（自己 `.part` + rename） | ✅ |
| 列四类内容 | `contents(slot, kind)`（`kind` = `mods`/`saves`/`maps`/`blueprints`） | ✅ |
| 模组按内部名找 | `extra.internalName` | ✅ |
| 模组批量开/关 | `gameSettings(slot)` + `writeGameSettings(slot, changes, done)` | ✅ |
| 选成员 | `pickContent(kind, title, head, cb)` | ✅ 四类都支持 |
| 导出内容 | `open(ItemInfo)` + `export`/`share`（插件自己打 zip） | ✅ |
| 删除内容 | `trashItem(ItemInfo, done)`（走中转站） | ✅ |
| 合集页 / 编辑成员 | `createView` / `prompt` | ✅ |
| 导入 / 导出配置 | **宿主现有整槽 zip** | ✅ 共用，不归插件 |
| 行徽标 / 按组合过滤 | `labels()` / `filter`+`options` | ❌ v1 不做 |

⇒ **"统一管理"本身插件现在就能做，四类内容都能列/选/导出/删除；只有"按组过滤"和"行徽标"是额外 UI。**

## 10. 风险 / 边界

- **方案管不了"没有的模组"**：成员缺失只能显示"缺 N 个"；要装还是走导入/手动。
- **重叠方案**：一个模组可属多个；"应用"不排斥别的方案；只有 `solo` 会把别的关掉（必须确认）。
- **游戏内乱动开关**：状态派生，不存；同整合包 §3.4。
- **游戏在跑**：拒绝写（`E_GAME_RUNNING`）；提示先退游戏。
- **整槽跳过**：`scan.skipModLoading` 时，写开关不等于"下次一定加载"（游戏仍可能整槽跳过）——
  卡上要说清，别让用户以为点了应用就好了。
- **改名/换版本**：按 `internal` 认；找不到再按 `file`；都没有标"缺"。改内部名 = 内容命名空间变了，标"被改过"。
- **方案文件随槽走**：整槽导出/导入/备份会带上；分享包（`SharePack`）也不会丢（不是身份文件）。
- **不要把它做成"第二份启用状态"**：只存成员关系，开关永远现读 `settings.bin`。

## 11. 做成插件？

> 用户 2026-11-10：「那有没有做成插件的可行性」

**结论：数据、批量开关可行；导入导出直接共用宿主现有的整槽 zip。**
**但你要的“一级折叠汇总 + 二级详情”是宿主 UI 模式 —— 插件只能加一行 `content` + 插件页：
第二个 `section` 会把 mods-health 的「模组体检」标题压成通用「插件」（见 §11.3）。**

| 需要 | 现有 API | 结论 |
|---|---|---|
| 读模组 + `enabled` / `failed` / 依赖 / 目标版本 | `contents(slot, "mods")` → `ItemInfo.extra`（`internalName` / `enabled` / `settingsKnown` / `depState` / `targetBuild`…） | ✅ |
| 读 `settings.bin` | `gameSettings(slot)`（v34） | ✅ |
| 批量写开关 | `writeGameSettings(slot, map, done)`（v34）：游戏在跑拒绝、写前备份、原子写、读回自检 | ✅ |
| 选成员 | `pickContent("mods", title, head, cb)`（v32，宿主勾选框） | ✅ |
| 方案页 | `content` 扩展 + `createView`（挂在 `mods` 页） | ✅ |
| 方案记录 | `slotDir()/mdt-groups.json`（插件自己写）或 `dataDir()` | ⚠️ 前者随槽走（`Data.contentRoots` 会带上），但**宿主不代管原子写/备份**；后者安全但不随槽 |
| **导入 / 导出** | **不归插件**：宿主现有「导入整槽 / 导出整槽」已经会带 `mdt-groups.json` | ✅ **共用，不新增按钮** |
| 行徽标 / 分组头 | `state()` 只有 7 个固定 token；`Finding.anchor` 只画"⚠ 标题"一行的插件结论 | ❌ 现在没有**中性标签**位；「⚠ 插件结论」是分析结论的样式，不该拿来当方案徽标（用户 2026-11-10 指出）。v1 不做，见 §11.2 |
| 摘要卡一行 | `Finding.summary()` | ⚠️ 能塞一条，但不是宿主原生行（同样偏"结论"样式） |
| 信任 | 插件与宿主**同进程、无沙箱**，能写 `settings.bin` 和槽内文件 | 🔴 只建议**官方 / 内置** |

- **成本**：插件 v1（`content` 行 + 插件页 + 方案 CRUD + 应用/关闭 + 写 `mdt-groups.json`）**2~3 轮**；
  宿主内建（一级折叠汇总卡 + 二级 `CardStack` 详情 + 行开关）**2.5~3.5 轮**。
- **建议**：
  - 要“一级折叠汇总 + 二级详情” ⇒ **宿主内建**（插件做不到这个位置；加 section 会压掉体检标题）；
  - 想“先有功能、可独立更新”且能接受“插件卡里一行 + 插件页” ⇒ **内置插件**（`api()` 报 **34**）；
  - **不建议第三方插件当唯一实现**：它要写 `settings.bin` 与槽内文件，信任成本太高。
- **迁移友好**：插件写的 `mdt-groups.json` 就在槽根，宿主以后内建可以**直接认这个文件**；
  卸载插件后文件留着（无害），整槽导出/备份也会带走。

### 11.1 导入导出：插件不用自己搞

用户 2026-11-10：「不想搞出一堆按钮，明明可以共用原有导入导出」——**对，v1 就这么办**：

- **导出**：现有「导出整槽」会把 `mdt-groups.json` 一起打进去（`Data.contentRoots` 已包含它）。
- **导入**：现有「导入整槽」把它当普通槽文件解出来；zip 里的 `mods/`、`saves/`、`maps/`、`schematics/` 一起进新槽。
- 插件**不新增** `pickFile` / `addItem` / `export` 入口；它只管槽内那份配置和开关。
- 唯一可能的宿主小改：`SlotZip.detectStrip` 把 `mdt-groups.json` 认成"根标记"（单层包裹目录时用），**无 UI 变化**。

> 下面这些原语**备查**：将来若真要做"只导出一个方案（不带整槽）"，插件才用得上；
> v1 不需要，也不建议为此加按钮。

| 能力 | 接口 | 说明 |
|---|---|---|
| 导出文件 | `export(name, mime, stream[, after])` / `share(name, stream)` | 插件自己造字节流（zip 用 JDK `ZipOutputStream`；宿主只管落盘/分享） |
| 选一个文件 | `pickFile(mime, cb)` | 系统 SAF，宿主复制到插件 `cache/` |
| 读已有条目 | `open(ItemInfo)` | 模组/存档/地图/蓝图，文件或容器条目统一入口 |
| 新建条目 | `addItem(slot, kind, name, stream, done)`（v35） | 只四种 kind、**不覆盖**、**不校验内容**（mod 里有没有 `mod.hjson` 归插件） |
| 替换条目 | `writeItem(item, stream, cb)` | 只替换**已存在**文件；游戏在跑拒绝 |
| 选已有内容 | `pickContent(kind, …)` | 这是"选"，**不是**导入 |
| 写设置 | `writeGameSettings(slot, map, done)` | 合并写 + 备份 + 读回；**不是整份 `settings.bin` 导入** |

**缺口**（v1 用不到）：没有 `SlotZip` 那种 inspect/extract、没有 `createSlot`、没有整槽原子导入、没有版本绑定。
⇒ 完整环境包仍归宿主；只模组的 group 包如果将来要"单独导出"，用上面的原语也能做。

### 11.2 行徽标：不是按钮，v1 可以不做

用户 2026-11-10：「所以徽标到底是啥？」——**就是模组行上、状态徽标旁边的一枚小文字**，例如：

```
Logic Tool  v1.2           [启用] [方案：QoL]
```

它**不是按钮**，不点、不弹窗；只是让用户一眼看到“这个模组属于哪个方案”。现在宿主没有这个中性标签位：
`Finding` 是**分析结论**（`⚠ 标题` / 「信息 · 」），拿它显示方案名语义不对，所以别硬借。

- **v1**：不做。插件页里能看到成员；模组行不显示方案名。
- **要做**：加一档中性 `labels()`（v37 候选），宿主画第二枚小徽标/副标题；多个插件最多两枚、超长截断。
- **分组头**更后：需要 `group(ItemInfo)` + 宿主按插件分组排序，改动比标签大；v1 不做。

### 11.3 和 mods-health（模组体检）共存

- **数据不冲突**：mods-health 是只读分析（`analyze` / `state` / `gates`），mod-groups 只通过
  `writeGameSettings` 写开关；宿主负责备份/原子写/读回。`ModsActivity.onResume` 会重扫，
  体检结论跟着更新（短暂旧值可接受）。
- **判定面会打架（必须避开）**：`PluginAnalysis` 的 `verdicts` / `gates` 都是 `path → …` 的 `put`，
  **后跑的插件覆盖先跑的**。mod-groups 若也实现 `state()` / `gates()`，会顶掉 mods-health 的逐项判定
  ⇒ **mod-groups 不实现 `state` / `gates` / `analyze` / `Finding`**。
- **UI 会打架（关键）**：mods-health 现在**没有 section**（只有 analyzer / filter / sort），
  卡片标题本来是通用「插件」；再加一段 section，`sectionHeading` 会把标题改成**那一段的名字**，
  体检结论仍以「分析结论」小标题混在同一张卡里 —— 不是标题被删，而是**一张卡里两件事、标题只报一件**。
  ⇒ 若分开做，mod-groups **不要用 `section`**，只用 `content` / `action` 一行（“模组方案…”）；
  若要动态汇总，**合并成一个插件**（§11.4）或宿主内建。
- **筛选/排序**：mods-health 可能有自己的筛选/排序；mod-groups v1 不加，避免“同时两个 ✓”。
- **结论**：
  - 要“一级折叠汇总卡 + 二级详情” ⇒ **宿主内建**（卡可以放在模组列表上方，不占插件卡）；
  - 要“插件先做” ⇒ 只加一行 `content` + 插件页，**不要 section**；一级汇总会退化成一行静态入口，
    做不出动态汇总；
  - 若要动态汇总，**合并成一个插件**（§11.4）或宿主内建；
  - 宿主若以后支持“多段 section 各自成卡/各自标题”，再拆开也不迟。

### 11.4 合并成一个插件（`mods-tools`）—— 备选，已否决

> 用户 2026-11-10 后续：「合并不太合适，毕竟还有地图/存档/蓝图，和其他插件也冲突」
> ⇒ **不作为 v1 方案**，保留在这里只作记录。

> 用户 2026-11-10：「要不然合成一个插件吧（）」

**可行，而且是插件路线里最顺的**：一个插件同时拥有 `section` + `analyzer` + `content`，
标题、结论、开关都归它，不会出现两插件抢 `verdicts` / `gates`、一张卡里两件事。

**结构**：

- `section`（**每页一条，四页各一**）：
  - 模组页：一级**可折叠汇总**（“模组工具” / “方案 2 个 · QoL 5/6 · 缺 1”），健康摘要 + 模组合集放一起；
  - 存档 / 蓝图 / 地图页：该页的**合集汇总**（“战役 3 份 · 缺 1”），可折叠；
- `analyzer`：现有 mods-health 的 `Finding` / `state` / `gates` 原样保留（只在模组页）；
- `content`（每页一条）：一行「管理合集…」打开插件页（二级详情，按 `api.page()` 过滤 kind）；
- `filter` / `sort`：现有冲突筛选/排序；“按合集”v1 不做；
- 动作按 kind：模组 = 应用/关闭/solo；存档/地图/蓝图 = 导出 zip / 删除（中转站）/ 只看这组；
- `api()` 从 **28 抬到 34**（`writeGameSettings`；当前宿主 36）。

**好处**：

- 没有 last-wins：`state` / `gates` 只有一份；
- 每页只有一段 section，标题就是这段的名字；
- 一个 APK、一个更新通道（`plugins-latest`），**不改宿主**；
- 合集文件仍是槽内 `mdt-groups.json`；导入导出仍走宿主整槽 zip。

**代价 / 风险**：

1. 🔴 **信任面变大**：mods-health 从“只读分析”变成“能写 `settings.bin`”。
   只建议官方 / 内置；`description` / `access` 要改，最好在启用时明说“会改模组开关”。
2. ⚠️ **API 28 → 34**：内置随宿主没问题；`plugins-latest` 更新包到旧宿主会被区间拒，
   更新清单 / 宿主版本要配套。
3. ⚠️ **名字 / 范围**：`mods-health` 不再准确。建议标题改「模组工具」，但**改 id 是迁移**
   （内置清单、旧版清理、update URL）；可以先保留 id、只改 title/description，减少迁移。
4. ⚠️ **体积 / 测试**：health 的 `Check.java` 46k + 合集逻辑；一个入口要覆盖两块，
   但共用 `ItemInfo` 解析，测试可复用。
5. ⚠️ **职责**：代码分包（`core/` 健康、`groups/` 合集），入口只做路由；别把开关逻辑塞进 `Conflicts`。

**成本**：合并 + 模组合集 + 四页合集/动作 + 折叠 section + 插件页 ≈ **4~5.5 轮**
（合集数据/动作 1.5~2 + 四页 section 与插件页 2~2.5 + 合并/测试 0.5~1；health 现有测试链复用）。

| | 合并插件 | 宿主内建 |
|---|---|---|
| 位置 | 插件卡（列表下方） | 模组列表上方 |
| 覆盖页 | **四页都有**（section 每页一条） | 四页都要改宿主 |
| 独立更新 | ✅ `plugins-latest` | ❌ 跟启动器发版 |
| 信任 | 插件可写 `settings.bin` | 宿主本来就能写 |
| 成本 | **4~5.5 轮** | 四页内建 >5 轮 |

**建议**：能接受“插件卡位置” ⇒ **合并**是最省事的插件路线；一定要“列表上方汇总” ⇒ 宿主内建。

### 11.5 插件能不能看其他插件的版本？

> 用户 2026-11-10：「现在插件能不能看目前启用的其他插件有什么和版本号」

**公开 API：不能。** `api.versions()` 是**游戏版本**，不是插件；`PluginApi` 没有 `plugins()`。

- 宿主内部有 `Plugins.active(ctx)` / `stateIds` / `stateGet` / `PluginMeta.read`，但插件要拿只能
  反射或读文件 —— **不是契约**，宿主一改就断，不建议。
- 如果确实要（例如“检测 mods-health 在不在、版本够不够”），加一档 **v37**：

```java
public final class PluginInfo {
    public final String id;        // 插件 id
    public final String version;   // 当前启用版本（active.txt 里的值）
    public final String title;     // plugin.json 的显示名
    public final boolean builtin;  // 内置 / 在线
}
List<PluginInfo> plugins();        // 只列**启用**的
```

- 不暴露 APK 路径 / 签名 / 权限；成本 **0.3~0.5 轮** + 一条自检。
- **合并成一个插件后不需要**：自己就是 mods-health，不用检测自己；四页 section 也不抢别人的。
- 如果分开做，建议宿主加“插件依赖/冲突”声明（`plugin.json` 里 `requires` / `conflicts`），
  比让插件互相反射干净；目前没有这套机制。

### 11.6 三个官方插件怎么兼容？能不能替换宿主接口？

> 用户 2026-11-10：「我是想着让原来的三个插件兼容这个」「甚至我是想着能不能让插件替换原来宿主接口」

**先分清两件事：**

1. **兼容合集配置**：可以，而且不需要宿主改 —— 三个插件同进程，都能 `slotDir()` 读同一个
   `mdt-groups.json`（schema 文档化）。也可以加只读 `collections(slot)` API（v37）统一解析。
2. **替换宿主接口/页面**：现在**不支持**，也不建议为这个功能做。

**三个插件的实际接口面**（`plugin.json`）：

| 插件 | 现在挂什么 | 和合集怎么接 |
|---|---|---|
| `mapstats` | maps 页 `action` + map-detail 页 `section` + maps 的 sort/filter | 可加“按合集统计”（读 `mdt-groups.json` 的 `maps` 组）；maps **列表页**加 section 汇总不冲突（它没有列表 section） |
| `usagestats` | slot 页 `section`（游玩时长） | 与内容合集无关；不接 |
| `mods-health` | mods 页 `analyzer` + filter/sort | **最终不合并**：虚拟组行由宿主渲染，findings 按成员 path 聚合（§11.9） |

**为什么“替换宿主接口”不做**：

- 现在模型是**宿主拥有页面/数据，插件只做扩展**（analyzer / section / content / action / filter / sort / probe / event）。
  这是有意的：插件缺失/崩溃/版本旧时，宿主页面仍然完整。
- 替换接口需要：稳定的 provider 接口 + 宿主 fallback + 插件信任/生命周期 + API 版本 + UI 一致性 + 空页兜底；
  不是加一个方法，是换架构（5+ 轮，风险高）。
- 技术上“注入同名类顶掉宿主类”也许能做到（classloader），但那是**未支持且危险**的：
  ART 多 CL、签名/更新、崩溃即白屏；不能当接口。
- 如果只是想要“完全自定义的一页”，现有 `content` 扩展已经给整页；不要替换核心页。

**折中（推荐）**：宿主加 3 个**小扩展点**，而不是 provider：

1. `collections(slot)` 只读（或继续用 `slotDir` 读文件）；
2. `labels()` 中性行标签（可选）；
3. `plugins()` 列已启用插件/版本（v37，0.3~0.5 轮）。

三个插件按需接：`mapstats` 加“按合集统计”；`mods-health` 合并/读配置；`usagestats` 不动。
这样“兼容”是**数据契约**，不是接口替换；成本低、可控。

### 11.7 探索：折叠/二级页面后 findings 怎么注入（历史）

> 用户 2026-11-10：「原先宿主模组没有二级页面，点进去就可以看到插件提示的模组冲突信息；
> 现在新插件合并并折叠了部分模组，模组冲突信息还是使用相同的接口去注入，由模组整合管理这个插件负责改接口」
> ★ 最终**不需要 `FindingsRouter`**：虚拟组行由宿主渲染，findings 仍按成员 path 聚合（§5 / §11.9）。
> 本节保留探索记录。

**现在的注入链**（判据在代码里）：

```
mods-health --Finding.anchorPath = ItemInfo.path--> 宿主 mIssues[path]
  ├─ 行上：短标签（`mods_plugin_warn_fmt`）
  └─ 详情弹窗：detail（`mods_plugin_head`）
```

**折叠/换页后为什么断**：

- `anchorPath` 只认**模组行**的 `ItemInfo.path`；行被折进组、或列表被插件页替换后，宿主没有目标行可画；
- 宿主**不会**把 `Finding` 转给另一个插件；插件页是插件自己画的，宿主也注入不进去；
- 所以“同一个接口”本身不够，缺的是**从 path 到新位置的路由**。

**四种做法**：

| 做法 | 谁改接口 | 成本 | 判断 |
|---|---|---|---|
| **A. 不替换宿主列表**，只在插件卡加折叠汇总 + 二级页 | 不改 | 0 | ✅ 宿主行还在，`mIssues` 照常；缺点：折叠只在插件卡里，不在主列表 |
| **B. 合并 mods-health 进管理插件** | 不改 | +1~1.5 | ✅ **推荐**：findings 在同一个插件里生成，想画在组汇总/二级页都行；无跨插件路由 |
| **C. 宿主定义 `FindingsRouter`，管理插件实现** | **宿主定缝，插件实现** | +1~2 | ⚠️ 可行：mods-health 不用改；路由把 `path` 映射到组/摘要/页；宿主负责渲染目标 + fallback |
| **D. 管理插件反射改宿主 `ModsActivity` / `PluginAnalysis`** | 插件猴补丁 | 低 | 🔴 不做：更新即断、白屏、不可审计 |

**“由管理插件负责改接口”的正确含义**：

- 不是“插件单方面改宿主接口”，而是**宿主先开一个适配缝**（C）；
- 管理插件负责实现 `route(Finding) -> Target`，决定“这条冲突挂在哪个组/哪一页”；
- 宿主负责：调用、渲染、插件缺失时回默认（按 `anchorPath` 找行/详情）；
- 这样 mods-health 的 `Finding` 接口一个字不用改，其他插件也能复用。

**建议（按用户 2026-11-10 最终意见修正）**：**不合并、不做独立合集页**，走 **宿主虚拟组行（§5）**：
组就是模组列表里的一行，成员收进二级详情；findings 仍按成员 path 注入，宿主在组行聚合、在详情逐条显示——
**不需要 `FindingsRouter`**，也不需要插件互相调用。C 只在“组详情要插别的插件结论”时才考虑。

### 11.8 让插件做虚拟组行：宿主加 `rows` 扩展点

> 用户 2026-11-10：「但我希望插件是可以做的这个功能的」

**今天插件做不到，不是因为插件能力不够，而是宿主没开“往列表里放行”的缝。**
正确做法是宿主新增一个 **`rows` 扩展点**（不是替换页面）：

```json
{ "id": "group-rows", "slot": "rows", "page": "mods", "entry": "com.example.Groups" }
```

```java
public final class VirtualRow {
    public final String id;            // 稳定 id（插件内唯一）
    public final String title;         // 组名
    public final String subtitle;      // "5 个模组 · 缺 1"
    public final String badge;         // 可选，宿主画在状态徽标位
    public final List<String> memberIds; // 条目 id：path 或 container!/entry（见下）
}
public static List<VirtualRow> rows(PluginApi api);   // 可选；v37
```

★ **`memberIds` 不是 `path`**：槽内文件用 `path`；游戏 APK / 模组 zip 里的地图、蓝图
`path == null`，要用 `container + "!/" + entry`（与 `PluginPicks.idOf` 同一个口径）。
v1 建议**只允许槽内文件进组**（`path != null`），自带条目可以显示、不参与。

**分工**：

| 谁 | 做什么 |
|---|---|
| 插件 | 读 `mdt-groups.json`、算成员/状态、返回 `VirtualRow`；组逻辑全归插件 |
| 宿主 | 把真实行里 `memberIds` 命中的**隐藏**（不是删文件）；插入虚拟行；用**宿主行样式**画；点击进**宿主渲染的组详情**（成员真实行 + mods-health findings）；搜索/筛选/排序把虚拟行当一行 |
| 宿主 fallback | 插件缺失/禁用/异常/旧 API ⇒ **不隐藏任何行**，回到现在的列表 |

**“把原来的删掉” = 删展示行，不是删文件**（用户 2026-11-10 强调）：

- 顶层列表 = `全部真实行 − union(所有虚拟行的 memberIds) + 虚拟行`；
- `Mods.scan` / `PluginData.pageItems()` **仍然返回全部真实模组**，只是列表不画；文件一个都不动；
- 插件缺失/禁用 ⇒ 隐藏集合为空，真实行全部回来；
- 一个模组只能属于一个虚拟行（v1）；重叠 ⇒ 只认第一个，并在日志里点出来；
- `memberIds` 里找不到的 path ⇒ 忽略；组行显示“缺 N”，不隐藏任何东西；
- 搜索要能搜到**被隐藏的成员名**（命中则组行出现）；“只看有问题的”只要任一成员有问题，组行就算有问题；
- 组详情里再画成员真实行；顶层不再重复；
- **分组/删组绝不删模组文件或改开关**；删组只是把成员行放回顶层。

**findings 不用改**：宿主仍按成员 `path` 存 `mIssues`；虚拟行只显示“2 条结论”，组详情逐条显示。
`mods-health` 一个字不改，`mapstats` / `usagestats` 也不受影响。

**约束**：

- 一个页面只认**一个** rows provider（多声明 ⇒ 只取第一个，其余忽略并提示）；
- 虚拟行不是 `ItemInfo`：别塞进 `PluginData.pageItems()`，分析器仍看全部真实模组；
- 一个模组只能属于一个虚拟行（v1），否则宿主不知道隐藏到哪一行；
- 插件 `rows()` 必须轻量（宿主每次重扫会调），重活自己缓存。

**成本**：

- 宿主：`rows` API + 行合并/隐藏 + 组详情 + 搜索/筛选/排序适配 + fallback ≈ **2~3 轮**；
- 插件：组模型 + `rows()` + 成员编辑/动作 ≈ **1.5~2.5 轮**；
- 合计 **3.5~5.5 轮**，比宿主内建多 1 轮左右，但**功能由插件实现**，且宿主不依赖它。

**这算“插件改宿主接口”吗**：不算。宿主定义 `rows` 契约，插件实现；宿主布局/fallback 不变。
和 `analyzer` / `section` 是同一类扩展点，只是作用在“列表行”上。

### 11.9 其他插件为什么不用改：数据契约不变，只换展示

> 用户 2026-11-10：「这样原来的页面的接口不就变了吗，我不想让其他插件都需要专门写一段代码适应这个」

**变的只是宿主内部的“行模型”，不是插件看到的接口。** 关键约定：

| 插件面 | 加虚拟行后 | 要不要改 |
|---|---|---|
| `contents(slot,"mods")` / `pageItems()` | **仍然返回全部真实模组**（虚拟行永不进去） | 否 |
| `ItemInfo.path` | 仍是真实模组文件路径 | 否 |
| `Finding.anchorPath` | 仍是成员 mod 的 path；宿主自己映射到组行/详情 | 否 |
| `state()` / `gates()` | 仍按**每个真实模组**调用 | 否 |
| `filter` / `sort` | 宿主先对**真实 items** 过滤/排序，再做分组展示 | 否 |
| `pickContent("mods")` / `open` / `addItem` | 仍操作真实内容 | 否 |
| `selectedItems()` | 语义不变（模组页本来就是空表） | 否 |
| `section` / `analyzer` / `action` | 照旧；虚拟行不占这些扩展点 | 否 |

**宿主必须守住的三条**：

1. **虚拟行不是 `ItemInfo`**：不塞进 `PluginData.pageItems()`，不新增 `KIND_GROUP`；
2. **`Finding` 的 key 不变**：还是成员 path；组行只做展示聚合，组详情逐条画；
3. **先插件过滤/排序，再分组**：插件看到的输入永远是真实 items；插件把某成员过滤掉，宿主就只显示还留着的成员。

这样：

- `mods-health` 不用知道“组”的存在，findings 照旧；
- `mapstats` / `usagestats` 更不受影响；
- 只有**实现 `rows` 的那个插件**要写新代码，其他插件零改动；
- 如果哪天插件想看合集，再加可选 `collections()` 只读接口，不强制。

**会破坏契约的做法**（不要做）：把虚拟行塞进 `pageItems()`、改 `Finding.anchorPath` 的含义、
让 filter/sort 收到组行、要求每个插件实现 `rows()`。这些才会逼所有插件适配。

---

## 12. 一句话

**组就是模组列表里的一行：宿主管展示/隐藏/fallback，插件通过 `rows()` 提供组；其他插件零改动。**
**四页底层不同，按“模组 → 地图/蓝图 → 存档”分阶段；先抽 `ContentRef`/`RowsModel` 小重构，不要大重写。**
**整合包降为“合集的导出格式”与“完整环境迁移”两条后置能力。**
