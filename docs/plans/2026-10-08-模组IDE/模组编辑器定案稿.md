## 1. D1：为什么是"移植成 Java"而不是"WebView 里跑 Anuken 内核"

### 1.1 内核确实可搬（评估稿的数字复核无误）

| 文件 | 行数 | `vscode.` 引用 | 依赖 | 判定 |
|---|---:|---:|---|---|
| `parser/mhjsonParser.ts` | 590 | **0** | **无 import** | ✅ 逐行可搬 |
| `schema/typeResolver.ts` | 714 | **0** | `path` + parser + schemaLoader | ✅ 搬（`path` 自己替） |
| `features/locate.ts` | 382 | **0** | parser + schemaLoader + vanillaContent | ✅ 搬 |
| `schema/schemaLoader.ts` | 181 | **0** | **`fs` `path`** | ⚠️ 换 IO |
| `schema/vanillaContent.ts` | 105 | **0** | **`fs` `path`** | ⚠️ 换 IO |
| `schema/nameListIndex.ts` | 50 | **0** | **`fs` `path`** | ⚠️ 换 IO |
| `features/diagnostics.ts` | 417 | 62 | + 6 个内核 | ⚠️ walk 是纯的，**造对象那层重写** |
| `features/completion.ts` | 213 | 39 | 同上 | ⚠️ 同上 |
| `features/hover.ts` | 160 | 36 | 同上 | ⚠️ 同上 |
| `features/colorProvider.ts` | 154 | 21 | 同上 | ⚠️ 同上 |
| `schema/contentIndex.ts` | 161 | 11 | `fs` `path` | ⚠️ 换扫盘 |
| `extension.ts` / `soundIndex` / `definition` | 239 | 35 | — | ❌ 弃（手机上无意义） |

⇒ 「2018 行、0 处 vscode 引用」是真的；**但那 2018 行里没有一行负责"画"**。

### 1.2 ★ 本机工具链盘点（这条是决定性的）

| 需要的东西 | 本机有没有 |
|---|---|
| `CodeMirror`（WebView 路线的编辑器内核） | ❌ **全盘没有**（`新版MDT` 全树 + 全局 npm 目录都搜过） |
| `typescript` / `esbuild`（把 TS 编成 JS） | ❌ **没有** |
| `.tmp-hjson-lab/node_modules` | ❌ 不存在（有 `package.json` / `package-lock.json`，**没装**） |
| 工程里现有 WebView 用法 | ❌ **`app/src` 里 `WebView` 引用数 = 0**（一条先例都没有） |
| 反过来：`javac` | ✅ 本机 JDK 25（`build.sh` 本来就在用） |

⇒ **WebView 路线的第一步就卡在"拿不到依赖"**：要么联网装 npm（本项目其他流程都靠本机 `SteamCommunity302` 走 GitHub，
npm registry 通不通**没验过**），要么把编好的 JS 当**生成物入库**（可以，但那就等于把"编辑器内核"变成一份我们不能改的二进制黑盒）。

### 1.3 三条理由（按重要性）

1. ★★ **语义只能有一份**。本工程反复吃"同一判据两处实现必分岔"的亏（§77 大小写、§111 前缀、§115 分隔线）。
   跑 TS 内核 ⇒ 同一份 hjson **两套解释**（JS 的 + 我们 `Hjson.java` 的）；高亮说 A、游戏/我们把 B 当真的，
   **而且没有任何症状**。移植成 Java ⇒ 与既有 `Hjson.java` 同一族、可对拍。
2. **零新增构建链**。本工程是**手写 `build.sh`、无 Gradle、无 npm** 的（这是它最值钱的特性之一）。
   WebView 路线要往这条链里塞一个 TS/npm 步骤，或者塞一份生成物 JS。
3. **i18n / 主题 / 自检 / `SelfTest.PAGES` 全在既有体系里**。WebView 里得把界面语言与深浅色**再喂一遍**
   （`LocaleMode` / `ThemeMode` 那套只作用于我们的 Activity）。

### 1.4 代价（不装糊涂）

| 代价 | 量 |
|---|---|
| 移植 | ~1900 行 TS → Java（机械，但真要写） |
| 渲染层 | 4 个 provider 的"造对象"层 + 高亮/悬浮/补全的原生实现 |
| 丢的东西 | ❌ **波浪下划线**（EditText 画不了 squiggly）⇒ 改成**问题列表**（反而更清楚） |
| 保留的东西 | ✅ 悬浮卡片、补全下拉、颜色预览（`ImageSpan` 小色块）、诊断列表 |

### 1.5 反方（留着，不排除）

如果将来愿意"联网装 npm / 把编好的 JS 入库"，WebView 路线**能省掉移植那 1900 行**。
⇒ 那时判据应该是：**"两种实现下同一份 hjson 的语义要逐条同判"**（拿 §8 那 68 条语料跑）。

## 2. 移植清单（照抄哪些、换掉哪些）

| 层 | TS 侧 | Java 侧对应 |
|---|---|---|
| 解析 | `mhjsonParser`（范围保留 AST：`range`/`valueRange`/`keyRange`/`quoted` + `comments[]`/`errors[]` + 重复键全留） | **原样搬**（零依赖，最该先搬的一个） |
| 类型 | `typeResolver`（路径推断 / `type:` 优先 / 泛型 / 简写） | 原样搬 |
| 定位 | `locate(offset) → {onKey,onValue,isMapEntries,contentRef,enumRef,effectRef,soundRef,teamRef,attributeRef,stackAmountRef}` | 原样搬（触屏给的是字符 offset，与光标无关） |
| 数据 | `schemaLoader` / `vanillaContent` / `nameListIndex` | **换 IO**：`fs` → 我们的 assets / 扫描器 |
| 渲染 | `hover` / `completion` / `diagnostics` / `colorProvider` | **重写壳**：造 `Spannable` / `PopupWindow` / 问题列表 |
| 编辑器本体 | （插件里没有，它是 VSCode 的） | ⚠️ **全新**：`EditText` + `Spannable` 高亮 + 滚动 + 撤销 + 输入法 |

🔴 **端口纪律**（本工程的老账）：`Hjson.java` 是"文本 → 标准 JSON 文本"（注释/格式/顺序**全丢**），
**两个生产调用点都只用它"读"**。⇒ **不要动 `Hjson.java`**，新解析器另起一个类（评估稿 §3.2 已写死）。

## 3. schema：payload、来源、以及插件缺的那一块

### 3.1 体积实测（决定"能不能全量进 APK"）

| 量 | 值 |
|---|---:|
| 文件数 | **418** |
| 原始 UTF-8 | **395 592 B** |
| deflate（`CompressionLevel.Optimal`） | **60 972 B** |
| 若走 Base64 文本常量 | 81 296 B |
| 带 `doc` 的字段 | **1386** |
| 带 `default` 的字段 | 2177 |

⇒ **全量进 APK 完全可行**：现产物 598 853 B，**+60 KB ≈ +10%**。
⚠️ **别用 Base64 Java 常量**：javac 的 class 文件里 `CONSTANT_Utf8` **上限 65535 字节**，81 KB 一坨会直接编不过
（`MapStatsTable.java` 那种 4 KB 的没事）⇒ 走 **`res/raw/mod-schemas.deflate`**（或分片常量），
生成器与版本写进文件头注释（与 `MapStatsTable.java` 同一条纪律）。

### 3.2 ★★ 插件**完全没有** `mod.json` / `mod.hjson` 的 schema —— 而那是被编辑最多的文件

评估稿 §4.2/§4.3 已指出：schema 目录里的 `mod.json` 是 **PartProgress 的取模运算**，不是元数据 schema；
417 个文件里搜 `minGameVersion` / `displayName` **零命中**。

⇒ **本轮用反射把真正的键表拿出来了**（`mindustry.mod.Mods$ModMeta`，160.4）：

```
name  internalName  minGameVersion  displayName  author  description  subtitle  version
main  repo  dependencies(Seq<String>)  softDependencies(Seq<String>)
hidden  java  iosCompatible  texturescale(float)  pregenerated  contentOrder(String[])
legacyCompatible
```

（`internalName` 是**算出来的**，不是 JSON 键；`Mods$ModDependency` = `{name, required}`。）

⇒ **交付物**：手写一份 `mod-meta` schema（约 18 个键 + 中文标签），**这是插件给不了、而用户天天用的一块**。
★ `minGameVersion` 是 `String`（与 REF §41「gradle 默认值 `custom` 要当没声明」一致）。

### 3.3 `doc` 是**英文**的（产品问题，见 §10 Q3）

1386 条 `doc` 是 Mindustry 源码里的 Javadoc 原文。悬浮卡片里要不要显示英文？
**结构化事实不需要翻译**（类型、可选值、枚举闭集、有无默认值），**散文需要**。

### 3.4 schema 从哪来（三选，我推荐第 3 条组合）

| 方案 | 成本 | 问题 |
|---|---|---|
| ① 用插件那份（build 160） | **0** | 🔴 **`default` 有 105/2177 条（4.8%）不能照原样显示**：**31 条形态坏掉**（`0.02f` → `"02"`、`"015"`、`"0001"`…，上游 `3a548135` 已修而插件早 11 天）+ **74 条非字面量**（`"60f * 6"` / `"oxygen"` / `"logicControlTimeout"`）；另有 44 条**假键**（§3.6） |
| ② 自己按上游 HEAD 重生成 | 中 | 要源码树 + javaparser + 跑一次 `HeadlessSetup`（要 natives） |
| ③ **①+修 + 反射补"存在性"** | 低 | 无（见下） |

★ **重磅好消息：②要的东西本机全都有，而且是离线的**：

| 需要 | 本机现状 |
|---|---|
| Mindustry 源码树 | ✅ `素材/Mindustry本体/Mindustry-master.zip`（**4511 条目**，`core/src` 下 **819 个 .java**，`tools/src/mindustry/tools/SchemaGenerator.java` 在位） |
| `javaparser-core` | ✅ **Gradle 缓存里有 3.28.2**（`~/.gradle/caches/modules-2/.../javaparser-core-3.28.2.jar`），另外 Gradle 发行版里还有 3.17/3.27/3.27.1 |
| Gradle | ✅ `~/.gradle/wrapper/dists` 里有 8.14.3 / 9.2.1 / 9.3.1 |

✅ **已现场核实（2026-10-06）**：`Mindustry-master.zip` 的 `build.gradle` 写着 **`versionNumber = '8'`** ⇒ 它是 **v8 开发线，≠ 160.4**
（`Version.java` 里 `build = 0` 是占位，真实版本来自构建期生成的 `core/assets/version.properties`，zip 里没有）。
⇒ **一期用方案 ①（build 160）是对的**；把方案 ② 留给"将来要跟 v8"（工具链已在本机）。

### 3.5 那 105 条不干净的 `default` 怎么处置

- **最省**：悬浮卡片**不显示 default**（`default` 占 2177 条，去掉还能再瘦 payload）。
- **最有信息**：显示但**过一遍形态闸**，闸门是**两个方向**（缺一不可）：
  ① **形态坏掉**（`^0\d+$`，即 `"02"`/`"015"`/`"0001"` —— 上游修复的判据就是"数值字面量不许被 `.` 切"）⇒ **31 条，判死**；
  ② **非字面量**（`"60f * 6"` / `"oxygen"` / `"logicControlTimeout"`）⇒ **74 条**，其中 `"oxygen"`/`"bullet"` 这类**是枚举常量、可以显示**，
     但 `"60f * 6"` 这种表达式**不能**当默认值给用户看 ⇒ 要按类型分别判，不能一刀切。
- 🔴 **绝不许**把 `"02"` 原样当成"默认值 02"给用户看（那就是"把不确定当事实"，§77.5 同族）。

### 3.6 ★ 数据侧实测（2026-10-06）：插件那份 schema 有 **44 条假键**

拿 **146~160.4 九个官方 jar** 逐个反射对账（`Versions.java`），剔掉生成器的伪键之后：

| 类别 | 条数 | 内容 |
|---|---:|---|
| **伪键**（不是字段，是生成器标记，要白名单掉） | **90** | `doc` 71 · `abstract` 9 · `values` 6 · `op`/`operation`/`ops`/`operations` 4 |
| 🔴 **假键**（九个 jar 里都不存在） | **44** | `research` ×8（`Item/Liquid/Planet/SectorPreset/StatusEffect/UnitType/Weather/Block`）· `UnitType.type/template/defaultController` · `Planet.sectorSize` · `Block.consumes` · 其余 31 条是 `mindustry.graphics.g3d.*` 网格内部字段 |
| **"缺失"的类** | 30 | 全是**嵌套类写法**（`DrawPart.PartProgress` = `DrawPart$PartProgress`）⇒ 加载器**两种写法都要试**，不是缺陷 |
| **146 之后才有的字段** | **528** | 这就是 §5 那张"逐字段最低可用版本"表的原料 |

⇒ **三条落地要求**（都是硬要求，不是优化）：
1. 🔴 **不能只信 schema**：必须按**每个版本反射出的存在性**过滤（`research` 这种假键会让悬浮提示骗人）；
2. 伪键要有**显式白名单**（否则 90 条会被当成真字段显示）；
3. `default` 要么不显示、要么过 §3.5 那两道闸。

## 6. 页面与交互（原生）

### 6.1 入口（D9）：**并进已有弹窗**，不动列表行

现状：`ModsActivity` 里**点一下模组行 = 开详情弹窗**（`ModsActivity.java:812~814 → showDetail(m)`）。
⇒ 「打开它的说明文件」做成**详情弹窗里的一个动作**。
★ 这正是第 115 轮的定案手法：**零宽度、零高度**，不碰行的宽度预算、不改常用动作的层数。

### 6.2 页面骨架（`ModFileActivity extends BaseActivity`）

```
表头：模组名（内部名）+ 文件路径 + 「只读 / 可改」徽标
├ 编辑器：EditText + Spannable 高亮（JSON/HJSON 词法 + 已知字段/未知字段两色）
├ 悬浮：点一个 token（或长按）⇒ PopupWindow 卡片
│    ├ 字段名 + 中文标签（能白拿就白拿，见 §6.4）
│    ├ 类型 / 取值范围 / 枚举闭集 / 有无默认值     ← 事实，不翻译
│    └ 「说明（原文）」可展开                        ← 英文 Javadoc，见 §10 Q3
├ 补全：输入时底部建议条（字段名 / 内容引用 / 枚举值 / 颜色名）
└ 问题列表：解析错 / 未知字段 / 类型不符（替代波浪线）
```

🔴 **三条既有硬约束**（漏了"编译通过 + 自检绿"也照样错）：
根节点 `@+id/root` + `Util.applySystemInsets(root)`；**必须注册进 `AndroidManifest.xml`**（`aapt2` 不查引用）；
必须进 `SelfTest.PAGES` + ㉛ 骨架名单。

### 6.3 只读 vs 可写（D7）—— ★ 目录形态**是官方一等公民**（定案前的现场核查）

**用户问的「游戏不认文件夹啊」不成立**，三份独立证据：

| # | 证据 | 内容 |
|---|---|---|
| 1 | ★ **我们自己的 PC 实测**（`.tmp-pctest/evidence-log2.txt`，现场与夹具都还在） | `[I] Loading mod: mdtprobe` / `[I] Loading mod: mdtprobe-report` / `RPT items=25`（基线 22）/ `RPT found=3` —— 夹具**就是文件夹**：`mods/mdtprobe/{mod.json, content/items/*.json, sprites/}` |

⇒ **目录形态不但能测，一期就能端到端验收**（新建目录模组 → 一键启动 → 游戏内容数据库里看见它）。

| 模组形态 | 一期 | 为什么 |
|---|---|---|
| **目录**（`mods/<名字>/`） | ✅ **可读可写** | 文件就在那儿；写入走既有纪律（§7） |
| ★ **zip / jar**（真机 **23/24** 是这个形态） | ✅ **"解包成目录"后可写**（见下） | **不需要重写 zip** —— 游戏两种都认 |
| zip / jar **原地改条目** | ❌ 不做 | 改一个条目 = **重写整个 zip**（条目顺序/压缩方式/时间戳），风险与收益不成比例 |

★★ **"解包成目录"这条路**（本轮新想到的，绕开了整个 zip 重写问题）：

```
mods/x.zip  →  解包到 mods/x/（先写 .part 目录，自证后再就位）
            →  原 x.zip 用 Trash.move 挪进中转站（Kind.MOD，不硬删）
            →  这一步之后它就是"目录形态" ⇒ 可编辑、可一键启动验证、随时能还原
```

| 前提 / 代价 | 说明 |
|---|---|
| 🔴 **含 `classes.dex` 的模组——"解包"硬拦（不是警告）** | 真机 A/B 实测：目录形态的 dex **加载不了** ⇒ 解包会把模组弄坏。判据现成：`Mods.Info.parts()` 的 `JAVA_DEX` 位。理由见 §6.3.1 |
| ⚠️ 条目多 | `饱和火力3.3.0.zip` 3510 条 / `Neon-vN14.zip` 2308 条 ⇒ 槽里多出一堆文件、`Mods.scan` 变慢 |
| 🔴 **不自动重打包** | 要不要变回 zip 由用户决定（我们只做"解开"，不偷偷"装回去"） |
| 🔴 启用/停用状态 | `settings.bin` 按 **内部名** 记账 ⇒ 解包后名字不变、状态保住（要断言） |

#### 6.3.1 🔴 含 `dex` 的模组**绝对不能解包**（真机实测，不再是推测）

**2026-10-06 真机 A/B 实测结论**（设备 Android 16 / API 36 + 官方 159.7；夹具是我们自己造的探针模组，
`dexdump` 复核过 dex 有效；**唯一变量 = 形态**）：

| 组 | 形态 | 结果 |
|---|---|---|
| A | **目录** `mods/mdtdex-probe/{mod.hjson, classes.dex}`（dex 已 chmod 444） | ❌ `ClassNotFoundException`（从 `ModClassLoader.findClass` 抛） |
| B | **zip** `mods/mdtdex-probe.zip`（**同一份** dex） | ✅ `Loading mod:` + 构造器跑通 |

⇒ **`DexClassLoader` 不接受目录**（`AndroidLauncher.loadJar` 把路径原样交给它）。

🔴 **所以规则要升级**（原来是"先闸住、等实测"，现在是"测出来就是不行"）：

| 模组 | 解包成目录 |
|---|---|
| **纯数据模组**（无 `classes.dex`）—— **我们的主打形态** | ✅ **可行**（zip 与目录游戏都认，PC 与真机都验过） |
| 🔴 **含 `classes.dex` 的 Java 模组** | ❌ **绝对不许** —— 解包 = **直接把这个模组弄坏（代码全丢）** |

⇒ 解包入口按 `Mods.JAVA_DEX`（判据现成）**硬拦**：**不是警告、不是"可能有问题"、不是"让用户自己决定"**。
⇒ 自检㊽第 11 条相应改成"**有 dex ⇒ 判死（不给解包）**；无 dex ⇒ 放行"。
★ 完整原始日志与清理复核：`.tmp-dex-probe/RESULT-目录形态能否加载-dex.md`

★ 一期真正的编辑对象 = **目录形态**（新建的 + 用户手工放的 + 解包来的）——这也让 v1 的"新建向导"与 v2 的"hjson 悬浮"**合体**：
**新建 → 得到目录形态模组 → 用带提示的文本编辑器写内容 → 保存 → 一键启动验收**。

一条都不许省（§51 那套 + 本项目红线）：


### 12.1 ★ 最后一条也跑完了（真机 A/B）：**目录形态加载不了 `classes.dex`**

设备 HONOR ELP-AN00 / Android 16（API 36）· 官方 APK **159.7** · 槽 `test`（数据根 = `files/`，legacy 归属）。
夹具 = 自己造的探针模组（`extends Mod`，**只在构造器里 `Log.info`**，不覆写任何方法 ⇒ 排除签名不兼容）；

| 组 | 形态 | 结果 |
|---|---|---|
| **A** | 目录（dex 已 `chmod 444`，给最好的条件） | ❌ `Failed to load mod file … Skipping` + `ClassNotFoundException`（从 `ModClassLoader.findClass` 抛） |

★ 读法：A 组 meta 读到了、**加载器也建起来了**（异常在 `findClass` 里）⇒ 是"loader 里没这个类"，
**不是**"模组没被认出来"，**也不是**权限问题。
★ 机制：`AndroidLauncher.loadJar` 把路径原样交给 `DexClassLoader`，而**它不接受目录**。
⚠️ 口径 = **159.7 + API 36** 实测；老版本未逐个验。

⇒ **产品硬结论**：解包**只对纯数据模组可行**；含 `classes.dex` 的**绝对不许解包**（§6.3.1）。
