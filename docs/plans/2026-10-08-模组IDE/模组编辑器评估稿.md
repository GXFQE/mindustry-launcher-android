## 0. 结论摘要

1. **Anuken 那个插件不能整体搬**（VSCode 扩展），**但它的"内脏"可以搬**：**2018 行纯逻辑，`vscode.` 引用数为 0**（§3.2）。
2. **它最值钱的东西不是它写的**：417 个 schema / 3084 字段 / 2177 默认值 —— 是 **Mindustry 自己的构建产物**（`SchemaGenerator`）。跟谁做编辑器无关。
3. 🔴 **但它那份 `schemas/` 是旧生成器产物，31 条 `default` 是坏的**（§4.1，有提交级实证）⇒ **自己按上游 HEAD 重新生成**。
4. 🔴 **它只认 `.hjson`**（作为产品）——但**那只是"语言注册"那一层**；schema 与文件格式无关，解析器吃严格 JSON 是子集（§4.7）。
5. **"内容写在 Java 代码里"的模组它帮不上**；但游戏**两条加载路都跑**，Java 模组顺带放的 `content/*.json` 照样被读（§4.8）。
6. ★★ **真机实测否掉了"手机内编辑 `content/*.hjson`"这个形态**：24 个模组里 **23 个是 zip/jar**，3 个样本的内容**全在 Java/Kotlin 类或 JS 里**（§5）。
7. ★ **但换到"从零造纯 JSON 内容模组"，形态就成立了**：最小形态 = **2 个纯文本文件**，不用图片、不用脚本、不用编译（§10）。
8. ★★ **5 条待验全部有答案了**（§10）：只有复数 `content/items/` 被读、无贴图不崩但没 region、无 bundle 显示内部名、`{}` 空 JSON 就能注册、名字带点能注册但贴图配不上。
9. ★ **参数暴露是主战场**：方块类有效字段 **180~290 个**；`有 default 可以不露`能砍掉 70.6%，但**"露哪些"没有自动答案，必须人肉挑**（§8）。mindmod 的解法是**手写 207 条词典 + 278 KB 表单代码**。
10. ★ **中文标签能白拿一部分**：游戏 `bundle_zh_CN` 里有 **98 个 `stat.*`**（对上 mindmod 词典 161 条的 25 条）+ **`item/block/unit/*.name` 一大批**（引用类下拉的中文直接白拿）（§8.4）。
11. ★ **贴图比想象简单**：游戏**运行时自己打包 mod 贴图**，我们只需把 PNG 写到对的位置、起对的名字（§9）。
12. **路线建议：都搞，但先可视化后文本**（三期，每期可单独交付）。两边共享 schema + `locate` 内核，只有渲染层分叉（§13）。
13. ★ **发现我们自己 backlog §2.3 的一个错判据**：`items=22` 是**原版基线**，不是"模组内容注册成功"的证据（§11）。
14. ★ **隔离机制专题**：桌面 `-Dmindustry.data.dir` **不会**改日志落点；**安卓端不会出同样问题**，因为我们读写共用 `Data.dirOf`（§12）。

## 2. 上游 schema 是怎么生成的

`tools/src/mindustry/tools/SchemaGenerator.java`（HEAD，334 行）：

| 环节 | 做法 | 行 |
|---|---|---|
| 字段名 / 类型 | **反射** `type.getFields()`，`getGenericType().getTypeName().replace('$','.')` | `:85~88` |
| 文档 / 默认值 | **解析源码**：JavaParser 扫 `../../core/src`，按类名找文件、按字段名找 `VariableDeclarator` | `:258~285`, `:97~106` |
| 继承 | `superclass` 写父类 FQCN | `:73~75` |
| `nullable` | 有 `@Nullable` 就写 | `:90` |
| 枚举 | 首次遇到写 `values: [...]` + `superclass: "Enum"` | `:120~138` |
| 原版内容表 | `writeDefaultContent()` → `allContent.json`（**要 `HeadlessSetup.setup()` 起一次游戏**） | `:40~55` |
| 手写补充 | 末尾 `new Fi("../../tools/extra-schemas").copyFilesTo(outputDir)` | `:222` |

**触发方式**（`tools/build.gradle` 原文）：

```groovy
tasks.register('updateScripts', JavaExec){
    mainClass = "mindustry.tools.ScriptMainGenerator"   // SchemaGenerator 从它里面被调
    workingDir = "../core/assets"
}
```
`outputDir = new Fi("../../build/schemas/")`（`SchemaGenerator.java:33`）⇒ 落到 `Mindustry/build/schemas/`。

**手写 schema 共 38 个**（`tools/extra-schemas/`）。

### 2.1 两条硬结论

1. 🔴 **设备上做不出 schema**：`doc`/`default` 来自**源码 Javadoc**，APK 里没有。设备侧反射最多拿"字段名 + 类型"。
2. ✅ **PC 侧重生成可行**：克隆 Mindustry → `./gradlew tools:updateScripts`（要 JDK + Gradle + JavaParser）。
   ⚠️ 它会顺带跑一次 `HeadlessSetup.setup()`，且与逻辑脚本文档生成**共用入口**。

**两个关键设计点**：

1. ★★ **`mhjsonParser` 是"范围保留 AST"**：每节点带 `range`/`valueRange`/`keyRange`/`quoted`，单独收集 `comments[]`/`errors[]`，**重复键全保留** ⇒ 能做**原位替换**。
   🔴 **我们已有的 `Hjson.java` 不是这个** —— 它是"文本 → 标准 JSON 文本"（arc 的 `Jval.read` + `toString(plain)`），**注释/格式/顺序全丢**。两个生产调用点 `Mods.java:1788`、`MapStats.java:1067` 都是"读"，够用；**要"编辑"必须有第二套**（别动 `Hjson.java`）。
2. ★★ **`locate(offset) → LocateResult`**（`locate.ts:70~147`）：一次给出"这一点底下是什么" —— `onKey`/`onValue`/`isMapEntries`/`contentRef`/`enumRef`/`effectRef`/`soundRef`/`teamRef`/`attributeRef`/`stackAmountRef`。与"光标"无关，换成触屏的字符 offset 照样成立。

### 3.3 被写成判据的"游戏语义"

- **路径推断**：`contentTypeFolders` 默认 `items→Item / blocks→Block / units→UnitType / liquids→Liquid / planets→Planet / sectors→SectorPreset / status|statuses→StatusEffect / weather|weathers→Weather`，按**路径段**匹配。
- **优先级**：显式 `type:` > 路径推断；嵌套 `type:` > 父字段推断。
- **泛型**：`Seq<T>` → 元素；`ObjectMap<K,V>` → 键任意、值按 V；⚠️ **`ObjectFloatMap` 等明确不支持**。
- **简写**：`"item/10"` 栈简写、属性 map、随机音效数组、`op: mod` 那类 PartProgress 运算。
- **颜色**：`arc.graphics.Color` 的裸 hex（6/8 位、`#` 可选），且必须"schema 说是 Color"**且**"文本能解析成 hex"。

## 4. 抄之前的坑（全部带实证）

### 4.1 🔴 那份 `schemas/` 是旧生成器产物，31 条 `default` 是坏的

**根因**（旧版 `determineJavadocAndDefault`）：

```java
//field
if(initValue.contains(".") && !(baseField.getType().isArray())){
    var split = initValue.split("\\.");
    initValue = split[split.length - 1];      // Category.turret -> turret
}
```
本意是"字段引用取末段"，**对 `0.02f` 也生效** ⇒ `["0","02f"]` → `"02f"` → 去 `f` → **`"02"`**。

**上游修复**：提交 **`3a548135`（2026-09-20）"Fixed some schema generation bugs"**，`+14/-3`，加了 `numeric` 守卫（注释原文 *"never applied to numbers"*）。
**插件最后更新 2026-09-09**（`6ee27f4`）⇒ **早 11 天，必然带病**。

**实测**：`default` 共 2177 条，**31 条**形态异常（`^0\d+$`）；实例：`Drill.json` 的 `drillEffectChance` 真值 0.02 → `"02"`，`warmupSpeed` 0.015 → `"015"`。
⚠️ 同提交还修了**第二个 bug**：旧版用 `getVariables().getFirst()`，多变量声明时所有字段都取第一个变量的 doc/default。

### 4.2 🔴 `mod.json` 这个文件名被占用了

schema 目录里的 `mod.json` **不是 mod 元数据 schema**，而是 **PartProgress 的取模运算 `op: mod`**（来源 `tools/extra-schemas/mod.json`）⇒ 按文件名查 mod 元数据会**静默拿到无关东西**。

### 4.3 🔴 `mod.hjson` 根本没有 schema

417 个文件里搜 `minGameVersion` / `displayName` —— **零命中**。`package.json:19` 的 `filenamePatterns` 虽然匹配 `**/mod.hjson`，但只给了**语法高亮**。

### 4.4 ⚠️ schema 是版本绑定的生成物（见 §2.1）

### 4.5 ⚠️ 一个目录混了三种东西 + 重复文件

FQCN 类 schema / 伪类型（`Consumes`/`Research`/`allContent`/…）/ PartProgress 运算名（33 个）；
还有 `DrawPart$PartProgress.json` 与 `DrawPart.PartProgress.json` 两种写法。

### 4.6 ⚠️ README 过期（见 §1.1）

### 4.7 ★ "它只认 hjson"的正确拆解

| 层 | 和 hjson/json 有关吗 |
|---|---|
| **schema 数据** | ❌ 完全无关（字段定义与后缀无关） |
| **解析器** | ⚠️ 吃"游戏那套宽松方言"，**严格 JSON 是子集**（`Hjson.java` 头注释："同时吃严格 JSON"） |
| **语言注册 / 文件名匹配** | ✅ **只有这一层要改**（把 `.json` 加进去） |

★ 而且**游戏自己两个后缀都收**（`Mods.java:884`）⇒ 我们生成 `.json` 是正规形态。
⇒ **"做 JSON 编辑器"与"抄那个插件"不冲突。**

### 4.8 ★ Java 模组：看"内容写在哪"，不是"模组是不是 Java"

游戏加载内容**两条独立的路，两条都跑**：

```java
Mods.java:837~843   先跑 mod.main.loadContent()        // 代码定义
Mods.java:868~895   再扫 content/<类型>/*.{json,hjson}  // 数据定义
```

⇒ 内容写在代码里 ⇒ 插件帮不上（**你说对了**）；但 **Java 模组顺带放的 `content/*.json` 照样被读**。
证据：`饱和火力3.3.0.zip` 是 Java 模组（`main: sf.SF`）却带了 474 个 JSON（塞在 `SFcontent/` 里，**目录名不对所以没被读**）。
**对我们两条硬结论**：① 只要编辑的是 `content/` 里的文件，模组里有没有 `classes.dex` 都安全；② 🔴 **永远不要碰 `classes.dex`**。

## 7. ★ 现有产品调研（2026-10-06，GitHub）

### 7.1 最相关：`lithiumr2/mindmod`

| | |
|---|---|
| 形态 | **Flutter**（含 `android/`） |
| 定位 | "Mindustry JSON & Hjson Mod Creator" —— **可视化表单 + 原始 HJSON 双模**，带贴图管理、Mod 分析器、GitHub 集成 |
| 许可 | **MIT**（`LICENSE` 原文：`Copyright (c) 2026 lithium`） |
| 发布 | **有 APK**：`beta`（2026-09-14，`app-release.apk` + `windows-x64.zip`）、`v1.0.0-experimental`（2026-09-11） |
| 成熟度 | ⭐1、**2 贡献者 / 100 提交 / 窗口 17 天**（2026-09-08→09-24）、无测试；`data/notes_*.txt` 是 AI 代理上下文笔记（西班牙语） |

**它怎么解"参数太多"**（§8.3 详述）：手写 **`docs/MINDUSTRY_DICTIONARY.md`（314 行 / 207 条 / 161 个去重字段名）**，再硬塞进可视化表单（表单相关 widget **≈278 KB Dart**）。

**它怎么解"图片"**：`lib/services/sprite_service.dart` **只有 1.4 KB**，内容是一条校验：

```dart
final expectedPixels = blockSize * 32;
if (image.width != expectedPixels || image.height != expectedPixels) → 报错
```

**它怎么解"导出"**：`export_service.dart` 用 `archive` 打 zip，目录用**老式复数**：
`content/items|blocks|liquids|units|status|sectors|weathers/` + `scripts/`
⇒ ★ **实测证明它全对**（含 `status` 不加 s 这个细节，与我们 §10.4 的实测一致）。

### 7.2 它的表有 4 条假字段（"怎么还有错的"）

161 条里 **157 条**能在 build 160 的 schema 里查到名字（96.5%）。查不到的 4 条：

| 名字 | 查到什么 |
|---|---|
| `chargeEffects` | 只在**第三方 fork** 里 —— `blahblahbloopster/mindustry-client` 的 `ChargeTurret.java` / `Blocks.java` |
| `emptyPower` / `restitution` / `waterVision` | Anuken 仓库**零命中**，全 GitHub 也只在各种 fork/模组里 |
| `MultiLib`（它代码里挂的"插件库"） | **搜不到任何公开仓库** |

⇒ **它把"原版字段"和"fork / 私有库字段"混在一张表里，还标成「V7/V8 百科词典」。** 这是手写表的典型病症：**没有权威来源，就必然会漂。**

★ **这条给出我们该守的规矩**：我们那张"露哪些字段"的小表，**每条都必须能被 schema 校验** ——
① 表里每个字段名必须在该类型的 effective fields 里，否则**构建失败**；
② **反向也要跑**（schema 新增字段要能被看见，§45.9「清单对 ≠ 清单全」）；
③ 加**元断言**：故意塞一个假字段，要求校验器**判死**。
⇒ mindmod 那种"表里有 4 个不存在的字段而没人知道"的事在我们这里**物理上不可能发生**。

1. **"手机上的可视化 JSON 模组编辑器"已经有人做出来了**（mindmod），但是 ⭐1 的个人 beta ⇒ **免费证明可行 + MIT 可直接读/借**，不是"竞品已占位"。

   ★ 支持"需求高"的证据另有其处：`MindustryTool/MindustryToolMod` ⭐**243**（在游戏里浏览/下载地图与蓝图）。
5. **没有找到「启动器 + 模组编辑器」二合一** ⇒ 我们的差异化点成立：**能直接写进当前槽的 `mods/`、能一键启动验证**。

## 8. ★ 参数暴露问题（量化）

### 8.1 有效字段数（按 `superclass` 链展开）

| 内容类型 | 有效字段 | 有 default | 无 default | 去掉 nullable/容器/贴图类后**真正要拿主意** |
|---|---:|---:|---:|---:|
| `Item` | 37 | 19 | 18 | **7** |
| `Liquid` | 45 | 22 | 23 | 9 |
| `StatusEffect` | 50 | 23 | 27 | 13 |
| `BulletType` | 178 | 161 | 17 | — |
| `Wall` | 228 | 167 | 61 | — |
| `GenericCrafter` | **233** | 168 | 65 | 33 |
| `Drill` | 240 | 171 | 69 | — |
| `UnitType` | **269** | 209 | 60 | — |
| `ItemTurret` | **290** | 222 | 68 | — |

⇒ **方块/单位这一档是 180~290 个输入框。**

### 8.2 两条出路与一条反证

1. **有 `default` 的可以不露**：全库 2177/3084 = **70.6%** 带默认值 —— 不写就等于默认。
2. ⚠️ **但"无 default"这个自动判据会捞进噪音**：`GenericCrafter` 那 33 个里 `update`/`solid`/`rotate`/`sync`/`saveData`/`destructible`/`configurable`/… **是引擎开关，不是内容参数**。
   ⇒ **「露什么」没有自动答案，只能按内容类型人肉挑** —— 这是**策划工作**，也是这个产品的主要成本。

### 8.3 内容类型分两档

| | 字段量 | 可视化 |
|---|---|---|
| **轻类型**`Item` / `Liquid` / `StatusEffect` | 37~50 | ✅ **甜区**（全渲染都行，或挑 7~13 个） |
| **重类型**`Block` / `UnitType` / 各种 Turret | 178~290 | ⚠️ 只能当"模板 + 十来个参数"，**全量渲染必死** |

### 8.4 ★ 中文标签能白拿多少（实测 `bundle_zh_CN.properties`）

游戏中文包 **3466 个键**。各前缀：

| 前缀 | 键数 | 能当什么用 |
|---|---:|---|
| `block` | 683 | **内容实例中文名**（`block.arc.name` = 劫难） |
| `unit` | 147 | 同上（`unit.aegires.name` = 玄武） |
| `sector` | 110 | 同上 |
| `stat` | **98** | **字段标签**（`stat.health` = 生命值、`stat.itemcapacity` = 物品容量…） |
| `item` | 47 | 内容实例中文名（`item.copper.name` = 铜） |
| `ability` | 43 | **能力类型中文**（`ability.armorplate` = 装甲板） |
| `lenum` | 113 | ⚠️ **不是枚举** —— 是**逻辑处理器（mlog）的指令表**（`abs`/`acos`/`ally`/`and`） |
| `setting` / `rules` / `editor` / `keybind` | 125/113/96/95 | 与内容字段无关 |

**能白拿的**：
- ✅ **引用类下拉的中文**（`Seq<Item>` / `result: liquid` / `ammo`…）—— `item.*` / `block.*` / `unit.*` / `sector.*` 一大批
- ✅ **能力类型中文** —— `ability.*` 43 条
- ⚠️ **字段标签只有一部分**：`stat.*` 对上 schema 字段名的 **59 个**；对上 mindmod 词典 161 条的**只有 25 条（15%）**
- ⚠️ **枚举取值只有一部分**（`category.*` / `database-category.*`，要逐个核对是哪个枚举的）

**手写不掉的**：字段中文标签（只覆盖露出来的那几十个）、枚举取值（闭集，一次性）、以及"每类露哪几个 + 顺序"。

### 8.5 ★ 改进方案：把硬编码压到最小

| 要素 | 来源 | 手写量 |
|---|---|---|
| 字段清单 / 类型 / 默认值 | **schema（上游生成，跟版本走）** | **0** |
| 引用下拉的中文 | **游戏 bundle 白拿** | **0** |
| 能力类型中文 | 游戏 bundle 白拿 | 0 |
| 字段中文标签 | `stat.*` 白拿 25 个 + 其余手写（只覆盖露出的几十个） | 小 |
| 枚举取值中文 | 手写（闭集） | 一次性 |
| **"每类露哪几个 + 顺序"** | **手写小表**（可参考 mindmod 的选表，但剔掉那 4 条假字段 + 加 attribution） | 小表 |
| 渲染器 | 写**一个通用**的（`number/text/bool/enum/color/内容引用/列表/嵌套`） | 一次性 |

⇒ **硬编码消不掉，但能从 mindmod 的「207 条词典 + 278 KB widget」压到「一张小表 + 一份枚举词表 + 一个通用渲染器」。**

### 10.3 ⚠️ 测试台的两个坑（踩过了）

1. 🔴 **`-Dmindustry.data.dir` 不会改日志落点**：实测 `settings.bin`/`cache`/`previews` 落进隔离目录，但 **`last_log.txt` 仍写到默认目录**（`%APPDATA%\Mindustry`）。源码对得上：`Vars.java:337` `dataDirectory = settings.getDataDirectory();`、`:459` `loadFileLogger(settings.getDataDirectory().child("last_log.txt"))` —— 日志句柄**在数据根被改之前**就打开了。

2. ⚠️ **启动命令的 `workdir` 必须已存在**（我第一把指了还没创建的目录 ⇒ spawn 失败），且**不要同时起两个实例**（会撞车 + 路径拼重）。
3. 🔴 **千万别把 `workdir` 设成仓库根** —— 游戏会在 **cwd** 下创建两个目录：

   · `saves/last_log.txt`（Steam 版更直接：`Vars.java:495~496` 的 `if(steam || Version.isSteam) settings.setDataDirectory(Core.files.local("saves/"))` —— **`Core.files.local()` 是 cwd 相对路径**，我第一次试 Steam 版就写到了仓库根）
   ⇒ 正确做法：**给游戏一个专用空目录当 workdir**（我这次就是漏了这条，事后走了回收站清理，`git status` 已回干净）。

### 10.4 顺带验证了 mindmod 的导出目录表

它用的 `content/items|blocks|liquids|units|status|sectors|weathers/` **全对** —— 与我们实测的 `oldName` 规则一致（复数为主，`status` 不加 s）。⇒ **可直接抄。**

### 10.5 编辑器硬规矩（由实测得出）

1. 🔴 **生成/写入的目录一律用复数**：`items/`、`blocks/`、`liquids/`、`units/`、`status/`、`sectors/`、`weathers/`

## 12. ★ 隔离机制专题（桌面漏日志 / 安卓为什么不会）

### 12.1 桌面（MDT-Dev）

- `ClientLauncher.java:42~44`：`String dataDir = System.getProperty("mindustry.data.dir", OS.env("MINDUSTRY_DATA_DIR")); Core.settings.setDataDirectory(files.absolute(dataDir));`
- `Vars.java:337`：`dataDirectory = settings.getDataDirectory();` ⇒ **数据根确实跟着重定向走**（`saves/`、`mods/`、`schematics/`、`server_list.json`、`last_log.txt` 全都由它派生）
- 🔴 **但实测日志仍落到默认目录** ⇒ **日志句柄打开得比 `setDataDirectory` 早**（§10.3）

**给 MDT-Dev 的修法建议**（已口头通知修）：
1. 定义**唯一**的 `dataDirOf(profile)`，所有地方从它取；
2. **读日志时不要假设**，并用启动日志里已有的 `数据目录=<dir>` 与"日志实际落点"对一次，发现漂移；
3. 加一条**真空断言**："本 profile 的数据根里存在 `settings.bin`" —— 比"我传了参数"强得多。

### 12.2 安卓端：**不会出同样的问题**（机制不同 + 设计如此 + 设备实证）

| | 桌面 | 安卓 |
|---|---|---|
| 数据根怎么定 | `ClientLauncher` 读属性/环境变量 | `AndroidLauncher.java:230~231` 在 **`onCreate` 里一次性设定**（值来自我们注入的同一属性） |
| 日志路径 | `Vars.java:459` | **同一行代码** |
| 结果 | 句柄早开 ⇒ 固定写默认目录 | 数据根在早期就设好 ⇒ **日志跟着数据根走** |

**设备实证（三份日志，各归各槽）**：

```
files/last_log.txt          381 B  2026-10-05 22:32   ← 见下（不是漏）
slot-default/last_log.txt   509 B  2026-10-05 17:04   ✅
slot-test/last_log.txt      442 B  2026-10-05 15:22   ✅
slot-冲突演示/last_log.txt   284 B  2026-10-05 14:41   ✅
slot-模组演示/               —— 没有日志（该槽从没被启动过）
```

**`files/last_log.txt` 那份不是漏**：设备自检报告 `hub/report-m3.txt` 第 258/260 行给出判据

```
258:    当前布局：marker=test  files/有内容=true  认定本体=test（在 files/）
260:  ✅ 不变式：槽「test」→ files/ ？ 实得 true，应为 true
262:  ✅ 不变式：槽「default」→ files/ ？ 实得 false，应为 false
```

对照 `Paths.java:23~25` 记录的**唯一例外**：**远古包（`build ≤ 146`，dex 里没有该属性）只能写 `files/`** ⇒ 那一刻本体被临时改名到 `files/`，由 `Data.legacyOwner` 标记记录，`Data.dirOf` 会把它翻译回来。
⇒ `files/` 里那一整套是 **`test` 槽"借住"时游戏写的**，是设计内行为。

### 12.3 我们天然躲过这个坑，靠的是一条纪律

**"日志在哪"只有一个判据来源 = `Data.dirOf(槽)`**：

| 用途 | 代码 |
|---|---|
| 日志页 | `LogActivity.java:261` `new File(dataRoot, "last_log.txt")`（`dataRoot` 来自 `dirOf`） |
| 主页「看日志」 | `MainActivity.java:595` `new File(Data.dirOf(this, useSlot), "last_log.txt")` |
| 模组页（冲突体检摘日志行） | `ModsActivity.java:505` 同上 |

而 `LogActivity.java:54~56` 把这条不一致风险**明写出来了**：

> 永远是**当前槽**的 `last_log.txt`。切了槽，这里看到的就是另一个槽的日志。F0 之后它通常是 `…/slot-<槽名>/last_log.txt`；**只有当远古包（`build ≤ 146`）正在／刚跑过、本体被临时借住 `files/` 时，才会回落成 `…/<pkg>/files/last_log.txt`**

⇒ **桌面那个 bug 的本质是"写的地方和读的地方不是同一个判据"**；我们读写共用 `dirOf`，结构上不会分叉。

### 12.4 安卓端真正要防的是另一件事（已有两道闸）

不是"日志漏写"，而是**注入整体失败**：游戏包不认 `mindustry.data.dir`（换 fork / dex 里没那个字符串 / 注入时机晚了）⇒ 游戏**静默**写默认根 `files/`，**存档与模组全在 `files/`**。

1. **`Compat.java:38`**：直接探 dex 里有没有 `mindustry.data.dir` ⇒ `MainActivity.java:1057` 据此决定走「真隔离（属性注入）」还是「改名交换」
2. **自检不变式**（报告 259~262）：`dirOf 指向 files/` ⟺ `该槽是 shared 或标记认下的本体` —— **注入失败会让它当场判死**

## 13. 路线建议：都搞，但先可视化后文本

### 13.1 为什么"都搞"不是 1+1

| 能力 | 文本侧 | 可视化侧 | 共享？ |
|---|---|---|---|
| schema 数据（字段/类型/默认值） | ✅ | ✅ | **完全共享** |
| 类型解析（"这个位置是什么类型"） | `locate(offset)` | "控件 ↔ 节点" | **完全共享** |
| 文本 ↔ 模型 映射 | 解析 + range | 序列化（反向才要 range） | **大部分共享** |
| 渲染 | 高亮/补全/悬浮 | 控件 | ❌ 只有这一层分叉 |

★ **文本侧的三件套（高亮/补全/诊断）就是 Anuken 那 2018 行内核** —— 0 处 vscode 引用、MIT ⇒ **原样跑在 WebView 里**（本来就是 TS），只写 DOM 层 + CodeMirror。⇒ **"文本编辑器很贵"这个判断要下调。**

★ **只做"新建向导"可以完全绕开最贵的内核**：需要序列化，**不需要**范围保留解析器 / locate / 补全 / 高亮。
⚠️ 一旦要"打开别人的 hjson 并用表单改"或"文本编辑"，就**必须**有无损 AST（注释/未知字段/重复键全保），否则**一切换模式就吃掉用户手写的东西**。

### 13.2 三期

| 期 | 做什么 | 要什么内核 | 交付价值 |
|---|---|---|---|
| **一期** | **新建向导：可视化 → 文本**，只做「物品」+ 一张图 | schema 字段表 + 序列化（**不碰 WebView**） | "在手机上从零做出第一个模组" |
| **二期** | **打开已有模组：只读文本 + 高亮 + 未知字段诊断** | 抄插件内核跑 WebView（**只读，不改文件**） | "看懂别人的模组"，**零写路径风险** |
| **三期** | **可写文本 + 双模切换** | 无损 AST | 真编辑器 |

★ 一期与二期**可并行**（一期不需要解析器，二期不改文件）。

### 13.3 一期最小闭环

```
槽页「模组」行 → 「新建内容模组…」
  → 填：模组名 / 显示名
  → 选：内容类型（item / block / liquid / status …）
  → 选：具体基类（下拉，来自 schema 里 abstract == false 的子类）
  → 表单填字段（按 schema 出控件，带 doc 说明与默认值）
  → 预览生成的 JSON
  → 保存到 <当前槽>/mods/<internalName>/mod.json + content/<复数目录>/<名字>.json
  → 用我们自己的 Mods/MapStats 扫一遍自证（★ 只是自证，不是验收）
  → 一键启动游戏 → 在内容数据库里看到它 = 真验收
```

**必须遵守的既有定论**：
- 🔴 写入位置走 `Data.dirOf` / 当前槽，**不许硬编码**
- 🔴 **文件名决定内容 id**（`<小写化模组前缀>-<文件名主干>`，§10.2 实测）
- 🔴 目录用**复数**（§10.2 实测）
- 🔴 内容名不许含 `.`（§9）
- 🔴 只往 `content/` 加文件，**永远别碰 `classes.dex`**（§4.8）

### 16.0 怎么跑的（一次启动答完四个问题）

  Java 侧按名匹配会找不到 ⇒ **造 zip 夹具要用 `ZipArchive.CreateEntry("content/items/x.json")` 手写条目名**（否则得到假阴性）

### 16.1 ★ 撤回一条硬规矩：**内容名/贴图名都可以含 `.`**

§9 与 §10.5 那条"不许含 `.`"是**读串了源码上下文**：

```java
:388  baseName = file.nameWithoutExtension(),
:389  regionName = baseName.contains(".") ? baseName.substring(0, baseName.indexOf(".")) : baseName;   // ← 只用于下面这条警告
:393  if(!prefix && !Core.atlas.has(regionName)) Log.warn("Sprite '@' in mod '@' attempts to override a non-existent sprite.", ...);
:410  String fullName = ((prefix && ...) ? mod.name + "-" : "") + baseName;   // ← 真正打包用的名字：**未截断**
:412  packer.add(getPage(file), fullName, new PixmapRegion(pix));
```

⇒ `regionName`（截断形态）**只服务于 `sprites-override` 的存在性警告**；`sprites/` 走前缀那条，打包名 = `mod.name + "-" + baseName`。
**实测**：`sprites/probe.dotted.png` ⇒ `RPT item mdtprobe-probe.dotted | has=true | region=mdtprobe-probe.dotted | w=32 h=32`。

⇒ 🔴 **编辑器不必禁止 `.`**（原规矩作废）。⚠️ 适用范围：实测口径 **160.4**；老版本未逐个验（要验就换 jar 跑同一条夹具）。

### 16.2 方块贴图尺寸**不校验**；无贴图的兜底是 `error` 张 48×48

| 夹具 | size | 贴图 | 结果 |
|---|---:|---|---|
| `pw1` | 1 | 32×32（对） | `has=true w=32 h=32 expect=32` |
| `pw2` | 2 | **32×32（故意错）** | `has=true w=32 h=32 **expect=64**` ⇒ **照收，不报错、不缩放** |
| `pw3` | 2 | 64×64（对） | `has=true w=64 h=64 expect=64` |
| `pw4` | 1 | 32×32（放在 `sprites/` **根目录**而非 `sprites/blocks/`） | region 名**一样**是 `mdtprobe-pw4` ⇒ **路径只决定 atlas 页归属，不参与 region 名** |

无贴图（`probe-a` / zip 里的 `zipitem`）：
```
RPT item mdtprobe-probe-a | has=false | region=error | w=48 h=48 | uiHas=false
```
⇒ 兜底是 **arc 的 `error` 区域（48×48 花图）**，且 `-ui` 图标也落空 ⇒ 编辑器文案可以照实写"会显示成花图"，**不用再推理**。
⚠️ 因此"贴图尺寸"这条**不能靠游戏报错来提示用户** ⇒ 只能**我们自己校验**（mindmod 那条 `size×32` 检查是必要的，不是多余的）。

### 16.5 ★★ 最后一条也跑完了：**目录形态的模组加载不了 `classes.dex`**（真机 A/B 实测）

设备 HONOR ELP-AN00 / Android 16（API 36）· 官方 APK **159.7** · 槽 `test` · 启动方式 = 启动器主界面「继续上次」。

**夹具**：自己造的探针模组（`extends Mod` 且**只在构造器里 `Log.info`**、不覆写任何方法 ⇒ 排除签名不兼容）；
`dexdump` 复核 dex 有效（`class_defs_size=1`、`Class descriptor = 'Lmdtdex/DexProbe;'`）。
**唯一变量 = 模组形态**：

| 组 | 形态 | 结果 |
|---|---|---|
| **A** | 目录 `mods/mdtdex-probe/{mod.hjson, classes.dex}`（dex **已 chmod 444**，给最好的条件） | ❌ `[E] Failed to load mod file … Skipping` + `ClassNotFoundException: mdtdex.DexProbe`（从 `ModClassLoader.findClass` 抛出） |
| **B（对照）** | zip `mods/mdtdex-probe.zip`（**同一份** dex） | ✅ `Loading mod: mdtdex-probe` + `RPT-DEX constructor ran` |

★ **读法**：A 组 meta 读到了（否则会报"没有 mod.json/mod.hjson"）、**加载器也建起来了**
（异常是 `ModClassLoader.findClass` 里抛的）⇒ 是"这个 loader 里没有这个类"，
**不是"模组没被认出来"、也不是权限问题**。
★ **机制**：`AndroidLauncher.loadJar` 把路径交给 `DexClassLoader`，而**它不接受"目录"**（要的是含 `classes.dex` 的 jar/apk/dex 文件）。
⚠️ 口径：实测于 **159.7 + API 36**；老版本未逐个验。
★ 完整原始日志与清理复核：**`.tmp-dex-probe/RESULT-目录形态能否加载-dex.md`**（+ `evidence-zip-form.log`）

🔴 **对产品的硬结论**：
1. 「**把 zip 解包成目录**」这条路 —— **只对纯数据模组可用**（我们的主打形态，✅ 仍然成立）；
2. 对**含 `classes.dex` 的 Java 模组绝对不能用** —— 解包 = **直接把这个模组弄坏（代码全丢）**；
3. ⇒ 解包入口必须按 `Mods.JAVA_DEX` **硬拦**（**不是**警告、不是"可能有问题"）。

（原判断是"源码读不出来、先闸住等验"；现在是**测出来就是不行** ⇒ 规则的依据从"谨慎"升级成"实测"。）
★ 避坑记录：`adb push <本地文件> <远端目录>/` 在这台机器上**把远端文件名截断成了 `mdtd`**（内容对、名字错）
⇒ 推完**必须用 `test -f` 复核名字**，别信 `push` 的"1 file pushed"。
