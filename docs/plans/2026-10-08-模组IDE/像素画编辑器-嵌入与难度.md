> 承接：`评估稿`（可行性）· `面板功能清单`（要哪些功能）· `开源可抄清单`（能抄哪一层）。

## 0. 结论

1. **你的直觉对：难度不低** —— 但我把账重算后发现，**难点分布极不均匀**：
   **画板本身（触摸/缩放/绘制）是"没先例但可控"**，**真正会埋雷的是"编辑器 ↔ 画板 ↔ JSON"三者的状态一致性**（§2）。
2. ★ **"嵌入"这个提法本身要改**：不该是"把画板嵌进编辑器"，而应该是
   **两者共享同一个「模组工程」模型，"嵌入"退化成"两个视图 + 一个入口"**（§4）。
3. ★ **前置顺序有硬约束**：**编辑器还不存在** ⇒ 现在谈"嵌进去"是无处可嵌。
   可行的顺序是 **先做画板（独立入口，不依赖编辑器）→ 编辑器落地后打通入口**（§6）。
4. ★ **降风险只有一条路：最窄的竖切** ——
   「打开一张**现有**贴图 → 改两个像素 → 存回 → 游戏里看见变化」，一次把全部不确定性打掉（§5）。

## 1. 难度分解（★ 比我上一版估的高，说明理由）

上一版我估 **1200~1600 行**。重算后上调到 **≈1500~1900 行**，差额来自两处我上次没算足：
**与模组/JSON 的耦合**、**落页面要交的"工程税"**（insets / PAGES / ㉛ / `Trans` / 两边资源 / 台账 / 自检）。

| 部件 | 量（行） | 难度 | 依据 / 为什么 |
|---|---:|---|---|
| **画布 View**：触摸→像素、整数缩放、平移 | 300~450 | 🔴 **最高** | 全仓库 `onTouchEvent`/自定义 `onDraw` **零命中**（唯一匹配是自检里的堆栈字符串）；开源那三个也**没给出可搬实现**（一个在 183 KB 的 Activity 里、一个在 `PApplet` 里、一个在 libGDX `Actor` 里） |
| 绘制工具：铅笔/橡皮/填充/取色/直线矩形 | 200~300 | 🟡 中 | 算法教科书级；但要按"**每个操作一个类**"（ansdoship 的 `editor/buffer/*` 就是这么分的）设计对 |
| 撤销 / 重做池 | 80~120 | 🟢 低 | 有现成架构可参考（`ToolBufferPool` 289 行）；⚠️ 上限要**按字节**不是按步数 |
| 调色板 + 取色器 | 150~250 | 🟢 低 | `PaletteView`(192) / `ColorPickerView`(222) 可直接搬（只依赖注解） |
| PNG 编解码 + 落盘 | ~100 | 🟢 低 | 两头都实测过：`Bitmap.compress` 的 PNG arc 能解；外部 PNG 写进 `sprites/` 游戏认 |
| 🔴 **与编辑器 / JSON / 模组的耦合** | 200~300 | 🔴 **高** | §2 —— 名字↔贴图、`size`↔画布尺寸、"谁是真源"、同名先问、游戏在跑先拦 |
| 页面壳 + 入口 + 文案 + i18n + 自检 | 300+ | 🟡 中 | manifest / `SelfTest.PAGES` / ㉛ 骨架 / `applySystemInsets` / `Trans` / `values`+`values-zh` / `SRC-02` 台账 / 新自检节 —— **一条都不能漏**（漏了都是"编译过、自检绿、真机不对"） |
| **合计** | **≈1500~1900** | | 参照量级：`Msch.java` 55 KB / 第 119~120 轮的 `ModSprites`+生成表+集成那一轮 |

★ **一句话**：**"画得出来"是中风险，"改对地方"才是高风险**。

## 2. ★★ 真正的坑：不是画板，是"两处真相"

文本编辑器改的是 **JSON**，画板改的是 **PNG**。两者动的是**同一份模组**，于是有三条**双向耦合**，
而每一条错了都是**静默的**（不崩、不报错，只有进游戏才看得出来）：

| # | 耦合 | 错了会怎样 | 依据 |
|---|---|---|---|
| **C1** | **内容名 ↔ 贴图名**：注册名 = `<模组名>-<文件名主干>` | 文本里改了内容名（= 改文件名）⇒ 贴图**失配**（旧图成了孤儿、新名字没有图） | REF §81.1/§81.2（注册名规则；目录层级不进注册名） |
| **C2** | **`size` ↔ 画布尺寸**：方块贴图应当 `size×32` | 文本里把 `size` 从 2 改成 3 ⇒ 画布该变 96×96，但 PNG 还是 64×64 ⇒ **游戏不报错、画出来错位**（游戏不校验尺寸，2026-10-06 实测） | REF §81.3 + 2026-10-06 实测 |
| **C3** | **谁是真源** | 两边同时开着、各自持有快照 ⇒ 后写的覆盖先写的（与 §85.14 那条"同一份判据两种详略"同族） | 本工程反复的教训：**判据只能有一份** |

★ 这三条**必须在"模型层"里一次性解决**（§4），不能塞在某个页面的 `onClick` 里 ——
否则又是"同一件事两处实现、迟早分岔"（§77 / §111 / §115 都栽在这上面）。

## 3. "嵌入"的四个选项

| 选项 | 长什么样 | 优点 | 代价 |
|---|---|---|---|
| **A. 同屏分栏 / 抽屉** | 编辑器页里有个"贴图"抽屉，展开就是画板 | 切换最快、上下文全 | 🔴 手机竖屏**装不下**（文本框 + 画布 + 工具条）；画布被挤小 = 画不准（像素画最怕这个） |
| **B. 两个页面互相跳** | 编辑器 ⇄ 画板，各自全屏 | 各自都能做好；符合现有导航（槽页→二级页） | 需要传"定位信息"并**在本页重算派生量**（§109 的教训） |
| **C. 字段就地弹窗** | 在 JSON 里点某处 ⇒ 弹小画板 | "嵌入"感最强 | 🔴 文本编辑器里做锚点交互成本高；小画板更难画 |
| **D. 两个独立入口** | 模组页两行：「编辑内容」/「贴图」 | 最省事、零耦合 | 用户在两边手动保持同步（= 把 C1/C2 的坑留给用户） |

★ **我的建议：B + D 的组合**，理由是：
- **B** 让两个工具各自全屏做好（画布不能被挤）；
- **D** 保证**画板不依赖编辑器** ⇒ 现在就能开工（§6）；
- 等编辑器落地，把"入口"从两个变成"互相跳"（**画板代码一行不改**，因为目标/落点都是**参数**）；
- **明确不做 A**：同一个屏幕上，"能看清 JSON"和"能画准像素"是互相打架的。

## 4. ★ 关键建议：不要"互相嵌入"，要**共享一个「模组工程」模型**

现在这些知识**散在三处**：`ModSprites`（贴图索引/注册名）、`MapStats*`（内容表）、`Mods`（元数据/扫描）。
画板要读它、编辑器也要读它 ⇒ 不抽出来就**必然出现第二份判据**。

建议抽一层（名字随便，比如 `ModProject`），**只做"这个模组工程的只读真实情况 + 两个写入口"**：

| 它该提供 | 内容 | 谁在用 |
|---|---|---|
| 定位 | 模组目录 / 内部名 / 形态（目录 or zip） | 两个视图 |
| 内容清单 | `content/<类型>/<名>.json` 读出来的：名字、`type`、**`size`**、朝向 | 编辑器（文本）、画板（尺寸） |
| 贴图清单 | 按 `ModSprites` 现有规则算出的：**注册名 ↔ PNG 路径** | 两个视图 |
| ★ **一致性判据（C1/C2）** | "这个内容的贴图应该是哪个名字、多大" —— **一份实现，两个视图都调它** | 两个视图 |
| 写入口 | 写 JSON / 写 PNG（共用 `.part` + rename + 同名先问 + 游戏在跑先拦） | 两个视图 |
| ⚠️ 明确不做 | 不做 UI、不做缓存策略、不持有"用户正在编辑的文本"（那是编辑器的事） | —— |

⇒ 有了这一层，"嵌入"就退化成：**两个视图 + 一个入口 + 一份一致性判据**。
⇒ 而且它**顺便服务已发布的既有功能**（蓝图缺件判定、地图统计都在这套知识上）。

---

## 5. ★ 降风险：只做"最窄的竖切"

不要一次做「画板 + 编辑器 + 联动」。先做这一条，**把全部不确定性一次打掉**：

```
模组详情弹窗 → 「贴图…」→ 列出这个模组的贴图（ModSprites 已经能列）
            → 点一张 → 打开画板（画布尺寸 = 这张 PNG 自己的尺寸，不用问 JSON）
            → 改两个像素 → 保存（.part + rename；同名先问；游戏在跑先拦）
            → 一键启动游戏，看见变化 = 真验收
```

**这条竖切覆盖**：触摸→像素映射、重绘、PNG 编解码、落盘纪律、游戏认不认。
**这条竖切不含**：新建内容、`size` 联动（C2）、调色板、取色器、编辑器的嵌入。

★ 它的价值**独立成立**：这就是"**修别人模组的贴图**"这个真实场景（`ModSprites` 已经把
"按注册名取 PNG 字节"做完了 ⇒ 起稿来源几乎白拿）。
★ 而且它**不需要"新建内容"** ⇒ **不依赖模组编辑器**。

## 6. 前置顺序（硬约束）

**编辑器不存在 ⇒ 现在无处可嵌。** 三条路：

| 路线 | 做什么 | 评价 |
|---|---|---|
| **① 先竖切画板**（推荐） | 上面的最小闭环；入口并进**模组详情弹窗**（§115 的定案手法：并进已存在的弹窗 = 零宽零高） | 现在就能开工、不依赖任何未落地的东西 |
| ② 先做编辑器 | 编辑器落地后再一起想嵌入 | 拖得久，而且画板的"画布那块"风险**一直没被验证** |
| ③ 先做共享模型层 | 先抽 `ModProject`（§4），两个功能都往上长 | 更干净，但**它唯一的消费者还没有**（等于先造抽象）——除非打算连着编辑器一起做 |

★ 我倾向 **① →（编辑器落地后）打通入口 → 需要时再补 ③**。
理由：本工程的教训是"**判据要在有第二个消费者时才抽**"（否则抽早了还要改）；
但**C1/C2 那两条一致性判据要一开始就写在"一份实现"里**（不能先在画板页里内联一份）。
