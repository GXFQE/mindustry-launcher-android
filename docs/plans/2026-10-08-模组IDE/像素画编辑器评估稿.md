## 0. 结论摘要

1. ✅ **可行，而且明显比模组编辑器那条线便宜** —— 因为"造贴图"要用到的底层能力**仓库里几乎全有了**（§1）。
2. 🔴 **真正全新的只有一件：可触摸的绘图面**（全仓库 `onTouchEvent` / 自定义 `onDraw` **零命中**，§1.2）。
   但**精度不是问题**：32×32 的画布铺满手机宽度时**每格约 30 px**，手指点得准；多格（96×96）才需要缩放。
3. ✅ **最关键的一环本轮实测通过**：Android `Bitmap.compress(PNG,100)` 的产物是 **8 位 RGBA、非隔行**，
   arc 的 `Pixmap(byte[])`（**游戏加载模组贴图走的就是这一句**）**逐张解开**（§2.2）。
4. ✅ **尺寸规则不用调研**：仓库 §81.3 已经定了 —— **32 px = 1 格，PNG 的宽高就是方块的 size**，
   而且 `ModSprites` 已经在读 PNG 的 IHDR 拿尺寸（§2.1 又补了原版普查）。
5. ⚠️ **真正的分叉不在技术，在"画完放哪儿"**：模组编辑器**还没落地**（Activity 列表里没有），
   而 zip 形态的模组**不能原地改**（上一轮真机实测：解包成目录会让含 `classes.dex` 的模组直接坏掉）。
   ⇒ 这是唯一需要你拍板的地方（§5）。

## 1. 仓库里已经有什么（成本已经被摊掉的部分）

### 1.1 现成能力盘点

| 能力 | 在哪 | 说明 |
|---|---|---|
| **读/解 PNG** | `MapLoad.java:64` `BitmapFactory.decodeStream`；`:192` `Bitmap.createBitmap(pixels,w,h,ARGB_8888)` | 从游戏 APK 的 zip 里直接取图 |
| **写 PNG** | `MapLoad.java:197` `bmp.compress(Bitmap.CompressFormat.PNG, 100, out)` | 已经在生产路径上用着（地图预览缓存） |
| **逐像素** | `MapPreview` / `MsavTiles`（纯 Java，可在 PC 单独验）；`MschSheet.pixels()` | 已经有"不碰 Android 的像素内核"这一层 |
| **region 命名规则** | `ModSprites.java`（16.9 KB，**照抄游戏 `Mods.java:382~411`**） | `sprites/**` 递归 → 注册名 = `模组名-文件名主干`；目录层级不进注册名 |
| **PNG 头读尺寸** | `ModSprites` 读 IHDR | 32 px = 1 格 ⇒ 贴图宽高**就是** size（REF §81.3） |
| **方块朝向** | `ClassRotateTable`（136 类 / 32 转）+ `BlockTable` | 画一张要转的方块时，编辑器可以提示朝向 |
| **配色来源** | `BlockTable.java:20` / `MapLoad` 读 APK 的 `sprites/block_colors.png` | 想做"游戏配色板"是现成的 |

### 1.2 缺的（就是要新建的）

🔴 **全仓库没有"能画的 View"**：`extends View` / `onTouchEvent` / `onDraw` **零命中**
（唯一匹配是 `SelfTest.java:3216` 里一条堆栈字符串）。

要新建的清单：

| # | 东西 | 量级（估） |
|---|---|---|
| 1 | `PixelCanvasView extends View`：缩放/平移/网格/透明棋盘底/屏幕坐标↔像素坐标 | 300~450 行 |
| 2 | 工具集：铅笔 / 橡皮 / 油漆桶（flood fill）/ 直线 / 矩形 / 椭圆 / 取色 | 200~300 行 |
| 3 | 撤销 / 重做（快照式：32×32×4 = **4 KB/帧**，100 帧 = 400 KB） | 60~100 行 |
| 4 | 调色板（当前色 + 前色 + 预设 + 取自现有贴图 / 游戏配色） | 150~250 行 |
| 5 | 保存向导（选模组 / 选内容名 / 尺寸校验 / 同名先问 / `.part` 就位） | 250~350 行 |
| 6 | 页面壳（`BaseActivity` + insets + manifest + PAGES + ㉛） | 100 行 + 布局 |
| 7 | 文案（走 `Trans`，`values/` + `values-zh/` 两边） | 40~60 条 |
| **合计** | | **≈ 1200~1600 行 Java + 1 个布局 + 1 个新自检节** |

★ 参照量级：`Msch.java` 55 KB / `ModSprites` 16.9 KB / `MschSheet` 14.3 KB。
⇒ **是一轮能交付的活**（第 119~120 轮做了 `ModSprites` + 生成表 + 集成，也是这个量级）。

## 2. 本轮新增实测（两个只读探针）

### 2.1 原版贴图尺寸普查（2201 张 PNG）

来源：`素材/01-游戏本体/Mindustry/源码/Mindustry-master.zip` 里的 **`core/assets-raw/sprites/**`**（游戏自己的原始图，不是图集）。

| 目录 | 文件数 | 尺寸分布（前几） | 对编辑器的意义 |
|---|---:|---|---|
| **items** | 33 | **33/33 都是 32×32** | ✅ **甜区**：尺寸唯一、没有叠加层 |
| **statuses** | 20 | 32×32 ×19（1 张 38×38） | ✅ 甜区 |
| **blocks** | 1660 | 32×32 ×818 · 96×96 ×258 · 64×64 ×173 · 128×128 ×104 | ⚠️ **= `size×32` 正方形**：`turrets` 128（size 4）、`production` 96（size 3）、`power` 160（size 5）⇒ 规则确认 |
| **units** | 288 | 48/64/96/128… | ⚠️ **不是帧动画**（`-N.png` 帧后缀 **0 个**），而是**本体 + 零件**（`-cell`/`-leg`/`-blade`/`-heat`/`-foot`/`-joint`）⇒ 单体好画、拼装难 |
| effects / ui / rubble / teams | 52 / 129 / 10 / 4 | 各种 | ❌ 不是"内容贴图"，不在一期范围 |

⚠️ 两条要记住的：
1. **方块有 `-top` / `-glow` / `-team` 这类同尺寸叠加层**（`defense/force-projector-top.png`、`build-tower-glow.png`），
   和本体**同尺寸**。一期只画本体是对的，叠加层放后面（§6）。
2. **非正方形有 69 张**（`blocks/` 下），都是 `environment/character-overlay*` 这种异形 ⇒ 与内容贴图无关。

### 2.2 ★★ Android 编码 → arc 解码（编辑器成立的关键一环）

**为什么要测**：编辑器保存时要走 `Bitmap.compress(PNG,100)`，而游戏加载模组贴图走
`DataImagePacker` → **`new Pixmap(file.readBytes())`**。这两头接不上，编辑器就白做。

**素材（都是真产物、不是我造的）**：设备 `hub/previews/*.png` —— `MapLoad.java:197` 用 `Bitmap.compress` 写的。

**做法**：只 pull 了 3 张到本地，用**游戏自己的 jar** 跑 `new Pixmap(bytes)`（与游戏同一句）。

| 文件 | PNG 头 | arc 解码 |
|---|---|---|
| `0089fac9c37ae39f.png`（20 036 B） | 125×125 · 位深 8 · **颜色类型 6 = RGBA** · 非隔行 | ✅ 125×125，`get(0,0)=D3D1FFFF` 等取样正常 |
| `0128a64f549ac27d.png`（14 409 B） | 100×100 · 8 · **RGBA** · 非隔行 | ✅ 100×100 |
| `03ca8dca3cfc87eb.png`（20 250 B） | 123×123 · 8 · **RGBA** · 非隔行 | ✅ 123×123 |

⇒ ✅ **Android 的 PNG 编码器产出标准 8 位 RGBA 非隔行 PNG，arc 完全能吃**。
配合 **2026-10-06 的 PC 实测**（外部工具生成的 PNG 写进 `sprites/` 后，游戏里 `has=true`、尺寸正确）
⇒ **"画 → 编码 → 游戏打包成 region"这条链，两头都有实测，中间那一句是同一个解码器**。

⚠️ 口径：3 张样本、都是地图预览（大图、基本不透明）。**32×32 带透明的贴图**没单独测过
（同一条 PNG 编码路径，风险低但按本工程纪律如实标注）。

## 3. 硬约束（照本工程既有纪律，不是新增调研）

| 约束 | 依据 |
|---|---|
| 🔴 **PNG 尺寸必须与方块 JSON 的 `size` 一致** | 游戏**不校验**（2026-10-06 实测：`size:2` 配 32×32 照收、不报错、画出来小一半）⇒ **编辑器必须自己保证**，写图时顺带写/校验 JSON |
| 🔴 **只对目录形态模组可写** | zip 原地改 = 重写整个 zip（已否决）；且真机实测过：**含 `classes.dex` 的模组解包成目录 = 直接坏掉**（`ClassNotFoundException`）⇒ 解包只能对纯数据模组 |
| 🔴 落盘：**`.part` + rename**；同名**先问**；游戏在跑**先拦** | 与地图 / 蓝图 / 存档三条线同一条纪律 |
| 🔴 路径只从 `Data.dirOf(ctx, slot)` 派生 | §12 那条"写的和读的必须同一个判据" |
| 🔴 新 Activity **五件套**：manifest 注册 / `SelfTest.PAGES` / ㉛ 骨架 / `Util.applySystemInsets(root)` / 文案走 `Trans` | 漏任一条都是"编译过、自检绿、真机不对" |
| 🔴 文案**两边都加**（`values/` + `values-zh/`）；**随正式版发出去过的 key 不许删** | `RES-01/02` 抓不到"只在默认目录存在的 key"；语言包靠 key 兼容 |
| ⚠️ 撤销内存设上限 | 160×160 = **100 KB/帧**，比 32×32 的 4 KB 大 25 倍 |
| ⚠️ 触屏文案：`Trans.bind` 对 `EditText` 是 `setHint` | 2026-10-07 真踩过（搜索框被筛空） |

## 4. 技术风险评估

| 风险 | 判 | 为什么 |
|---|---|---|
| 触摸精度 | **低** | 32×32 铺满 ≈30 px/格；单格方块 32、双格 64，只有 3 格以上需要缩放 |
| 缩放 / 平移与绘制抢手势 | **中** | 需要一个明确的"画笔 / 移动"模式切换或双指平移；这是这块最需要打磨的地方 |
| PNG 编码 | **低** | 已实测（§2.2）；且 `MapLoad` 生产路径在用 |
| 透明通道 / 边缘渗色 | **低** | 8 位 RGBA 实测能解；游戏自己有 bleed 处理（`Mods.java:383` 的 `linear`/`pregenerated`） |
| 颜色管理（sRGB/预乘） | **低** | `ARGB_8888` + `PNG` 是无损直通，不做色彩变换 |
| 撤销内存 | **低** | 加个帧数上限即可 |
| i18n / 门禁 | **低** | 走既有流程（`Trans` + 两边资源 + 台账 + 自检） |
| **"写进去之后游戏认不认"** | **低** | 两头都实测过（§2.2） |

⇒ **没有"研究级"的不确定性**，都是工程量。

## 5. ★ 真正的分叉：画完放哪儿

现状（三条都成立）：

1. **模组编辑器还没落地** —— 当前 Activity 列表里没有它（`ModsActivity` / `SlotActivity` / `MapsActivity` /
   `BlueprintsActivity` / `SavesActivity` / `TrashActivity` / `SettingsActivity` / `LogActivity`…就是没有编辑器）；
2. **zip 不能原地改**（重写整个 zip，已否决）；
3. 所以贴图能落的地方只有 **目录形态的模组** —— 而目录形态的模组目前只有：用户手放的、`dirmod-demo` 那种夹具、
   **未来模组编辑器造出来的**。

三个选项：

| 选项 | 说明 | 代价 |
|---|---|---|
| **A. 独立入口 + 只写目录形态模组** | 从模组详情页（"这个模组在哪个目录"）进去，给某个模组加/改一张 `sprites/<名>.png` | 需要一套"选模组 → 选内容名 → 定尺寸"的向导；对 zip 模组只能"画完导出" |
| **B. 挂在模组编辑器里**（"给这个方块画贴图"） | 体验最顺、上下文最全（尺寸/朝向都知道） | **依赖模组编辑器先落地** |
| **C. 只做"导出"**（画完存到用户选的位置） | 零写入风险、最快能交付 | 丢掉本启动器唯一的差异化（写进当前槽 + 一键启动验证） |

★ **建议 A 先做、B 后补**：A 不依赖模组编辑器，而且**画板本身与落点解耦**（选模组那段只是一层向导）；
等模组编辑器落地，把 B 的入口接上去就行（同一块画板复用）。
另外 A 里有个**几乎白拿的高价值功能**：**"从已有贴图起稿"** —— `ModSprites` 已经能按注册名取到 PNG 字节，
所以"打开某个模组的某张图接着改"是现成的，这对"修别人模组的贴图"最有用。

## 6. 分期建议

| 期 | 内容 | 要什么 |
|---|---|---|
| **一期** | **物品 / 状态效果（32×32）+ 单格方块（32×32）**；铅笔 / 橡皮 / 油漆桶 / 取色 / 撤销 / 缩放 / 网格 / 透明棋盘；保存到目录形态模组的 `sprites/` | 画板 + 工具 + 向导（§1.2 的 1~5） |
| **二期** | **多格方块（`size×32`，最大 160×160）** + **游戏内比例预览**（1:1 / 放大 / 平铺看效果）+ **从已有贴图起稿** + 调色板取自游戏 | 缩放体验 + 调色板 |
| **三期** | 叠加层（`-top` / `-glow` / `-team`）+ 与模组编辑器合流（B 选项）+ "从蓝图/地图里那一格直接开画" | —— |
| **不做** | 帧动画（原版 units 里 `-N.png` 帧后缀是 **0**）、单位零件拼装、effects/ui 贴图 | 不是内容贴图 |
