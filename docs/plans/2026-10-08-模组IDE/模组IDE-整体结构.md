## 1. 现状结构（真实摊开，作为共同基线）

```
主页 MainActivity
├─［版本行 ×N］ 每行一个「槽」按钮（换槽）
├─［启动］btn_continue（继续上次 / 启动）
├─［添加游戏］───────┐
├─［存档与备份］→ SlotsActivity（槽列表）      │ 弹窗二选一
│                    └ 点一个槽 → SlotActivity ┘
│                                 ├［模组］  → ModsActivity ── 点行 ⇒ 详情弹窗
│                                 │              └ 槽 / 导入 / 跨槽复制 / 冲突体检 / 筛选
│                                 ├［存档］  → SavesActivity
│                                 ├［地图］  → MapsActivity → 详情页
│                                 ├［蓝图］  → BlueprintsActivity → 详情页
│                                 ├［槽操作］→ SlotOps（整槽更新/补齐/覆盖、克隆…）
│                                 └［导出］  → 整槽 zip
├─［工具卡］中转站 → TrashActivity ｜ 运行日志 → LogActivity
└─ 右上齿轮 → SettingsActivity
```

**判据来源**：`MainActivity` 绑了 `row_add_game` / `row_saves` / `row_trash` / `row_open_logs`；
`SlotActivity` 绑了 `row_slot_mods` / `row_slot_saves` / `row_slot_maps` / `row_slot_blueprints` /
`row_slot_ops` / `row_slot_export`。⇒ 现有结构是一棵**四级树**：
**主页 → 槽列表 → 槽页 → 内容页 → 详情页**。

### 1.1 既有"读模组知识"的消费者（结构上必须摆对位置）

| 消费者 | 吃什么 |
|---|---|
| 蓝图**缺件判定** | 内容表（`MapStatsMods`）+ 模组贴图（`ModSprites`）+ bundle 旁证 |
| 地图**统计** | 内容表 + 方块表（含模组方块贴图尺寸） |
| 模组页**冲突体检** | 元数据 / dex / 脚本 / 全局钩子引用 |
| 模组页**类型与启停** | 元数据 + `settings.bin` |

⇒ 这些**都在读同一套知识**，但**各读各的**。这正是"整体结构"要解决的第一件事（§4）。

## 2. ★★ 结构分叉：**"工程"的家在哪**

这是决定后面一切的那个问题。三种结构：

### 甲：就地编辑 —— **工程 = 槽里的那个模组**

```
槽页 → 模组页 → 点一个模组 →┌──────────────────────────┐
                            │  打开工程（IDE）          │
                            │  内容清单 / 问题          │
                            │  文本（mod.hjson、content）│
                            │  贴图（画板）             │
                            └──────────────────────────┘
                                    ↓ 改的就是槽里那份
```

| | |
|---|---|
| ✅ 优点 | 零新概念；直接复用槽 / 备份 / 中转站 / 一键启动验证；"改完立刻进游戏看"是天然的 |
| 🔴 缺点 | ① **只能改已经在槽里的** ⇒ "从零造一个新模组"要先想办法在槽里建出来；② **zip 不能改**（真机 **23/24** 是 zip）；③ **改的是正在玩的槽**（改坏了直接影响游戏）；④ 同一模组在多个槽里要各改一遍 |

### 乙：独立工坊 —— **工程 = 工坊里的一份工作区**（与槽解耦）

```
主页 →［模组工坊］→ 工程列表 →┌──────────────────────────────┐
                              │  工程（= 一个目录）            │
                              │  总览：文件 / 内容 / 贴图 / 问题 │
                              │  文本：mod.hjson、content/**    │
                              │  贴图：像素画板                 │
                              └───────────────┬──────────────┘
                                              │ ［安装到槽…］
                                              ▼
                                   slot-<槽>/mods/<名字>/（目录形态）
```

| | |
|---|---|
| ✅ 优点 | ① **zip 有救了**：把 zip **解包成工程**再改，改完装进槽 ⇒ 直接解决 23/24 的问题（⚠️ 只对**纯数据模组**成立；含 `classes.dex` 的解包会让代码失效 —— 真机实测过）；② **不碰正在玩的槽**（改坏了最多是工程坏了）；③ **一个工程能装到多个槽**；④ "从零造一个模组"终于有地方发生；⑤ 这才是"IDE"的自然形态（工程 → 编辑 → 构建/安装） |
| 🔴 代价 | ① **多一层概念**：工程 ≠ 模组，要有一条"安装/同步到槽"的路；② 工程占用空间（要纳入**存储占用**）；③ **两处真相**的风险（同名的工程与槽里的模组：谁新？）—— 必须有一条明确判据 |

### 丙：乙 + 从槽里"复刻"（**混合**）

= 乙，外加：**模组页 →「复刻到工坊…」**（把槽里那份（含 zip）复制成一个工程）与
**工程 →「装到槽…」**。两个方向都有入口，**但真相只有一份**（见 §4 的 V9）。

---

## 3. 我推荐 **丙**（= 乙 为主 + 双向搬运）

理由（按重要性）：

1. **zip 才是有用的那 96%**：甲对 zip 完全无能为力，而我们实测过"解包只对纯数据模组安全" ⇒
   乙/丙把"能改的集合"从"目录形态"扩大到"**除 Java 模组以外的全部**"。
2. **它给"从零造"一个家**：用户最初的需求是"做一个纯 JSON 内容模组"（造贴图 + 写 JSON）——
   甲里这件事**没有发生的地点**。
3. **它是唯一"像 IDE"的结构**：工程 → 多视图 → 安装。甲本质上是"模组详情页增强"。
4. **风险更低**：甲是"直接改正在玩的槽"，丙是"改工作区 + 显式安装"。

★ 但**代价必须一起认**：丙要比甲多写"工程仓库 + 安装到槽 + 两处真相的判据"（约 +250~350 行）。

## 4. 推荐结构（丙）下的分层与职责

```
┌─ 入口层 ──────────────────────────────────────────────────────┐
│ 主页［模组工坊］→ ProjectsActivity（工程列表）                   │
│ 模组页 ［复刻到工坊…］（把槽里那份搬成一个工程）                  │
└───────────────────────┬──────────────────────────────────────┘
                        ▼
┌─ 工程层（★ 新增，冻结层）──────────────────────────────────────┐
│ ModProject   只读快照：元数据 / 内容清单 / 贴图清单 / issues()   │
│ ModWriter    唯一写入口（工程内写文件 / 写 PNG）                 │
│ ProjectStore 工程仓库：hub/projects/<工程名>/                   │
│              · 新建 / 列表 / 改名 / 删除（进中转站）/ 导入(zip)    │
│              · ★ 与槽的搬运：importFromSlot / installToSlot       │
└───────────────────────┬──────────────────────────────────────┘
                        ▼
┌─ 视图层（免责层）──────────────────────────────────────────────┐
│ ★ 文件视图（**首页** = 文件管理器：面包屑 + 当前目录列表）        │
│   内容/贴图/问题（语义视图）  文本视图  贴图视图  预览视图         │
│ ★ 五个视图**只吃 ModProject**，不许自己算注册名 / 尺寸 / 路径     │
└───────────────────────┬──────────────────────────────────────┘
                        ▼
┌─ 复用层（既有，不重写）────────────────────────────────────────┐
│ ModSprites(注册名/尺寸) · MapStatsMods(内容表) · Hjson(宽容解析) │
│ Mods(internalNameOf/扫描/importPackage/copyMods) · Data · Trash  │
└───────────────────────────────────────────────────────────────┘
```

### 4.1 ★ 工程仓库放哪（**结构性决定**）

| 位置 | 是什么 | 好处 | 坏处 |
|---|---|---|---|
| `hub/projects/`（**外部**，`Paths.externalHub`） | 与 `backups/` `cas/` `previews/` 并列 | **用户看得见、能自己备份、能被"存储占用"统计到**；不在游戏的 copy 范围（AGENTS 已验） | 用户可能手改/手删（但那也算"他的数据"） |
| `app_hub/projects/`（**内部**，`Paths.privateDir`） | 与 `config.json` `import/` 并列 | 游戏绝对碰不到；不会出现在文件管理器里 | 用户看不见、**卸载即丢**、`adb` 要看还得 `run-as` |

★ 我倾向 **`hub/projects/`**：本工程的一贯口径是"**用户的数据放在用户看得见的地方**"（`hub/` 里已经有备份/中转站/CAS）。

### 4.2 新增两条"搬运"路径（对应甲缺的那部分）

| 动作 | 语义 | 复用 |
|---|---|---|
| **复刻到工坊**（槽 → 工程） | 把 `slot-<槽>/mods/<名字>`（目录 **或 zip**）复制成 `hub/projects/<工程名>/`；zip **解包**，且**含 `classes.dex` 的拒绝并说明理由** | `Mods.copyMods` 的口径 + `ZipFile` 解包 |
| **安装到槽**（工程 → 槽） | 把工程复制成 `slot-<槽>/mods/<名字>/`（**目录形态**）；同名**先问**（覆盖 ⇒ 旧的进中转站） | `Mods.importPackage` / `Trash.move` |

### 4.3 ★★ 第五个视图：**文件视图（文件管理器）**——用户 2026-10-08 指出

**为什么它是结构里缺的一块（不是"顺手加的"）**：

1. **语义视图只覆盖我们建模过的东西**。模组里还有 `bundles/bundle.properties`、`scripts/*.js`、
   `sprites-override/**`、`mods/<名>/config.json`、音效/音乐、`patches/**`、`classes.dex`……
   ⇒ 只看"内容清单 + 贴图清单"，用户**看不见这些**，也就**改不了、删不掉、不知道它们存在**。
2. **"从零造一个模组"必须能建任意文件**：`content/items/铜.json` 之外还要
   `bundles/bundle.properties`（不然游戏里显示内部名）、可能还要 `sprites/`。
3. **它是"入口的枢纽"**：文本视图要"打开哪个文件"、贴图视图要"打开哪张 PNG" ——
   这两个入口**天然从文件视图来**（而不是各自再造一套选择器）。

**形态定案（手机优先，不抄桌面 IDE）**：

| 项 | 定案 | 理由 |
|---|---|---|
| 导航 | ★ **面包屑 + 当前目录列表**（进/出目录），**不是**可折叠的整棵树 | 手机上缩进树很容易点错；面包屑 + 列表是手机文件管理器的通用形态 |
| 附加开关 | 「**全部文件**」（平铺 + 搜索）+「显示隐藏文件」 | 找文件时比一层层点快；隐藏文件默认藏（与 `Data.contentSkipped` 同口径：点开头 / `.part` / `.tmp`） |
| 每个条目显示 | 名字 ·（目录/文件）· 大小 · **已知类型徽标**（内容 JSON / 贴图 / bundle / 脚本 / 未识别） | "未识别"要**如实说**（本工程一贯：不认识就说不认识） |
| 点文件 | 按扩展名分派：`.json`/`.hjson` → 文本视图；`.png` → 贴图视图（能不能编辑取决于尺寸/类型）；其余 → **只读文本**（或"没有能打开的编辑器"） | 一个枢纽、两条去路 |
| 长按条目 | 动作表：改名 / 复制 / 删除 / 导出（单文件） | 与既有"弹窗二选一"同族 |
| 新建 | 「新建文件夹」/「新建文件（**从模板**）」：内容 JSON（按类型）/ `mod.hjson` / `bundles/bundle.properties` / 空白文本 | 模板是"从零造"的关键——否则用户不知道 `bundle.properties` 要写什么 |
| 改名联动 | 改 `content/<类型>/<stem>.json` 后 ⇒ **问题列表立刻重算**（本页重算，§109 口径），C1 会当场报"贴图失配" | 这是 C1 在文件管理器里的正面价值：**改名的那一刻就告诉你后果** |

★ **它同时让 IDE"诚实"**：我们没建模的东西**照样看得见**，而不是假装模组只有内容和贴图两类文件。

🔴 **两条与结构有关的新决定（不可逆级）**：

| # | 定案 | 可逆性 |
|---|---|---|
| **I-4** | **删除文件 ⇒ 复用既有中转站**（`hub/*-trash`，新增一类 `Kind.PROJECT_FILE`），**不另造一个工程内回收站** | 🟡 中：复用=一套机制一份实现；但一旦发出去，删除物的落点就定了 |
| **I-5** | 文件视图的**写能力只在工坊工程里存在**；槽里的模组（含 zip）**只读**（沿用 S2） | 🔴（其实是 S2 的推论，写下来免得以后开口子） |

## 5. 三条主用户路径（结构定完，路径就自然了）

| 路径 | 走法 |
|---|---|
| **A. 从零造一个纯 JSON 内容模组** | 主页 → 模组工坊 →［新建工程］（填名字）→ 总览 → 贴图视图画一张 → 文本视图写 `content/items/x.json` → 问题列表清零 →［安装到槽］→ 一键启动看效果 |
| **B. 修一个下载来的模组（zip）** | 槽 → 模组页 → 点模组 →［复刻到工坊］（解包）→ 改 →［安装到槽］→ 启动验证 |
| **C. 只是看看这个模组有啥问题** | 槽 → 模组页 → 点模组 →［复刻到工坊］或直接看**只读总览** → 问题列表（不需要安装） |

★ 路径 C 提示一个细节：**"只读总览"应该也能直接对槽里的模组用**（不必先复刻）——
所以 `ModProject` 的**读**能力要同时支持"槽里的模组"与"工坊里的工程"两种来源（§6）。

---

## 6. 由此定下的两条结构结论

| # | 结论 | 为什么 |
|---|---|---|
| **S1** | `ModProject` 的**读**能力对"槽里的模组"和"工坊里的工程"**一视同仁**（同一个类，两种来源参数） | 路径 C 要用；而且避免"两套只读逻辑" |
| **S2** | `ModWriter` 的**写**能力只管**工程内部**（`hub/projects/<名>/`）；**写槽**只有一条路 =［安装到槽］ | 否则就变成"甲"，两条写槽的路必然分岔 |

★ S2 是这一整套结构里**最值钱的一条**：**"改正在玩的槽"这件事在一期根本不存在** ⇒
风险从"可能弄坏用户的槽"降到"可能弄坏自己的工程"。

## 7. 与既有功能的关系（**并列，不搬**）

- 现有"冲突体检 / 蓝图缺件 / 地图统计 / 模组类型"**继续待在原处**，不搬进 IDE。
- `ModProject` 是**同一层知识的另一种封装**；将来若要让它们共用，**只准挪判据进模型层，不准把视图搬来搬去**。
- ★ 反过来说：`ModProject` **不许**把"冲突体检"的判据重写一遍（那是 `Mods.findConflicts` 的事）。

## 8. 结构定了之后，上一份《接口定案 1/2》要改哪里（**诚实清单**）

| 1/2 里的写法 | 选丙之后改成 |
|---|---|
| `ModProject.load(Context, String slot, Mods.Info info)` | `ModProject.load(Context, Source)`，`Source` 两种：槽里的模组 / 工坊里的工程 |

**结构 → 接口 → 界面细节**。

### 9.1 ★ 真正**不可逆**、必须先定死的只有三条（都是"用户数据"层面的）

| # | 问题 | 我的定案 | 为什么它不可逆 |
|---|---|---|---|
| **I-1** | **工程的元数据格式**：除了游戏自己的 `mod.hjson`，我们**要不要**再存一份工程信息（来源槽 / 创建时间 / 备注）？ | **存**，落在工程根目录的 **`.mdt-project.json`**（点开头 ⇒ 不会被 `Data.contentSkipped` 之外的任何逻辑当成模组内容；游戏也不读它） | 用户一旦建了工程，这个文件名与字段就**只能加不能改**（改了要写迁移） |
