# 热更新与 APK 更新的结合 —— 可行性验证（2026-10-29）

> **性质：验证产出，未实现。** 换方向前读这里。

> 上游结论：`ref/43` 第 23 条（内核不可搬进插件）· `ref/01` §11（`PackageInstaller` 四道闸门 + 回调坑）·

---

## 0. 一句话

**能结合，而且"该走哪条路"可以被机器算出来**（已用真实构建产物验过，见 §2）。
但结合的真正成本不在判据，而在两处：**core 页面化**（约 11.6 k 行 Activity 的入口改造，§4）
和**壳的版本契约**（壳不能改 ⇒ 契约只能加法演进）。

热更能覆盖的只有一种情况：**清单完全不变的纯代码 / 资源更新**。
凡碰清单（权限 / 组件 / intent-filter / targetSdk / 应用名与图标）就必须装 APK ——
这不是设计取舍，是 Android 的安装期语义。

---

## 1. 三层能力边界

| 层 | 能不能热更 | 判据 |
|---|---|---|
| 数据（asset / 存档 / 配置 / 内容文件） | ✅ 一直能 | 不需要任何机制，改文件即可 |
| 代码与资源（`classes*.dex` / `res/` / `resources.arsc`） | ✅ **只在清单不变时** | §2 的分派器 |
| APK 自身（清单能力 / 签名 / targetSdk / 版本号） | ❌ 只能走系统安装器 | `ref/01` §11 的四道闸门 |

**"清单不变"是严格的字面意思**：`AndroidManifest.xml` 除 `versionCode` / `versionName` 外
逐项相同。排除这两个是因为它们每次发版都变、且不改变运行时行为。

---

## 2. 分派器（可计算）

判据 = 两个 APK 的「清单指纹 + 代码条目指纹 + 签名证书」三类比对：

| 差异出现在 | 判定 | 理由 |
|---|---|---|
| 包名 / `sharedUserId` | **apk** | 换了就是另一个应用 |
| `uses-permission` / `uses-feature` / `uses-library` | **apk** | 权限按 UID 授予，壳没声明就是没有 |
| `uses-sdk`（min / target） | **apk** | 跟着壳 |
| `application.*`（name / process / debuggable / label / icon / theme / hasCode …） | **apk** | 都是安装期解析的 |
| `activity` / `service` / `provider` / `receiver`（增删改，含属性与 `intent-filter`） | **apk** | 组件表是安装期静态的 |
| 签名证书 | **apk** | 换签名只能卸载重装（会丢槽） |
| 只有 `classes*.dex` / `res/` / `resources.arsc` / `assets/` | **hot** | 这才是热更能覆盖的那一档 |
| 除版本号外完全一致 | **none** | — |

实现要点（都在 `probe.py` 里，两段函数）：
- 清单走 `aapt2 dump xmltree --file AndroidManifest.xml`，用**缩进栈**解析（aapt2 固定：元素每级 +4 空格、属性 +2）；
- 代码条目比 `(name, size, CRC)`，**不比文件哈希**（见 §3.2）；
- 签名比 `apksigner verify --print-certs` 的**证书** SHA-256，不比签名块（v2 签名覆盖整个文件，内容一动它就变）。

### 2.1 真实产物上的结果

四个场景，都是本机现构的产物（`./build.sh`，未 install）：

| 场景 | 构造方式 | 判定 | 正确？ |
|---|---|---|---|
| 同源码重建 | 连跑两次 `build.sh` | `none` | ✅ 内容可重现（CRC 全同；**文件哈希不同**，见 §3.2） |
| 改一行 Java | `LauncherApp` 一句日志 | `hot`（只有 `classes.dex`） | ✅ |
| 改 `app_name` 资源 | `strings.xml` 一条字符串 | `hot`（只有 `resources.arsc`） | ❌ **误判**，见 §3.1 |
| 产品 vs dev | 现成的两个包 | `apk`（唯一差异 `application.debuggable`） | ✅ 保守正确 |

### 2.2 合成输入（验判据，10 条全过）

自己 vs 自己 → none · 只改版本号 → none · 只改代码 → hot · 加/删权限 → apk ·
改 targetSdk → apk · 加 Activity → apk · 换签名 → apk · debuggable 变化 → apk · 改应用名 → apk。

## 3. 两个真实盲点（本次验证抓到的）

### 3.1 清单**引用的资源**变了，分派器会误判 hot

实测：把 `app_name` 从 `Mindustry Manager` 改成 `Mindustry Manager X`（清单里仍是
`android:label="@string/app_name"`，字面一字未动）⇒ 分派器判 `hot`，**但这是错的**：

`android:label` 是 **PackageManager 在安装期解析**成字符串存起来的 —— 热更改了 `resources.arsc`，
应用内顶栏会变（我们自己 `setTitle`），**桌面图标下与应用信息里的名字不会变** ⇒ 两处不一致。

⇒ 判据要补一条：**清单里"安装期解析"的属性（`label` / `icon` / `roundIcon` / `permission` 的 label…）
所引用的资源，其内容变了也算能力变更**。
实现上要么解析 `resources.arsc` 拿 ID → 值，要么改用下面的硬约束（更省事）：

> **热更能改的资源只许是 core 自己带的；壳的资源（清单引用的那些）永远冻结。**

### 3.2 内容可重现，容器不可重现

同一份源码连构两次：**所有条目的 `(size, CRC)` 全同**，但**整个 APK 的 SHA-256 不同** ——
差在 zip 的元数据 / v2 签名块。⇒ 两件事：
1. 判"代码有没有变"必须比内容（CRC），**不能比文件哈希**，否则永远判"变了"；
2. 签名只比**证书**（同一 keystore 不变），不比签名块。

### 3.3 资源 ID 冲突（尚未验，已确认存在）

本包 `resources.arsc` 的 package id = **`0x7f`**（`aapt2 dump resources` 实测）。
任何用默认参数 `aapt2 link` 打出来的包也都是 `0x7f` ⇒ **core 若带自己的资源，会和壳撞 ID**。
可选解：`aapt2 link --package-id 0x80`（Android 允许 0x7f~0xff）—— 但 **`Resources` 在
`addAssetPath` 之后认不认非 0x7f 的 app package、`R` 常量怎么对上，没验过**。

## 4. 成本量化（core 页面化）

现工程清单里注册 **17 个** Activity（15 个页面 + `GameSlot` 坑位 + `PluginsActivity`），`app/src` 里对应 17 个具体类：

| 类 | 行数 | 自己处理的回调 |
|---|---:|---|
| `ModsActivity` | 1825 | onCreate, onResume, onActivityResult, onSaveInstanceState, 菜单 |
| `MapsActivity` | 1379 | onCreate, onActivityResult, onSaveInstanceState |
| `LogActivity` | 1222 | onCreate, onResume, onActivityResult |
| `SettingsActivity` | 1085 | onCreate, onResume, onActivityResult |
| `MainActivity` | 1066 | onCreate, onResume, onPause, onActivityResult, onNewIntent, 菜单 |
| `BlueprintsActivity` | 982 | onCreate, onResume, onActivityResult, onSaveInstanceState |
| `PluginsActivity` | 913 | onCreate, onResume, onDestroy, onActivityResult, onBackPressed, 菜单 |
| 其余 8 个 | 142~591 | 多为 onCreate + onResume |
| `BaseActivity` | 188 | 已统一转发 `onActivityResult` |
| **合计** | **≈ 11.6 k** | — |

**适配面 = 6 个回调**：`onActivityResult`（SAF，9 个页面在用，最大的一块）· `onSaveInstanceState`（6 个）·
`onResume`（10 个）· `onCreateOptionsMenu` / `onOptionsItemSelected`（3 个）· `onBackPressed`（1 个）·
`onNewIntent`（2 个）。一个 `PageHost` 接口能全覆盖，但**每个页面都要改入口**（`onCreate` → 建 View）。

**好消息**：业务逻辑基本能原样保留（文件读写、解析、列表适配都不依赖 Activity）；
**坏消息**：SAF 选择器必须由 Activity 发起，View 拿不到 `startActivityForResult` ⇒ 全走壳转发。

**已存在的两块地基**（不是从零开始）：
- `PluginsActivity` 打开插件页时就是 `setContentView(R.layout.activity_plugins)` + 把
  `PluginHost.createView(l)` 挂进容器 —— **"插件提供一整页内容"已经被生产代码证明**，
  只是那个页面仍住在宿主的 Activity 里；
- `BaseActivity.attachBaseContext` 已统一做了「深浅色 + 语言 + 屏幕方向」的 configuration 包装，
  `onPostCreate` 也已统一挂插件动作区 ⇒ **"页面身份"这个概念已经收口**（`pluginPageId()`）。

**新发现的一个坑**：`PluginHost` 给插件的 `Resources` 是**创建那一刻**的
`new Resources(am, host.getResources().getDisplayMetrics(), host.getResources().getConfiguration())`
—— 之后用户在设置页切语言 / 切深浅色，插件的 `Resources` 不会跟着重建
（壳的 `BaseActivity` 只重建自己的 context）。core 页若沿用这条路，
**切语言后 core 页会停在旧语言**，直到页面被销毁重建。这条要在 `PageHost` 设计时一起解决。

热更包体积（实测，同一份构建）：`classes.dex` **495 KB**（zip）/ `resources.arsc` 247 KB /
整个 APK 826 KB ⇒ 只换代码约 **60%** 的包体，但**免安装**才是收益所在。

## 5. 建议的落地顺序

| # | 做什么 | 成本 | 独立价值 |
|---|---|---|---|
| 1 | 更新器 + 版本源（下载 / 校验 / 只读落盘 / 原子切换 / 回滚） | 中 | **两条路共用**；M4a/M4b 都缺 |
| 2 | 分派器进构建链（`build.sh` 末尾跑一次，输出这次该发什么） | 低 | 让"该发 APK 还是热更"不再靠人记 |
| 3 | 插件页升一等公民（返回栈 / 标题 / 菜单 / 结果回调） | 中低 | 新功能立刻能热更，**不用拆宿主** |
| 4 | core 页面化（`PageHost` + 15 个页面改入口） | 高 | 内核 UI 也能热更 |

> 🔴 **2026-10-29 用户定案：只做第 1 步**（APK 自更新），理由「启动器挺轻量的，也没必要啥都热更新」。
> ⇒ 第 2~4 步与本文 §4 的 11.6 k 行改造**全部搁置**，不再当待办。
> 更新器设计见 [`2026-10-29-更新器设计.md`](2026-10-29-更新器设计.md)。

**前三步做完，其实已经实现了"结合"**：APK 管清单、插件管新功能、更新器管分发。
第 4 步只多解决"内核 UI 也能热更"——而内核恰恰是"基本不会变化"的那部分（`ref/43` 第 23 条）。

## 6. 待验证（spike 清单，按性价比排）

- [ ] **`PageHost` 形态**：壳里一个容器 Activity + core 提供 `View`，跑通一个**中等复杂度**页面
      （建议 `SavesActivity`：508 行、有 SAF、有列表、有 `onSaveInstanceState`）。
      判据：能显示 / 能返回 / SAF 能回 / 旋转后状态在 / 换 core 包后重启生效。
- [ ] **资源 ID**：`--package-id 0x80` 的包 `addAssetPath` 后，`Resources.getColor/getString`
      与 `R` 常量对不对得上（§3.3）。
- [ ] **冷启动失败路径**：core dex 缺失 / 坏包时，系统实例化坑位 Activity 会不会
      `ClassNotFoundException` 闪退；兜底必须由壳的 `MainActivity` 在 `startActivity` **之前**判。
- [ ] **清单引用资源**的完整清单（哪些属性是安装期解析）—— 决定 §3.1 用"补判据"还是"硬约束"。
- [ ] **切语言 / 切深浅色后的 core 页**：`PluginHost` 给插件的 `Resources` 是创建时快照（§4 末），
      core 页要么每次重建时重新取，要么由 `PageHost` 在配置变化时主动重建页面。
- [ ] **一次只变一个**：APK 安装会杀进程，与"待生效的 core"叠加时谁先谁后（§5 第 1 步要定）。

## 7. 明确不做

- 不做 Shadow / VirtualApp 式的 `Instrumentation` hook（自己的 core 类名可约定，不需要通用框架）；
- 不做 dex 字节码注入（那是 `2026-10-28-补丁机制-ART路线.md` 的领域，针对游戏本体）；
- 不让 core 顶掉壳的类（`ref/43` 第 23 条：内核能力 + 安全阀必须留在壳里）；
- 不追求"连清单变更也免安装"——那只有把 UI 搬进 WebView 才可能，而它做不了启动器本体。
