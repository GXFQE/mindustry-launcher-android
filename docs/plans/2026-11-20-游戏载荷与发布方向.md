# 游戏载荷与发布方向（空壳 / 载荷 / 来源 / 自动更新）

> 2026-11-20。**方向说明，不是实现方案**：本文件只记"已定的判断"和"为什么否掉另外几条路"，
> 代码一行没动。触发：用户问「官方 APK 里哪些文件在我们启动器里其实不需要」→ 一路推到
> 「游戏其实就是个补丁」「空壳 + 载荷」「Action 编译 + 自动更新 + 会不会被冒充」。
> 引号内是用户原话。

## 一、一句话

**我们本来就是单应用**：游戏从来不是 App，是 `:game` 进程里的 dex + so + assets。
所以"空壳"不需要新建，只需要**把"载荷必须喂官方 APK 原字节"这条假设去掉**；
随之而来的一切问题（身份、来源、冒充）都落在**载荷清单（manifest）与它的签名**上。

## 二、已经成立的事实（不是设想）

1. 游戏由 `Injector` 六步装进**我们自己的** `:game` 进程；`mindustry.android.AndroidLauncher`
   只是我们清单里的一条**空声明**（类体来自注入的 dex）。游戏从未被安装过。
2. 装载层只碰四样东西：

   | 步骤 | 读什么 |
   |---|---|
   | ⓪① dex | `DexClassLoader(整个 APK)` → 只要 `classes.dex` |
   | ② native | `lib/<一个 ABI>/libarc.so`、`libarc-freetype.so`（`Compat.pickAbi` 只挑一个） |
   | ④ 资产 | `addAssetPath(APK)` → 游戏只看得见 `assets/**` |
   | 显示 | `getPackageArchiveInfo` → 只为包名/版本名，不参与启动 |

3. 官方 APK 里"**装成 App 才用**"的只有三样（合计约 0.18 MB，包内）：
   `AndroidManifest.xml`（5.8 KB）、`resources.arsc` + `res/`（0.11 MB）、`META-INF/` v1 签名（0.06 MB）。
   判据见附录 A：资源表全表只有 4 个图标 + `string/app_name` + `style/ArcTheme`；
   dex 里 `R$drawable` / `R$mipmap` / `ic_launcher` 引用数 **0**。

## 三、载荷模型（要定的三件）

```
GameRef = { gameId, build, contentHash, payload: [dex, so:<abi>, assets, …] }
```

1. **格式自由化**：载荷是我们自定义的 zip（`classes.dex` + `lib/<abi>/*.so` + `assets/**`），
   可以由官方包转换、裁剪、差分装配或源码编译得到。
   ⚠️ 沿用原包的 `assets/` 条目**必须照抄压缩方式**（图集走 `openFd`，STORED 的不能压）。
2. **身份换锚**：身份从"APK 文件 sha256"改成 **manifest 的哈希**；
   补丁的 `targets/<apkSha256>` 随之改成 pin 到 `(gameId, contentHash)`。
   这是唯一"以后不好改"的迁移点，趁更新还没做先定。
3. **装配 = 基线 + 差分**：`Injector.Plan.assetBase` / `assetDeltas` 就是这个形状（字段在，逻辑未实现）。

## 四、来源与签名（两层锚，别混）

| 对象 | 锚 | 需要谁给什么 |
|---|---|---|
| 用户自带的**官方原包** | Anuke 的签名证书（常量） | 只要证书；**不需要 Anuke 的私钥**，证书在 APK 里就有 |
| 我们产出的**载荷 / manifest / 差分** | **我们自己的专用清单钥匙** | 一把只签清单的钥匙 + 公钥内置 |

- 官方证书指纹（2026-11-20 实测，v146 与 v160.7 **同一张**）：
  `CN=Anu Ken`，`SHA-256 87e2cba385052d3f7146b091a9bab1477d4a2a57bfcee4ccb92ca99b6d032bf3`。
  `getPackageArchiveInfo(GET_SIGNING_CERTIFICATES)` 对**未安装**的 APK 也能读，且顺带验完整性。
- 裁剪/重打 zip 之后 Anuke 的签名**必然失效**（v1 覆盖条目集、v2/v3 覆盖整份文件）——
  所以"来自官方"只能靠 manifest 记录 + 可复算，不能靠 APK 自带签名。
- **签名防的是冒充，不是本人**：用户的信任根在"装我们启动器"那一刻就给了；
  签名只回答"这份东西是不是我们发的"。约束我们自己的是**可复现**，两件事别混。

★ **2026-11-20 定案：不做签名。** 信任模型 = **信传输通道**，只验传输/存储完整性
（下载后按 manifest 里的 sha256 校一遍、查 zip 是否完整），不引入钥匙、不签 manifest、不签载荷。
理由（用户原话："用户也没法知道有没有被改，我们验传输完整性就可以了"）：
签名能多防的只有"服务端/账号被攻破"这一层，而那一层用户本来也无法自行验证；
为它引入一把钥匙、一套 CI 签名作业、一套轮换规则，成本大于收益。
⇒ 下面 §五、§六 里所有关于"签名"的内容，**降级为记录**（哪天要自动更新到多镜像，
再回头读）。`source{apkSha256, build}` 仍然记录，但那是**排查用的来源**，不是安全判据。

## 五、冒充的结论（用户反复追问的那条）

**不签名 ⇒ 谁都能冒充。** 他只要把包放出去，我们的 App 照装，用户看名字分不出来。
**签了名 ⇒ 冒充不了**，除非拿到私钥。

> ★ 2026-11-20 定案：**不签名**（见 §四）。本节及下一节保留为"当时怎么推的"记录，
> 不再是要做的事——真要防冒充时再回来读。落到实现上只有一条：**验传输完整性**
> （HTTPS + 按 manifest 校 sha256 + zip 完整性），不做验签。

公开的 Action **不构成冒充途径**：

```
他造包                    → App 内置公钥验签 → 没有我们的签名 → 拒
他照抄公开 Action 跑一遍   → 产物内容与我们一致 → 那本来就是我们发的东西
他改任何一行再跑           → 哈希/签名对不上 → 拒
```

"造包"从来不需要 CI（zip + 文本编辑器就够）；决定成败的是 **App 收不收**，不是"谁编的"。

⚠️ 公开 CI 唯一被放大的风险：**签名步骤若跑在会执行他人代码的 workflow 里**，
谁能让它跑自己的代码，谁就可能借钥匙签名。防法三条 ——
只挂 `schedule` / `workflow_dispatch`、actions 钉 commit SHA、`permissions` 最小化；
签名作业单独一个 job，任何 PR 触发路径都不碰密钥。

## 六、分发与更新（全自动、不需要用户的机器）

```
cron（每天）→ 查官方 release → 有新版本才构建
  → runner 编译 / 装配 → 生成 manifest（逐文件 sha256 + source 记录）
  → 发布：manifest.json + 差分/载荷 → release tag
App：下载（HTTPS）→ 校 sha256 + zip 完整性 → 版本单调 → 装配
```

- **没有本机常开机器**：也不需要——没有签名步骤就没有钥匙；cron 自己查、runner 自己编。
- **用户端不重跑任何东西**：下载后按 manifest 校一遍哈希（毫秒），与商店更新同构。
- **不需要人守着**：cron 自己查；官方发版不频繁（160 → 160.7 这类补丁版隔很久）。
- ~~签名、专用钥匙、GitHub secret、environment 审批、KMS~~：**全部不做**（§四 定案），留作记录。

★ **边界（2026-11-20 用户订正）**：**手动导入 = 用户自担风险，不需要签名**。
本工程本来就会加载插件与补丁，任意包都能折腾——"游戏载荷"不是新的信任面。
⇒ 连"自动更新那条路要签名"也一并撤销：见 §四 定案，**整条链路都不签**，只验传输完整性；
导入时最多显示"官方签名 / 非官方 / 未签"作提示（读 `GET_SIGNING_CERTIFICATES`，纯读）。

## 七、已明确否掉的选项（别再重开）

| 选项 | 为什么否 |
|---|---|
| **签名**（专用钥匙 / 公钥内置 / CI 签名作业） | 2026-11-20 定案**不做**：只多防"服务端 / 账号被攻破"一层，而用户本来也无从验证；**验传输完整性够用**。钥匙、CI 签名、轮换规则全省掉 |
| 让用户重跑 Action 验证 | 荒谬；那是审计路径，不是下载路径 |
| 让 Anuke 给私钥 | 拿不到，也**不需要**——我们的载荷不是他签的 |
| 本地手签 | 要人守着每次发版，与"全自动"冲突 |
| 自托管 runner | 用户没有常开机器 |
| 把签名放进会被 PR 触发的 workflow | 等于把钥匙交给任何能提 PR 的人 |

## 八、还没定（实现前要回答）

1. **首次获得**：壳里没有游戏，第一份谁给？用户自带官方包（零托管、零风险）还是我们托管载荷（GPL 分发义务 + 带宽）。
2. **主路径**：转换（有官方包当外部锚）还是源码编译（没有外部锚；按 §四 定案不签名，
   就等于"信主机 + 验完整性"）——用户当前的意图是"Action 负责编译"。
3. **编译链选型**：Gradle 原链（省事、难复现）/ 半自建（Gradle 出 jar + 我们自己 d8、组包）/ 全手写（最可控）。
4. **差分粒度**：~~版本对版本（简单）还是 CAS 对象池（任意跳版本，要托管对象）~~ ⇒
   **2026-11-21 定：按条目 CAS（对象池）**。桌面版就是这么做的（附录 C），安卓实测 5 个包
   去重省 61.9%（附录 D）；任一版本对任一版本都只补缺的对象，不必按"版本对版本"预生成。
   "版本对版本"降为可选加速（同一对版本反复更新时才做成预打包）。见附录 E。
5. **删除清单**：增量层只能覆盖/新增，**不能删**；被删资产会残留（`146→158` 有 161 个）。
6. **GPL 与来源说明**：分发裁剪/编译产物时的许可与"改了什么"的文案。

## 九、落地顺序（最小三件，都不动现有行为）

1. **manifest**：字段定好（`files[]` / `source{apkSha256, build}`；导入官方包时顺带记
   `signerCertSha256` 供界面显示"官方 / 非官方"），导入每个版本时**纯读**算出来并存档。
   **不设** `sig` / `keyId`（§四 定案）。
2. **官方证书三态判定**：官方 / 非官方 / 无签名。做成**设置页的可选项**（默认开，
   只提示、**不阻断**导入——导 fork 是正常需求；觉得吵可以关）。
3. **完整性校验**：下载后按 manifest 校 sha256 + zip 完整性 + 版本单调（不验签）。

## 十、下一步候选：把游戏本体打包成「游戏补丁」（只是想法，未定）

思路：**复用已经验证过的补丁链**（`Patches` 的导入 / 校验 / 只读 seal / 按实例启用 / 冲突检测
+ `Injector` 的注入与挂链），把官方 APK 转成补丁格式，而不是另写一套载荷装载。

转换器产物（离线）：

```
gamepatch/
├── patch.json                     # targets 里记录来源 APK 的 sha256 —— 天然留了来源记录
└── targets/<apkSha256>/
    ├── game.dex                   # 整份游戏代码（一个 dex，或按需拆多份）
    └── assets.zip                 # 条目必须沿用原包的压缩方式（图集走 openFd）
```

两处缺口（做之前必须解决）：

1. **native 没有槽**：补丁格式只认 dex + assets。要在同一个 zip 里加 `lib/<abi>/*.so`，
   并让 `Injector.loadNatives` 从载荷取（现在只从 `plan.apk` 的 `lib/` 取）。
2. **没有基础包**：`Injector.launch` 目前**要求** `plan.apk` 存在（预热 / 注入 / native 都从它读）。
   要么加一个"载荷模式"分支，要么保留一个只有清单的占位容器。

顺序建议：**先做转换器**（离线，能算出包、能用 `unzip` 检查）→ 再真机验"只含 dex + assets + lib
的载荷能不能起"（这是唯一决定成败的实验）→ 最后才接 UI / 身份 / 更新。

实测规模：

| 项 | 数值 |
|---|---|

| 对象池 | **33,884 个对象 / 555,660,039 B（529.9 MiB）**，256 个分片目录 `00`~`ff` |
| 对象大小 | <1 K 8,537 · <64 K 23,939 · <1 M 1,317 · ≥1 M 91 |

## 附录 E：方案——按条目 CAS（与桌面同构）

```
app_hub/pkgs/objects/<sha 前2>/<sha 后62>          # 条目内容，只读、不可变（内部存储）
app_hub/pkgs/manifests/<类型>_<版本>.json          # {format, type, version, apkSha256,
                                                  #  signerCertSha256?, entries:{路径:{sha,size}}}
app_hub/cache/<类型>_<版本>.apk                    # 按需物化：STORED，跳 lib/** 与 META-INF/**
```

1. **导入**：`Importer.importApk0`（`Importer.java:50-138`）现在把 78 MB 拷成
   `import/<名>.apk`。改成：源包上跑 `readVersion` + `Compat.probe` → 逐条目 ingest
   （`objects` 里已有同一 sha 就只记引用）→ 写清单 → **删原包**。
   原来那套 `.part`、`bytes<1024` 拒、`setReadOnly`、预热两次、原子 rename 的顺序保留，
   只是目标从"整包文件"变成"清单"。
2. **启动**：`GameSlot` 不再 `plan.apk = import/<名>.apk`，而是取/物化
   `cache/<类型>_<版本>.apk`（只读、可被多个实例共享）；`Injector` 两个入口
   （`DexClassLoader`、`addAssetPath`，`Injector.java:437/461`、`:812-820`）都吃重组包。
   同一版本第二次启动直接命中缓存，不重复物化。
3. **补丁**：清单里保留 `apkSha256` ⇒ 补丁 `targets/<APK sha256>` 的语义今天就能保住；
   将来 §三 的"身份换锚到 manifest 哈希"再一起迁移。
4. **GC**：引用 = 全部版本清单 + 正在跑的物化包（按实例登记表/进程存活判），
   mark-sweep（沿用备份池的 `Cas`；本体池在**内部** `app_hub`，备份池在外部 `hub`，两套分开）。
5. **迁移**：现有 `import/*.apk` 逐个 ingest，校验通过后再删原件（可回退）；
   同分区可以用"哈希+rename"省一次拷贝（575 MB 约 1 s）。
6. **存储口径**：`Storage` 改成"对象池 + 物化缓存 + 其它"，不再把 `import/*.apk` 原样计入。

与桌面的差异只有一处：桌面每次启动现拼 jar（1.9 s 也认），我们**缓存物化包**（首次
0.2~0.5 s，之后免费）；顺带支持"同一版本多实例共享一份只读物化包"。

## 附录 F：工期、成本、风险

| 步 | 内容 | 估时 |
|---|---|---|
| 1 | 对象池 + 清单格式 + 导入 ingest（含旧包迁移路径） | 2~3 天 |
| 2 | 物化 + `GameSlot`/`Injector` 接线 + 真机验 dex/assets | 2~3 天 |
| 3 | GC / 存储口径 / 界面文案 / 迁移收尾 | 2 天 |
| **合计** | | **6~8 天** |

**最小试点（0.5~1 天，建议先做）**：只拿 v160.7 一个包：ingest → 物化 → 真机启动一次。
它同时打掉两个最大风险：①ART 吃不吃重组包（`DexClassLoader` + `addAssetPath`）；
②物化耗时是否落在冷启动可接受范围内。验完再决定动不动产品路径。

风险：

1. **物化在冷启动路径上**：首次 +0.2~0.5 s（预计）；可缓存，且无补丁时不必现算 APK sha256
   （清单里已有 `apkSha256`）。
2. **多实例共享物化包的删除时机**：物化包只读可共享；删除按"引用计数 + 实例退出后"，
   别在游戏运行中删（沿用 `WriteGate`/`Instances` 的判据）。
3. **assets 压缩方式**：图集走 `openFd`，物化时必须照抄原条目的压缩方式
   （原包 STORED 的不能压；本方案整体 STORED，天然满足）。
4. **`lib/**` 不在物化包里**：native 由 `Injector` 从 `app_hub/pkgs/objects` 直出到
   `natives/<abi>/<tag>/`（现有布局不变）；别让后面的人以为物化包里"缺了 lib"是 bug。

## 附录 G：否决记录——整包 CAS（2026-11-21 探针实测，已否）

探针：`app/src-dev/io/mdt/launcher/CasBench.java`（dev 口 `--es dev_casbench 1`，
池建内部 `app_hub/casbench/`，跑完删净；命令行见构建日志），源包 `v160.apk` 78,586,374 B。
设备 HONOR ELP-AN00 / Android 16，page cache 热：

| 操作 | 耗时 | 速率 |
|---|---|---|
| 纯拷贝 75 MB | 108 ms | 694 MB/s |
| 只算 sha256 | 80 ms | 937 MB/s |
| 首次 put（new=true） | 154 ms | 487 MB/s |
| 重复 put（去重命中，new=false） | 183 ms | 410 MB/s |
| `has(sha)` × 2000 | 74 ms | **0.037 ms/次** |
| `getTo` verify=true | 127 ms | 590 MB/s |
| `getTo` verify=false | 89 ms | 842 MB/s |
| GC 扫描 1 个对象 | 1 ms | — |

否定理由：

1. **省不了空间**：设备上 7 个 `import` 包的 sha256 **全不同** ⇒ 整包 CAS 去重收益 **0**；
   "三槽共用一份包"是假想（`import/` 是全局的，槽不持有 APK）。
2. **去重命中仍在白写**：`Cas.put` 先照写一份 75 MB 的 tmp 再删（`Cas.java:196-201`），
   命中时比首次还慢。
3. 对象由 `FileOutputStream` 创建（0600 可写），**没 `setReadOnly()`** ⇒ 拿去喂 ART 会失败
   （dex 必须只读），本体池还必须在内部存储。
   ⇒ 整包 CAS 只保留了"对象池速率参考"，不进入设计。

仍然有用的三个数：写穿对象池 ≈ **0.82 ×（纯拷贝 + 单算哈希）**；`has()` 单次 0.037 ms
（ingest 时判重几乎免费）；gc 扫描极便宜。这三条正是附录 E 里"按条目 ingest"的成本依据。
