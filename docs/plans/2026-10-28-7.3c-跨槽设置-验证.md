# 7.3c 跨槽设置 / 键位搬迁：详细验证（2026-10-28）

> 结论先行：**设置搬迁可行（1~2 轮）**，但「键位」有一个必须加的门 ——
> `KeyCode` 存的是 **ordinal**，官方 159/160/160.4 顺序相同（189 个），

## 四、键位：为什么必须加“同版本”门

`arc.input.KeyBind.settingsKey()` 的前缀是 `keybind-default-keyboard-`，
后缀 `-key` / `-single` / `-min` / `-max`；`-key` / `-min` / `-max` 存的是
**`KeyCode.ordinal()`**（int），不是键名。`KeyCode` 的 enum 顺序一旦变，ordinal 就全错位。

实测（`apkanalyzer dex code --class arc.input.KeyCode` 的 `<clinit>`）：

| 包 | 常量数 | 顺序 |
|---|---|---|
| 官方 159.7 / 160 / 160.4 | **189** | 三者**完全相同**；`mindustry.input.Binding` 类也逐字节相同 |
| MindustryX（本机安装） | **190** | 在 index **183** 插入 `useDefault`；官方 183 是 `application`，MX 183 是 `useDefault`，其后 `application` / `asterisk` / `capsLock` / `pause` / `printScreen` / `scrollLock` 全部后移 1 |

⇒ 同一个 ordinal 在官方与 MX 上可能指向**不同的键**。例如：

| ordinal | 官方 | MindustryX |
|---|---|---|
| 183 | `application` | `useDefault` |
| 184 | `asterisk` | `application` |
| 186 | `pause` | `capsLock` |
| 187 | `printScreen` | `pause` |
| 188 | `scrollLock` | `printScreen` |

键位复制若跨了这条边界，用户会得到“按 A 出 B”。

### 你说得对的部分：官方线低→高确实没问题

- **官方 159.7 → 160 → 160.4**：`KeyCode` 189 个、顺序完全相同；`Binding` 类也逐字节相同
  ⇒ 键位 **低→高、高→低都安全**（不是“低→高才行”，是这三版表本来一样）。
- **但“低→高”不是充分条件**：MindustryX 是把 `useDefault` **插在中间**（190 个），
  官方 160 → MX 是“低→高”，但 183 之后的键位照样错位；MX → 官方也一样错。
- **未来官方版本**也可能不是纯追加；没比过表之前，不能按方向猜。

### 门禁（按“表兼容”判，不按方向判）

1. 源 / 目标槽各自能唯一确定一个版本 key（`Versions.scanAll` + `Config` 的 `version_slots` /
   `version_extra_slots`；一个版本绑多个槽时按 `Versions.slotFor`）。
2. **已知表兼容**才复制 `keybind-default-keyboard-*`：
   - 同一个版本 key；或
   - 两槽都在**官方 {159.7, 160, 160.4}** 这组（`KeyCode` 与 `Binding` 都已逐字节比过）。
3. 含 MindustryX / 未知版本 / 目标槽绑多个版本 ⇒ **跳过键位**，但**安全键照搬**；
   界面上明确写「键位：跳过（目标版本与源版本的键表不兼容）」——不许静默丢掉。
4. 以后新增官方版本，先按同一方法比 `KeyCode.<clinit>` + `Binding`，再决定是否加入兼容组；
   MX 已证明“都是 Mindustry”不能当兼容依据。

键位值 `-key` / `-min` / `-max` 是 `KeyCode` 的 ordinal，`-single` 是 bool；要跳一起跳，不做“只搬一半”。

## 五、建议的界面 / 流程

- 入口：槽页 ⋮ →「从其他槽复制设置…」；选源槽 → 预览（会改哪些键、哪些跳过）→ 确认。
- 门禁：`Data.gameAlive(ctx)` 为真就拒绝（任何 `:game` 进程在跑都别写，保守）；
  目标 `settings.bin` 不存在时，若目标槽是空槽则提示“先启动一次游戏”，不硬造。
- 写：`SettingsBin.applyValues(target, backupDir, map)`；`backupDir` =
  `Mods.settingsBackupDirOf(ctx, target)`；已有备份/自检/还原/修剪。
- 报告：`Result.ok` / `noop` / `verified` / `changeDesc` / `diffBytes` / `backup`；
  只在 `ok && verified` 时说成功（与 `RestoreResult` 同一条纪律）。
- 目标独有的键**不动**：源覆盖目标，目标有而源没有的键保留（避免误删）。

## 六、边界 / 成本

- **目标 `settings.bin` 不存在**：`applyValues` 能新建，但空槽写一份设置会让它“看起来有内容”
  （备份 / 空壳判定会变）⇒ 建议目标槽没有 `settings.bin` 时提示“先启动一次游戏”，不硬造。
- **源 / 目标文件损坏**：`SettingsBin.read` 会拒绝（头荒谬 / 尾部多余 / 类型未知）；
  读取失败就整次放弃，并提示“先让游戏正常退出一次”，**不要**拿坏文件覆盖。
- **目标槽绑多个版本**：键位跳过（版本不唯一）；安全键照搬，预览里说明。
- 当前 7 个槽 **0 个 `keybind-*` 键**（用户没改过键位，默认值在游戏里）⇒ 键位夹具要
  自己造一个改过键位的 `settings.bin`，不能拿现有槽当“键位已验”。
- 跨版本安全键的键名也可能变；白名单按**当前 159/160/MX 的真实键名**挑，
  换大版本要重新核（`sameValues` 只能证相等，不能证“与进度无关”）。
- 成本：**1~2 轮**（数据层已通；主要工作在 UI + 版本门 + 夹具 + 自检）。
- 未做：没有实现 7.3c；没有真机跑游戏改键位；没有把 `KeyCode` 表从游戏 APK 读进宿主
  （那会变成“跨版本键位翻译”，是另一条更大的路）。
