# 7.3c 跨槽设置搬迁（键位附录）：详细验证（2026-10-28）

> **2026-10-28 用户指出：手机主路径没有键盘** —— 已核：Android 设置里 `keyboard` 开关默认关，
> 只有打开它（外接键盘模式，切 `DesktopInput`）才会出现「控制」按钮；触摸用户根本看不到键位页。
> ⇒ **v1 只搬 16 个官方设置键，键位不做**；下面第四节保留给“外接键盘 / 以后要做”的附录，
> 不是 v1 的前置。
>
> 结论先行：**设置搬迁可行（1 轮）**；键位如果以后要做，不能按方向猜 ——
> `KeyCode` 存的是 **ordinal**，官方 159/160/160.4 顺序相同（189 个、`Binding` 也相同），
> **MindustryX 是 190 个，在 183 位插了 `useDefault`**，其后全部错一位。
> 官方三版可互搬；含 MindustryX / 未知版本必须跳过键位。
> 音量 / 画面 / UI 那 16 个官方设置不受影响，可以照常搬。

## 四、键位：为什么 v1 不做（附：如果以后要做）

### 手机主路径没有键盘

反编译 `SettingsMenuDialog`（160.4）可见：

- `addSettings()` 的移动端分支加的是 `keyboard` 开关（默认 **false**）；只有打开它才
  `setInput(new DesktopInput())` + `Core.input.setUseKeyboard(true)`；
- `rebuildMenu()` 里「控制」（`@settings.controls` → `Vars.ui.controls`）这个按钮的显示条件是
  **非移动端，或移动端且 `Core.settings.getBool("keyboard") == true`**；
- 触摸用户默认 `keyboard=false` ⇒ **设置里根本没有「控制」入口**，键位页不存在。

本机 7 个槽 **0 个 `keybind-*` 键**，和这条一致。⇒ **7.3c v1 只做设置，键位不做**；
外接键盘 / Android TV 用户是少数，等有真实需求再按下面的表兼容门做。

### 如果以后要做：键位值是 ordinal，不是名字

`arc.input.KeyBind.settingsKey()` 的前缀是 `keybind-default-keyboard-`，
后缀 `-key` / `-single` / `-min` / `-max`；`-key` / `-min` / `-max` 存的是
**`KeyCode.ordinal()`**（int），不是键名。`KeyCode` 的 enum 顺序一旦变，ordinal 就全错位。

> ⚠️ **桌面独立 jar 确实会用同一份 `Mindustry` 数据目录**（`DesktopLauncher` / `Vars` 里的 app 名都是
> `Mindustry`，没有单独的 `MindustryX` 目录）⇒ `settings.bin` 可能共用。但没炸是因为触发面窄：
> **默认键位不在 settings 里**（只有用户手动改过的才写 `keybind-*`）；只有 ordinal **≥183** 的特殊键
> （`application` / `capsLock` / `pause` / `printScreen` / `scrollLock`）会错位，字母 / 数字 / F 键都在
> 183 之前；`useDefault` 本身也不是常用物理键。⇒ QQ 群没反馈是正常的，不是差异不存在。
> 手机独立 APK 是另一个包名 / 数据目录；**作为 mod 注入官方**时 parent-first 走官方 189。
> 只有我们**主动把 A 槽的自定义键位原值复制给 B 槽**才会把触发面放大 —— v1 不做键位。

### MindustryX 有两种形态，别混

- **独立 APK**（本机 `com.github.tinylake.mindustryX`）：自带 `arc.input.KeyCode` **190** 个，
  自己的包名 / 数据目录；正常切端不跟官方共用 `settings.bin`。
- **作为 mod 注入官方**（`dexed-*.loader.jar`，`mod.hjson` 的 `main: mindustryX.loader.Main`）：
  `AndroidImpl.withSafeClassloader` 建的是
  `new DexClassLoader(jar, …, parent = arc.Core 的 ClassLoader)`，**parent-first**
  ⇒ `arc.input.KeyCode` 仍是官方的 **189**；jar 里那份 190 不会被用来读官方 settings。
  ⇒ 这条常用路径**没有** 190/189 跨表问题。

实测（`apkanalyzer dex code --class arc.input.KeyCode` 的 `<clinit>`）：

| 包 | 常量数 | 顺序 |
|---|---|---|
| 官方 159.7 / 160 / 160.4 | **189** | 三者**完全相同**；`mindustry.input.Binding` 类也逐字节相同 |
| MindustryX 独立 APK / 桌面独立 jar（X38、X36） | **190** | 在 index **183** 插入 `useDefault`；官方 183 是 `application`，MX 183 是 `useDefault`，其后 `application` / `asterisk` / `capsLock` / `pause` / `printScreen` / `scrollLock` 全部后移 1 |

⇒ 同一个 ordinal 在官方与 MX 上可能指向**不同的键**。例如：

| ordinal | 官方 | MindustryX |
|---|---|---|
| 183 | `application` | `useDefault` |
| 184 | `asterisk` | `application` |
| 186 | `pause` | `capsLock` |
| 187 | `printScreen` | `pause` |
| 188 | `scrollLock` | `printScreen` |

键位复制若跨了这条边界，用户会得到“按 A 出 B”。

### 你说得对的部分：官方线低→高确实没问题

- **官方 159.7 → 160 → 160.4**：`KeyCode` 189 个、顺序完全相同；`Binding` 类也逐字节相同
  ⇒ 键位 **低→高、高→低都安全**（不是“低→高才行”，是这三版表本来一样）。
- **但“低→高”不是充分条件**：MindustryX 是把 `useDefault` **插在中间**（190 个），
  官方 160 → MX 是“低→高”，但 183 之后的键位照样错位；MX → 官方也一样错。
- **未来官方版本**也可能不是纯追加；没比过表之前，不能按方向猜。

### 门禁（按“表兼容”判，不按方向判）

1. 源 / 目标槽各自能唯一确定一个版本 key（`Versions.scanAll` + `Config` 的 `version_slots` /
   `version_extra_slots`；一个版本绑多个槽时按 `Versions.slotFor`）。
2. **已知表兼容**才复制 `keybind-default-keyboard-*`：
   - 同一个版本 key；或
   - 两槽都在**官方 {159.7, 160, 160.4}** 这组（`KeyCode` 与 `Binding` 都已逐字节比过）。
3. 含 MindustryX / 未知版本 / 目标槽绑多个版本 ⇒ **跳过键位**，但**安全键照搬**；
   界面上明确写「键位：跳过（目标版本与源版本的键表不兼容）」——不许静默丢掉。
4. 以后新增官方版本，先按同一方法比 `KeyCode.<clinit>` + `Binding`，再决定是否加入兼容组；
   MX 已证明“都是 Mindustry”不能当兼容依据。

键位值 `-key` / `-min` / `-max` 是 `KeyCode` 的 ordinal，`-single` 是 bool；要跳一起跳，不做“只搬一半”。

## 五、建议的界面 / 流程

- 入口：槽页 ⋮ →「从其他槽复制设置…」；选源槽 → 预览（会改哪些设置键）→ 确认。
  **v1 预览里不出现键位**（触摸主路径没有键位页）。
- 门禁：`Data.gameAlive(ctx)` 为真就拒绝（任何 `:game` 进程在跑都别写，保守）；
  目标 `settings.bin` 不存在时，若目标槽是空槽则提示“先启动一次游戏”，不硬造。
- 写：`SettingsBin.applyValues(target, backupDir, map)`；`backupDir` =
  `Mods.settingsBackupDirOf(ctx, target)`；已有备份/自检/还原/修剪。
- 报告：`Result.ok` / `noop` / `verified` / `changeDesc` / `diffBytes` / `backup`；
  只在 `ok && verified` 时说成功（与 `RestoreResult` 同一条纪律）。
- 目标独有的键**不动**：源覆盖目标，目标有而源没有的键保留（避免误删）。

## 六、边界 / 成本

- **目标 `settings.bin` 不存在**：`applyValues` 能新建，但空槽写一份设置会让它“看起来有内容”
  （备份 / 空壳判定会变）⇒ 建议目标槽没有 `settings.bin` 时提示“先启动一次游戏”，不硬造。
- **源 / 目标文件损坏**：`SettingsBin.read` 会拒绝（头荒谬 / 尾部多余 / 类型未知）；
  读取失败就整次放弃，并提示“先让游戏正常退出一次”，**不要**拿坏文件覆盖。
- **目标槽绑多个版本**：v1 不涉及键位，安全键照搬；以后若做键位再按版本门跳过。
- 当前 7 个槽 **0 个 `keybind-*` 键**（触摸用户没改过键位，默认值在游戏里）；只有外接键盘 +
  打开 `keyboard` 开关的用户才可能产生键位键 ⇒ **v1 不做键位，也就不需要键位夹具**。
- 跨版本安全键的键名也可能变；白名单按**当前 159/160/MX 的真实键名**挑，
  换大版本要重新核（`sameValues` 只能证相等，不能证“与进度无关”）。
- 成本：**1 轮**（设置搬迁：UI + 白名单 + 夹具 + 自检）；键位若以后做，再 +1~2 轮
  （版本表兼容门 + 外接键盘夹具）。
- 未做：没有实现 7.3c；没有真机跑游戏改键位（v1 也不需要）；没有把 `KeyCode` 表从游戏 APK
  读进宿主（那是“外接键盘跨版本翻译”，另一条更大的路）。
