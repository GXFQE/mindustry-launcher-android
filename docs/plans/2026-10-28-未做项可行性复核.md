## 一、③ 插件数据面

### 它其实是两件事

| 子项 | 现在的状态 | 数据住在哪 |
|---|---|---|
| **A. 插件间数据** | 没有共享通道；每个插件一个 `DexClassLoader`（[PluginHost.java](../../app/src/io/mdt/launcher/PluginHost.java#L265-L276)） | 各插件自己的 `dataDir()`（`<hub>/plugins/<id>/data`） |
| **B. 游戏内展示** | 只能在宿主页面显示；游戏内没有入口（README「Plug-in data」） | 进程内探针能反射游戏类，但没有 UI 通道 |

### A. 插件间数据：可行，但需求未证

- **能做的最小形态**：宿主给一个共享目录（如 `<hub>/plugin-shared/`）或一个极薄的
  `publish/read` 键值面；插件自己写 JSON、自己保证原子性。**1~2 轮**。
- **通用 typed bus**（topic / 版本 / 权限 / 生命周期 / 跨进程）**3~5 轮**；但当前只有
  “崩溃归因插件想读模组冲突结论”这一个具体需求，而它完全可以**重跑一遍冲突分析**或读
  `report-mods-conflict.txt`，不值得先造 bus。
- **判据**：两个插件各写一个夹具文件，B 能读到 A 的结论；A 不装时 B 优雅降级。
- **结论**：**可行，但不是当前的瓶颈**；先做共享目录约定（1~2 轮），有第二个消费者再谈 bus。

### B. 游戏内展示：技术上有路，但不是稳定的宿主 API

- **已验的部分**（[plugin-probes.md](plugin-probes.md#L58-L74)）：`:game` 进程里注入游戏 dex 后，
  探针能 `Class.forName("mindustry.Vars", false)`（136 个字段），插件探针 APK 能在 `:game` 里
  加载、实例化、写 telemetry。⇒ **“读游戏状态”已经成立**。
- **没验的部分**：`Vars.ui.hudGroup` / `Core.app.post` / arc Scene2D 画 HUD。理论上进程内探针
  可以反射这些类，把 `Table` 挂到 HUD；但：
  - `ProbeEnv` 只有 `dir/pid/slot/version/dataDir/versionInfo`，**没有 Context / Activity / post**
    （[ProbeEnv.java](../../app/src/io/mdt/launcher/api/ProbeEnv.java#L9-L56)）；
  - `sample()` 在后台线程，画 UI 必须自己反射 `Core.app.post` 切到渲染线程；
  - 字段名 / 类名随游戏版本变，插件作者自己适配；崩溃是**游戏崩**（进程内探针的固有风险）。
- **三条路**：
  1. **插件侧反射**（进程内探针 + `Vars.ui`）：宿主只需文档 + 可选 `ProbeEnv.post(Runnable)`
     便利方法，**1~2 轮**；但它是“插件自担风险”，不是宿主保证的稳定 API。
  2. **宿主画 Android View 覆盖层**：要跨进程拿到游戏 Activity 的 window，或申请
     `SYSTEM_ALERT_WINDOW`；前者难、后者要用户授权 ⇒ **不建议**。
  3. **游戏 mod / 插件**：另一条产品线，不是启动器插件。
- **结论**：**“让插件在游戏里画”技术上可行，但只能作为插件侧能力（反射 + 自担风险）；
  做成通用宿主 API 的 4~7 轮估算偏乐观，且稳定性差。** 当前没有具体插件提出这个需求，
  建议只写文档 / 加 `post` 便利方法，不承诺稳定 overlay。

## 二、7.3c 跨槽设置 / 键位搬迁

> 详细验证（数据、夹具、逐条断言、KeyCode 顺序对比）：[`2026-10-28-7.3c-跨槽设置-验证.md`](2026-10-28-7.3c-跨槽设置-验证.md)。

### 数据与现状【已核实】

- 每个槽的 `<数据根>/settings.bin`；读写已有唯一实现：
  [`SettingsBin`](../../app/src/io/mdt/launcher/SettingsBin.java#L219-L408)（读 / 编码 / 原子写 /
  `sameValues` / `diffBytes`），路径与备份落点见
  [`Mods.settingsFileOf` / `settingsBackupDirOf`](../../app/src/io/mdt/launcher/Mods.java#L580-L599)。
- 写路径已经带**备份 + 原子写 + 读回自检 + 失败还原**（`applyValues`，
  [SettingsBin.java](../../app/src/io/mdt/launcher/SettingsBin.java#L645-L719)）；模组启停和插件设置面
  已经在用，**不是新原语**。
- 真实数据：本机 7 个槽的 `settings.bin` 解析出 **5~76 个键**；安全偏好键白名单 20 个
  （`musicvol` / `sfxvol` / `ambientvol` / `chatopacity` / `lasersopacity` / `unitlaseropacity` /
  `bridgeopacity` / `bloomintensity` / `bloomblur` / `screenshake` / `fpscap` / `uiscale` /
  `uiscalechanged` / `uiEdgePadding` / `maxmagnificationmultiplierpercent` /
  `minmagnificationmultiplierpercent` / `saveinterval` / `maxMsgRecorded` / `joininfo` /
  `logicSupport.visible`）。当前几个槽的值**全部相同**（都是默认）⇒ 现在搬是 no-op，
  必须用夹具（改音量 / 改一个键位）才能验。
- **写路径的实测**：拿真实 `slot-模组演示.bin`（76 键）与 `slot-default.bin`（23 键）做 PC 往返：
  20 个安全键 + 4 个键位键 → `applyValues` → 读回 **keys=27、target 原有 23 键一个不少、
  lastBuild/lastBuildString/MetricCollector.lastPost 不变、uuid/mod-* 未复制、备份逐字节等于改前、
  4 个哨兵值 musicvol=55/sfxvol=44/fpscap=123/screenshake=7 真的写入、compressed 分支保留压缩**；
  `diffBytes=173`，全部断言 `ALL OK`。⇒ 写路径不是纸面可行。
  （用的是真实 `SettingsBin`；PC 侧只补了一个 `Util.isZlibHeader` 桩。）
- **键位键名已从字节码确认**：`arc.input.KeyBind.settingsKey()` 的前缀是
  `keybind-default-keyboard-`，后缀 `-key` / `-single` / `-min` / `-max`（`javap` 自
  `Mindustry-160.4.jar`）。但**当前 7 个槽一个键位键都没有**（用户没改过键位，默认值编在游戏里）
  ⇒ “键位搬迁”这条要先造夹具，不能拿现有槽当已验。
- 🔴 **键位值是 `KeyCode.ordinal()`，跨版本会错位**：官方 159.7 / 160 / 160.4 的 `KeyCode`
  都是 **189** 个常量、顺序完全相同，`Binding` 类也逐字节相同 ⇒ **官方这三版之间低→高、高→低都可搬**；
  **MindustryX 是 190 个，在 index 183 插了 `useDefault`**（官方 183 = `application`，MX 183 = `useDefault`，
  其后全部后移 1）⇒ 官方 160→MX 是“低→高”但照样错。
  **判据是表兼容，不是方向**：同版本 key，或两槽都在官方 `{159.7, 160, 160.4}` 才复制键位；
  含 MX / 未知版本 / 目标槽绑多个版本 ⇒ 跳过键位（安全键照搬），预览里说明原因。

### 要排除的（进度 / 身份 / 模组 / 插件状态）

`lastBuild`、`lastBuildString`、`lastplanet`、`serpulo-last-sector`、`erekir-last-sector`、
`last-sector-save`、`*-campaign-stats`、`save-sector-*`、`turn`、`campaignselect`、`uuid`、
`MetricCollector.lastPost`、`mu-last-check-at`、`mod-*`、以及模组 / 插件自己的键
（`logicsugar.*`、`rbm-*`、`overlayUI.*`、`mmplus-*`、`cm-*`、`fst.tokens.*`、`bhk-groups`、
`bek-*` 等）。**只搬白名单**，不做“全键交集”——交集里天然含 `lastBuild` 这类进度键。

### 做法与成本

- 两槽：读源 / 读目标 → 白名单交集 + 只取源里**存在**的键 → `applyValues(target, backupDir, map)`
  → 读回自检（已有）→ 报告“搬了哪些 / 跳了哪些”。
- 语义 = **源覆盖目标**；目标独有的键**不动**（避免误删 / 误搬进度）。
- 键位：同版本 key，或两槽都在官方 `{159.7, 160, 160.4}`（表兼容）才复制；含 MX / 未知版本 /
  目标槽绑多个版本 ⇒ 跳过并在预览里写明原因。
- 门禁：任何 `:game` 进程在跑就拒绝（`Data.gameAlive`，保守；不要只判目标槽）。
- UI：槽页 / 设置页一个“从其他槽复制设置…”→ 选源槽 → 预览 diff → 确认；**约 1 轮**；
  加夹具（音量 / 键位 / 进度键不变 / 跨版本跳过）和自检，**总共 1~2 轮**。
- **结论：可行，低风险；1~2 轮。** 唯一容易说错的是“键位”——默认没有键位键，
  要造一个改过键位的夹具；且键位有跨版本 ordinal 门，不能无条件复制。

## 三、平板 / 横屏布局

### 现状【已核实】

- `app/res` 只有一套 `layout/`（39 个 XML），**没有 `layout-land` / `layout-sw600dp`**。
- [`OrientationMode`](../../app/src/io/mdt/launcher/OrientationMode.java#L27-L29) 自己写着：
  强制横屏 = “同一套竖屏布局按横屏宽度铺开”，不是排过的横屏版式。
- F2c 已经修过“横屏底下按钮点不到”（整页可滚 + 四边 insets），所以**横屏是可用的**，
  只是观感是“拉宽的竖屏”；平板分栏没有。

### 可行性

- **技术**：加 `layout-land` 或 `layout-sw600dp` 变体、按最常用的 6~8 个页面先做，
  不动数据层；**2 轮**是合理下限，做全页面 / 真分栏要 **3~4 轮**。
- **需求**：没有平板设备 / AVD 实测，也没有用户提出“平板分栏”的具体痛点；
  当前“强制横屏”设置只是让用户能看，不是“横屏版式已做”。
- **结论：技术可行，需求未证。** 不建议现在开工；若只是“横屏太像拉宽的竖屏”，
  先做一个主页面 `layout-land` 试样即可，不必上平板分栏。
