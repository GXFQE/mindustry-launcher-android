## 0. 一句话

在 ART 上做「类 Mixin 效果」，但不走 JRE、也不改字节码：补丁是一份**完整的替代类**（独立 dex），
启动时 prepend、靠 ClassLoader 的加载顺序顶掉原类；游戏本体（原 APK）一个字节不动；
宿主只负责「补丁怎么活」，生成器（dexlib2/ASM/d8）外置。

**两层抽象**：开发者可以用完整 Mixin（`@Inject` / `@Redirect` / `@Overwrite`）写补丁，
由生成器展开成完整类；**用户和宿主只面对「完整类替换」**，不需要理解注入语义。

---

## 1. 为什么是这条路

- **原版模组的边界**：Mindustry 模组能注册内容、挂事件、反射，但不能改方法体 / 私有字段 /
  其他模组 / 加载流程（机制见 `ref/33`）。
- **Copper 的两种实现**：
  - **ART 路线**：桌面 Jar + 源码包 → 构建期 Mixin → d8 → dex 缓存；不拖 JRE，
    但换模组要 build、要游戏源码包。
  - **android-bridge**：设备上起真 JVM 跑桌面版；Mixin 是加载期的，但拖 JRE（约 40MB）。
- **本工程的选择**：走 ART 式「构建期生成替代类」，但比 Copper 轻——**直接从官方 APK 的 dex
  提取原类、生成一份同名完整类**，不需要源码包、不需要重建 Android 外壳、不需要 JRE。
- **不选 bridge 的理由**：JRE 体积 + 性能/功耗 + 版本适配成本；本工程的定位是 ART 原生。

## 2. 核心机制：prepend 覆盖类定义

> **术语：这不是「改字节码」。** 改字节码（Mixin / ASM）是「在原类的方法里插入 / 改写指令」；
> 本方案是「提供一份同名完整类，靠 ClassLoader 顺序顶掉原类」（class shadowing / class replacement）。
> 区别：前者原类还在、只改局部；后者原类不被加载、补丁类是唯一版本。
> 代价：补丁类必须完整（成员齐全）、只能「整个方法替换」、不能「只插一段」、不能改类结构。

- ClassLoader 按 `dexElements` 顺序找类，**先找到的赢**；
- 补丁 dex prepend 到 base CL 最前（`Reflect.injectDex(..., prepend=true)`）；
- 同名类先命中补丁版本。

**S0 已验证**（第 130 轮，`next/13`、`ref/43`）：

| 情况 | 结果 |
|---|---|
| 同名类：宿主 dex 在前（append） | 插件赢不了 |
| 同名类：**已加载过**再 prepend | **换不掉** |
| 同名类：**未加载过**再 prepend | **顶掉**（`PLUGIN-v2-2`） |
| 同一个 dex 注册给两个 CL | `InternalError: multiple class loaders` |

⚠️ 两点注意：
1. S0 覆盖的是**宿主夹具类**（`PluginProbe`），不是 `mindustry.*` 游戏类；游戏类覆盖还需实测（见 §8）。
2. 「同一 dex 注册两次」与「两个 dex 同名类」是两回事：前者报错，后者按顺序先到先得。

## 3. 补丁外置

- 游戏本体（原 APK）**不动**；
- 补丁是独立 dex 文件，只含被替换的**完整类**；
- 启用列表 = 运行时把哪些补丁 dex prepend；
- **组合不落盘合并**，不产生新文件；
- 存储：`<补丁库>/<补丁id>/<补丁版本>/<目标APK哈希>/patch.dex`，多槽 / 多组合只**引用**，不复制；
- **引用计数**：一份补丁文件被 N 个槽 / 版本引用时只存一份；删除槽 / 停用补丁只减计数，
  **计数归零才删文件**（不是「一删槽就删补丁」）。

### 为什么外置

- 动本体 = 每个补丁组合一份完整游戏 dex/APK；游戏版本还没有 CAS ⇒ **存储爆炸**；
- 外置 = 本体 1 份 + 补丁 N 份；补丁按 id + 目标版本唯一存放；
- **补丁不需要 CAS**：它不是「同一内容多份副本」，而是「一份唯一文件 + 多处引用」。
  CAS 留给存档备份那类真正重复的东西；补丁只在导入时按 sha256 判重（轻量，避免重复导入）。

## 4. 分工

| 层 | 谁 | 做什么 |
|---|---|---|
| **机制** | 宿主 | 补丁目录、启用/禁用、冲突检测、加载顺序、prepend、失败回退、来源标注、报告 |
| **生成** | **外置**（桌面工具 / dev-only 插件） | 读原 APK 的 dex → 提取类 → 替换方法（可支持完整 Mixin：`@Inject`/`@Redirect`/`@Overwrite`）→ 拼完整类 → d8 → 写 `patch.dex` + `patch.json` |

- 宿主只认「`patch.json` + `patch.dex`」，不关心怎么生成；
- **复杂度分层**：Mixin 的「只改一小段」只存在于生成器（开发者体验）；产物统一是「完整类」。
  宿主永远只做 prepend 完整类，不实现注入点匹配、不带 Mixin 引擎；
- 生成器带 dexlib2/ASM/d8（几 MB），**不进产品 APK**；
- 普通用户只导入预构建补丁包；手机生成是后续可选（dev-only，不是产品功能）；
- 参考：联机工具同理——重能力（原生库/VpnService）走独立组件 App，启动器插件只做桥接。

## 5. 补丁包格式与版本匹配

**一个补丁包可以带多个版本**（同一份改动，针对不同游戏版本各生成一份 dex）：

```
patch.zip
├── patch.json
└── targets/
    ├── <apkHashA>/patch.dex       （类，prepend）
    ├── <apkHashA>/assets.zip      （可选：素材，addAssetPath；条目必须住在 assets/ 下）
    └── <apkHashB>/...
```

`patch.json` 至少要有：

| 字段 | 说明 |
|---|---|
| `id` / `version` | 补丁身份与版本 |
| `targets` | **数组**：每个 target = `{ apkHash, gameVersion, dex, assets? }`；允许一个包带多个版本 |
| `classes` | 改了哪些类（冲突检测用） |
| `assets` | 可选：这个 target 要挂的素材文件（相对路径）；同改一个素材也要按冲突处理 |
| `conflicts` | 与哪些补丁冲突（声明式） |
| `tool` | 生成器版本 / 补丁格式版本 |

**加载判据**：按当前 APK 的 sha256 在 `targets` 里**精确匹配**；没有对应 target ⇒ 拒绝 +
提示「这个补丁不适用于当前版本」，不硬上（硬上 = `NoSuchMethodError` / 游戏起不来）。
匹配到哪个 target，就只加载它那份 dex——包里其它版本的 dex 不碰。

### 素材（资源）的规矩（2026-11-05 真机验证，见 §8）

- **容器**：普通 zip 或 aapt2 打出的 APK 都行；条目**必须在 `assets/` 下**
  （根布局的 zip 挂得上、但游戏读不到 —— 实测 `FileNotFoundException`）。
- **顺序**：素材包挂在游戏 APK **之后** ⇒ **后挂覆盖先挂**（同名文件最后一个赢）。
  多个补丁同改一个素材 = 静默覆盖，与「同改一个类」一样必须在 `patch.json` 里声明、由宿主拒绝。
- **stored vs deflate**：`Fi.length()` / `Fi.map()` / `openFd` 只对 zip 里 **stored（不压缩）** 的条目有效；
  deflate 条目 `openFd` 抛 `FileNotFoundException`。需要 fd 的素材要打成 stored。
- **只做 `assets/`**：`res/` 与 `resources.arsc`（资源表）不在第一版范围。
- **别改打包图集**：`sprites.aatls` + 页码 png 是一套；单换 `sprites/logo.png` 这类散图不会改菜单里的图
  （`logo` 是 atlas 里的 region）。补丁要加贴图就**新增自己的文件**，在补丁类里显式加载。


### 为什么精确匹配

补丁改的是字节码，不是数据：方法签名、指令、字段可能每个版本都变。所以补丁的版本声明
必须是**精确版本（APK 哈希）**，不能像模组那样给 `minGameVersion` 区间。

## 6. 存储与版本

- 补丁严重依赖游戏版本：同一补丁在不同游戏版本上的产物不同，**不能跨版本复用**；
- 按 `id + 补丁版本 + 目标 APK 哈希` 唯一存放（一个补丁包导入后可拆成多份 target dex）；
- **引用计数**：多槽 / 多组合引用同一份，不复制；删除槽 / 停用补丁只减计数，归零才删文件；
- 不需要 CAS（见 §3）；补丁的「版本」按 `id + version` 存放，也不是 CAS 场景；
- 一个补丁包可以同时声明多个游戏版本（§5 的 `targets`），但每份 dex 仍按目标哈希独立存放——
  「共用」的是**补丁记录**，不是 dex 文件；不同版本的 dex 不能互换。

---

## 7. 安全与信任

- 同 UID、全权限；**Android 沙箱是唯一边界**，宿主做不了真隔离（与插件同一结论，`ref/43`）；
- 能做的三件（低成本，不是安全机制）：
  1. 来源标注（官方 / 第三方）；
  2. 启用前告知一次（「这会替换游戏代码」）；
  3. 失败回退（不阻塞启动）。
- 补丁比模组更需要可信：它直接改游戏代码，不是数据；第一版至少要有来源声明。

## 8. 验证记录与 spike 清单

### 2026-10-30 真机实验（dev 变体 · MindustryX 2026.09.X37）

- 夹具：v160 APK 用 apktool 反编译出 `mindustry.game.Objectives` / `mindustry.core.Version` 的 smali，
  各加一个 `PATCH_MARKER` 静态字段，`apktool b` 汇编成只含这两个类的 `patch.apk`（1.1 KB）。
- 做法：`ProbeLab` 新增 `patch-lab`（dev 专用）：把补丁复制到内部存储、置只读，
  `Reflect.injectDex(cl, copy, cacheDir, prepend=true)`，然后反射读两个类的标记。
- 结果（`hub/report-patch-lab.txt`）：
  - `injectDex(prepend) = 3 elements`（宿主 2 + 补丁 1），`suppressed=0`；
  - `mindustry.game.Objectives` marker=**true**（补丁版本赢）；
  - `mindustry.core.Version` marker=**false**（补丁里没有它，没被误覆盖）；
  - `:game` 进程活着（828 MB），主菜单正常，logcat 无 FATAL。
- **反例（版本必须精确匹配）**：先用 v160 的 `Version` 覆盖 MindustryX 2026.09.X37 ⇒ 启动时
  `NoClassDefFoundError: arc.util.OS$$ExternalSyntheticOutline0`（fork 的合成类/引用不同）⇒ 崩。
  这正是 §5「按 APK 哈希精确匹配」的实证。
- 结论：**prepend + 同名类覆盖 + 游戏能跑**在 ART 上成立；补丁类必须从**目标 APK 自己的 dex** 提取。

### 2026-10-30 真机实验 ②：改方法（v160 官方 APK）

- 在 `Version` 上改两个方法（补丁类仍从 v160 的 dex 提取）：
  - `buildString()` → 返回 `patch-lab-v160`；
  - `combined()` → 返回 `patch-lab-v160`（主菜单版本号用的是这个）。
- 结果：
  - 反射调用 `Version.buildString() = patch-lab-v160`（方法体确实被替换）；
  - **主菜单版本号从 `release build 160` 变成 `patch-lab-v160`**（UI 调用 `combined()`，肉眼可见）；
  - `:game` 进程活着、无崩溃。
- 坑：`Version.buildString()` 被 `Vars` 初始化时缓存（`Vars.version`），只改它 UI 不变 ——
  要改**游戏实际调用的那个方法**；`Vars` 这类缓存了旧值的静态状态，覆盖类也救不回来。

### 2026-10-30 存储层原型（纯 JVM，不进 APK）

- `PatchStoreProto`：`targets` 数组解析、按 `apkHash` 精确匹配（缺失 → null）、
  引用计数 2→1（保留）/ 1→0（删文件）/ 0 时 release 安全 —— **7 条全 PASS**。
- 结论：多版本 `targets` + 引用计数的逻辑成立；落到 Android 侧只需换成真实文件操作。

### 2026-10-30 真机实验 ③：两个补丁改同一个类

- 造 `patchA` / `patchB`（都改 `Version.combined()`，分别返回 `patch-A` / `patch-B`），
  `patch-lab.txt` 写两行、按顺序依次 prepend。
- 结果：
  - 顺序 A→B：`inject[0]=3`、`inject[1]=4`，`Version.combined() = patch-B`；
  - 顺序 B→A：`Version.combined() = patch-A`。
- 结论：**后注入的赢**（prepend 插到最前），**没有冲突检测、静默覆盖**。
  ⇒ 第一版必须按 `classes` 做声明式冲突检测（同改一个类就拒绝），不能依赖顺序。

### 2026-10-30 真机实验 ④：静态类 `Vars` 覆盖（v160）

- 补丁 = 从 v160 反编译的 `mindustry.Vars` 全量 smali + 一个 `PATCH_MARKER` 字段（10.6 KB）。
- 结果：`target = mindustry.Vars, marker = true`（注入前未加载）；`:game` 进程活着（542 MB），
  主菜单正常，无崩溃 —— **核心静态类覆盖在 v160 上安全**（`<clinit>` 原样复制，单例照常创建）。
- 但注意：`Vars.version` 这类「初始化时缓存的值」仍是原版（见实验 ② 的坑）；覆盖类不改启动前已缓存的值。

### 2026-10-30 真机实验 ⑤：`d8` 产物 + 裸 dex（v160）

- `PatchProbe.java`（`javac --release 8`）→ `d8` → `classes.dex`（744 B）→ 直接当补丁 prepend（不打包 APK）。
- 结果：`inject[0] = 3 elements, 0 ms`（**裸 dex 也行**）；`PatchProbe.probe() = d8-ok`；
  `:game` 进程活着（543 MB）。
- 结论：**d8 产物过 ART 校验、方法可调用；补丁不一定要 APK，裸 dex 也能 prepend**。
- 体积/性能数据点：补丁 2.7 KB（两小类）/ 10.6 KB（Vars）/ 744 B（d8 小类）；
  prepend 注入 0 ms（小 dex），合并后 3 elements。

### 2026-10-30 跨版本矩阵（同名类覆盖，v160 官方 APK）

| 环境 | 注入耗时 | Objectives | Version | buildString() | 游戏进程 |
|---|---|---|---|---|---|
| Android 8.0（mdt26 AVD） | 60 ms | marker=true | marker=true | patch-lab-v160 | 活着 |
| Android 10（mdt29 AVD） | 3 ms | marker=true | marker=true | patch-lab-v160 | 活着 |
| Android 14（mdt34 AVD） | 7 ms | marker=true | marker=true | patch-lab-v160 | 活着 |
| Android 16（真机 HONOR） | 0 ms | marker=true | marker=true | patch-lab-v160 | 活着 |

- 结论：**prepend 同名类覆盖在 Android 8.0 / 10 / 14 / 16 上都成立**（老 ART、dex 只读规则、最新版都过）。
- Android 15 未跑（14 与 16 之间，预期无差异）；AVD 是 x86_64，v160 官方 APK 自带 x86_64 的 arc so。
- 数据点：安卓 8.0 注入 60 ms，10/14/16 为 0~7 ms（小 dex）。

### 2026-11-01~02 MDTX loader 对照实验（整包当补丁）

- **MDTX loader 的机制**（字节码确认）：`mindustryX.loader.AndroidImpl$1` 是自定义 `DexClassLoader`，
  重写 `loadClass`，对 `mindustry` / `arc.` / `rhino.` 前缀**先查自己的 dex**（`arc.func` 除外）——
  即「子 CL + 打破双亲委派」；loader jar 含 1226 个 `mindustry/` 类 + 46 个 `arc/` 类。
  和本工程的 prepend（同一 base CL + dex 顺序）**效果等价、机制不同**。
- **自己覆盖自己**：loader dex → MDTX X37 APK，`inject=3 elements, 21 ms`，到 MDTX 主菜单——
  两份类同源、零结论（只证明「大 dex prepend 能起」）。
- **跨版本/跨 fork**：
  - loader dex（B500，160.5）→ 官方 v160：崩 `labels_en`（`mindustryX.features.ui.MenuFloatLabel` 读 MDTX 的 assets）；
  - MDTX APK 的 dex（B509，160.7）→ 官方 160.7：崩 `$$ExternalSyntheticLambda1`（合成类签名不同）；
  - **同版本** loader jar 的 dex（B509，160.7）→ 官方 160.7：**同样崩 `labels_en`**（版本差被排除）。
- **桌面端对照**：官方 160.7 + loader jar 当 mods 模组 → **正常**（`Start mindustryX client`、
  `[MindustryX] Hooks.init`、`Total time to load: 12164ms`）。
- **跨平台差异**（`Vars.clientLoaded`）：`clientLoaded=true` 的唯一赋值点在 `ClientLauncher.update()`
  （第一帧）。桌面 `Vars.loadAsync` 同步走完、`Mods.load()` 在 `update` 之前 ⇒ `preload` 执行；
  安卓 `loadAsync` 异步，GL 线程 `update()` 先跑、设 `clientLoaded=true`，`Mods.load()` 在后 ⇒ `preload` 直接 return。
  所以「loader 当模组」在安卓无效是**时序**，不是 loader 本身不支持安卓。
- 结论：**loader 整包不能当补丁**——两个死穴：assets 不跟（`labels_en`）、合成类签名（`$$ExternalSynthetic*`）。

### 2026-11-02 补丁的能力边界：类 + 资源

- **prepend 只换类**：`AssetManager` 只读 APK 的 assets，dex 里加不了文件 ⇒ 补丁类读 `labels_en` 这类
  MDTX 自有资源就崩。这是当前设计的**能力边界**，不是理论必然。
- **资源补丁的落地**：`:game` 里反射 `AssetManager.addAssetPath(assetApk)`，把补丁的 `assets.apk`
  挂进资源路径；补丁包扩成两层：

  ```
  patch.zip
    patch.json                   （targets / classes / assets）
    targets/<apkHash>/patch.dex  （类，prepend）
    targets/<apkHash>/assets.apk （资源，addAssetPath）
  ```

  - `addAssetPath` 是隐藏 API（Android 14+ 可能受限），时机在游戏 `AssetManager` 初始化前/时；
  - 同名资源谁优先取决于路径顺序，要实测（**2026-11-05 已实测：后挂赢，见下**）。
- **补丁动不了「加载时机」**：安卓端「loader 当模组不生效」要修，补丁的候选动点全部不可行——
  `Main.preload()` 去检查 ⇒ 已加载游戏上引导 ⇒ 崩；`ClientLauncher.update()` 的 `clientLoaded`
  是每帧无条件赋值，改它牵连 `GameService`/`AutoUpdate`；`AndroidLauncher.onCreate()` 改启动顺序
  ⇒ 改安卓启动根流程、版本锁定。**唯一可行的是启动器在 `:game` 启动早期调 `preload`**（不改游戏），
  但 `Core.app` 在 `AndroidApplication.init()`（`onCreate` 里）才设，`attachBaseContext` 注入点太早
  ⇒ 需要 hook `ActivityThread`/`Instrumentation` 或替换 `AndroidLauncher`——不是现成注入点能做到的。
- **差异补丁**：从 MDTX 提取「与官方不同的类」塞补丁，体积小一点，但仍撞依赖闭包（`mindustryX/*`）、
  合成类、资源三关 ⇒ **提取 ≠ 可行，重写才行**（参考 MDTX 的差异，自己写只改目标方法、不引外部资源的最小补丁）。

### 2026-11-05 真机实验 ⑥：素材（资源）补丁 —— `addAssetPath` 追加路径

**问题**：类补丁只能换代码；补丁要带自己的素材（文本 / 贴图 / 音频 / bundle）能不能成立、
有什么打包规矩。夹具在 `.dsh/research/2026-11-05-patch-assets/`（不入库），5 个增量包
（411 B ~ 117 KB）：

- `assets-lab.zip`：`assets/version.properties`（改 `commitHash=assetlab`）+ 新文件 `assets/patch-lab/hello.txt`；
- `assets-root.zip`：**不带 `assets/` 前缀**的对照（`patch-lab-root/hello.txt` 在 zip 根上）；
- `assets-lab.apk`：aapt2 打出的真 APK（manifest + 空 `resources.arsc` + assets）；
- `assets-bundle.zip`：整份 `bundle_zh_CN.properties` 改一行（`campaign`），外加一个 **stored** 条目；
- `assets-lab2.zip`：第二个 `version.properties`（`commitHash=assetlab2`），测顺序。

**做法**：dev 口 `hub/asset-lab.txt` → `ProbeLab.decorate` 在 `Injector.launch` **之前**填
`Injector.Plan.assetDeltas`；六步管线 ④ 把 `[游戏APK, delta1..n]` 按序 `addAssetPath` 到两份 AM，
游戏 activity 的那份由 `LauncherApp.preCreated` 再补挂一遍。产品行为不变（release 的 `ProbeLab` 是空壳）。
设备：HONOR ELP-AN00 / Android 16；游戏：官方 v160；报告 `hub/report-asset-lab.txt`（已拉回
`evidence/round341/`）。

**结果**：

| 问题 | 结果 |
|---|---|
| 同名素材能否覆盖 | ✅ 能：`version.properties` 读到补丁那份；主菜单版本号 `release build 160` → **`release build 160 (assetlab)`**（截图） |
| 游戏里没有的新文件 | ✅ 能：`patch-lab/hello.txt` 24 B 可读；`list("")` 多出 `patch-lab` |
| 容器格式 | ✅ 普通 zip（cookie=11）与 aapt2 APK（cookie=13）都认 |
| 是否必须 `assets/` 前缀 | ✅ 必须：根布局那个包挂上了，但 `patch-lab-root/hello.txt` 读不到（`FileNotFoundException`） |
| 多个素材包同改一个文件 | ✅ 后挂赢：`assets-lab2.zip` 排在最后 ⇒ 读 `assetlab2`，主菜单变 `(assetlab2)` |
| `openFd` / `Fi.length()` / `Fi.map()` | ⚠️ 只对 **stored** 条目有效：deflate 条目 `openFd` 失败；改成 stored 后成功（121 B / 19 B 两个对照） |
| 文本类素材（bundle） | ✅ 整份 `bundle_zh_CN.properties` 改一行 ⇒ 主菜单按钮显示 `战役模式【资源补丁】`（截图） |
| 图集里的图 | ❌ 单换 `sprites/logo.png` 不会改菜单 —— `logo` 是 `sprites.aatls` 里的 region；补丁要加贴图就新增自己的文件 |
| 成本 | 5 个 delta 的 `assetMount` = **1 ms**；挂链后游戏正常起，logcat 无 FATAL |

**组合验证（补丁类读补丁素材）**：另造一个 2.6 KB 的补丁 dex（`d8`，`io.mdt.launcher.PatchProbe`），
它的 `probe()` 起一个 daemon 线程等 `Core.files != null`（游戏 `AndroidApplication.init()` 之后才有），
再 `Core.files.internal("patch-lab/hello.txt").readString()`。同一次启动里既挂 `assets-lab.zip`
又 prepend 这个 dex：

- `report-patch-lab.txt`：`inject[0] = 3 elements, 0 ms`、`PatchProbe.probe() = scheduled`；
- `report-asset-probe.txt`：**`OK after 208 ms: [hello from patch assets]`** —— 补丁里的类、
  在游戏进程里、通过游戏自己的 `Core.files` 读到了**只在补丁素材包里**的文件。

⇒ 「类 + 素材」这套组合是通的；剩下的只是生成器 / 宿主落地的工程量。

**结论**：**资源补丁在 ART 路线上可行**，且与类补丁正交 —— 类由 prepend、素材由 `addAssetPath`，
两者都在 launch 前装填即可。代价是三条打包规矩：条目必须在 `assets/` 下、需要 fd 的素材存 stored、
别去改打包图集（新增自己的文件）。多补丁同改一个素材与同类冲突一样要显式拒绝。

### 2026-11-05 真机实验 ⑦：极限验证 —— 原版 + MDTX loader 补丁 = MindustryX

素材关打通后，直接用 **MindustryX 官方的 loader 产物**当补丁，验证「原版 + 补丁 = fork」：

- **基座**：官方 `[Android][v160.7]Mindustry.apk`（78,237,736 B）。
- **补丁 · 类**：`dexed-MindustryX-2026.10.10.B509.loader.jar` 里的 `classes.dex`（7,278,488 B；
  1,186 个 `mindustry/` + 268 个 `mindustryX/` + 987 个 `kotlin/` 类 —— MDTX 是 Kotlin 写的，
  stdlib 跟着 dex 走）。
- **补丁 · 素材**：把 MDTX B509 APK 的 `assets/` 与官方 160.7 做**逐文件 sha256 差分**：
  **新增 13 个 / 改动 12 个 / 删除 0 个**，差分包 **7,602,083 B**（新增只有 bundle-mdtx、
  `labels*`、`sprites-override/*`、`mod.hjson` 等 84 KB；改动主要是图集页 `sprites*.png` 与 `sprites.aatls`）。
  整份 MDTX assets 是 72,225,950 B —— **不需要全量**，差分就够。
- **做法**：还是本轮的 lab 口（`hub/patch-lab.txt` prepend dex、`hub/asset-lab.txt` 挂素材），
  产品代码零改动。

**结果**（截图 `evidence/round342/menu-diff-assets.png`，日志 `mdtx-last-log.txt`）：

- 游戏直接进 **MindustryX 主界面**：自定义 logo（`sprites-override/ui/logo.png` 生效）、
  版本行 `release build 160.7` + `MindustryX custom-dev`、多出「核心数据库」、左侧齿轮、
  右下 `Report Issue` / `QQ Group` / `检测更新`；
- `[MindustryX] Hooks.beforeInit` → `MDTX: bundle has been loaded.` → `[Mindustry] Version: 160.7`
  → `[MindustryX] Hooks.init`，`Total time to load: 5186 ms`，`Fetched 272 community servers.`
- 点「载入游戏」出的是 **MDTX 自己的存档对话框**（搜索框 / 过滤图标 / 「没有找到任何存档！」/
  「导入存档」）—— 不是只渲染了主菜单，MDTX 的 UI 代码真在跑。
- 成本：7.3 MB dex `inject` = **19 ms**；7.6 MB 素材 `assetMount` = **1 ms**。
- 全量 72 MB assets 同样能起（`menu-full-assets.png`）；差分只是更省。

**结论**：

1. **「原版 + 补丁 = fork」成立**。之前（2026-11-02）判定「loader 整包不能当补丁」，
   唯一致命项是 **assets 跟不上**（`labels_en`）；素材关打通后，那个结论**被推翻**——
   loader jar 本身是自洽的（桌面端拿它当 mod 跑的原班产物），没有撞合成类。
2. 对 MDTX 这种 fork，**每个游戏版本本来就有一份官方 loader jar**（B500→160.5、B509→160.7 …），
   它天然就是「按精确版本匹配」的补丁产物；补丁包 = loader dex + 与官方 APK 的 assets 差分。
   本组合计约 **15 MB**（7.3 + 7.6）。
3. 边界：**必须版本精确匹配**（本实验基座是官方 160.7；换 160 / 160.1 要换对应 loader 产物）；
   只验到主菜单 + 载入游戏对话框，**没有跑完整一局**；产品侧还差补丁包格式 / 导入 / 启用 / 冲突检测；
   另外 MDTX 与 Mindustry 都是 **GPLv3**，分发这种补丁要满足源码可得等义务。

## 9. 明确不做（第一版）

- 不做手机生成（生成器外置）；
- 不做字节码级注入（不做 Mixin 的 `@Inject` / `@Redirect`；只做「整类复制 + 替换方法」）；
- 宿主不实现 Mixin 引擎 / 注入点匹配（Mixin 只存在于生成器）；
- 不做 CAS（补丁不需要）；
- 不做多补丁合并（同改一个类 / 同改一个素材都直接拒绝）；
- 不做 `res/` 资源表（`resources.arsc`）补丁 —— 素材只走 `assets/`；
- 不改打包图集（`sprites.aatls` + 页码）；补丁要贴图就新增自己的文件；
- 不做在线补丁库（分发走现有导入 / 分享通道）。

## 附：外置组件的通用原则（联机工具引出的）

- 宿主内置**机制**，重能力（原生库 / 大依赖）外置成组件 App 或工具；
- 外置组件要有**版本契约**（`componentApi` 区间）、发现（PackageManager）/ 降级（不可用不影响基础功能）；
- Android 不能静默安装，更新只能「提示 + 跳转」；
- 组件与插件的兼容只保证「相邻区间」，不做全矩阵。

## 12. 2026-11-05 验证矩阵（正常客户端补丁）

> 只统计**不碰第二进程 / 清单 / native / res** 的“正常客户端补丁”。
> 详细记录：`docs/plans/2026-11-05-MindustryY-补丁可行性.md`、`evidence/round341|342|344-*`。

### ✅ 已验证

| 项 | 结果 |
|---|---|
| 类补丁（prepend dex） | 小 probe / MDTX B509 loader dex（7.3 MB）/ MindustryY 全量（4211 class，8.5 MB）都能替换 |
| 素材补丁 | 同名覆盖、新增文件、`assets/` 前缀、后挂优先（`addAssetPath` 顺序）都验过 |
| 基座版本 | 官方 160.7 APK；自建官方 160.4 APK（`8-official-160.4`，80,492,750 B） |
| 到 UI | MDTX：主菜单 + 载入对话框；MindustryY：主菜单 + 共享战役创建 + 战略地图 |
| 耗时 | `inject` 19 ms、`assetMount` 1 ms（单次，未做 A/B） |

### ⚠️ 未验证（正常情况内）

- 完整一局（进游戏 / 存档 / 退出 / 再读）；
- 声音 / 音乐 / atlas（`openFd` 只对 stored 有效；打包图集不能单图覆盖）；
- mods 共存（补丁改基类后 mod 类加载）；
- 版本 / 哈希不匹配的拒绝（产品补丁机制尚未实现，lab 是硬塞）；
- 补丁包格式 / 导入 / 启用 / 冲突检测；
- 性能 A/B（原版 vs 补丁，同夹具多轮）；
- 坏补丁 / 回滚；160 / 160.1 / 160.5 等其它基座。

### ❌ 已知不支持（机制边界）

- 清单组件 / 权限 / 第二进程；
- native `.so`；
- `resources.arsc`（图标 / 布局 / 字符串资源）；
- R8 后的 **synthetic 精确差分**：最小差量会撞名
  （`mindustry/core/UI$$ExternalSyntheticLambda7` 构造签名不同 ⇒ `NoSuchMethodError`），
  可靠做法是 **全量覆盖 `mindustry/**` + `arc/**`**；全量后还需补 ArcY 新增的
  `arc.Events$EventBus`。

### 关键工程结论

1. fork 的 APK 构建可能被 R8 卡住（MindustryY 的 `java.lang.Record` synthetic 报错，
   AGP 8.2/8.9/8.13 都复现）；**桌面 jar 可直接 d8 成补丁 dex**，绕开 R8。
2. 官方 160.4 没有现成 APK，可用上游源码逐文件重建；两个夹具：
   `core/assets/version.properties` 种子、`merged_java_res/debug/base.jar` 补空 jar。
3. 「原版 + 补丁 = fork」对**纯类 + 素材**的 fork 成立；对把功能做进 Android 组件/进程模型的
   fork（如 MindustryY 的 `:sharedhost`）不成立。
