# 补丁机制（ART 路线）—— 设计草案（2026-10-28）

> **性质：讨论产出，未实现。** 先落文档，换方向前读这里。
> 起因：用户看到 Copper Launcher 的「Copper Loader + Mixin」形态，问 MDT 能不能做到；
> 讨论后确定：**不拖 JRE、不重打游戏本体、补丁外置、宿主只做机制、生成器外置。**
> 依据：`ref/43`（插件化 / S0 同名类实验）、`ref/33`（模组机制）、`ref/29`（硬约束）、
> `docs/PLUGIN-API.md`。Copper 参考：[ART 平台](https://mdtcopper.github.io/loader-wiki/zh/developers/android-art/)、
> [android-bridge](https://mdtcopper.github.io/loader-wiki/en/developers/android-bridge/)。

---

## 0. 一句话

在 ART 上做「类 Mixin 效果」，但不走 JRE、也不改字节码：补丁是一份**完整的替代类**（独立 dex），
启动时 prepend、靠 ClassLoader 的加载顺序顶掉原类；游戏本体（原 APK）一个字节不动；
宿主只负责「补丁怎么活」，生成器（dexlib2/ASM/d8）外置。

**两层抽象**：开发者可以用完整 Mixin（`@Inject` / `@Redirect` / `@Overwrite`）写补丁，
由生成器展开成完整类；**用户和宿主只面对「完整类替换」**，不需要理解注入语义。

---

## 1. 为什么是这条路

- **原版模组的边界**：Mindustry 模组能注册内容、挂事件、反射，但不能改方法体 / 私有字段 /
  其他模组 / 加载流程（机制见 `ref/33`）。
- **Copper 的两种实现**：
  - **ART 路线**：桌面 Jar + 源码包 → 构建期 Mixin → d8 → dex 缓存；不拖 JRE，
    但换模组要 build、要游戏源码包。
  - **android-bridge**：设备上起真 JVM 跑桌面版；Mixin 是加载期的，但拖 JRE（约 40MB）。
- **MDT 的选择**：走 ART 式「构建期生成替代类」，但比 Copper 轻——**直接从官方 APK 的 dex
  提取原类、生成一份同名完整类**，不需要源码包、不需要重建 Android 外壳、不需要 JRE。
- **不选 bridge 的理由**：JRE 体积 + 性能/功耗 + 版本适配成本；MDT 的定位是 ART 原生。

---

## 2. 核心机制：prepend 覆盖类定义

> **术语：这不是「改字节码」。** 改字节码（Mixin / ASM）是「在原类的方法里插入 / 改写指令」；
> 本方案是「提供一份同名完整类，靠 ClassLoader 顺序顶掉原类」（class shadowing / class replacement）。
> 区别：前者原类还在、只改局部；后者原类不被加载、补丁类是唯一版本。
> 代价：补丁类必须完整（成员齐全）、只能「整个方法替换」、不能「只插一段」、不能改类结构。

- ClassLoader 按 `dexElements` 顺序找类，**先找到的赢**；
- 补丁 dex prepend 到 base CL 最前（`Reflect.injectDex(..., prepend=true)`）；
- 同名类先命中补丁版本。

**S0 已验证**（第 130 轮，`next/13`、`ref/43`）：

| 情况 | 结果 |
|---|---|
| 同名类：宿主 dex 在前（append） | 插件赢不了 |
| 同名类：**已加载过**再 prepend | **换不掉** |
| 同名类：**未加载过**再 prepend | **顶掉**（`PLUGIN-v2-2`） |
| 同一个 dex 注册给两个 CL | `InternalError: multiple class loaders` |

⚠️ 两点注意：
1. S0 覆盖的是**宿主夹具类**（`PluginProbe`），不是 `mindustry.*` 游戏类；游戏类覆盖还需实测（见 §8）。
2. 「同一 dex 注册两次」与「两个 dex 同名类」是两回事：前者报错，后者按顺序先到先得。

## 3. 补丁外置

- 游戏本体（原 APK）**不动**；
- 补丁是独立 dex 文件，只含被替换的**完整类**；
- 启用列表 = 运行时把哪些补丁 dex prepend；
- **组合不落盘合并**，不产生新文件；
- 存储：`<补丁库>/<补丁id>/<目标APK哈希>/patch.dex`，多槽 / 多组合只**引用**，不复制。

### 为什么外置

- 动本体 = 每个补丁组合一份完整游戏 dex/APK；游戏版本还没有 CAS ⇒ **存储爆炸**；
- 外置 = 本体 1 份 + 补丁 N 份；补丁按 id + 目标版本唯一存放；
- **补丁不需要 CAS**：它不是「同一内容多份副本」，而是「一份唯一文件 + 多处引用」。
  CAS 留给存档备份那类真正重复的东西；补丁只在导入时按 sha256 判重（轻量，避免重复导入）。

## 4. 分工

| 层 | 谁 | 做什么 |
|---|---|---|
| **机制** | 宿主 | 补丁目录、启用/禁用、冲突检测、加载顺序、prepend、失败回退、来源标注、报告 |
| **生成** | **外置**（桌面工具 / dev-only 插件） | 读原 APK 的 dex → 提取类 → 替换方法（可支持完整 Mixin：`@Inject`/`@Redirect`/`@Overwrite`）→ 拼完整类 → d8 → 写 `patch.dex` + `patch.json` |

- 宿主只认「`patch.json` + `patch.dex`」，不关心怎么生成；
- **复杂度分层**：Mixin 的「只改一小段」只存在于生成器（开发者体验）；产物统一是「完整类」。
  宿主永远只做 prepend 完整类，不实现注入点匹配、不带 Mixin 引擎；
- 生成器带 dexlib2/ASM/d8（几 MB），**不进产品 APK**；
- 普通用户只导入预构建补丁包；手机生成是后续可选（dev-only，不是产品功能）；
- 参考：联机工具同理——重能力（原生库/VpnService）走独立组件 App，启动器插件只做桥接。

## 5. 补丁包格式与版本匹配

```
patch.zip
├── patch.json
└── patch.dex
```

`patch.json` 至少要有：

| 字段 | 说明 |
|---|---|
| `id` / `version` | 补丁身份与版本 |
| `targetApk` | **目标 APK 的 sha256**（精确匹配，不学模组的 `minGameVersion`） |
| `gameVersion` | 人读版本号（提示用） |
| `classes` | 改了哪些类（冲突检测用） |
| `conflicts` | 与哪些补丁冲突（声明式） |
| `tool` | 生成器版本 / 补丁格式版本 |

**加载判据**：当前 APK 哈希匹配才加载；不匹配 ⇒ 拒绝 + 提示「这个补丁不适用于当前版本」，
不硬上（硬上 = `NoSuchMethodError` / 游戏起不来）。

### 为什么精确匹配

补丁改的是字节码，不是数据：方法签名、指令、字段可能每个版本都变。所以补丁的版本声明
必须是**精确版本（APK 哈希）**，不能像模组那样给 `minGameVersion` 区间。

---

## 6. 存储与版本

- 补丁严重依赖游戏版本：同一补丁在不同游戏版本上的产物不同，**不能跨版本复用**；
- 按 `id + 目标 APK 哈希` 唯一存放；
- 多槽 / 多组合引用同一份，不复制；
- 不需要 CAS（见 §3）；
- 补丁的「版本」按 `id + version` 存放，也不是 CAS 场景。

---

## 7. 安全与信任

- 同 UID、全权限；**Android 沙箱是唯一边界**，宿主做不了真隔离（与插件同一结论，`ref/43`）；
- 能做的三件（低成本，不是安全机制）：
  1. 来源标注（官方 / 第三方）；
  2. 启用前告知一次（「这会替换游戏代码」）；
  3. 失败回退（不阻塞启动）。
- 补丁比模组更需要可信：它直接改游戏代码，不是数据；第一版至少要有来源声明。

## 8. 待验证（spike 清单）

- [ ] ART 对「两个 dex 有同名类」的行为（**游戏类**，不是宿主夹具类）
- [ ] 补丁类完整性：成员 / 签名 / 内部类 / 注解 / `<clinit>`
- [ ] d8 产物过 ART 校验（类型 / 寄存器 / 异常表）
- [ ] 静态状态 / 单例（`Vars`、`ContentLoader`）覆盖是否安全
- [ ] 加载时机：游戏类有没有被框架提前碰（`LauncherApp` / `GameSlot`）
- [ ] 冲突规则：两个补丁改同一个类（拒绝 vs 合并）
- [ ] 体积 / 性能：补丁大小、prepend 开销、首次生成耗时

**最小 spike**：ASM 复制一个**无状态小类** + 改一个方法 → d8 → prepend → 验证游戏用了补丁版本
（判据：方法行为变了、游戏能起）。别拿 `Vars` 当第一个试验品。

---

## 9. 明确不做（第一版）

- 不做手机生成（生成器外置）；
- 不做字节码级注入（不做 Mixin 的 `@Inject` / `@Redirect`；只做「整类复制 + 替换方法」）；
- 宿主不实现 Mixin 引擎 / 注入点匹配（Mixin 只存在于生成器）；
- 不做 CAS（补丁不需要）；
- 不做多补丁合并（同改一个类直接拒绝）；
- 不做在线补丁库（分发走现有导入 / 分享通道）。

---

## 10. 与现有架构的对接

- `Injector.Plan` 已有 `assetBase` / `deltas`（代码 / 资源分离）；
- `Reflect.injectDex(..., prepend)` 已有；
- `PluginHost` 的信任模型 / 来源标注可复用；
- 版本 key / APK 哈希已有（`Versions` / `Importer`）。

## 11. 未定问题

1. 补丁的「完整类」从原 APK 的 dex 提取（dexlib2）还是从源码编译？
   —— 倾向 dex 提取；源码编译的字节码不可靠（编译器版本 / lambda / 内部类差异）。
2. 生成器放桌面工具还是 dev-only 插件？—— 倾向桌面工具；手机生成是后续可选。
3. 补丁包是否走分享包通道？—— 可以，但要带来源 / 完整性校验。
4. 多补丁同改一个类：拒绝还是合并？—— 第一版拒绝。
5. 补丁失败的回退粒度：跳过整个补丁 vs 跳过单个类？—— 倾向跳过整个补丁（一致）。

---

## 附：外置组件的通用原则（联机工具引出的）

- 宿主内置**机制**，重能力（原生库 / 大依赖）外置成组件 App 或工具；
- 外置组件要有**版本契约**（`componentApi` 区间）、发现（PackageManager）/ 降级（不可用不影响基础功能）；
- Android 不能静默安装，更新只能「提示 + 跳转」；
- 组件与插件的兼容只保证「相邻区间」，不做全矩阵。
