## 0. 三条定案（其中两条是对旧文档的修订/反转）

| # | 定案 | 性质 |
|---|---|---|
| A | **网络/GitHub 下载：开放** —— 不是给插件"网络权限"（同进程无沙箱，它本来就能开 socket），而是把宿主已经调好的**下载基建**（超时/302/Accept/镜像/校验/进度/前台服务）开成接口 | **反转** [2026-11-10 插件能力与互操作](2026-11-10-插件能力与互操作.md) §7「插件不该有网络」 |
| B | **补丁写：开放**；**插件启停：仍归宿主**（信任模型 / 安全阀是宿主的锚） | 新定案（用户 2026-11-13） |
| C | **"无感" = 能力，不是强制**：宿主给足插入位置与宿主组件，让想无感的插件零门槛做到；插件愿意自绘另一套 UI 也允许。宿主只保留一条硬义务：**插件停用/没装时不留空壳** | **修订** 上一轮讨论里"宿主强制渲染"的提法 |

对 C 的展开（评审/验收时别把它当红线去卡插件）：

- 判据 1（不出现"插件"痕迹）**是宿主提供的能力**：插件能把内容挂进宿主本来的卡片/行里；
- 判据 2/3（同一套视觉 / 交互）**会随 1 自然成立**——内容挂在宿主卡片里，用的就是宿主的样式与点击；
- 判据 4（无空壳）**是宿主自己的义务**，与插件无关，进宿主自检。

## 1. 网络 / GitHub 下载接口

### 1.1 现状与理由

- 插件与宿主**同进程、无沙箱**：想联网的插件现在就能自己 `HttpURLConnection` —— 所以开这个接口
  **不新增权限面**，它解决的是"每个插件都会各自踩一遍 302 / 镜像 / 半截文件"。
- 宿主这条链已经踩完坑（`UpdateClient` 头注释那三条：15s/60s 超时、跟随 302、正文上限；
  `Accept` 必须按接口给，列表只认 `application/json`、asset 只认 `application/octet-stream`）。
- 用户的**更新线路**（[`Mirrors`](../../app/src/io/mdt/launcher/Mirrors.java) 四个预设 + 直连）只对
  `github.com` 域名生效；插件自己实现不会遵守用户的选择。

### 1.2 接口形状（草案）

```java
// 拉一段文本：https only，有正文上限（清单 / JSON）。回调在后台线程。
void fetchText(String url, int maxBytes, Fetch callback);

// 列 GitHub release：复用 GitHubReleases.parseStrict，返回 tag / prerelease / publishedAt /
// assets(name / apiUrl / browserUrl；size 现在的 Release 模型里没有，顺手从 JSON 加一个字段)。
// ⚠️ 不吃宿主自更新的 "v* 只认" 规则（GitHubReleases.pick 是自更新专用）。
void githubReleases(String repo, Releases callback);

// 下载：复用 Mirrors.assetUrls（GitHub URL 才有镜像候选）+ UpdateDownload（.part → sha256 → 改名）
// 落点固定在插件自己的 cache/downloads/；成功后回调给 File + 实际 sha256 + bytes。
void download(String url, String expectedSha256, Download callback);
```

配套类型建议：结果用 `Result` 风格（`ok` + 机器码 `reason`），码表：

| reason | 含义 |
|---|---|
| `bad-url` | 不是 https / 空 / 超长 |
| `network` | 连不上 / 非 200 / 超时 |
| `size` | 超过上限 / 长度与声明不符 |
| `sha` | sha256 不匹配 |
| `io` | 落盘失败 |
| `rate-limited` | GitHub API 配额用尽（宿主统一记账） |
| `canceled` | 插件任务被取消（`Task.cancel`） |

线程/生命周期：全部**后台线程**，与 `submit(label, body)` 同底座；进度走现有 `progress(done,total)`
（前台服务，页面关掉照跑）；回调在 UI 线程（与既有 `After` / `Done` / `Cancel` 一致）。

### 1.3 宿主必须守的约束

1. **https only**：`UpdateClient.open()` 现在不校验 scheme（`new URL(url)` 什么都收）⇒ 在 API 层挡掉
   `http:` / `file:` / `content:`，只放 `https:`。
2. **体积上限**：文本 `maxBytes` 默认 512 KB；下载给一个明确上限（建议 1 GB，够放游戏包/补丁，
   不让"一个坏 URL 写满盘"）。上限值写进文档，不藏在常量里。
3. **GitHub API 配额是共享的**：未登录 60 次/小时，**宿主自更新也吃这一份**。插件轮询把配额打光
   ⇒ 启动器自更新停摆（表现是"永远查不到新版本"，极难归因）。⇒ 宿主层必须做：
   - 按 repo 的 **TTL 缓存**（建议 10 分钟）+ 当日请求计数；
   - 超限返回 `rate-limited`，文档告诉插件"别轮询"；
   - 自更新与插件接口**共用同一个记账**（同一份缓存）。
4. **镜像只在 GitHub URL 上启用**（`Mirrors.isGithubUrl`）；非 GitHub 的 https 直连。
5. **落点只能是插件自己的目录**：`<插件>/cache/downloads/<插件给的文件名>`；文件名过白名单
   （不许 `/` `\\` `..` / 控制字符 / 超长），不给任意路径。
6. **`UpdateDownload` 目前把落点写死 `.apk`**（`out = key + ".apk"`）⇒ 面向插件要抽一个"后缀/原名可参数化"
   的版本，或者在插件 API 层先下到 `.part.bin` 再交给插件改名。**别直接把插件下载叫 .apk**。
7. 并发：建议**每插件同时最多 1 个下载**（第二的排队/拒绝），防止一个插件把前台服务占满。
8. 不做：任意 socket / 长连接 / 上传 / 自定义 User-Agent（保持"只读下载"）。

### 1.4 测试

- **纯逻辑自检**：URL 闸门（http / file / 空 / 超长）、配额缓存（同一 repo 10 分钟内只查一次）、
  大小上限、sha 校验、`.part` 清理、结果码。`UpdateDownload` / `GitHubReleases` 本来就是纯逻辑，
  PC 上可跑（`PcDownloadCheck` 已存在）。
- **真机**：dev 口用宿主服务器/镜像下载一个小文件，验证 ①镜像回退 ②进度通知 ③sha 不符判死
  ④取消。GitHub 真网络只在 dev 手验，不进自检（不稳定）。

## 2. 补丁写接口

### 2.1 分工（定案）

| 谁 | 能做什么 |
|---|---|
| 宿主 | 插件启停 / 安全阀 / 补丁的**注入实现**（dex 插在哪、素材怎么挂） |
| 插件 | 补丁的**管理动作**：启用 / 停用 / 导入 / 删除 / 冲突预检 —— 全部经宿主现成实现 |

理由（用户原话）：补丁"只是个更强的模组而已"；它没有信任/安全阀那一层，冲突检测与写门禁宿主已有。

### 2.2 接口形状（草案）

```java
void patchEnable(String versionKey, String slot, String ref, Done callback);   // ref = id@version
void patchDisable(String versionKey, String slot, String ref, Done callback);
void patchImport(InputStream zip, PatchImported callback);   // 成功回调给 ref
void patchDelete(String ref, Done callback);                  // 挪进中转站（不是裸删）
void patchConflicts(String versionKey, String slot, String ref, Conflicts callback); // 启用前预检
```

- `versionKey` / `slot` 语义与 v38 `patches(vk, slot)` 一致；`slot` 空 = **这一页的槽**。
- `patchImport` 的 `InputStream` **由宿主关闭**（与 `export` / `share` 同一约定）；宿主先写插件
  cache 里的临时 zip（`Patches.importPackage(File)` 只吃 File），导入完删临时件。
- `patchConflicts` 是重 IO（读 dex class_defs + 素材条目）⇒ 后台线程，结果给冲突补丁**名字列表**
  （与界面 `Patches.conflicts` 同一份实现）。

### 2.3 复用映射（全部已存在，别重写）

| API | 宿主实现 |
|---|---|
| `patchEnable` | [`Patches.enable(ctx, ikey, record, apkSha256)`](../../app/src/io/mdt/launcher/Patches.java)（内含 `WriteGate.blockedInstance`、`filesOk`、`applies`、已启用、冲突检测） |
| `patchDisable` | `Patches.disable(ctx, ikey, record)` |
| `patchImport` | `Patches.importPackage(ctx, tempZip)`（清单三道校验 / 原子 rename / 已存在拒绝） |
| `patchDelete` | `Patches.delete(ctx, record)`（被启用时 `C_IN_USE` 拒；删 = `Trash.move` 进 `patches-trash`） |
| `patchConflicts` | `Patches.conflicts(ctx, ikey, record, apkSha256)` |

### 2.4 Result 码表（直接沿用 `PatchException` 的码，别再发明一套）

`no_match`（补丁不适用这个 APK）/ `conflict`（附冲突名列表走单独回调）/ `missing`（文件缺失）/
`enabled`（已经启用）/ `in_use`（删除时被启用）/ `game_alive`（该启动项实例在跑）/
`bad_zip` / `bad_json` / `schema` / `field` / `no_targets` / `bad_hash` / `bad_path` /
`missing_entry` / `bad_dex` / `bad_assets` / `dup` / `too_big` / `io` / `record_gone`。

成功时 `patchImport` 回调带 `ref`；其余成功 = `Result.ok()`。文案仍归插件（与 `Result` 头注释一致）。

### 2.5 不做

- 不开放**插件**启停（`Plugins.enable/disable/uninstall`）——即使技术上同 UID 也能改文件，
  契约不给就不是路；安全阀与信任等级是宿主的责任锚。
- 不开放注入细节（dex 路径、插入下标、`report-patch-launch.json` 写侧）。
- 暂不做"宿主统一确认框"：插件自己决定要不要确认（想一致就用第 4 节的 `showCard`）。

### 2.6 测试

- 补丁组已有大量夹具（导入合法/坏包/冲突/删除进中转站/实例隔离）⇒ 新 API 直接复用同一批夹具，
  加一层"经 `PluginHost$PContext` 真调"的断言（v38 已有 `newPContext` 反射夹具）。
- 重点：`game_alive`（用 fake 实例登记）与 `in_use` 两条拒绝路径要有分辨力；`patchDelete` 后
  中转站里能看到（`Trash.Kind.PATCH`）。

### 3.3 顺手发现的真 bug：`trash()` 漏了两种中转站

[`PluginData.trash()`](../../app/src/io/mdt/launcher/PluginData.java) 用的是**平行数组**：

```java
String[] cats = {"maps","mods","saves","slots","schematics","plugins"};
for (int i = 0; i < dirs.length && i < cats.length; i++) { ... }
```

而 `Trash.allDirs()` 现在返回 **8** 个目录（第 357 轮加了 `patches`，更早加了 `versions`）⇒
**插件永远看不到"删掉的补丁 / 删掉的导入版本"**，以后再加 Kind 还会继续静默漏。

**修法**：改成遍历 `Trash.allDirs(ctx)` + `Trash.list(dir)` 拿 `Trash.Item`
（kind / slot / name / stamp / bytes / files 都有），`category` 由 `Trash.Kind` 唯一的映射出；
配一条元断言"`Trash.Kind` 每个值都能在 `trash()` 里出现"（新 Kind 漏了自检会红）。

## 4. 插入能力（"无感"的主战场）

### 4.1 现状盘点

| 面 | 落点 | 谁渲染 | 问题 |
|---|---|---|---|
| `content` | 「插件」卡里一行 → 打开**插件自己的整页** | 插件 | 自绘整页，和宿主像两个 App |
| `action` | 「插件」卡里一行 → 原地 `run()` | 插件（行为） | 位置固定在聚合卡里 |
| `section` | 宿主页面里的一块（塞进同一张「插件」卡） | 插件（raw View） | 集中在共用「插件」卡；卡片套卡片踩过（第 335 轮） |
| `analyzer` / `state` / `gates` / `summary` | 行徽标 / 详情门 / 结论卡 | **宿主** | ✅ 已经是"无感"的样子 |
| `filter` / `sort` | 筛选/排序菜单 | 宿主 | ✅ |
| `playtimeTotal` | 主界面摘要卡一行 | **宿主** | ✅ 但只支持"一个整数"，是特例 |

结论：**凡是宿主渲染的那几类，用户根本看不出是插件；凡是插件自绘的，都在提醒"这是插件"。**
所以这一批不是"再加扩展点"，是把"宿主渲染的贡献点"补成一套。

### 4.2 插入能力包（P0，建议单独立一轮）

| # | 能力 | 具体落点 | 兼容性 |
|---|---|---|---|
| 1 | **`place` 锚点**（插件自述 `extensions` 加字段） | `actions` = 宿主**操作卡**（和"导入/导出/删除"同一张卡）；`summary` = 页面摘要卡追加一行；`detail` = 详情弹窗追加「标签：值」行；不写 = 现行为（共用插件卡） | 旧插件零改动；宿主按 `place` 分派 |
| 2 | **宿主组件 `api.ui()`** | 给自绘插件用的宿主零件：卡片 / 行（图标+标题+副标题+箭头）/ 按钮 / 分割线 / 键值 / 小标题 —— 全部用宿主资源与主题 | 纯加法；插件愿意就用 |
| 3 | **`showCard(title, body, buttons, cb)`** | 插件确认/选择走宿主 `CardStack`（现在只有 choose/confirm/prompt 三种固定形状） | 纯加法 |
| 4 | **`openPage(page, slot)` / `openPluginPage()`** | 从 section/action 里打开宿主某页或自己的插件页（现在只能靠 content 行绕） | 纯加法；页面 id 白名单 |
| 5 | **三个新页面钩子**：`version` / `patches` / `resources` | 这三页 `extends BaseActivity` 但没 `pluginPageId()`、布局里没 `plugin_section`（其余 12 页都有）⇒ 补上即可挂 `section`/`action` | 纯加法；补丁页尤其需要（第 345 轮之后补丁成体系了） |

实现注意：
- `place` 的实现要**页面提供锚点才有位置**：先只给"有稳定锚点"的页（内容四页的摘要/操作卡、主界面动作区、
  两个详情弹窗），其余页面 `place` 回落到现行为并在文档里写明"这一版只支持这些页"——不要假装全支持。
- `api.ui()` 的组件必须用**宿主 Context / 宿主布局资源**造（`PContext.getBaseContext()`），
  不能借插件自己的资源（那会拿到插件主题）。
- 插件页（`content`）不强制改造：它已经有宿主顶栏/滚动，只是内容区自绘；等 `api.ui()` 落地后
  文档建议"页面里也优先用宿主组件"。

### 4.3 明确"不是现在做"的

| 项 | 原因 |
|---|---|
| 声明式节点树（插件返回 Text/Row/Button 节点，宿主统一渲染） | 用户已确认"插件自绘也行"；先做能力包，真不够再上终态，避免两次翻改 |
| `rows` 虚拟行 / 列表内组行（[详细设计](2026-11-10-虚拟组行-详细设计.md)） | 成本 2~3 轮，独立立项；"无感"不依赖它 |
| page provider / 替换核心页 | 旧定案不动（插件缺失必须完整回落） |
| 插件之间互相调用 | 仍然只走宿主中介/共享文件契约 |

### 4.4 验收（"无感"的可判定形式）

1. **无空壳**（宿主义务、进自检）：停用/卸载插件后，每个页面回到原样，不多标题、不留空白卡；
2. **归位**（真机截屏）：声明 `place=actions` 的插件行出现在宿主操作卡里，和"导入/导出"同卡同高同色，
   且**不再出现在「插件」卡**（那张卡因此变空时整块 `GONE`，不是留一张空卡）；
3. **同一套交互**：`showCard` 弹出的按钮/返回/点击反馈与宿主弹窗一致（截图对照）；
4. 新增三页的 `section` 真机可见、空态整块 `GONE`；
5. 文档：`PLUGIN-API.md` 加「插入能力」一节 + `place` 字段表 + "推荐先行/自绘也行"的说明。

## 6. 风险与开放问题（实现前要拍板的）

1. **GitHub API 配额**：缓存 TTL 取多少（建议 10 分钟）？要不要在设置页显示"插件用掉了配额"？
   —— 建议先做缓存 + `rate-limited`，不加设置项。
2. **下载体积上限**：1 GB 还是按"插件声明 + 宿主上限"？建议固定 1 GB 写进文档。
3. **`place` 首批支持哪些页**：建议只做内容四页 + 主界面 + 两个详情弹窗；其余页明确"这一版不支持"。
4. **补丁写是否要宿主级二次确认**：暂不做（插件自己用 `showCard` 确认）；
   如果以后出现"插件乱开补丁把游戏搞崩"，再讨论宿主确认。
5. **插件页壳**：`content` 页要不要强制套宿主卡片外壳？建议先给 `api.ui()`，不强制。
6. **网络回调线程**：沿用"回调在 UI 线程"的既有约定，还是允许插件选后台？建议沿用既有约定。
