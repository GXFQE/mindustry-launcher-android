## 0. 五种形态，结论不同

| 形态 | 里面有什么 | 能不能 | 卡点 | 量级 |
|---|---|---|---|---|
| **A 薄包**（推荐） | 清单 + 模组 + 地图/存档/蓝图 + 模组启停 | ✅ 能 | 无硬卡点 | **3~5 轮** |
| **B 厚包** | A + 游戏 APK（官方 / MDTX） | ✅ 技术上能 | README「**打包游戏本体**：请自行准备 APK」；78 MB；版本一换整包作废 | +1~2 轮 |
| **C 在线包** | mdtbbs `Pack`（≤100 成员）一键装 | ✅ 技术上能 | README「近期不做应用内下载」；`download-grants` 10/60s、文件 60/60s | +3~5 轮 |
| **D 旧嵌套包** | 外壳 + 一堆模组 + 根上 `mod.hjson`（§1.1） | ✅ 能**拆开安装**（§1.3） | 外壳带 `main` / `classes.dex` 时不能自动拆 | +1 轮 |
| **E 模组方案**（2026-11-10 提议，**推荐先做**） | 槽里的命名模组集合（只记成员，不搬文件） | ✅ 能 | 无；只能管理**本槽已有**的模组 | **2.5~3.5 轮**（核心） |

★ 你记得的那次是 **D 的反向用法**：把「嵌套」当成**运行期格式**。我们只把它当**迁移来源**（拆开），不当运行格式。
★ **E 不是"包的另一种"**：它把主线从「分发」换成「管理」——方案只写开关、不搬文件、可逆；
包降为 E 的导出格式（`kind=group`）与完整环境迁移（`kind=environment`）。
详见 [模组方案：多模组整合管理](2026-11-10-模组方案-多模组管理.md)（§3.7 是摘要）。
★ 本文的「能」指的是**数据层与流程**：包怎么来、怎么验、怎么落进一个槽、怎么绑版本。
**分发**（谁把包放上网、要不要审核）不在本文件里 —— 那是产品/合规决定，不是技术问题。

## 1. 为什么那些做法结构上必然差

分两种说：**1.1 嵌套模组**（你记得的那种，游戏内玩法）、**1.2 数据包 / APK / `Android/data`** 那几条。
结论一样：不是没做好，是路子本身不成立。

### 1.1 嵌套模组：把 N 个模组伪装成 1 个

**游戏侧的事实**（判据 = 游戏源码 + 本工程 `Mods.readOne` / `resolveRootPrefix` 的镜像实现）：

- 扫 `mods/` 时**一个顶层条目 = 一个模组**；只有当这个条目里**只有一个子目录**时，才允许下潜一层
  （`resolveRootPrefix` / `resolveDir`）。容器里的第二个 `mod.hjson` **永远不会被读到**。
- 一个模组在游戏里同时是 **8 条边界**；嵌套就是把这 8 条压成 1 条 ⇒ 每一条都会以某种方式坏：

| 边界 | 正常模组 | 嵌套以后怎么坏 |
|---|---|---|
| **类加载** | 每个模组一个 `ClassLoader`（安卓 = `DexClassLoader` 吃**整个包**） | 内层共用外层 loader ⇒ 同名类串、跨 loader 的 `instanceof` 失败、静态状态两份；另起一个 ⇒ Android 14+ 只读 dex / 优化目录 / 父子关系都要自己处理 |
| **内容命名空间** | `<模组名>-<内容名>`，存档按这个 ID 记 | 内层内容只能挂外层前缀 ⇒ 两个内层模组同名方块/物品直接撞；换个包版本，存档里的 ID 对不上 = 内容丢失 |
| **资产 / 语言** | `sprites/` `bundles/` `sounds/` 以**包根**为准 | 内层的贴图/翻译看不见（黑块 / 缺字 / `[red]` 未翻译） |
| **生命周期** | `init()` → `loadContent()` → `ContentInit` 由游戏按阶段调 | 在 `init()` 里动态加载内层，赶不上 `loadContent` 的时序；热重载（游戏自己退出重载）再跑一遍 ⇒ 重复注册 |
| **版本门** | 每个模组各自 `minGameVersion` 被检查 | 只查外层 ⇒ 内层要 154 的模组在 146 上照样进来，运行期才炸 |
| **启停** | `mod-<名>-enabled` 一个模组一个键 | 只有外层一个键 ⇒ 一个成员坏掉只能整包关，没法单独排查 |
| **联机身份** | 发给服务器的是 `名字:版本` 列表 | 只报外层 ⇒ 两边内层版本不同也通过校验，进游戏才 desync |
| **崩溃归因** | 栈帧能指到具体包 | 只指到外层 —— 我们的崩溃分析也只能点名整包 |

**而且两种"嵌套"其实都不成立**：

- **外壳无代码**（只有 `mod.hjson` + 一堆 jar）⇒ 内层**根本没加载**。这就是"装上了、进游戏没效果"那一类反馈。
- **外壳有 `main`**，用反射 / `ClassLoader` 去加载内层 ⇒ 上表那一串 bug 全来；
  再加上 Android 上内层 jar 必须是 `classes.dex` 形态（桌面 `.class` 不认）、内层 dex 还得从 zip 里解出来才加载得了。

⇒ 所以嵌套不是"整合包"，是**把多个模组伪装成一个模组**。游戏把"一个模组"当成 8 条边界的整体，
  这 8 条边界全都只认最外层那一个名字。

### 1.2 数据包 / APK 那几条路

| # | 数据包那条路的硬伤 | 依据 | 我们为什么不会踩 |
|---|---|---|---|
| 1 | **一个数据根，导入 = 覆盖**。原生「设置 → 数据 → 导入数据」会**先删** `saves/` `assetCache/` `tmp/` 再解包 | `SlotZip` 类注释（源码核实 Mindustry 160.4 `SettingsMenuDialog`） | 每槽独立 `mindustry.data.dir`；包只装进**新槽**，现有存档一个字节都不碰 |
| 2 | **版本对不上**（Mindustry 里通常是**模组比游戏新**，不是"包只适合旧版"）：模组 `minGameVersion` 不满足 ⇒ 游戏**整槽跳过**（写 `-failed` 记账），用户看到的是「游戏坏了」 | `Mods.stateOf` / `Mods.resolveDependencies`；`ref/29` §86 | 包**不锁**游戏版本；装完按**绑定的那个版本**逐模组 `stateOf` + 依赖图预检；不兼容的只写 `-enabled=false` |
| 3 | **没有清单**：不知道包里有什么、给谁做的、缺什么、能不能装 | — | `mdtpack.json`（§4） |
| 4 | **手机摸不到 `Android/data`**：所谓「解压到 mods 目录」在 Android 11+ 不成立，只能游戏内逐个导 | 本工程整体前提（hub 目录 + SAF） | 导入走 SAF + 我们自己的 hub + `SlotZip` 的落盘路径 |
| 5 | **没有隔离/回滚**：一个坏包毁掉全部存档，且没有「先看看再装」这一步 | — | `SlotZip` 的「先 inspect 再 extract」+ `.part` + 中转站 + 整槽备份 |
| 6 | **包只认自己那份格式**（根上必须有 `settings.bin`），制作者只能猜 | `SlotZip.Info.nativeFormat` | 我们既认原生格式，也认「根级零散文件」和「包裹目录」（三态 `tagRes`） |

另外两条也常见（都不是"整合包"该走的路）：

- **重打包 APK 那条路**：把模组塞进游戏 APK 里再重签名 ⇒ 签名一换就不能覆盖升级、模组不能单独更新、
  包体积 78 MB 起；而且**游戏只从数据目录读 `mods/`**，塞进 APK 的资源未必会被加载。
  我们根本不碰这条：**官方 APK 原样当插件加载**，模组放在槽里。
- **「解压到 `Android/data/.../mods`」那条路**：Android 11+ 文件管理器看不见那个目录；
  能用的只有游戏内 SAF 逐个导入 —— 一个 20 个模组的包就是 20 次选择文件。

### 1.3 我们的做法：安装期打包，运行期扁平

一句话：**包只在「安装」这一刻存在**。装完以后，槽的 `mods/` 里是 N 个独立模组，
游戏根本不知道"整合包"这回事 —— 上面那 8 条边界一条都不动。

| 他们要的 | 嵌套模组的做法 | 我们的做法 |
|---|---|---|
| 一个文件装完 | 一个包 = 一个模组 | 一个 zip = 清单 + N 个模组 + 内容 |
| 模组一起装 | 塞进外壳 | 导入时逐个落进 `mods/`（`Mods.importPackage` 逐个验） |
| 一起关 / 一起删 | 外层一个开关 | 卸载 = 删槽；关 = 批量写 `-enabled=false` |
| 版本对得上 | 只查外层 | 每个模组各自 `minGameVersion` + 目标 build 预检 |
| 出问题能查 | 只指到外壳 | 每个模组单独启停 / 单独归因（现有崩溃分析） |
| 成员单独更新 | 重打整个包 | 直接换 `mods/` 里那一个文件 |

★ 顺带能做的是**旧嵌套包的「拆开安装」**：检测"外壳里还有 `mod.hjson` / jar"，逐个 `readOne` 验过，
拆成扁平模组。但**只对「外壳没有代码」的容器安全**；外壳有 `main` / `classes.dex` 时**不自动拆**
（它可能自己在加载内层，拆了会双载）。建议先只做「检测 + 提示」，别一上来就改用户的包。

## 2. 我们已有的零件（全部是现成代码，不用重写）

| 能力 | 实现 | 在整合包里怎么用 |
|---|---|---|
| 每槽独立数据根 | `Data` / `GameSlot` / `Injector`（`mindustry.data.dir`） | 包装进**新槽**，不动现有槽 |
| 整槽导出 | `Exporter` + `Data.contentRoots`（`SLOT_EXCLUDE` 唯一口径） | 包的**数据面现成**；且是原生 `exportData` 的**超集**（游戏自己也能吃） |
| 整槽 zip 导入 | `SlotZip`：`stage` → `inspect` → `extract`，zip-slip 防护、`.part`、可先清空 | 导入的执行层；`stage` 已经落在 `app_hub/zip-import.tmp` |
| 模组导入即验 | `Mods.importPackage`（落 `.part` → 游戏自己的 `readOne` → 就位） | 包里的每个模组逐个过同一道判据 |
| 版本 / 依赖判据 | `Mods.stateOf` + `Mods.resolveDependencies`（游戏口径，逐行复刻） | 导入前算「这个模组在这个槽里会不会加载」+ 缺依赖 / 循环依赖 |
| 模组启停 | `Mods.setEnabled` / `SettingsBin.applyBools`（**成对写** `-enabled` + `-failed`） | 不兼容的模组自动关掉，槽仍能启动 |
| APK 导入 | `Importer`：`Compat` 能力探测 + 置只读 + 预热预检 + 登记 | 厚包 / 用户补 APK 时走这条路 |
| 版本 → 槽绑定 | `Config.setSlotOf` / `Versions.slotFor` | 装完自动绑好「启动项」 |
| 批量四类内容 | `BatchIo`（三态 `Probe`、`expand`、`plan` 同名只问一次、目录模组打 zip） | 地图/存档/蓝图/模组的落位与重名处理 |
| 脱敏 | `SharePack`（剥 `usid-*` / `uuid` / `ip` / `server_list.json` …） | 分享出去的包必须走这条；自用包不走 |
| 下载 + 校验 | `UpdateDownload`（sha256 + `.part` + 镜像回退）+ `UpdateClient` | **C 形态**现成的下载层；不用从头写 HTTP |

⇒ 所以这不是「从零做整合包」，是「**把已有零件接成一条包安装流水线 + 补一份清单**」。

## 3. 缺的正是「整合包」本身

### 3.1 清单：包根 `mdtpack.json`（schema 1）

```json
{
  "schema": 1,
  "name": "XX 整合包",
  "version": "1.0",
  "author": "……",
  "note": "一句话说明",
  "game": { "variant": "official", "package": "io.anuke.mindustry",
            "build": 159, "revision": 7, "version": "159.7" },
  "mods": [ { "file": "mods/xxx.jar", "name": "xxx",
              "sha256": "…", "minGameVersion": "146" } ],
  "content": { "saves": 3, "maps": 2, "schematics": 1 },
  "scrubbed": true,
  "created": "2026-11-01T12:00:00+08:00"
}
```

三条设计纪律：

1. **包根仍是原生布局**（`settings.bin` + `saves/` + `maps/` + `mods/` + `schematics/` …）——
   清单只是**多出来的一层**。好处：**没有清单 = 现在的「整槽 zip」**（向后兼容）；
   有清单的包**降级**时游戏自己也能「导入数据」（只是不校验版本/模组）。
2. **`game` 是「要求」不是「内容」**：薄包不带 APK，只说「我是给哪个 build 做的」。
3. **`scrubbed` 只对分享包有意义**：`true` = 已按 `SharePack` 剥过身份；自用包 `false`，导入时不提示。

### 3.2 导出侧

- 两条出口各加一份清单：「导出整槽」→ `scrubbed=false`；「分享包」→ 先跑 `SharePack.plan`，再写 `scrubbed=true`。
- `settings.bin` **不能原样带**：里面除了 `mod-<名>-enabled`，还有作者的键位、音量、语言、`usid-*`。
  ⇒ 包里的 `settings.bin` **只保留模组键**（`mod-*-enabled`，以及 `modcrashdisable` 这类"整槽行为"键）；
  这样它仍是合法的 `settings.bin`（游戏导入也能吃），但收包的人不会继承作者的手感。
- 文件名：`mdt-<包名>-<槽>-<日期>.zip`；**仍用 `.zip`**（QQ/网盘/系统选择器都认），靠包根清单识别，不发明新后缀。

### 3.3 导入侧（一键流程）

1. 选 zip → `SlotZip.stage` 暂存到 hub（SAF 流只能读一遍）
2. 只读一遍：清单 + 条目统计 + 每个模组的 `readOne`（**不写槽**）
3. 预览卡：包名/作者/目标版本/模组 N 个（其中 M 个与目标版本不兼容）/内容数量/是否脱敏
4. **目标槽：只允许新建槽或空槽**（硬规矩 —— 不往现有槽里合并，否则 `settings.bin` 合并语义会变成第二个"整槽覆盖"）
5. 版本解析：
   - 已装同 build ⇒ 直接绑定；
   - 没装 ⇒ 提示「这个包要 159.7」+ 两个出口：「导入 APK」（走 `Importer`）或「仍要装（不保证能跑）」
6. 解包：先解到 hub 下的**暂存目录**，成功后整体换入槽（比直接写槽更安全；`SlotZip` 现在是直接写槽，这一步要加）
7. 逐项落位：模组走 `Mods.importPackage`（失败的那一个跳过并记账）；内容走现有落位；不兼容的模组写 `-enabled=false`（成对写 `-failed=false`）
8. 绑定版本 + 结果页：装了什么 / 跳过什么 / 哪个模组被判不兼容 / 去哪启动

★ **装完的判据**：槽的 `mods/` 下是 **N 个顶层条目、每个都是独立模组**，没有「外壳」这一层 ——
这就是它和嵌套包的根本区别（游戏看到的永远是 N 个正常模组，不是一个套娃）。

### 3.4 管理器侧：包是**一等对象**（"整合"落在账本上）

> 用户 2026-11-01：「但是管理器也应该让他是整合的」—— 对，**磁盘扁平 ≠ 管理器里散着**。两层要分开：

| 层 | 形态 | 为什么必须这样 |
|---|---|---|
| **磁盘 / 运行时** | 槽的 `mods/` 下 N 个独立条目 | 游戏只认这个；Android 上也没法把包"挂"进去（见下） |
| **管理器** | 一个「包」对象：id / 名字 / 版本 / 清单 / 成员表（文件名 + sha256 + 角色）/ **提示版本** / 安装时间 | 整包开关、整包删除、整包更新、按包分组、崩溃归因都靠它 |

**包记录放哪**：槽数据根顶层 `mdt-pack.json`（游戏忽略未知文件；`Data.contentSkipped` 不拦它）。
跟着**整槽导出 / 备份 / 换机**走 —— 槽换台手机，"包"还在；不写进 `config.json`（那是全局的，跟着槽走不对）。
一个槽可以有多份记录（数组或 `mdt-packs/` 子目录），每个包一条。

★ **槽在哪（2026-11-01 现查）**：`/storage/emulated/0/Android/data/<包名>/slot-<槽名>` ——
  是游戏默认数据根 `files/` 的**兄弟目录**（`Paths.slotParent` = `externalRoot` 的父目录）；
  **只有 `app_hub` 在内部**（`/data/user/0/<包名>/app_hub`：`config.json` / 导入的 APK / `natives` / 槽记录）。
  ⇒ 槽是**外部存储**。能不能搬内部？能（`mindustry.data.dir` 只是一个绝对路径），但要迁移全部槽、
  备份/导出/分享路径全变，而且**换不来链接**：`Os.link()` 连内部 f2fs 也拒（SELinux 的 `link` 权限），
  `Os.symlink()` 只在内部可用 ⇒ 除非"槽 + 包库"全搬内部再符号链接，否则还是一份展开的文件。**不建议为这个改布局。**

**游戏内一定会有人乱动开关**（用户 2026-11-01 提醒）—— 所以「包的状态」只能是**算出来的**，不能存的：

| 场景 | 包这一侧怎么表现 | 不许做什么 |
|---|---|---|
| 在游戏里关掉 2 个成员 | 组头「部分启用（3/5）」，两个成员行显示关 | 不许把「包 = 关」存下来；不许自动改回去 |
| 在游戏里全关 | 组头「已全部关闭」 | 不许把包记录改成禁用 |
| 点包的「全部开启 / 全部关闭」 | 一次 `SettingsBin.applyBools` 写全部成员（备份 + 读回）；确认框写明「会把你在游戏里单独关掉的 N 个也一起打开」 | 不许逐个写、不许写第二份状态 |
| 游戏崩溃后写了 `-failed` / 自动关模组 | 组头带「上次整槽被跳过」；成员行标失败 | 不许把失败算成「用户关的」（§86.7） |
| 用别的工具 / 我们自己的模组页删了成员 | 组头「包不完整（缺 N）」+ 提供「修复 / 移除记录」 | 不许自动重下 / 自动补文件 |
| 成员被换成别的版本（哈希不符） | 标「被改过」 | 不许静默覆盖 |
| 游戏里新导入了一个模组 | 按「散装」显示，不属于任何包 | 不许硬塞进最近的包 |

★ 一句话：**包记录只记「应该有哪些成员」，不记「现在开没开」；开没开永远现读 `settings.bin`。**

**包级动作**（全部走现成零件）：

| 动作 | 实现 | 判据 / 注意 |
|---|---|---|
| 整包启停 | `SettingsBin.applyBools` **一次读写**全部成员的 `mod-<名>-enabled`（成对写 `-failed`） | 不逐个写、不 N 次备份 |
| 整包删除 | 成员进中转站（`Trash`），再删记录 | 成员被别的包 / 手动安装共用 ⇒ 只解绑、不删文件（引用计数） |
| 整包更新 | 新清单 diff：加 / 删 / 换（sha256 不同） | 用户手改过的成员（哈希不符）单独提示，不静默覆盖 |
| 按包分组 | 模组页读记录 → 组头（包名 / 版本 / 开关）+ 成员行 | 无记录的模组仍按「散装」显示 |
| 崩溃归因 | 现有分析点名成员，再按记录补一句「属于包 X」 | 成员 → 包 的映射只此一处 |
| 包不完整 | 扫描时对账：记录里有、`mods/` 里没有 / 哈希不符 | 标「包不完整 / 被改过」，**不自动修** |

**为什么不把包做成一个文件 / 目录挂进 `mods/`**（"整合"最容易走偏的地方）：

- Android app 域**不能硬链接**：API 26/29/34/35/36 实测 `Os.link()` **全部 EACCES**（内部 f2fs 也拒；外部 sdcardfs EPERM / FUSE EACCES）；
  `Os.symlink()` **只在内部存储可用**，而槽（`slot-*`）在外部 ⇒ 挂不进去（`ref/49`）。
- 每次启动把包展开进 `mods/` ⇒ 几十 MB 拷贝 + 双份占用，且「上次启动到现在改了什么」无从对账。
- 游戏读的是 `mods/` 的**顶层条目**；外面再套一层壳，游戏就看不见（§1.1）。

⇒ **磁盘必须扁平，整合只能落在管理器账本上。** 这不是妥协，是把「游戏要的形态」和「用户要的形态」分开：
游戏看到 N 个模组，管理器看到 1 个包、N 个成员。

**可选加强（不是运行时形态）**：hub 里留一份**包库**（原始 zip + 清单），用于「重装 / 分享 / 找回原文」；
  它不参与加载，只是备份。

### 3.5 参照：MC 整合包（2026）的架构

> 用户 2026-11-01：「我是想知道现在 MC 的整合包是什么架构」—— 查了 Modrinth / CurseForge / MCBBS / packwiz 的规范，以及 PCL2 的安装实现。
> 一句话：**MC 的整合包不是「一个包」，是三层**；「整合」同样落在启动器的实例上，运行时还是扁平 `mods/`。

| 层 | 是什么 | 谁产生 |
|---|---|---|
| **清单** | 名字 / 版本 / 游戏版本 / 加载器 / 文件表（ID 或 URL + 哈希 + 端 + 可选） | 作者 |
| **overrides** | `config/` `scripts/` 资源包等「作者要覆盖的文件」 | 作者 |
| **实例** | 启动器在本地建的游戏目录（`mods/` 扁平 + `config/` + `saves/`） | 启动器 |

★ **包通常既不带游戏、也不带模组本体**：CurseForge 用 `projectID/fileID`，Modrinth 用 `URL + sha1/sha512`，
MCBBS 用 `addons` + 下载前缀；**游戏本体由启动器按 Mojang 清单下载**，加载器（Forge / NeoForge / Fabric / Quilt）另装。
⇒ 「整合」在 MC 里也是**启动器层的实例**，游戏看到的还是扁平 `mods/` —— 与 §1.3 / §3.4 同构。

格式对照（PCL2 的识别顺序，2026 源码 `ModModpack.vb`）：

| 格式 | 根标记 | 关键内容 |
|---|---|---|
| **MCBBS / HMCL 系**（国内老标准，PCL/HMCL 仍认） | `mcbbs.packmeta`（或带 `addons` 的 `manifest.json`） | `addons[{id,version}]`（game / forge / neoforge / fabric / quilt / optifine）、`launchInfo`、`overrides/`；同包常带 CurseForge `manifest.json` 做兼容 |
| **CurseForge** | `manifest.json` | `minecraft.version` + `modLoaders[].id`、`files[{projectID,fileID,required}]`、`overrides` |
| **Modrinth** | `modrinth.index.json` | `files[{path, hashes{sha1,sha512}, downloads[], fileSize, env{client,server}}]`、`dependencies{minecraft, forge/neoforge/fabric-loader/quilt-loader}`、`overrides/` `client-overrides/` `server-overrides/` |
| **MMC（Prism/MultiMC）** | `mmc-pack.json` + `instance.cfg` | `components[{uid,version}]`（net.minecraft / net.minecraftforge / net.neoforged / net.fabricmc.fabric-loader） |
| **HMCL** | `modpack.json` | `gameVersion` + `minecraft/` |
| **packwiz**（开发侧 / 自更新） | `pack.toml` + `index.toml` + `*.pw.toml` | 每个文件 URL + hash；`preserve` 不覆盖用户改过的；`packwiz-installer` 启动前对比 index 更新 |

安装流水线（PCL2 就是标准流程）：识别格式 → 取游戏/加载器版本 → 解压 overrides 到实例 →
按清单换下载地址 → 下载到 `mods/` 等 → 装原版 + 加载器 → 写实例配置（内存 / JVM / 版本隔离）→ 启动。

**为什么能这么薄**：中心化 registry（CurseForge/Modrinth 有稳定 ID + CDN + 哈希）、Mojang 版本清单、
加载器 meta/installer；**依赖解析在作者侧完成**（packwiz `update`），启动器只按钉死的版本下载。

**对我们**：

| MC 有什么 | 我们有没有 | 结论 |
|---|---|---|
| 中心 registry（projectID/fileID/versionId + CDN） | ❌（mdtbbs 只有一部分，模组 V1 还没版本化文件） | 包大概率**自带模组**，或带 URL + sha256；两者同一份清单 |
| 独立加载器（Forge/Fabric…） | ❌ 游戏 APK 就是"加载器" | 包**不锁**目标 build（`game` 只当提示），用户自备 APK |
| 依赖**版本**解析（版本约束 / 中心 registry） | ❌ 只有**名字**依赖（`dependencies` / `softDependencies`），没有版本约束、没有中心 registry | 不做版本解析；按名字查依赖图（`Mods.resolveDependencies`，逐行复刻游戏） |
| 客户端/专用服务器 | ❌ 只有本地 | `env` 端标记可省 |
| `preserve`（更新不覆盖用户改过的） | — | **要抄**：对我们「游戏内乱动开关」同样重要 |
| 实例 = 包 | ✅ 槽 | 一个包一个槽；更新 = 清单 diff |

★ 一条 2026 的旁证：PCL2 现在连 MC 本体下载都因合规关掉了（`RestrictMcDownload`）——
「包不带游戏本体」不只是我们的选择，也是行业现状。

### 3.6 MC 的旧版生态 vs Mindustry：版本矩阵可以砍掉

> 用户 2026-11-10：「MC 有很多人会玩旧版，但 MDT 不是，很少有人设计的一个模组只适合旧版」。

- **MC 的版本是断代的**：1.7.10 / 1.12.2 / 1.16.5 / 1.20.x 各一套生态，mod 与 loader 二进制不兼容
  ⇒ 整合包必须钉死 `game` + loader，启动器要管理多套游戏/加载器，包库按版本分。
- **Mindustry 不是这个形状**：
  - 玩家绝大多数在**最新版**（本工程记录里出现的是 159.7 / 160.x / MDTX；v146 这类老包是少数）；
  - 模组绝大多数**面向最新版**维护，`minGameVersion` 是"最低许可"，不是"只适合这一版"；
  - Android 上还有一条硬门槛：Java 模组 `minGameVersion` 必须 ≥ 154（`ref/29` §85.11），
    "只适合旧版"的 Java 模组在安卓上本来就不成立。
- ⇒ **设计后果**：
  1. **不做版本矩阵 / 包库按版本分**：v1 一个包一个槽，包**不锁**游戏版本；
  2. 清单里的 `game` **只是提示**（预选 / 诊断），不是门禁；没装它说的那一版，照样能装、能绑别的版本；
  3. 绑定目标版本：优先清单提示的已装版本 → 否则**最新已装** → 也可以「先不绑」；
  4. 兼容性仍然逐模组查（`stateOf`），因为"模组比游戏新"是真问题，只是它**不是**"整合包只适合旧版"；
  5. 反过来：用户真有一份老版本 + 只适合它的模组，同一条路照样能用（绑那个老版本），只是不为此做矩阵。
- **代价变化**：P1 里"版本解析"从 MC 式匹配降为「一个提示 + 一个选择器」，少约 0.5 轮；
  省下的精力放在依赖 / 命名空间 / 管理器账本上。

### 3.7 换个主线：模组方案（多模组整合管理，2026-11-10 提议）

> 用户：「我觉得我们是不是可以搞成多模组整合管理而不是整合包那样？」

- **判断：更贴 MDT。** 方案 = 槽里一个命名成员集合；动作是**开/关**（只写 `settings.bin`），
  不搬文件、不建槽、可逆。整合包 = 分发完整环境（MC 需要，因为版本断代 + 大包 + 中心 registry）；
  MDT 的日常痛点是"槽里十来个模组，想成组开关 / 成组排查 / 换着玩"，不是"一次装 50 个"。
- **模型**：`mdt-groups.json`（槽根，随整槽导出/备份走）；成员按 `internal`（内部名）认，`file` 只用于显示；
  一个模组可属多个方案（方案是视图/动作，不是所有权）；**不存开关**。
- **动作**：应用 / 关闭 / solo（可选，破坏性）/ 加成员 / 删成员 / 改名 / 删除；
  全部**一次** `SettingsBin.applyBools`；游戏在跑拒绝。
- **状态**：`Mods.scan` + `Mods.resolveDependencies` + `Mods.stateOf` 派生（同 §3.4 那条纪律）；
  缺文件 / 被改过 / 不兼容照 `PackRecord` 那套。
- **与包**：方案是主对象，包是 transport —— 导出 `kind=group`（只模组，合并进当前槽）；
  完整环境 `kind=environment`（整槽，新槽）后置。
- **代价**：核心 2.5~3.5 轮（`ModGroup` + `ModGroups` + 模组页 UI）；导入/导出 **0**（走现有整槽 zip）。
  ⚠️ 2026-11-10 最终形态改为**虚拟组行**（宿主 `rows` + 插件），成本见方案文档 §9；
  本节的“独立合集页”只是探索，不再作为主线。
- **插件可行性**：数据、批量开关都够（`contents` / `gameSettings` / `writeGameSettings` / `pickContent`）；
  **导入导出共用现有「导入整槽 / 导出整槽」**（`mdt-groups.json` 是槽文件，`Data.contentRoots` 会带上），
  不新增按钮、插件不用 `pickFile`/`addItem`；配置只需 `{"schema":1,"groups":[…]}`。
  缺的是**中性行标签**（`Finding` 的"⚠ 结论"位不该拿来当方案徽标）——v1 可以不做。
  插件同进程、无沙箱 ⇒ 写 `settings.bin` 只建议官方/内置。详见方案文档 §7.2 / §11。
- 详见 [模组方案：多模组整合管理](2026-11-10-模组方案-多模组管理.md)。

## 4. 成本与顺序

| 阶段 | 内容 | 轮 |
|---|---|---|
| **P1 薄包** | `PackManifest` 解析/写出 + 自检；导出加清单；导入向导（预览卡/目标槽/版本解析/预检/结果）；真机往返 | **3~5** |
| **P1b 管理器整合** | `mdt-pack.json` 记录 + 扫描对账 + 模组页按包分组 + 整包启停/删除（`SettingsBin.applyBools` / `Trash` + 引用计数） | **+1~2** |
| **P2 厚包** | 包内 APK 解出 → `Importer`（需要补一个 File 入口或复用 `ShareProvider`）；信任提示；README 立场要先改 | +1~2 |
| **P3 在线** | mdtbbs `Pack` 浏览/授权/下载/限流（复用 `UpdateDownload`）；README「不做下载」口径要先改 | +3~5 |

P1 里最花时间的**不是解包**（`SlotZip` 已经做完），是：
导入向导的边界（重名 / 不兼容 / 半途失败 / 大包空间 / 包内目录形态的模组）+ 自检夹具 + 真机往返。

P1b 的最难点是**对账**：用户可能在模组页单独删/换成员、备份恢复后记录与文件不一致
⇒ **记录只能当「意图」，文件才是事实**；扫描时以 `mods/` 实际内容为准，记录对不上的标出来，不自动改。

## 5. 风险与边界（写清，别当万能）

- **包 = 可执行代码**：模组是 dex，进 `:game` 进程跑。预览卡必须列出模组名，文案要说「只装信得过的包」。
- **拆旧嵌套包有双载风险**：外壳带 `main` / `classes.dex` 时它可能自己在加载内层，拆开再装 = 同一份代码加载两次；
  ⇒ 这种包**只提示不自动拆**，并建议找原作者要扁平版。
- **版本一换未必还能跑**：包里带了模组启停状态，但升级游戏后 `minGameVersion` 要重判；清单里的 `game.build` 只是"出包时"的事实。
- **内容 ID = 模组内部名 + "-" + 文件名**（`ContentLoader.transformName`）⇒ **包永不改写 `mod.hjson` / 永不合并模组**；
  改内部名 = 旧存档/蓝图/地图"丢内容"（机制与判据见 `ref/23` §77）。跨模组**内容**互访靠前缀名 + `dependencies`；
  跨模组**类**引用不成立（每个模组一个 `ClassLoader`，`dependencies` 不合并 classpath）—— 这不是包能解决的，见落地文档 §2.1。
- **内部名重复 = 包坏了**：游戏后写者覆盖前者；导入预检直接拒（`Mods.scan` 的 `Info.duplicated` 会标）。
- **fork 差异**：官方 / MindustryX 的模组兼容不同。`variant` 只做提示，**不阻断**（用户可能就想试）。
- **`settings.bin` 是跨设备配置**：分享包必须 `SharePack` 先剥；自用包也要只留模组键。
- **空间**：暂存（zip 本身）+ 解包后内容 ≈ 2 倍；`Storage.Report` 已有口径，导入前要判一次。
- **包内路径安全**：`SlotZip.cleanPath` 已有；清单里的 `mods[].file` 也要走同一套规范化。
- **在线包**：`download-grants` 10/60s、文件下载 60/60s、Pack ≤100 成员 ⇒ 必须节流 + 队列 + 失败重试；
  且 mdtbbs 的模组在 V1 里还没有版本化文件（见 `ref/34` §87.3），走 legacy 端点时要抽一层"源"。

## 6. 要定的六件事（定了才好开工）

1. **带不带游戏本体？** 我建议**不带**：APK 78 MB、README 已写「不打包游戏本体」、版本一换整包就废；
   改成「用户自备/已装，包只记一个提示版本」。要带就得先改 README 与发版口径。
2. **包的识别**：只认「`.zip` + 根上 `mdtpack.json`」，还是给专用后缀（`.mdtpack`）？
   我建议前者（兼容性最好，QQ/网盘/系统选择器都不折腾）。
3. **包这条线先做哪条**：本地文件（A）先落地，还是直接冲在线（C）？我建议 A → 看真实反馈 → 再 C。
4. **旧嵌套包（D）做不做**：建议先做「检测 + 提示 + 拆开安装（仅外壳无代码）」，
   带代码的只提示；不做的话，用户把旧包丢进来至少要能说清「游戏只会把它当 1 个模组」。
5. **模组放包里还是只放 URL？** MC 两种都有（CurseForge 只放 ID，MCBBS 可放文件/前缀）。
   我们建议：**能拿到稳定 URL + sha256 就只放 URL；拿不到就带文件** —— 同一份清单，不分成两种格式。
6. **包要不要锁游戏版本？** 建议**不锁**（`game` 只当提示）。MC 的旧版断代生态不适用于 MDT：
   玩家都在最新版、模组也面向最新版维护（§3.6）⇒ 不做版本矩阵，装的时候按已装版本选。
7. **主线选方案还是包？** 建议**方案优先**（§3.7）：方案只写开关、不搬文件、**2.5~3.5 轮**就能日常用；
   包要清单 + 解包 + 新槽 + 版本绑定（5~7 轮），更适合"分享 / 换机"。方案导出成包（`kind=group`）后置 +1~2。

## 7. 一句话

**能，而且这次结构上成立**：嵌套那条路是把 8 条边界压成 1 条，怎么修都会漏；
我们做的是「**磁盘/运行期扁平，管理器里整合**」—— 游戏看到 N 个正常模组，
管理器里有 1 个包对象（清单 + 成员 + 哈希 + 提示版本），整包开关 / 删除 / 更新 / 归因都靠它。
原版缺的三样（独立数据根 / 版本对不上 / 导入前验证）我们都有现成的；而 MC 那种"包锁死游戏版本"
在 MDT 里没必要（§3.6），包**不锁**版本，只把版本当提示。
剩下的是「清单 + 一条安装流水线 + 一层包记录」，量级 **5~7 轮**（落地细化后的 P1+P1b；见代码落地文档 §9），
最大变量是「包要不要带游戏本体」这条产品立场。
