# 跨槽共享：Android 版本矩阵（2026-10-28）

> **用途**：回答「硬链接 / 符号链接到底是不是 Android 16 的特例」。
> 结论先行：**不是。`link()` 从 Android 8.0 起就被 SELinux 拒；版本差异只改变 errno，不改变失败。**
> 受影响的是 [7.3b 活文件共享](../../docs/backlog/09-七-代码复核后的功能池.md#L79-L102) 与
> [4.4b 游戏本体 CAS 的硬链接装配](../../docs/backlog/06-四-P2P3-交互与美化.md#L171-L191)；
> **备份层的跨槽 CAS 不受影响**（它不用链接，只读 / 写 / `rename`）。

## 一、方法

- 探针 APK：`io.mdt.linkprobe`，12 KB，`minSdk 26` / `targetSdk 36`；
  在 `onCreate` 里对四个目录各写一个 3 B 文件，然后调：
  - `android.system.Os.link(src, dst)`
  - `android.system.Os.symlink(src.getName(), link)`
  - 失败捕获 `ErrnoException.errno`；成功用 `Os.stat().st_ino` 校验硬链接同 inode。
- 四个目录：
  1. `getFilesDir()`（内部）
  2. `getDir("hub", MODE_PRIVATE)`（内部 `app_hub`）
  3. `getExternalFilesDir(null)`（外部，槽 / hub 同栈）
  4. `getExternalFilesDir(null)/hub`（外部 hub）
- 设备：4 台 x86_64 AVD（`mdt26` / `mdt29` / `mdt34` / `mdt35`）+ HONOR ELP-AN00 真机；
  全部 `Enforcing`。AVD 是 `userdebug`，真机是 `user`。
- 真机那一组用的是启动器 dev 口的同款探针（`dev_link_probe`），结果与探针 APK 一致；
  探针源码与 APK 留在临时目录，未进产品代码。

## 二、矩阵

| Android | API | 外部栈 | internal `link` | internal `symlink` | external `link` | external `symlink` |
|---|---|---|---|---|---|---|
| 8.0 AOSP | 26 | FUSE | ❌ EACCES | ✅ OK | ❌ EACCES | ❌ EACCES |
| 10 AOSP | 29 | sdcardfs | ❌ EACCES | ✅ OK | ❌ EPERM | ❌ EPERM |
| 14 AOSP | 34 | FUSE | ❌ EACCES | ✅ OK | ❌ EACCES | ❌ EACCES |
| 15 AOSP | 35 | FUSE | ❌ EACCES | ✅ OK | ❌ EACCES | ❌ EACCES |
| 16 HONOR | 36 | FUSE | ❌ EACCES | ✅ OK | ❌ EACCES | ❌ EACCES |

- `internal` 的两列在 `files` / `app_hub` 上结果相同；
- `external` 的两列在 `files` / `hub` 上结果相同；
- 只有 API 29 的外部栈是 sdcardfs（`EPERM`），其余是 FUSE（`EACCES`）；
- **硬链接：5 个点全失败；符号链接：内部全 OK，外部全失败。**

## 四、怎么读这张矩阵

1. **内部 `link()` 的 EACCES 不是文件系统问题**：`/data` 是 f2fs/ext4，本身支持硬链接；
   是 SELinux 的 `link` 权限在 `untrusted_app` 域上被拒。`runas_app` 的 AVC 也明确
   `denied { link }` on `app_data_file`；`plat_sepolicy.cil` 里查不到给 `app_data_file` / `fuse`
   授 `link` 的 allow 规则。
2. **外部失败有两层**：API 29 的 sdcardfs 直接 `EPERM`（不支持硬链接 / 符号链接）；
   API 26/34/35/36 的 FUSE 是 `EACCES`（SELinux 拒）。两条外部栈都覆盖了，不是某一种栈的毛病。
3. **符号链接是唯一稳定的"链接类"原语**：内部 5 个点全 OK；外部 5 个点全失败。
   所以任何"共享"方案必须把落点放**内部存储**，且只能建**符号链接**。
4. **与 targetSdk 无关**：探针 `targetSdk 36` 在 API 26/29 上同样跑出上述结果；
   `link` 的 SELinux 判定不看 targetSdk。外部目录用的是应用自己的 `getExternalFilesDir`，
   不受 scoped storage 影响。
5. **OEM 差异**：只测了 AOSP 26/29/34/35 与 HONOR 36；其他 OEM 没设备，不能替它们下结论。
   但平台策略在 26~36 一致，OEM 要放行得额外加 allow；不要按"某个 OEM 可能允许"设计。

## 五、对三条线的影响

| 线 | 影响 | 结论 |
|---|---|---|
| **备份跨槽 CAS**（F16） | 不用 `link` / `symlink`，只读 / 写 / 算 sha256 / `rename` | ✅ **不受影响**；8.0~16 都能跑 |
| **7.3b 活文件共享** | 原方案 `Os.link` 5 个点全失败；外部 `symlink` 也全失败 | ❌ 硬链接版不可行；只剩「槽数据搬内部 + 内部符号链接」= **10+ 轮** |
| **4.4b 游戏本体 CAS** | 硬链接装配 5 个点全失败；内部 `symlink` 全 OK | ⚠️ 路线 ③ 硬链接作废；路线 ③' **内部符号链接装配**是剩余候选，前提是 `addAssetPath(<目录>)` / `DexClassLoader(<目录>)` 两个探针先过；否则只剩全量装配、省空间卖点消失 |

## 六、边界

- 未逐版跑 27 / 28 / 30~33；26/29 与 34/35/36 把 sdcardfs / FUSE 两端夹住了，
  且拒绝是 policy 级，预期不会变；要绝对全版本可以再补 28 / 30 / 33 三台。
- 未测其他 OEM ROM（只有 HONOR 36）；未测 root / system app 场景（本产品不是）。
- 探针只验了 `link` / `symlink` 两个系统调用；没有验 `rename` / `delete` 的语义
  （那是 7.3b 走符号链接路线时才需要，见 7.3b 的写入口审计）。

## 七、复现

探针 APK 的核心（完整工程在临时目录，未进仓库）：

```java
File src = new File(dir, "src");
File dst = new File(dir, "dst");
File sl  = new File(dir, "sl");
try {
    Os.link(src.getAbsolutePath(), dst.getAbsolutePath());
    // success: Os.stat(src).st_ino == Os.stat(dst).st_ino
} catch (ErrnoException e) {
    // log e.errno + e.getMessage()
}
try {
    Os.symlink(src.getName(), sl.getAbsolutePath());
    // success: Os.readlink(sl).equals(src.getName())
} catch (ErrnoException e) {
    // log e.errno + e.getMessage()
}
```

构建：`aapt2 link` → `javac --release 8` → `d8` → `zipalign` → `apksigner`；
装到 AVD 后 `am start -n io.mdt.linkprobe/.ProbeActivity`，读 `logcat -s LINKPROBE`。
