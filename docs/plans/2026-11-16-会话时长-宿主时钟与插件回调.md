# 会话时长：宿主时钟 + 插件回调（自动备份的结束时刻）

> 2026-11-16 定案；**2026-11-17 实现**（用户「感觉没啥问题，开吧」）。实现形状以本文档 §二~§五为准，
> 与定案的三处偏差都来自 2026-11-17 用户的追加决定：判定统一 +20 秒、没有检查点就跳过、
> 宿主用完即删（记录归插件）。
>
> 相关：`docs/plans/2026-11-14-多实例实施路线.md` 阶段 2.3（记账）、
> `docs/plans/plugin-probes.md`（B1 / 「插件探针自己写」）、
> `docs/plans/2026-10-31-多实例并行可行性.md` §12.14（会话分账）/ §12.23（config 抢写）。

## 一、问题：现状的「正常记录」很窄

- `at` = 点「启动」那一刻（`Config.sessionStart`，`MainActivity.startVersion` 在 `startActivity` 之前写）；
- `AutoBackup.settle` 只在 `MainActivity.onResume` 跑；`minutes = (now - at) / 60000`；
- ⇒ 记录到的「这一局玩了多久」实际是「启动 → 下一次让**启动器主界面**回到前台」。
  - 切回来落在别的页（设置 / 存档 / 版本页）不算，要退回主界面；
  - 游戏死的时候如果已经坐在主界面，也没有新的 `onResume`，要等下一次切换。

| 你怎么结束这一局 | 现在记到的时长 | 准吗 |
|---|---|---|
| 游戏内退出 / 按返回，回到启动器 | 启动 → 回到启动器 | ✅ 秒级 |
| 划掉游戏卡，紧接着打开启动器 | 启动 → 打开启动器 | ✅ |
| 划掉 / 系统在后台杀掉，隔一阵（甚至隔天）才开启动器 | 启动 → 打开启动器 | ❌ 多出中间空档 |
| 玩 A → 在启动器点 B（A 被 `ensureGameProcessDead` 杀掉）→ B 玩完回启动器 | A 的记录含 B 整局 | ❌ 偏大很多 |
| 游戏还活着时打开启动器看一眼 | 不结算（继续挂着） | — |

代码里把这条偏差写成「有意接受：只会偏大、不会漏」（`AutoBackup` 类注释）。
2026-10-26 第 252 轮起，**宿主不写 usage 流水**，时长归 `usagestats` 插件
（`PlaytimeProbe`：`onForeground` 累计 + 20 秒采样，只算游戏 activity 在前台的时间；
`plugin.json` 里 `inProcess: true` ⇒ 它跑在 **`:game`**，不在 `:probe`）。

### 历史（为什么会有「`:probe` 心跳」这个记忆）

- **更早（进文档前）**：要的是「**运行时长**」——进程活了多久；`:probe` 轮询 `/proc` 就能给
  ⇒ 当时的口径是「`:probe` 就能解决」，也因此对「往 `:game` 里塞代码」非常谨慎。
- **2026-10-22/23（第 219 轮）**：口径收紧成「**只算游戏在前台的时间**」——`:probe` 看不到前台，
  才需要 `:game` 里的 lifecycle 回调；这一版是宿主在 **`:game` 进程**记 `run.tsv`
  （`S/B/E/C/SC`，**每 30 秒一次 `B` 心跳**，只记下界、绝不多算），
  「展示 / 聚合 / **绘图**全部由插件做」。
- **第 252 轮**：用户「注入游戏脚本完全由插件负责写，宿主只负责给注入」⇒ 删掉宿主的 `UsageLog`。
- **第 254 轮**：`usagestats` 插件 + `inProcess: true`（仍在 `:game`）；v29 的 `onForeground`
  **只发给 in-process 探针**（用户坚持要这个接口才加的），`:probe` 收不到前台事件。
- 所以「心跳 + 绘图」两个词都来自原设计，但心跳在 `:game`、绘图只是计划里给插件的、**从未实现**。
  `:probe` 是探针平台（2026-10-23）对「不想碰游戏进程」的**默认选项**，`usagestats` 是例外
  （要前台事件）。**「`:probe` 就能解决」和「`:game` 心跳」其实对应两个不同的口径**：
  前者只要运行时长，后者要前台时间——文档只记了收紧后的口径，所以看起来像「进文档前就偏了」。

## 二、定案

一句话：**宿主在 `:game` 里量这一局（不是 `:probe`），20 秒落一个检查点；算完这一局的时长后，通过 `game-exit`
给插件回调一次。插件不再自己采样。**

1. **宿主时钟**（`SessionClock`，`:game` 内，`GameSlot` 在 `Instances.publish` 之后启动）：
   - 起点 = 自己启动的时刻；用现有的 `GameActivityWatcher` 前后台事件累计 `activeMs`（不新增钩子）；
   - 每 **20 秒**写一拍；pause / resume 立即写；游戏 activity **真结束**（`isFinishing` 的
     destroy）最后一拍 + 停表（只 `finish` 不退进程时，不能让进程被缓存的那段继续记）；
   - 线程是 **daemon**（不能因为计时器让 `:game` 进程赖着不走）。
2. **检查点**：`app_hub/instances/<started>-<pid>.time`，一行 JSON：
   `{v,pid,proc,vkey,slot,started,lastSeen,activeMs}`，原子写。
   - 20 秒是**落盘频率**（被 SIGKILL 时最多丢一拍），**不是判活**；
   - 文件名用 `<started>-<pid>`（数字，安全），槽/版本在 JSON 里；不用槽名进文件名；
   - **只用于判断"用不用备份"，处理完就删**（用户 2026-11-17：「宿主不记录文件，
     处理完就删，记录由插件负责」）⇒ **不做 7 天过期、不进 `Recovery`**。
     唯一的清扫是孤儿：`pid` 已死 + 没有对应 `sessions` 账的 `.time`（config 写竞争弄丢账时的垃圾）。
3. **结算**：先按进程存在性判活（`stillRunning` / `WriteGate`），还活着就跳过；
   进程没了才读检查点，`end = lastSeen`，判定用
   `ms = lastSeen + 20 秒 - session.at`（`SessionClock.FLUSH_MS` 同一个常量）；
   **没有检查点 ⇒ 跳过**（用户 2026-11-17「倒是可以」）：不回退 `now`，
   不拿"第二次打开启动器的时刻"充数。读完立即删（`SessionTime.deleteSlot`）。
4. **插件回调（每个实例一次）**：宿主算完时长后，把 `started / ended / activeMs / wallMs`
   （+ 版本身份 `key`）放进 `game-exit` 的 data，插件的入口类（`plugin.json` 的 event 条目）
   收到**一次**。
   - 不是每 20 秒回调；20 秒那笔只给宿主自己用。
   - 主进程在游戏期间是冻结的 ⇒「每 20 秒回调到主进程」做不到；要实时 tick 只能进 `:game`
     的 in-process 探针（本批不做）。
   - **顺序兜底**：`AutoBackup.settle` 与 `game-exit` 的先后不保证（分屏 / 多开下游戏在启动器
     可见时被杀，settle 会先跑并删文件）⇒ settle 把这一拍的观测**只在内存**交给
     `PluginEvents.noteExitStats`；事件派发时优先用它，没有才现读 `.time`。
     进程被杀则这条事件本来也会丢（和现状一致）。
5. **插件不再采样**：`usagestats` 删掉 `PlaytimeProbe`，改收 `game-exit`、追加账本、
   更新 `total.txt`。性能类探针（`:probe`）不变。
   - ⚠️ `usagestats` **目前没有图表**（页面只有文字行）；图表是插件侧**后续新增**，
     本次只保证事件里给够数据，不承诺画图。2026-10-22/23 的原设计写过「绘图全部由插件做」，
     但从未实现。
6. **判活永远是进程存在性**：`:probe` 的 2 秒 `/proc` 检查、宿主的 `Instances` /
   `getRunningAppProcesses`。绝不用「下一拍检查点」判活——那会让「去一趟启动器」看起来像结束。

## 三、语义：两个数，别混

| 数 | 定义 | 谁用 |
|---|---|---|
| `lastSeen`（`wallMs = lastSeen - started`） | 最后一次被调度到的墙钟，≈ 进程活到什么时候 | **自动备份门槛**（与桌面版「启动 → 退出」对齐） |
| `activeMs` | 游戏 activity 在前台的累计（`onForeground` 累加） | 插件展示（与 `usagestats` 现在的口径一致） |

- 游戏进后台但**还没被冻结**时，时钟照样在走（进程活着，桌面版也这么算）；被系统冻结后
  `lastSeen` 就停在冻结前。`activeMs` 更早：它在 pause 那一刻就停了。
- 因此这次改变了「只偏大」的方向：`lastSeen` 可能早于「进程真正死掉的时刻」（冻结期间），
  但不会把「隔天才打开启动器」那段算进去。
- **判定统一 +20 秒**（用户 2026-11-17：「统一 +20s 不就完了」）：落盘最多丢一拍 ⇒
  `AutoBackup.judgedMs = lastSeen + FLUSH_MS - session.at`，门槛比较只用这个数；
  报告里观测值与判定值都写。**+20 秒补不了冻结**（冻多久就少算多久）——这是接受的语义：
  "最后一次真正在跑"比"进程活着"更接近"玩了多久"。
- `activeMs` 与 `lastSeen - started` 一般不相等；备份用后者（+容差），插件用前者。

## 四、实现形状

### 4.1 宿主时钟

- `SessionClock`（新类）：`GameSlot.handle` 在 `prepareSlot` / `Instances.publish` 之后启动
  （此时 slot / vkey 已确定）；异常全部吞掉，失败只写日志——**时钟失败不许影响游戏**。
- 安全边界：时钟**不引用游戏类、不做反射**，只用 `System.currentTimeMillis` /
  `ActivityLifecycleCallbacks` / 文件 IO；线程是 daemon。相比"插件探针在 `:game` 里跑"，
  少一层 `DexClassLoader` 和插件代码。
- 前台累计：复用 `GameActivityWatcher` 的 `onActivityResumed/Paused`（`GameSlot` 已有监听口，
  与 `ProbeRunner.foreground` 同源，不新增注册）。
  - ⚠️ 这个类**不是为计时建的**：2026-10-05（第 102~105 轮「游戏打不开」）它先是为**资产链**建的
    （`onActivityPreCreated` 必须早于游戏 `onCreate`）；前后台事件是 v29（第 254 轮）为探针加的
    第二个用途。本次只用第二条，第一条不动。
  - 事件源放在 `GameSlot` 的监听回调里，同时喂 `ProbeRunner` 与 `SessionClock`；**别让时钟依赖
    「这一局有没有插件探针」**（插件全关时也得走）。
  - 备选：`:game` 里也可以轮询自己的 `RunningAppProcessInfo.importance`（`getMyMemoryState()` 很轻）
    来判断前后台；但档位粗（分屏 / 画中画 / 熄屏的边界要自己解释）、误差一个轮询周期，不如已有的事件。
    `:probe` 同 UID 也能读到 `:game` 的 `importance`，但同样粗、还要跨进程轮询——只够
    「进程活着 / 在跑」这个级别，不够 `activeMs`。
- flush：daemon 线程每 20 秒 + pause / resume 立即；游戏 activity 真结束（`isFinishing` 的
  destroy）最后一拍并停表。
- 文件：`app_hub/instances/<started>-<pid>.time`，`Util.atomicWriteText`。
- 清理：**`settleOne` 里读完就删**（`SessionTime.deleteSlot`）——用户 2026-11-17：
  「宿主不记录文件，处理完就删」。删之前先把这一拍用 `PluginEvents.noteExitStats` 交给
  事件层（内存），否则「settle 先跑、`game-exit` 后到」时事件拿不到数。
  不做 7 天过期、不进 `Recovery`；只有"pid 已死 + 没有对应 `sessions` 账"的孤儿在
  `settle` 开头清一次。
- `Instances.scan` 只处理 `*.json`，不会误删 `.time`。

### 4.2 结算（`AutoBackup`）

- `settleOne`：`stillRunning` 为真 ⇒ 跳过（现状）；
- 否则 `SessionTime.read(ctx, slot, session.at)`（**唯一实现**）：
  - 扫 `instances/*.time`，筛 `slot` 相等且 `lastSeen >= session.at`；
  - 取 `lastSeen` 最大的一条；
  - **没有 ⇒ 跳过**（`AutoBackup.judge` 返回 `SKIP_NO_CHECKPOINT`，不回退 `now`）；
  - 判定 = `judgedMs(at, lastSeen)`（+20 秒）和 `min_minutes * 60000` 比；
  - **读完立即删**（`SessionTime.deleteSlot`），再清 `sessions` 的账。
- `PluginEvents` 的 `game-exit` 用**同一个** `SessionTime.read`（现读文件）或 settle 的内存交接，
  不要各算一遍。

### 4.3 事件（`game-exit`）

- `data` 加：`started` / `ended` / `activeMs` / `wallMs` / `key`（毫秒字符串 + 版本 key）；
  `backfill=1` 时也带（补报读同一份 `.time`，或 settle 的内存交接）。
- `key` = `SessionTime.Summary.vkey`（检查点里就有）⇒ 插件不必自己拼；
  插件用 `key` 去 `PluginApi.versions()` 的 extra 取 `tag` / `title` / `rawName` / `upstream`
  （不再需要把整份版本快照塞进事件，也不需要给 `PluginApi` 加新方法）。
- 老插件忽略多出来的键；`PLUGIN-API.md` 的事件表补这几个键（**加键不抬版本**，与
  `PluginHost` 对 `extra` 的既有约定一致）。

### 4.4 插件（`usagestats`）

- `plugin.json`：删 `telemetry.probes` 的 `PlaytimeProbe`；加 `events` 条目（`game-exit`）。
- `UsageStats`：收到 `activeMs` 后 `Playtime.put(...)`（base + 本局 activeMs）→
  `ledger.tsv` / `total.txt`；页面不变。图表现在没有，是后续新增（本次不做）。
- 主界面摘要卡那行仍然读 `total.txt`（`playtimeTotal`），宿主只排版、不解析账本。

## 五、不做 / 边界

- **不做** 插件侧的计时（`PlaytimeProbe` 删除）；**不做** `Probe.onPlaytime` 实时 tick
  （以后真需要再给 `Probe` 加默认方法）。
- **不做** 宿主历史账本：宿主只写**用完即删**的检查点；历史归插件
  （252 的「宿主不写 usage 流水」没有被反转：宿主只写"这一局跑没跑够"的临时判据）。
- **不引入脚本运行时**：「插件给宿主一段脚本」= `plugin.json` 的 event 入口类（现成机制）。
- **不解决** `config.json` 的整份写竞争（`:game` 的 `setLastVersion` 可能覆盖主进程刚写的
  `sessions`）——那条仍要在多实例 A 之前单独修
  （`docs/plans/2026-10-31-多实例并行可行性.md` §12.23 表 / §12.24 D）。
  本次的检查点是**新文件**，不增加 config 写者。
- `:probe` 继续管性能数据（帧时间 / 内存 / `/proc`）与「进程还在不在」的检查（2 秒 `/proc`），
  与时长无关。

### 曾考虑、但没采用的

1. **`:probe` 心跳**（每 2 秒把「最后看见游戏活着」写进文件）：
   - `:probe` 只能看 `/proc`，看不到游戏 activity 在前台还是后台 ⇒ 给不了插件现在的 `activeMs`；
   - 它自己被冻结 / 停掉时，戳会停在冻结前 ⇒ 只能当「最后看见」，还可能少算；
   - 插件若仍要 `activeMs`，就得保留自己的 `PlaytimeProbe` ⇒ 变成两套计时，和
     「把心跳功能给宿主」相反。
2. **插件探针心跳**（保留 `PlaytimeProbe` 当计时源）：它是插件私有数据，宿主不解析
   （252 的定案），没法拿它当自动备份的门槛。
3. **给 `:probe` 升前台服务**（挂常驻通知）：能多活一阵，但多一条通知，ROM 清理照样可能带走。
4. **只在 pause 写一笔**（不做 20 秒检查点）：方向会从「只偏大」翻成「可能少算」，否掉。

> 采用宿主时钟的理由：`:game` 里**本来就有**插件的 `PlaytimeProbe`（in-process，20 秒采样 +
> `onForeground` 累计）。换成宿主的 `SessionClock` 后，`:game` 里的计时器数量不变，数据从
> 「插件私有」变成「宿主可读」；所以这不是「再往 `:game` 加一个心跳」，而是把已有的那个换主人。
>
> 产品理由（2026-11-17 用户）：「至少不是一个官方内置插件还会一直崩溃提示」——`usagestats`
> 是官方内置，它的 in-process 探针住在 `:game`，崩了就是游戏崩，崩溃报告还会标「有插件参与
> （官方，进程内）」；宿主时钟把这段从插件挪回宿主，少一个官方插件在游戏进程里跑。
> 探针调用本身有 try/catch（`ProbeRunner.tick` / `foreground` 都吞异常），但少一层
> `DexClassLoader` / 插件代码总是更好。

## 六、验证

- 自检（纯函数优先）：`SessionTime` 的写 / 读最新 / `since` 过滤 / 用完即删 / 孤儿清扫；
  `AutoBackup.judge` 的 `+20 秒` 门槛边界与三种跳过（关 / 没检查点 / 不够）；
  `PluginEvents.attachExitStats`（现读文件 / 内存交接两条路）；`.time` 不被 `Instances.scan` 删。
- 真机（dev）：
  1. 启动 → 第一拍立即出现、之后每 20 秒 `lastSeen` 在走；`started` 不变；
  2. Home（pause）→ 立即 flush；回游戏 → `activeMs` 接着涨；
  3. 划卡 → 回启动器 → `report-autobackup.txt` 的「观测」≈ 划卡时刻（不是打开启动器），
     「判定」= 观测 + 20 秒；`.time` 已被删；
  4. 启动后立刻整包 force-stop → 回启动器 → 用最后一拍（≤20 秒误差）；
  5. 玩 3 分钟 → 划卡 → 隔 10 分钟开启动器 → **不备份**（现状会备份），报告写「不够门槛」；
  6. `usagestats`：一次退出后 `ledger.tsv` / `total.txt` 的增量 ≈ 这一局的 `activeMs`
     （不是 wall；图表不在本次范围）。
- 不出现「启动器打开时刻」被当成结束时刻；不出现「暂停一下被当成结束」；
  不出现"结算后还有 `.time` 留着"（除了有账 / 活进程的）。
