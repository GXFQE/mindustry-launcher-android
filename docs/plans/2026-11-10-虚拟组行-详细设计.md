# 虚拟组行：详细设计（2026-11-10）

> 用户 2026-11-10：「不止需要插入，还得把原来的删掉」「这样原来的页面的接口不就变了吗，
> 我不想让其他插件都需要专门写一段代码适应这个」。
> 这份把**宿主内部怎么换行、插件契约为什么不变、哪些边界要钉**讲清楚。
> 目标：组在模组列表里就是**一行**，成员收进二级详情；其他插件零改动；插件缺失自动回退。

---

## 0. 三层，别混

| 层 | 是什么 | 谁拥有 |
|---|---|---|
| **数据层** | `Mods.scan` 扫出来的真实模组、`PluginData.pageItems` 的 `ItemInfo`、磁盘文件 | 宿主 |
| **插件契约** | `ItemInfo` / `Finding` / `state` / `gates` / `filter` / `sort` / `pickContent` | 宿主定义，插件使用 |
| **展示层** | `ModsActivity` 列表怎么画、组行、详情页、搜索/筛选后的 `mShown` | 宿主 |

**关键**：虚拟组行只存在于**展示层**；数据层与插件契约一个字不改。

## 1. 现在的真实调用链

### 1.1 扫描与列表

`ModsActivity.rescan()`：

```java
mScan = Mods.scan(this, mSlot);
mResolved = Mods.resolveDependencies(mScan.mods);
mTarget = Mods.targetsFor(this, mSlot);
mVerdicts.clear();
mIssues.clear();
rebuildList();
fillHeader();
refreshCrashVerdict();
PluginEntries.attachPage(this, Extensions.PAGE_MODS, mSlot, null);
```

`ModsActivity.rebuildList()`：

```java
List<Mods.Info> all = mScan.mods + mScan.broken;
List<Mods.State> sts = ...;                       // 宿主判定
List<Mods.Info> shown = Mods.filterAndSort(all, mQuery, mSort, mOnlyProblems, mType, sts);
shown = PluginPicks.applyFilters(shown, mPluginFilters, MOD_ID);   // 插件筛选
shown = PluginPicks.applySort(shown, mPluginSortIds, MOD_ID);      // 插件排序
mShown = shown;
// 登记"这一屏看得见的"给 pickContent 当默认勾选
PluginPicks.noteView(PAGE_MODS, mSlot, viewIds, narrowed);
for (Mods.Info m : shown) { inflate(item_mod); bindRow(...); }
```

### 1.2 插件分析

`PluginEntries.attachPage()` 在后台调用：

```java
PluginAnalysis.analyzePage(...);   // 内部用 PluginData.pageItems(page, slot)
```

`PluginData.scanMods()` 是**独立扫盘**：

```java
Mods.Scan scan = Mods.scan(ctx, slot);
Mods.Resolved resolved = Mods.resolveDependencies(scan.mods);
// 每个真实模组（含 broken）一个 ItemInfo；extra 带 enabled/internalName/depState/...
```

⇒ **`pageItems()` 返回的是全部真实模组，和 `mShown` 无关。**

### 1.3 findings 落点

`ModsActivity.onPluginFindings()`：

```java
for (Finding f : fs) mIssues.get(f.anchorPath).add(f);   // key = 真实模组 path
```

`bindRow()` 在行上显示短标签；详情弹窗显示 `detail`；都是按 `pathOf(m)` 取 `mIssues`。

## 2. 加 `rows` 之后怎么变

### 2.1 插件侧

```json
{ "id": "group-rows", "slot": "rows", "page": "mods", "entry": "..." }
```

```java
public final class VirtualRow {
    public final String id;
    public final String title;
    public final String subtitle;
    public final String badge;          // 可选
    public final List<String> memberIds; // 真实条目 id（见 §2.1.1）
}
public static List<VirtualRow> rows(PluginApi api);
```

插件做三件事：

1. 读 `slotDir()/mdt-groups.json`（schema + kind + members）；
2. 用 `contents(slot,"mods")` 的 `extra.internalName` 把成员名映射成 **条目 id**（见 §2.1.1）；
3. 返回 `VirtualRow` 列表；找不到的成员不放进 `memberIds`（组行 subtitle 里写“缺 N”）。

#### 2.1.1 身份不是 `path`：地图 / 蓝图的内置条目

`ItemInfo.path` 可能为 **null**：游戏 APK 自带、模组 zip 里的地图/蓝图，只有 `container` + `entry`。
所以 `memberIds` 用**和 `PluginPicks` 同一个 id**：

```java
String id = it.path != null ? it.path : it.container + "!/" + it.entry;
```

| kind | 成员 id |
|---|---|
| `mods` | 槽内文件路径（`path`） |
| `saves` | 槽内文件路径（`path`） |
| `maps` | 槽内地图 = `path`；自带 / 模组图 = `container!/entry` |
| `blueprints` | 槽内蓝图 = `path`；自带 / 模组蓝图 = `container!/entry` |

**注意**：

- 宿主隐藏/详情/搜索一律按这个 id 匹配，不能只看 `path`；否则自带地图永远匹配不上；
- 自带条目的 `container` 是 APK/zip 的绝对路径，**换版本可能变** ⇒ v1 **只允许把槽内文件（`path != null`）放进组**；
  自带/模组条目可以显示，但“加入合集”按钮禁用（或只在当前版本内有效，后面再说）；
- 槽内地图/蓝图用 `path` 是稳定的（换槽会变，但合集本来就随槽走）。

### 2.2 宿主侧

`rebuildList()` 末尾多一步（建议后台拿、缓存，别每次主线程加载插件）：

```java
List<VirtualRow> vrows = RowsProvider.rows(this, mSlot);   // 失败 ⇒ 空表
Set<String> hidden = union(vrows.memberIds);
mRows = mergeRows(vrows, mShown, hidden);                  // 展示用
mContainer.removeAllViews();
for (Row r : mRows) {
    if (r.isGroup) addGroupRow(r);     // 宿主行样式
    else addModRow(r.mod);             // 现有 bindRow
}
```

**`mShown` 不变**（仍是过滤/排序后的全部真实模组），**新增 `mRows` 只给展示**。
这是不破坏现有行为的关键：

- `mShown` 还用于删除弹窗、导出、`PluginPicks.noteView`；
- 这些语义保持“全部真实模组”，不因隐藏而变；
- 展示层才用 `mRows`。

### 2.3 组行

- 用宿主行样式（复用 `item_mod` 或新 `item_group`）；
- 标题 = 组名；副标题 = “5 个模组 · 缺 1 · 2 条体检结论”；
- 徽标 = 聚合状态（全开/部分/全关/不兼容）；
- 点击 → 组详情（宿主渲染）：成员真实行 + 每条 `mIssues` + 组开关。

### 2.4 组开关

- 宿主从 `memberIds` 找到真实条目（按 id 匹配）；
- 一次 `SettingsBin.applyBools` 写全部成员（成对清 `-failed`）；
- 游戏在跑 ⇒ 拒绝；成功后 `rescan()`；
- 部分状态：点开关 = 全开/全关（确认框写清“会改 N 个”）。

## 3. 其他插件为什么不用改

| 插件面 | 加组行后 | 结论 |
|---|---|---|
| `contents(slot,"mods")` / `pageItems()` | 仍返回**全部真实模组**（虚拟行永不进去） | 不改 |
| `ItemInfo.path` | 仍是真实文件路径 | 不改 |
| `Finding.anchorPath` | 仍是成员 path；宿主映射到组行/详情 | 不改 |
| `state()` / `gates()` | 仍按每个真实模组调用 | 不改 |
| `filter` / `sort` | 宿主先对真实 items 过滤/排序，再分组展示 | 不改 |
| `pickContent` / `open` / `addItem` | 仍操作真实内容 | 不改 |
| `selectedItems()` | 语义不变（模组页本来就是空表） | 不改 |
| `section` / `analyzer` / `action` | 照旧；虚拟行不占扩展点 | 不改 |

**会逼所有插件适配的做法（不要做）**：

- 把虚拟行塞进 `pageItems()` / 新增 `KIND_GROUP`；
- 改 `Finding.anchorPath` 的含义；
- 让 filter/sort 收到组行；
- 要求每个插件实现 `rows()`。

## 4. 边界情况（实现时要钉）

1. **过滤/搜索**：
   - `mShown` 是真实模组过滤结果；
   - 组行可见 = 组名/副标题命中 **或** 任一成员在 `mShown`；
   - 组详情默认显示**全部成员**（可标“其中 N 个匹配当前筛选”）；
   - 若组名命中但成员全被过滤，组行仍可见，详情里成员标灰。
2. **“只看有问题的”**：
   - 任一成员有问题/有 findings ⇒ 组行算有问题；
   - 组行聚合数 = 成员里 `mIssues` 非空的数量。
3. **排序**：
   - v1 组行按组名排；不把成员排序结果硬套到组上；
   - 插件排序仍只对真实模组生效，不影响组行位置（或组行按“最佳成员名次”排，二选一，先定前者）。
4. **重叠**：
   - 一个模组只属于一个组（v1）；插件返回重叠 ⇒ 宿主只隐藏一次，日志点名，组行都可以显示；
   - 更干净：插件自己保证唯一。
5. **缺成员**：
   - `memberIds` 只放存在的 id；缺的只体现在 subtitle；
   - 不隐藏任何不存在的行。
6. **坏包**：
   - `mScan.broken` 也是真实行；组可以包含；`pageItems` 也包含；
   - 组详情照常显示坏包行。
7. **fallback**：
   - 插件缺失/禁用/异常/API 低于 v37 ⇒ `vrows` 空 ⇒ `hidden` 空 ⇒ 全部真实行回来；
   - 不缓存“隐藏集合”，每次按当前 provider 重算。
8. **异步 findings**：
   - `onPluginFindings` 回来后只重画 `mRows`，不重扫、不重新加载插件（除非组行 subtitle 需要更新）；
   - 组行聚合数在 `bindRow` 时算，不另存。
9. **删除/导出**：
   - `mShown` 仍是全部真实模组，删除弹窗/导出行为不变；
   - 若希望“只删看得见的”，另开需求，别顺手改；组详情里的删除走单独确认。
10. **性能**：
    - `rows()` 在宿主重扫时调用，必须轻量；插件缓存 `mdt-groups.json` + `contents` 映射；
    - 宿主缓存 `vrows`，设置变化/组文件 mtime 变化才重载。

## 5. 自检（宿主侧，能离线）

| # | 判据 |
|---|---|
| 1 | 有组时，`pageItems("mods")` 的数量 == `Mods.scan.mods + broken` 的数量（虚拟行不进去） |
| 2 | 成员 `Finding.anchorPath` 仍能在 `mIssues` 里找到；组行聚合数 = 成员 issues 数 |
| 3 | 插件 filter 去掉一个成员 ⇒ 组行仍显示（其他成员在），详情里该成员标灰；全去掉 ⇒ 组行隐藏 |
| 4 | 搜索成员名 ⇒ 组行出现；搜索组名 ⇒ 组行出现；真实行不重复出现 |
| 5 | 插件禁用/异常 ⇒ `hidden` 为空，真实行数量恢复 |
| 6 | 组开关写一次 `settings.bin`，成员 `-enabled` 全变；不碰非成员 |
| 7 | 组详情里成员的 findings/detail 与模组页一致 |
| 8 | 删除/导出仍按 `mShown`（全部真实模组），不因隐藏少东西 |

## 5.1 地图页不是纯复制：三个额外点

> 用户 2026-11-10：「按照这个逻辑改地图页面时也不会冲突吧」

**逻辑一样，不会和 `mapstats` 冲突**：`mapstats` 的 action 走 `pickContent("maps")`（全部地图都在，
不依赖可见行），filter/sort 也只看真实 `Maps.Item`；宿主先过滤/排序，再分组展示，插件零改动。
`mapstats` 的 section 在 **map-detail** 页，不在 maps 列表；合集页/组详情不挂 section，碰不到它。

但地图页有三处不能照抄模组页：

1. **身份**：自带 / 模组地图的 `ItemInfo.path == null`，只有 `container!/entry`。
   `memberIds` 必须用 §2.1.1 的 id；v1 只允许槽内地图（`path != null`）进组。
2. **适配器/下标**：`MapsActivity` 用 `MsavListAdapter` 的三个数组 + `mShown` 下标 + `shownIndexOf`
   刷新缩略图；加组行必须引入 `mRows` 行模型、行→Item 的映射、缩略图跟着组行/成员行走，
   不能像模组页那样直接 `for (mShown) inflate`。**这是 +1~1.5 轮的主要来源。**
3. **组详情**：成员地图点进去仍走现有 `MapDetailActivity`（`mapstats` section 照常工作）；
   组详情本身只列成员 + 导出/删除，不重复画统计。

`mapstats` 的“导出统计…”默认勾选仍来自 `PluginPicks.noteView(mShown)`——**`mShown` 保持全部真实地图**，
隐藏只发生在 `mRows`，所以默认勾选不会因为组行变少。`saves` / `blueprints` 同理，只是蓝图也可能有
`container!/entry` 身份（同样 v1 只让槽内文件进组）。

## 5.2 四个页面的底层机制确实不一样

> 用户 2026-11-10：「我现在怀疑四个页面底层机制都是不一样的吧」

**怀疑是对的。** 共同点只在**插件层**（`PluginData` / `PluginPicks` / `PluginEntries` / `BatchIo`），
**列表层各写各的**：

| 页面 | 数据 | 列表实现 | 点击 / 下标 | 身份 | 组行改动 |
|---|---|---|---|---|---|
| 模组 | `Mods.Info` | `mContainer` LinearLayout + `item_mod` + `bindRow` | 行 View 监听 | `path` | 中 |
| 存档 | `File[]`（`mAll` / `mFiles`） | `SlotIo.fillSaves(...)` 填 `mList` | `mRowClick` + `mFiles` 下标 | `path` | 中 |
| 地图 | `Maps.Item` | `MsavListAdapter`（标题/副标题/缩略图三数组） | `position → mShown` | `path` 或 `container!/entry` | **大** |
| 蓝图 | `Blueprints.Item` | `MsavListAdapter`（同上） | `position → mShown` | `path` 或 `container!/entry` | **大** |

它们各自有：

- 各自的 `X.filterAndSort`（`Mods` / `ListQuery` / `Maps` / `Blueprints`）；
- 各自的缩略图/行填充路径（模组手写 View、存档 `fillSaves`、地图/蓝图数组适配器）；
- 各自的点击下标映射（地图/蓝图 `position → mShown`，存档 `mFiles`，模组 View 持有 `Info`）。

⇒ `rows` 的**插件契约可以统一**（`VirtualRow` + `memberIds` + 宿主按 id 隐藏），
但**宿主不能只改一处**：四个页面要各自接 `mRows`/适配器；`RowsMerge` 这种“隐藏 + 插组行”的
纯逻辑可以抽一份共用，**UI 适配必须一页一页来**。

**成本重估**：

| 页面 | 额外轮 |
|---|---|
| 模组（先做） | 2.5~3.5 |
| 地图（适配器 + 缩略图 + 下标） | +1~1.5 |
| 蓝图（同地图，可共用 helper） | +1~1.5 |
| 存档（`fillSaves` 另一条路） | +1~1.5 |
| 四页合计 | **6~8.5** |

**建议顺序**：先模组（验证 `rows` 契约）→ 地图/蓝图（同一适配器，抽共同 helper）→ 存档。
如果四页都做，先花 0.5~1 轮抽 `RowsMerge`/`GroupRow` 共用逻辑，别把同一段隐藏逻辑抄四遍。

## 5.3 能重构吗？能，但分“小重构 / 大重构”

> 用户 2026-11-10：「也是神了，那这东西能重构吗」

**能。** 而且插件层已经有一半基础：`PluginData` 用 `ItemInfo` 统一了四类内容，
`PluginPicks` 用 `IdOf` 统一了筛选/排序，`BatchIo` 用 `kind` 统一了导入导出。
乱的是**列表层**：四个页面各自持有数据、适配器、缩略图、下标映射。

### 小重构（推荐，够支撑组行）

抽三样，**不动四页的扫描/业务**：

1. `ContentRef`：统一的条目身份
   ```java
   static String idOf(String kind, Object item); // mods=path; maps/blueprints=path 或 container!/entry
   ```
2. `RowsModel<T>`：只做“过滤/排序后的真实 items + 组行”的合并
   ```java
   final class RowsModel<T> {
       List<T> filtered;          // 页面 filter/sort + PluginPicks 之后
       List<VirtualRow> groups;
       List<Row<T>> rows;         // 组行 + 未被隐藏的真实行
       Set<String> hidden;        // union(memberIds)
       boolean groupVisible(VirtualRow g);  // 搜索/只看有问题时的可见性
   }
   ```
3. `GroupRow` View + 聚合 badge 的纯函数；`RowsMerge` 纯逻辑（可进自检）。

四页只做“把 `rows` 喂给自己的适配器”：

| 页面 | 适配改动 |
|---|---|
| 模组 | `mContainer` 循环 `rows`；组行用 `GroupRow`，真实行仍 `bindRow` |
| 地图 / 蓝图 | 扩展 `MsavListAdapter` 接受 `rows`（组行无缩略图），两页共用 |
| 存档 | `SlotIo.fillSaves` 接受 `rows` 或换成同款适配器；最后做 |

**成本**：模型层 1.5~2.5 轮 + 模组 1~1.5 + 地图/蓝图 1.5~2 + 存档 1~1.5 + 回归 1
≈ **5~7 轮（宿主侧，不含插件开发）**（比四页各抄 6~8.5 便宜，且以后加“合集”之外的功能也能复用）。

### 大重构（不推荐现在做）

把四页合成一个 `ContentListActivity` / 一个通用适配器：**6+ 轮**，且要重做
缩略图异步、点击下标、空态、批量选择、插件卡；回归面太大，收益主要是“少四份代码”。
除非以后四页还要加很多共同功能，否则不值得。

### 重构的硬边界

- `PluginData.pageItems()` / `PluginPicks` / `PluginEntries` / `BatchIo` 的**对外语义不变**；
- 每页的 `filterAndSort` 保留，别把四套筛选规则硬合并；
- 异步缩略图的“全量下标 vs 筛选后下标”映射（§83.5 那个坑）要在 `RowsModel` 里只写一次；
- 每页真机点一遍：行点击、搜索、筛选、批量、空态、插件卡。

## 7. 一句话

**虚拟组行只改 `ModsActivity` 的展示层（`mRows`），不动 `mShown`、`pageItems`、`Finding.anchorPath`；
组逻辑由插件通过 `rows()` 提供；其他插件零改动，插件缺失自动回退。**
