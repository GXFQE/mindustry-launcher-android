# 插件能力与互操作：现状、缺口、怎么加（2026-11-10）

> 用户 2026-11-10：「现在感觉插件能干的事情很少，而且插件之间的兼容基本上没有」。
> 这份不是"再做一个插件"，是把**插件平台本身**的边界说清：哪些是刻意不开、哪些可以便宜地开、
> 哪些一开就要换架构（不建议混在合集功能里做）。
> 结论：**插件现在是"扩展点"，不是"服务/替换"；要提升，先加"发现 + 契约"，不要先加"替换宿主"**。
> ★ 2026-11-10 合集最终选 **`rows` 扩展点**（宿主定契约、插件返回 `VirtualRow`），
> 不是 provider/替换；详见 [虚拟组行详细设计](2026-11-10-虚拟组行-详细设计.md)。
> 本文 P0/P1 仍适用；P2（provider 仲裁）暂缓。
>
> **2026-11-13 落地（第 372 轮）**：P0 第 1 条 `plugins()` 已实现（API **v38**，数据走 `ItemInfo`
> 快照而不是本节草稿里的 `PluginInfo` 类 —— 与 `versions()` / `logs()` / `trash()` 同一套；
> 见 `docs/PLUGIN-API.md`「插件与补丁清单」）。同一轮还加了 `patches()` / `patches(versionKey, slot)`：
> 插件能读**已导入的游戏补丁**及其按启动项算的 `enabled` / `applies`。
> `provides` / `requires` / `conflicts`（P1）与 `collections()` 仍未做。

---

## 1. 现在插件到底能做什么

| 面 | 能做的 |
|---|---|
| 读 | `contents(kind/slot)` 四类内容 · `pageItems` / `selectedItems` · `slots` / `versions` / `logs` / `trash` · `open(ItemInfo)` 读字节 · `gameSettings(slot)` · `baseBundleKeys` · `modsSkipped` / `gameRunning` |
| UI | `section` / `content` / `action`（每页都能挂）· `analyzer`（`Finding` / `state` / `gates`）· `filter` / `sort`（四页）· `choose` / `confirm` / `prompt` · `pickContent` / `pickFile` · `progressCard` |
| 写 | `writeGameSettings`（合并写 + 备份 + 读回）· `addItem` / `writeItem` / `trashItem`（四类内容）· `export` / `share` |
| 后台 | `runBackground` / `submit`（进程内任务）· 探针（`:game` / `:probe`）· `game-start` / `game-exit` / `boot` / `app-foreground` 事件 |
| 存储 | `dataDir()`（插件自己的）· `slotDir()`（当前槽根）· `usageDir()` |

## 2. 为什么感觉"少"

- **宿主拥有页面与核心数据**，插件只拿**快照**（`ItemInfo`）和**有限写**（四类内容 + settings）。
  这是有意的：插件缺失 / 崩溃 / 版本旧时，宿主页面仍然完整（fallback）。
- **UI 只能"加"，不能"换"**：`section` 塞进共用「插件」卡，`content` 开自己的整页；
  不能把模组页/存档页换成插件页，也不能用宿主的 `CardStack`/`layout`。
- **没有服务层**：插件不能注册 provider、不能给别的插件提供接口、不能替换宿主内部实现。
- **API 是加法演进**：每加一个能力都要宿主测试 + 安全边界 + 旧宿主拒绝策略，所以开得慢。

## 3. 为什么"互操作基本没有"

| 缺什么 | 现状 |
|---|---|
| 插件清单里没有能力声明 | `plugin.json` 只有 entry/name/version/extensions/telemetry；没有 `provides` / `requires` / `conflicts` |
| 插件看不到别的插件 | 没有 `plugins()`；`versions()` 是**游戏版本**，不是插件 |
| 没有共享契约 | 每个插件自己解析自己的数据；`mdt-groups.json` 是第一个"可以共享"的文件，但还没定成契约 |
| 宿主判定面会互相覆盖 | `PluginAnalysis` 的 `verdicts` / `gates` 是 `path → …` 的 `put`，**后跑的覆盖先跑的** |
| 一张卡只能有一个标题 | `sectionHeading` 只在恰好一段 section 时用那段的名字；两段就退回「插件」 |

⇒ 不是插件作者不努力，是**没有"发现 + 契约 + 仲裁"**这三样。

## 4. 建议：先加"发现 + 契约"，不急着"替换"

### P0（便宜，0.3~0.5 轮/项）

1. ✅ `plugins()`：列**已启用**插件的 `id / version / title / builtin / provides`
   —— **2026-11-13 落地（v38）**：实际列**全部**已装插件（含停用 / 待生效 / 已隔离，
   状态在 `extra["state"]`），字段见 `docs/PLUGIN-API.md`；`provides` 仍未做；
2. `collections(slot)`：只读解析 `mdt-groups.json`（宿主校验 schema），四类 kind 统一；
3. `labels()`：中性行标签（可选；v1 可以不做）；
4. `openPage(id)`：从 `section`/`action` 打开**自己的**插件页（现在只能靠 `content` 行绕）。

### P1（0.5~1 轮）

`plugin.json` 加能力声明，宿主检查并显示：

```json
"provides": ["collections"],
"requires": [{ "id": "mods-health", "minVersion": 3 }],
"conflicts": ["old-groups"]
```

- 缺依赖 ⇒ 界面提示、不静默；冲突 ⇒ 二选一；
- `plugins()` 把 `provides` 带出去，插件不用反射；
- 官方三件套先自己用：`mods-health` 提供 `collections`，`mapstats` 声明 `requires`，`usagestats` 不声明。

### P2（1.5~2 轮，真要做才做）

宿主做**一个域**的 provider 仲裁（建议先做 `collections`）：

- 一个插件注册"合集读写"，其他插件只读；
- 宿主负责 schema 校验、原子写、fallback；
- 这是"服务"不是"替换页面"，仍然不碰核心页。

## 5. 不建议做的

- 🔴 **让插件替换核心页/宿主接口**：provider 架构要 5+ 轮，且插件缺失就白屏；插件应有的自由度已经由 `content` 整页给到。
- 🔴 **注入同名类顶掉宿主类**：ART 多 CL / 签名 / 更新都会炸；不是接口。
- 🔴 **插件之间直接反射/调用**：版本一换就断；应走宿主中介或共享文件契约。

### 5.1 为什么“宿主在插件缺失时也要完整工作”？

> 用户 2026-11-10：「为啥？」

**这不是技术定律，是产品/工程选择。** 四条理由：

1. **可用性**：启动器的核心是“启动游戏 / 管槽 / 导入导出”。用户禁用插件、插件更新失败、
   第三方插件被拒（API 太低）都是常态；核心路径不能跟着消失。
2. **生命周期**：插件是**可卸载、可禁用、可回滚**的。若核心页归插件，卸载/回滚就等于把功能删掉；
   宿主连“提示去装回来”的页面都可能没有。
3. **信任**：插件与宿主同进程、无沙箱，能写 `settings.bin` 和槽内文件。核心页（尤其是导入/导出/删除）
   留在宿主，是唯一可审计的信任锚；否则一个第三方插件就能伪装成“官方导入页”。
4. **支持/测试**：宿主自检覆盖核心页；插件页各自实现，宿主无法保证布局、主题、失败兜底。
   用户看到白屏只会说“启动器坏了”。

**它不意味着“插件不能提供页面”**：

- `content` 扩展已经能给插件一个**完整页面**（用户主动点开，不是默认页）；
- 如果要做“用插件页替换核心页”，正确形态是 **用户显式选择 + 宿主 fallback**：
  设置里“模组页使用插件 X”，插件缺失/禁用/更新失败 ⇒ 自动回宿主页；
- 这需要：稳定的页面契约 + 路由 + fallback + 能力声明 + 版本校验 + 空页兜底，是一套 **page provider**，
  不是“插件默认接管”。

**所以**：不是“插件永远不能替换”，而是**默认不允许无兜底替换**；要做就单独立“插件化 v2 / page provider”，
别和合集功能混在一起（那是 5+ 轮的另一场改造）。

### 5.2 “插件改宿主接口”要分清四种

> 用户 2026-11-10：「我知道宿主不能依赖于插件，但我觉得插件改宿主接口没啥问题啊」

**你说得对一半：如果指“插件实现/替换宿主定义的接口”，没问题，而且现在代码里已有先例。**
要分清的是这四种：

| 形态 | 例子 | 判断 |
|---|---|---|
| **实现宿主定义的接口**（provider） | 宿主定 `CollectionService`，插件实现；宿主查表、没有就用默认实现 | ✅ **推荐**；宿主不依赖插件，fallback 天然成立 |
| **用户可选地替换页面** | 设置里“模组页用插件 X”；插件缺失自动回宿主页 | ⚠️ 可做；需要 page provider / 路由 / fallback |
| **改接口定义/签名** | 插件给宿主接口加方法、改参数 | ❌ 契约归宿主；其它插件和宿主一起崩，版本灾难 |
| **运行时猴补丁/覆盖宿主方法** | 反射改字段、注入同名类、hook 宿主方法 | 🔴 不是接口；更新即断、安全不可审计 |

**为什么“实现接口”没问题**：

- 宿主定义接口 + **默认实现**；插件注册 provider 只是“可选的更好实现”；
- 宿主编译期不依赖插件；运行时查不到/版本不匹配/崩了 ⇒ 用默认实现；
- 这和现在 `ModsActivity.stOf` 一样：插件给 `state` 就用，没给就回落 `Mods.stateOf`；
  `PluginAnalysis`、`PluginEntries` 也都是“有则用、无则跳过”。

**如果想让插件改“行为”而不是只加 UI**，正确做法是宿主定义**钩子**，不是猴补丁：

```java
// 宿主定义，插件可选实现
interface ModHooks {
    default boolean beforeToggle(String internalName, boolean on) { return true; } // false = 否决
    default void afterToggle(String internalName, boolean on) { }
}
```

- 钩子有明确签名、调用点、失败语义；宿主可以超时/吞异常/回退；
- 猴补丁没有这些，宿主更新一次就断，且无法审计。

**结论**：**“插件实现宿主接口”完全可以；“插件改宿主接口的定义/实现”不行。**
前者是 provider/hook，后者是猴补丁；差别不在“能不能”，在“有没有契约和 fallback”。

## 6. 和合集功能的关系

- 合集先落 `mdt-groups.json`（`schema` + `kind` + `members`），**这就是第一个共享契约**；
- 官方三件套按需接：`mods-health` 合并/提供，`mapstats` 读 `maps` 组，`usagestats` 不动；
- 第三方插件以后通过 `collections(slot)` 读，不各自解析文件；
- 先不要为合集去改 provider 架构——P0 的 `collections()` 就够。

## 7. 参考 Mindustry Java 模组：哪些能借，哪些不能

> 用户 2026-11-10：「你参考下游戏的 java 模组的能力」

| 能力 | Mindustry Java 模组 | 启动器插件 | 差距 |
|---|---|---|---|
| 生命周期 | `init` / `loadContent` / `postInit` + 各阶段事件 | `createView` / `run` / `unload` + 少量事件 | 缺“加载/启用/停用/卸载”与 app / slot 生命周期 |
| 事件 | `Events` 总线（加载、建造、聊天、结算…） | `boot` / `game-start` / `game-exit` / `app-foreground` + 探针 | 缺 slot 切换、导入/导出、设置变化、插件启停、页面打开 |
| 注册 | 内容 / 贴图 / 音效 / bundle / UI / 设置 | `plugin.json` 静态声明扩展 | 没有运行时注册 / 能力注册 |
| 全局表 | `Vars.content`（内容表）、`Mods.getMod` | 无 | 没有“插件列表”和“共享数据表” |
| 依赖 | `dependencies` / `softDependencies` | 无 | 没有 `provides` / `requires` / `conflicts` |
| 设置 | 模组可加设置项，游戏 UI 渲染 | 没有声明式设置，只能自绘页 | 缺“插件设置由宿主渲染” |
| 跨模组 | 通过游戏的内容表 / 事件互访；**类仍受 classloader 限制** | 无 | 连内容表都没有 |
| 失败隔离 | 崩了可能带走游戏 | 宿主 catch，页面还在 | 启动器更好，别丢 |

**能借的四样**：

1. **生命周期 + 事件**：`onLoad` / `onEnable` / `onDisable` / `onUnload`；事件至少补
   `slot-change` / `import-done` / `export-done` / `settings-changed` / `plugin-enabled`；
2. **发现 + 能力声明**：`plugins()` + `provides` / `requires` / `conflicts`；
3. **只读全局表**：`collections(slot)`（合集就是启动器版的 `Vars.content`，但只读、宿主校验）；
4. **声明式设置**：插件给 schema，宿主画设置项（语言/主题/开关都走宿主）。

**不能借的三样**：

- 🔴 **任意类互访**：Java 模组能互访是因为游戏定义了内容类；启动器插件各自的 `ClassLoader` 不同，
  插件 A 自定义的接口，插件 B **cast 不过去**。要互操作，接口必须定义在**宿主 `api`** 里
  （例如 `CollectionService` / `Group` 数据类），由宿主中介；不能指望插件之间直接 `new` 对方的类。
- 🔴 **网络 / 任意系统权限**：游戏模组能发包；启动器插件不该有（信任/安全）。
- 🔴 **替换核心页 / 宿主接口**：游戏模组是“内容”，启动器插件是“扩展”；宿主必须能在插件缺失时完整工作。

**所以“像 Java 模组一样强”不是把游戏 API 搬过来，而是补三件事**：
**生命周期/事件、能力发现、宿主定义的共享接口**。合集就是第一个共享接口的试金石。

## 8. 一句话

**插件现在少，不是因为它不该多，而是因为宿主只开了"扩展点"；先加 `plugins()` / `collections()` / 能力声明，
把"发现 + 契约"补齐；"替换宿主接口"是另一场架构改造，别和合集混在一起。**
