## M3 设计要点

**「槽」= 一套互相隔离的游戏数据。** 数据根由包名决定、多版本共享会互相破坏（M2 已实证），
所以隔离的唯一手段是启动前目录改名交换；M3 把它做成用户可管理的对象。

- **当前槽的数据就在数据根本体里**，其余槽是平级的 `slot-<名>`。
  ⇒ `Data.dirOf(ctx, slot)` 一条函数把两种情形统一成"一个普通目录"，
  于是**给非当前槽做备份/恢复根本不需要交换目录**（比探针阶段的"换回来再操作"安全得多）。
- **槽记录的唯一来源是 `app_hub/mdt-slot.txt`**，不是 config.json：
  交换由 `:game` 进程执行、config 由主进程维护，两个进程同时写会打架。
  而「版本 → 槽」的**分配**存在 config.json（那是主进程的单方意图），
  执行仍在 `:game` 的 `Data.swapTo` —— 两侧职责不重不漏。
- **备份口径 =「槽内容 − 排除名单」**（`Data.SLOT_EXCLUDE` = `config.json` / `import` / `natives` /
  `tmp` / `cache`，外加通用跳过 `.` 开头 / `*.part` / `*.tmp`），**不是白名单**。
  ⚠️ **2026-10-02 改的口径**，**需求**：备份槽不要用白名单（有的模组会乱放配置文件）：
  模组会把用户数据（如 `logic-tool/history/*.json`）放**数据根顶层**，白名单**结构上必然漏**，
  而且漏得**没有症状**。⇒ 判据只能是「凡是我们没法重造的用户数据都要在」。
  ★ 这张表**与「整槽导出」共用同一份实现**（`Data.contentRoots`）—— 两者问的是同一个问题。
- **恢复 = 只覆盖、不删除**（有意）：快照里没有的文件原样留着。
  ⇒ **恢复的顺序不可颠倒：先逐文件校验对象内容，再动手覆盖。**
  任何一项对不上就**不写出去**（该项失败、其余照常），自检里有负例证明"没有半截恢复"。
  真要整槽替换走「整槽导出 + 导入」那条路。
- **`.msav` 文件名保留非 ASCII** —— 游戏存档列表直接显示 `saves/` 下的文件名，
  文件名就是玩家看到的存档名。只剔掉文件系统非法字符（`/ \ : * ? " < > |` 与控制字符）。
- **对当前槽的写操作要求 `:game` 已退出**：游戏持有数据根，边写边覆盖结果不可预期。
  非当前槽不受此限。
- **数据根体检只认正证据**，光名字像不算：config.json 要能解析且含 HUB 键、
  import/ 要有 .apk 且 app_hub/import 同名命中、natives/ 要有 libarc*.so。
  证据不足的进"只报告不清理"一档 —— 宁可留着。
