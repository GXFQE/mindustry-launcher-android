# 15 · 客户端真正开局 / 继续：数据损坏**不产生崩溃报告**（2026-10-08，真机）

> 这是 F23（崩溃分析）最后一类"没被任何实验覆盖过"的输入：**玩家真的开局/继续时，地图或存档坏了**。
> 结论一句话：**这条路上不存在崩溃报告** —— 游戏自己接住了，弹一句人话，日志里留一行 `[E]`。
> ⇒ 归因器（只吃"游戏崩了写下的报告"）**不可能被它误导**，也**不需要**为它加判据。
> ⚠️ 但它不是"测了没崩"就完事：坏的形状、逐字的日志指纹、以及**哪些坏法没测**都在下面，
> 将来真机上真冒出这一族报告时，可以直接照这里的指纹写判据。

## 1. 实验怎么做的（GUI 自动化，命令行可复现）

（`stealth-path.zip` —— 刻意装着，好回答"会不会冤枉模组"）。地图与存档都放**副本**。

## 2. 五种地图坏法 + 游戏的反应（**都只到"自己的错误对话框"为止**）

| 夹具 | 坏法 | 逐字错误（`slot-maplab/last_log.txt`） | 用户看到 |
|---|---|---|---|
| `1cut` | 压缩流截断到 1/4 | `Caused by: java.io.EOFException: Unexpected end of ZLIB input stream`（预览阶段） | 列表里缩略图是 `oh no` |
| `2bitflip` | 压缩流中间改 1 字节 | `Failed to generate preview!: java.io.IOException: Error reading region "preview_map".` → `Caused by: java.lang.ClassCastException: mindustry.content.Blocks$86 cannot be cast to mindustry.world.blocks.environment.Floor`（`MapIO.colorFor`） | 同上 |
| `3badver` | 解压后版本号改 9999 | `[E] Failed to load custom map file '…/3badver.msav'!` + `java.io.IOException: Unknown save version: 9999. Are you trying to load a save from a newer version?`（`MapIO.createMap`） | 列表里**没有**这张图 |
| `4cutinner` | 合法 zlib 流、**内容截断到 60%** | 开局时：`[E] mindustry.io.SaveIO$SaveException: java.io.IOException: Error reading region "map".` ← `World.loadMap` ← `Control.playMap` → `Caused by: NullPointerException: … 'short mindustry.world.Tile.x' on a null object reference in method 'void mindustry.maps.filters.GenerateFilter$GenerateInput.set(mindustry.world.Tile)'` | **「发生错误 · 加载地图时出错。地图文件损坏或无效。」**（对话框里一个「确定」） |

★ 最值得记的一条：`4cutinner` 的失败**就发生在渲染线程上**
（`arc.backend.android.AndroidGraphics.onDrawFrame` ← `arc.util.Timer$1.run`），
**照样被 `UI.loadAnd` 接住**（否则这就是一份崩溃报告）。

## 4. 这条边界对 F23 意味着什么

1. **归因器没有输入** ⇒ 不可能把"地图/存档坏了"冤枉成某个模组（我们最怕的假阳性，在这条路上**不成立**）。
2. 用户拿到的答案来自游戏自己（对话框 + 日志页里的游戏日志那一段）—— 启动器**不需要**再解释一遍。
3. 与语料对得上：`11-安卓设备现成报告.md` 那 **12 份安卓真机报告里，数据损坏类签名 0 处**
   （`ZipException` / `EOFException` / `SaveIO` / `Error reading region` 一个都没有）；
   有这一族的是 **`09b-桌面报告-数据损坏.md`**（桌面客户端才会崩到写报告）。
   ⇒ **别为了让桌面报告好看，给安卓这边加一条没有真实输入的判据**（判据要从真输入里长出来）。
4. 如果将来真机上真冒出这一族报告，照 §2/§3 的指纹写判据即可：链里同时出现
   `mindustry.io.SaveIO` / `SaveVersion` / `SaveFileReader` 与 `Error reading region "…"`，
   或 `zlib`/`ZipException`/`EOFException` 且**没有任何模组针命中**。

## 5. 没做的（诚实清单）

- **没试"会造成 OOM 的坏法"**（例如把地图尺寸字段改成极大）：那类可能绕过 `UI.loadAnd` 的
  try/catch 变成**真崩溃**（也会有真报告）。⇒ 这条路上"一定不产生报告"**没有**被证明，
  只证明了这 7 种坏法不产生。
- 没试启动器**自己**读这些坏文件的路（那是 F10/F21 的 `.msav` 解析器，不是游戏）。
- 没试世界数据里"数值合法但语义荒谬"的坏法（例如把方块 ID 改成另一个合法 ID ⇒ 可能不报错但画面不对）。

## 6. 三个 GUI 自动化的坑（都害过我一次）

1. 🔴 **游戏的地图列表按"内部名"显示，不是文件名**：我最初 5 份夹具的内部名都叫「始发地区」
   ⇒ 界面上根本分不清点的是哪一份。修法 = 改 MSAV 头里的名字，
   **等长替换**（中文名 12 字节 UTF-8 → 12 字节 ASCII，`writeUTF` 的长度前缀才不会被改坏）。
2. 🔴 **列表是内存里缓存的**：改完 `maps/` 不重启游戏，列表不变（我删掉 4 份后列表still 显示 5 份）
   ⇒ 每次改夹具都要 `am force-stop` + 重新拉起游戏。
3. ⚠️ **"我点到了"不能只看 `dumpsys window` 的焦点**（它一直写着那个 Activity）：
   判据 = **截图哈希**（同一屏重复截会得到同一个 hash，说明界面根本没动）
   + **游戏自己写的 `last_log.txt`**（错误/成功都记在那里）。
