# 4.4 ★ 存储模型核实：现在到底是不是 CAS？（2026-10-01，F15 附带 / REF §31.5）

**待确认**：游戏本体和存档备份是否都是 CAS 存储？
**答：都不是 —— Android 版目前一行 CAS 都没有。桌面版才有。**

| 对象 | 桌面版 | Android 版（本工程） |
|---|---|---|
| **游戏本体（版本 APK / 资产）** | ✅ **真 CAS**：`storage.py` 的 `CASStore`，路径 `objects/<sha256 前 2 位>/<后 62 位>`，`store_file` / `store_directory` / `restore_directory` / `garbage_collect` 齐全，配 `_BULK_WRITE_LOCK` 与 `_GC_GRACE_SECONDS = 600.0`；`gui_core.py` 建了两个 store（`versions` / `backups`） | ❌ **没有**。M1 是「官方 APK 原样落盘到版本目录」；`Injector.Plan` 里的 `assetBase` / `assetDeltas` **注释明确写着"留给 M4 的 CAS 装配"** ⇒ 字段在、逻辑**未实现** |
| **存档备份** | 走同一个 `CASStore`（`backups`）⇒ 天然去重 | ✅ **2026-10-01 晚已补上（F16）**。原本是「**白名单原样拷贝 + `manifest.txt` 记 md5**」——md5 只是**校验/完整性**，不是寻址键；同一份文件在两个槽/两次备份里**各存一份**，不去重。现在改成 `sha256` 寻址的对象池（`Cas.java` + `<hub>/cas/`），v1 清单保留只读兼容 + **自动迁移**。见 **REF §33** |

**"已核实"的依据**（可复查）：桌面版里 `CASStore` 的完整实现（含

字段注释；`Backup.java` 的 manifest 写读路径。
（`sha256` vs `md5` 的差别也在这一层：**CAS 用内容哈希当路径 = 寻址**，我们只拿 md5 当**指纹**。）

# 4.5 ★★ CAS 存档实测：桌面端 27 份真实备份的账（2026-10-01 晚，实地核对）

**动机**：桌面端的实际效果显示，CAS 存档反而优势很大。

拿桌面版的对象池 + 27 份真实备份清单实测（只读脚本 `工具/_cas_report.py` / `_cas_by_dir.py` / `_cas_android_projection.py`）。

# 4.5.1 桌面端实测数字

| 池 | 份数 | 逻辑总量 | CAS 实际 | 节省 |
|---|---|---|---|---|
| **存档备份** `Backups/objects` | 27 份 | **5.1 GB** | **328.6 MB** | **93.7%**（15.8x） |
| 游戏版本 `versions/objects` | 26 个 | 2.6 GB | 524.8 MB | 80.0% |

| `cache` | 706.5 MB | 27.2 MB | 96.2% | |
| `maps` | 178.0 MB | 7.0 MB | 96.1% | |
| `previews` | 103.5 MB | 3.9 MB | 96.3% | |
| `settings_backups` | 70.4 MB | 20.1 MB | 71.4% | |
| `settings.bin` | 12.9 MB | 11.5 MB | 11.1% | 这个才是真·每次全变 |

**单份备份的构成**（最后一版，214.5 MB / 1094 文件）：

```
mods              129.7 MB  60.5%   18 文件  ← 就 18 个文件，占六成
saves              40.9 MB  19.1%  313 文件

1. **`mods` 是最大头（60~74%）**，而且它跨备份、**跨槽**都不变 —— 收益和"游戏本体资产复用"

# 4.5.4 真正的价值不在"省空间"

省 93% 只是账面。**行为层面的改变才是重点**：

- **现状（无 CAS）**：`max_backups` 默认 20 ⇒ 一份 156 MB ⇒ **3 GB**。手机上没人敢留 20 份，
  用户会调到 3~5 份 ⇒ **回滚能力被磁盘逼到很弱**。
- **有 CAS**：20 份 = **241 MB**，几乎无感 ⇒ 用户**敢开着 20 份**，容错能力提升 4~6 倍。
- **多槽**：3 个槽 20 份 = 448 MB。没有 CAS 是 9.1 GB —— 这个数字直接就是"功能不可用"。
- **附带收益**：CAS 对象**不可变**，写对象用 `tmp + os.replace` 原子替换 ⇒
  备份过程被打断**不会留半成品备份**（当前 `Backup.java` 的 `copyRecursive` 是直接写目标，
  中断 = 半个快照）。

# 4.5.5 现在的结论

**优先级要提前**：从"M4 之后"提到 **5.5 —— 即排在「模组管理」（第 6 项）之前**。
理由：
1. 收益 13~24x，比游戏本体 CAS（80%）还高；
2. **不依赖任何新原语** —— 桌面端 `CASStore` 已被 27 份备份 + 26 个版本长期验证，
   移植到 Java 是纯搬运（`store_file` / `store_directory` / `restore_directory` /
   `garbage_collect` 四个方法 + 两级分片 + GC 宽限期）；
3. **有兼容性设计可抄**：桌面端 `collect_referenced_objects()` 扫所有清单收集引用，
   我们只要读 `manifest.txt` 里的哈希列即可，结构天然对接；
4. ★ **必须赶在模组管理前面**：`mods` 正是收益最大的一项（占一份备份 74%），
   而模组管理会大量读写它 ⇒ 先有 CAS 就不必二次改造。

⚠️ **三个必须照抄的设计**（都是踩出来的，见 `storage.py` 顶部注释）：
- `_GC_GRACE_SECONDS = 600.0` —— **太新的对象一律不删**（锁只管本进程；两个实例/被强杀只能靠年龄兜住）；
- 批量写（导入/备份）**必须持 `_BULK_WRITE_LOCK`** —— 否则"对象已落盘、清单还没写"的空档里
  GC 会把它们全删掉，而清单随后照样写成功 ⇒ 症状极难查（列表正常、一恢复才报对象丢失）；
- **先落对象、最后写清单**，且清单要**原子写**。

| ③ | 「继续上次」也要带版本号 | `updateContinue()`：`e.label` → **`e.displayName()`** |

**为什么只能在显示层做**：`versionName` 是 APK 清单里的原文（官方 `8-official-159.7` / fork `8-official-2026.09.X37`），
由构建脚本写死；一个启动器要同时吃多渠道（换渠道就是 `9-beta-`）⇒ **在代码里硬编码 `8-official` 会立刻过期**。

**两个坑（都踩过：显示规范化只能有一处实现；`buildTitle()` 的 `indexOf` 同源陷阱）**：

- ★ **显示的规范化只能有一处实现**。`displayVersion()` 是唯一出口，复用它的人（列表行 / 继续上次 /
  详情 / 冲突提示 `title()`）**自动对齐**；只要有一处图省事写 `e.versionName`，同一屏就又会冒出两种叫法。
- 🔴 **`buildTitle()` 的 `indexOf` 同源陷阱**：它靠 `plain.indexOf(versionName)` 定位**染色区间**——
  拿**原始**串去 `indexOf` 一个**已剥前缀**的串 ⇒ 恒 -1 ⇒ **染色静默失效**（不崩、不报错、字也对）。
  ⇒ **取显示串和取染色基准必须同源**（本轮改成 `e.displayVersion()`）。

**正则刻意收紧**（`^\d+-[A-Za-z][A-Za-z0-9]*-`：首段纯数字 + 次段以字母开头）：
`1-2-3`、`2.1.0-rc-3` **永不误剥** —— **宁可漏剥，不许误剥**（漏剥只是不好看，误剥是错数据）。
有损显示必须留追溯路径：详情弹窗多一行 `原始版本名: 8-official-2026.09.X37`。

**验收**：自检 **79/79**（新增 ⑥b 共 12 条断言）；真机三处一致（列表行 `Mindustry  159.7` /
`继续上次 · MindustryX  2026.09.X37` / 详情标题）；竖横屏均不折行、不截断。
布局侧：`continue_text` 由 `singleLine` 改 **`maxLines="2"`** —— **版本号在末尾 ⇒ 单行 + ellipsize 最先切掉的正是版本号**
（与 F7 版本行同一个坑，REF ⑥e 早写着"行内文字别用 singleLine"）。

# 4.6.4 「共用提示只有一个版本不合适」+「自检结论放到开头」（2026-10-02 第三十一轮，F17d / REF §35.13）

**两条反馈**：

> **共用提示只写一个版本不合适（共用得多时可以用「类似 XXX 等多个版本」的写法）**
> **自检截图的判读方式不行 —— 在开头先显示总体情况，出了问题再往下翻**

两件独立的小事，共同点：**信息没错，但"给的位置"错了**。

# 一、冲突提示：说出"一共有几个"

原实现 `Versions.Entry other = l.get(i == 0 ? 1 : 0)` —— **永远只取第一个对手**，
组内 3 个版本共用一槽时**每一行都只报同一个对手** ⇒ 用户以为只有两个在抢。
（原注释自己写着"各报第一个对手，够用"—— 它不够用。）

⇒ 抽成类级纯函数 `Versions.conflictPeerDesc(firstName, total)`：

| 组内数 | 输出 |
|---|---|
| 2 | `⚠ 与「A」共用此槽，存档会互相覆盖` |
| 3 | `⚠ 与「A」等 3 个版本共用此槽，存档会互相覆盖` |

⚠️ `total` 是**含自己**的版本总数（中文"与张三等三人同行" = 共三人）。
⚠️ **书名号由 desc 带、fmt 不带** —— 否则"等 N 个版本"会掉到书名号**外面**。
   这类错**不崩不报错、界面照常显示**，只有人眼能发现 ⇒ 已用断言钉住书名号**数量**。

# 二、自检报告：结论前置 + 弹窗标题恒定显示

```

# 4.7 ★★ 两条「静默出错」防线：备份口径反转 + 拒绝跑不了的包 ✅ 已实现（2026-10-02，F19 / F18）

# 4.7.1 备份口径：白名单 → 「除排除名单外全打」（第三十五轮，F19 / REF §38）

**触发**：备份槽不能用白名单 —— 有的模组会乱放配置文件。

**为什么白名单在结构上必然漏**：判据只能是「**凡是我们没法重造的用户数据都要在**」，
而"模组把配置放哪儿"**事先不可能枚举** —— 第三方作者爱在数据根顶层建什么目录就建什么。
实证：`logic-tool/history/*.json` **33 个 / 418 KB**，全是用户纯手工创作、**丢了不可重建**。
同类还有 `random-mod/`、`mods/config/`、`server_list.json`、`be_builds/`、`screenshots/` …
⇒ 只能**反过来**枚举"哪些确定不是用户数据"。

**排除表**（`Data.SLOT_EXCLUDE`）+ 理由（每项都有依据，不是猜）：

| 项 | 为什么能排 |
|---|---|
| `config.json` / `import` / `natives` | HUB 自己被游戏首启**抄进数据根**的残留（"数据根体检"的对象） |
| `tmp` | 游戏自认的临时目录（`Vars.tmpDirectory`），它导入数据时也会先删掉 |
| `cache` | ★ **源码坐实**：每次启动 `Vars.setup()` 都会先 `deleteDirectory()` ⇒ 打它等于打"下次必然被删的东西" |
| 通用（`Data.contentSkipped`） | `.` 开头 / `*.part` / `*.tmp` —— `*.part` 是**写一半的文件**（本项目导入就是"先落 `.part` 再改名"） |

⚠️ **故意保留、别顺手加进表里的**：`crashes/` 与 `last_log.txt` —— **故障前的唯一证据**，
体积又是 KB 级。

**★ 收口**：备份与**整槽导出**问的是同一个问题 ⇒ **共用一份实现** `Data.contentRoots`。
反过来（导出全、备份少）会得到一个**没有任何症状**的坏状态：
用户拿备份恢复完发现地图/蓝图/模组配置没了，**而备份本身"看起来是成功的"**。

**★ 顺手炸出的两个"靠侥幸工作、毫无症状"的缺陷**：
1. **顶层文件的相对路径算成空串** ⇒ 拼出 `"settings.bin/"`（带尾斜杠），
   而 `new File(root, "x/")` 会**丢掉尾斜杠** ⇒ 恰好能用。
2. **备份那条路没有"跳过写一半文件"的判据**（它原本只写在导出的递归里）⇒ `.part` 会进对象池。

**吸收掉的两条历史分歧**：`Exporter.relOf` 与 `Backup.rel` 两份实现合到 `Util.relOf`；
`EXPORT_EXCLUDE` 与 `BACKUP_WHITELIST` 两张表合成 `SLOT_EXCLUDE`。

# 4.7.2 显式拒绝"跑不了"的包（第三十四轮，F18 / REF §37）

**触发**：需要显式拒绝接受远古版本（防止真往里导入然后静默出错）。

**判据是能力、不是版本号**（已定案）：同为远古，`v104.10`（`number=5`）**真跑不了**
（只有 `libgdx.so`），而 `v105`（6）/`v146`（7）**完全能跑** ⇒ 按 `number ≤ 7` 一刀切
会**误伤一整段**。⇒ `Compat.java` 四项硬判据 + 一道软判据，**导入时 + 启动前**两道拦。
**顺带修掉**一个更坏的：`Injector` 的 `static sLoadedLibs` **跨 launch 不清空**
⇒ 同生命周期第二次启动 native 缺失的包**连错都不报** —— 那才是"静默出错"的最坏形态。
