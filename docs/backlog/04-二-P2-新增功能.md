# 2.1 `.msav` 解析器（查看存档/地图数据）【已核实：纯解析器即可，比原判断简单】

★ **修正原判断**：原稿建议"不要手写解析器、改用反射游戏类"——**偏保守了**。
已写出纯 Java 解析器（零游戏依赖、不需要 dex 注入），实测：

```

★★ **为什么能跨 9 个版本不炸**（这是敢于手写的依据，不是运气）：
`SaveVersion.getMeta(DataInput)` **只定义一次**（`SaveVersion.java:48`），`Save1..Save13` 全部继承它，
内容恒为 `readInt()` 长度 + `readStringMap()`。⇒ **元数据布局是版本无关的**。
（地图体才随版本变，所以解析器**只读元数据区**，内存开销与文件体积无关。）

**路线（两层，不再二选一）**：
- **主力 = 纯解析器**：无游戏、无注入、任何界面直接调；
- **备用 = 反射游戏类**：**仅在需要读地图体（真正的地形/方块数据）时**才用，
  且必须放抛弃式进程（原判断的 NPE 风险说对了，只是适用范围要缩小）。

⚠️ **容器格式是 zlib 不是 gzip**（原稿写错了）：
`SaveIO.getStream()` = `new InflaterInputStream(...)`，写入侧继承 `DeflaterOutputStream`。
实证：从 mindustry.top 下载的 `.msav` 首字节 `78 9c`、`Content-Type: application/zlib`。
⇒ 2.5 的"魔数校验"要用 zlib 魔数（`78 01` / `78 9c` / `78 da`）。

**三个顺带的大收益**（所以它不只是"能看数据"）：
1. **备份列表从时间戳升级成"这是什么存档"**（地图名 / 尺寸 / 游玩时长 / 波次）—— 现在只能看到 `20260930-234012`；
2. **备份校验从 md5 升级成"结构可解析"** —— md5 只能证明"没被改过"，不能证明"游戏读得出来"；
3. **槽健康检查**：开游戏前就告诉用户哪个存档已经坏了，而不是进去点一下才发现。

# ★★ 2.2b HJSON 解析器选型【2026-10-01 实测：不是一种语义，是两种】

完整证据见探针工程的 `28-HJSON语义实测-三实现对照.txt`。结论先行：

**同一个 mod.hjson、同样的字节，在 Mindustry 159.x 和 160.x 上会被解析成不同的值。**
所以「用哪个 HJSON 库」这个问法本身是错的；要问的是「**替哪个版本解析**」。

| | 官方 hjson-java 3.0.0 | arc 159.7（官方 APK 实测） | arc 160.x（MindustryX 160.1 实测） |
|---|---|---|---|
| `name: QX4   // ZZC` | `"QX4   // ZZC"` | `"QX4   // ZZC"` | `"QX4"` |
| `name: QX5   # ZZC` | `"QX5   # ZZC"` | `"QX5   # ZZC"` | `"QX5"` |
| `version: 4.6.0   // ZZC` | `"4.6.0   // ZZC"` | `"4.6.0   // ZZC"` | `"4.6.0"` |
| `{name: QX1}`（单行） | ✗ 抛异常 | ✗ 抛异常 | `"QX1"` |
| `{name: QX2, version: "1"}` | ✗ 抛异常 | ✗ 抛异常 | `"QX2, version: \"1\""` ← 吃掉后面的成员 |
| `"description": "line one⏎line two"` | ✗ 拒绝 | ✓ 接受 | ✓ 接受 |
| `'''⏎'''`（空多行） | ✗ 崩（CVE-2023-39685） | ✗ 崩 | ✗ 崩 |
| `=` 分隔符 / BOM / `\` 续行 | ✗ 拒绝 | ✗ 拒绝 | ✗ 拒绝 |

- **159.7 ≡ 官方 HJSON 规范**（10 条对照逐条相同）；差异只有「引号里的裸控制字符」一处
  —— arc 删掉了 `else if (current<0x20) throw expected("valid string character");`。
- **160.x 是偏离规范的那一侧**：它把 `}` `#` `//` 并进了无引号值的终止集
  （`Arc-160.4/…/Jval.java` 第 545~546 行）。好处是单行对象终于能解析；
  代价是注释不再进值（与 159/规范相反），且**对象里的 `,` 不终止**，会静默吃掉后面的键。
  ⚠️ 更正（拿到 159.7 源码后核对）：`]` **在 159.7 就已属于 `isEol`**，不是 160 新折进去的。
  159.7 的写法是「`}` `#` `/` 放在 `if` 条件里、但**不在 `isEol` 里**」，而 `return` 只由
  `if(isEol)` 把守 ⇒ 那些字符走完关键字/数字检测后**继续 append 进值**，这才是注释进值的机制。
- ⚠️ **`blackdeluxecatschematicparse.zip` 是真实反例**：它的 `mod.hjson` 里 `description`
  跨 3 个物理行，官方 hjson 拒绝、两个游戏版本都接受。用官方库直接当解析器 ⇒
  MDT 会把这个模组判成「无法识别」，而游戏照常加载它。

⇒ **选型结论：不要「官方库一把梭」，也不要「移植某一版 arc 就完事」，要写一个带
`CompatProfile` 的宽容解析器**（`ARC_159` / `ARC_160`，行为按上表；profile 由目标游戏
的 build 号选）。骨架可以用官方 hjson-java（MIT，27 个同名方法里 13 个与 arc 逐字节相同，
其余等价重写，改动面可控），但必须补：① 引号内允许裸控制字符；② 终止规则的 profile 开关；
③ 捕获 `Throwable`（空多行抛的是 `StringIndexOutOfBoundsException`；深嵌套会栈耗尽）。
⚠️ 若用官方库，**用 3.1.0 而不是 3.0.0**（3.0.0 带 CVE-2023-39685 / CVE-2023-34620，
而 MDT 解析的是**从网上下载的、不可信的模组**），并重跑对照表。
★ 多版本启动器的独特价值：两个 profile 解出的值不同时**在 UI 上标出来**
（`scrap  ⚠160.x→scrap / 159.7→"scrap // 改成掉废料"`），别当成麻烦。
★ 「按扩展名选解析器」永远不要做——扩展名在 `Mods.findMeta` 里毫无意义（见上）。
✅ 可直接复用的回归资产：探针工程内的 HJSON 语法电池 **41 条** + **10 条三实现对照**（K 组）。

**关键判断：走 JS，不走 Java。** —— 现在这句是**结论**，不是推断了。

★★ **决定性证据**（真机 `io.mdt.hubprobe` 进程内，探针 mod 见探针工程内的 JSTest 探针）：
```

[I] ... MDTJS-T2 closure ok, 6*7=42

`$Proxy4` 从哪来：脚本里 `run()` 来自 `core/assets/scripts/global.js` 的
`const run = method => new java.lang.Runnable(){run: method}` → 触发 Rhino **JavaAdapter**
→ **运行时生成 Java 字节码** → `AndroidRhinoContext.BaseAndroidClassLoader.defineClass()`
用 `com.android.dx` 翻成 dex → `InMemoryDexClassLoader` 加载回来
（源码 `android/src/mindustry/android/AndroidRhinoContext.java:94~112, 182~205`）。
**这条链断任何一环都打印不出这行** ⇒ JS 能注册事件回调、能访问全部游戏内容。

★ **顺带**：API ≥ O 走 `InMemoryDexClassLoader`（**全程内存、不落盘**），只有 API < O 才写 `<id>.dex`。

**模板的硬规则**（`Mods.java:802~830` `loadScripts()`）：
- 触发条件 = `scripts/` 目录存在，**`mod.json` 里不需要 `hasScripts` 字段**（探针就没写）；
- `scripts/` 下只有 **1 个** `.js` → 用它（不要求叫 `main.js`）；有**多个** → **必须叫 `main.js`**；
  找不到 `main.js` → 日志 `No main.js found for mod`，该模组跳过。
  ⇒ **生成器永远输出 `scripts/main.js`，这是最稳的写法。**
- ★ **脚本报错不致命**：异常被 `loadScripts` 捕获、打成 `[E] [<mod>/<script>]: ...` 后继续加载。
  （这条是**自己踩出来的**：第一版探针写了不存在的 `Vars.version.build`，脚本在第一个 `print` 就中断，
  游戏照常进主菜单 —— 既证明了隔离，也解释了"为什么日志里一条 `MDTJS` 都没有"。）
  ⇒ 因此**探针/模板脚本必须每层独立 `try/catch`**，否则首层失败会吞掉后续所有证据。
- 输出通道：`print()` → `<数据根>/last_log.txt`，行首带 `[<mod>/<script>]` 前缀。

**产品形态不变：不是"IDE"，是"模板 + 填空"**：
```
选模板（新物品 / 新方块 / 新单位）→ 填参数 → 生成 mod.hjson + scripts/main.js
→ 打包成 zip/jar → 放进当前槽的 mods/ → 一键启动验证
```
⚠️ 写文件的位置是**当前槽的 mods/**（在数据根里、会被槽交换带走）⇒ 必须走 `Data.dirOf`，不能硬编码路径。
⚠️ **未实测**：把生成的 mod 打成 zip/jar 后能否照样加载（本轮只验了目录形态；源码里 `.zip`/`.jar` 同分支，风险低）。
⚠️ **未实测**：模板真的注册出新物品/方块（本轮只验机制，没做端到端）。

# 2.7 「另一个窗口」（设想：像微信和微信小程序一样同时存在）—— 裁决

这个比喻对应**两种不同的技术现实**，必须先拆开：

**(a) 微信 + 小程序 = 同一个 App 内的两个窗口**（小程序跑在微信进程里）
⇒ **完全可做**，而且就是套壳的标准形态（MDTHub 官方 App 就是这么个东西）。
做法：在 MDT 里再开一个 `WebActivity`，或做成主界面上的可拖动浮动面板
（`PopupWindow` / Dialog 化 Activity）。

**(b) 游戏 + 网页 = 两个 App 真的同时可见**（用户可能真正想要的那个）
⇒ **这台设备做不到**，实测证据（探针工程的 `30`）：

| 请求 | 落地结果 |
|---|---|
| `--windowingMode 1` FULLSCREEN | `mode=fullscreen`，bounds 整屏 ✅（预期） |
| `--windowingMode 3` SPLIT_SCREEN_PRIMARY | task `mode=3` 但 **bounds 仍是 `Rect(0,0-1224,2700)`** ❌ 降级 |
| `--windowingMode 5` FREEFORM | **完全被忽略**，`mWindowingMode=fullscreen` ❌（无 `android.software.freeform` feature） |
| `--windowingMode 6` MULTI_WINDOW | task `mode=multi-window` 但 **bounds 仍是整屏** ❌ 降级 |

决定性实验：官方 Mindustry 在跑时请求 MDT 进分屏 →
`Task{...io.mdt.launcher mode=3}` 在前，而游戏 task 变成
**`visible=false visibleRequested=false`**（被完全遮住，不是"占一半"）。
截屏确认整屏都是 MDT，游戏不在屏幕上任何位置。

⇒ 结论：**adb 侧无法把 Activity 真的放进分屏**；
`HwMagicWindowService`（厂商多窗服务）存在但**无 dumpsys 查询接口、也无法从 app 侧驱动**；
**Android 没有任何 API 能让应用主动请求分屏**（只能被动 `isInMultiWindowMode()` 感知）。
被测 ROM 的分屏入口是系统手势/侧边栏，属于**系统给的能力**，产品设计**不能依赖它**。
（另：PiP feature **存在**，是唯一"两 App 真同时可见"的原生机制，但固定小窗对网页几乎不可用，
且与游戏的 `IMMERSIVE_STICKY` 冲突 ⇒ **不建议**。）
⚠️ 之前记的 `landScapeFreeformFlag:1` **不可靠**，本次它又出现在 fullscreen 的 config 里。

**⇒ 产品判断：把"另一个窗口"实现为 (a)，不要为 (b) 做设计。**
(a) 已能满足 99% 的真实需求（一边玩一边查论坛/下地图），
且 L2 的复杂度（拖拽/缩放/焦点管理）相比 L1 收益有限 ⇒ **先做 L1，看反馈再决定 L2**。

**(a) 落地形态已定 —— 形式 ④：`WindowManager` 子窗口 + `FLAG_NOT_TOUCH_MODAL`**

| ① 普通 Activity | ✗ 完全遮住 | ✗ | ✗ | 无 |
| ② 半透明 Activity（dim） | ✓ 可见 | ✗ 触摸被自己的全屏窗口吃掉 | ✗ | 无 |

★★ **两个必踩的坑（都实测撞过，抄代码时直接照抄）**：
1. `TYPE_APPLICATION_PANEL` 的 `token` 必须是 **`decorView.getWindowToken()`**，

**(b) 的正确解法不是分屏，是形式 ⑥ 悬浮窗** —— 实测已跑通：

启动官方 Mindustry（满屏）后，MDTHub 网页**完整浮在游戏之上且渲染完成**（截图 13）；
切到 MDT 也一样在（截图 12）；点浮层内「关闭」有效（`FLAG_NOT_FOCUSABLE` 只挡输入法焦点，不挡点击）。

⇒ 产品文案可以直接写「**边打游戏边看攻略**」。但**必须做成用户主动开启的开关（默认关）**：
- 权限门：`SYSTEM_ALERT_WINDOW` **不是 runtime permission**，
  `pm grant` **无效**，也没有运行时弹窗，只能

  `Settings.ACTION_MANAGE_OVERLAY_PERMISSION` 跳系统设置手动开。
- ⚠️ 实现注意：`token = null`（跨 App 悬浮窗**不要** token）、
  `FLAG_NOT_FOCUSABLE`、Activity 销毁时必须 `removeView`（否则窗口泄漏到全系统）。
- ⚠️ **绝不能首次启动就弹授权** —— 那是被差评的经典死法。

- ★ 被压后台**不杀进程**：`AndroidApplication.onPause():218` 只在 `isFinishing()` 时

- ★ 但 `onDestroy():246` 无条件 `System.exit(0)`（"force exit to reset statics"）⇒

  游戏 Activity 一旦被销毁（用户划掉最近任务 / 系统回收），整个 `:game` 进程直接退出。
- ★ 游戏自己**反复抢回全屏**：`onWindowFocusChanged` 每次都重跑 `useImmersiveMode(true)` +

## 登录：MindAuth（**不在论坛 API 里**，在 `auth.mdtbbs.cn`）

论坛那 145 个操作里 `authorize`/`token`/`login` 命中 **0**。登录是**独立的账号系统**，
标准 OIDC 发现可用：`https://auth.mdtbbs.cn/.well-known/openid-configuration`（实测 200）——

```
authorization_endpoint  /api/authorize      token_endpoint  /api/token
userinfo_endpoint       /api/userinfo       revocation_endpoint  /api/revoke
introspection_endpoint  /api/introspect     ← 服务端专用，Public Client 不能调
code_challenge_methods  ["S256"]            grant_types  ["authorization_code","refresh_token"]
token_endpoint_auth_methods  ["client_secret_post","none"]   ← none ⇒ 无需 secret
```

四步：① `auth.mdtbbs.cn/developer` 网页申请（**提交后要管理员审核**）→ `client_id`；
② **系统浏览器**打开 `/api/authorize?…&code_challenge_method=S256`；③ `POST /api/token`（**只吃 JSON**）
换 access/refresh；④ 刷新 `grant_type=refresh_token`（可选 `Idempotency-Key`）/ 撤销 `/api/revoke`。
账号注册与手机验证**只能在网页**完成，第三方不得接管。

**Android 的三条硬约束**：Redirect URI 必须是应用自己的 scheme（如 `mdtlauncher://oauth/callback`，
**要与 `AndroidManifest.xml` 里的 intent-filter 逐字节一致**）· 必须用系统浏览器 · 🔴 **没有设备码流程**
（`device_auth: false`，`grant_types` 里没有 `device_code`）⇒ 只能靠 scheme 跳回，
**必须有"授权没完成，再试一次"的界面**，不能把用户卡在一个没反应的按钮上。

**实测的错误契约（★ 与文档不完全一致）**：

| 探测 | 实测 |
|---|---|
| `/api/authorize` 缺参数 / 假 client_id | `invalid_request` / `invalid_client`（✅ 与文档一致） |
| `/api/userinfo` 无 token | `401 invalid_token` |
| `POST /api/token` **表单编码** | 🔴 `400 unsupported_grant_type`（**它没解析表单体**）⇒ 只吃 JSON，写成表单会得到误导性错误码 |
| `POST /api/token` JSON 字段齐全但 client 未注册 | 🔴 **`500 {"success":false,"message":"服务器错误"}`** ⇒ 真机拿到 500 先查"client 未批准 / redirect 未登记" |
| 论坛 `/v1/me` 假 Bearer | `401 {"error":{"code":"HTTP_ERROR",…}}`（是通用码，别按细码精确分支） |

★★ **最关键的坑**：**一旦请求带上 Bearer，连"匿名也能看"的接口也会改按 scope 校验**
（OpenAPI 标 `x-oauth-scopes-if-bearer`）⇒ 只申请"浏览论坛"的话，**登录状态下拉资源列表会 403
`INSUFFICIENT_SCOPE`**。所以 `resource.read` + `resource.download` 要一起申请。
