## 7.2 【不做】设备内开服（原 2.x 构想，2026-10-21 实测否定）

**构想**：用已导入的 APK 在 `:server` 进程里跑 headless 服务端，直接读同一个槽的存档 / 模组。

**实测方法**（可复跑）：解出 `classes*.dex`，`grep -a -o "<类描述符>" classes.dex | wc -l`。
有效性对照：`Lmindustry/core/World;` 必须 ≥ 1（否则说明检索本身写错了）。

| 描述符 | 官方 v159.7 | MindustryX 2025.11.X22 |
|---|---|---|
| `Lmindustry/server/`（整个包） | **0** | **0** |
| `Lmindustry/core/ApplicationCore;` | **0** | **0** |
| `Lmindustry/core/NetServer;`（游戏内联机） | 1 | 1 |
| `Lmindustry/android/AndroidLauncher;` | 1 | 1 |
| `Lmindustry/core/World;`（对照） | 1 | 1 |

**结论**：R8 把**整条服务端路径树摇掉了** —— Android 客户端路径不引用 `ServerLauncher`，
于是它和 headless 的 `Application` 实现一起被裁。`NetServer`（游戏内联机）还在。

⇒ **"拿用户导入的 APK 直接开服"不成立**。剩下的两条路都贵得多：

1. **自编一份只含服务端的 dex 当插件加载** —— 能跑，但**版本必须与槽里的游戏版本严格对应**
   （内容 ID / 网络协议不一致 = 连上去就崩），等于每导入一个版本都要配套编一份；
2. **自驱 `NetServer`** —— 要自己实现 headless `Application` 并驱动 `Time`/`Logic` 循环，
   实质是重写 `ServerLauncher`。

两条都是 20+ 轮量级、且与"预发布、别当稳定版"的定位冲突。**建议撤销该提案**，不在 v1 范围内。

**★ 顺带定一条纪律**：凡是"用游戏 APK 里某个类"的构想（不只是开服），**先做这次 dex 检查再谈成本**。
二十行 grep 就能定生死，比做完发现类不存在便宜太多。这也把"APK 原样当插件"的边界说清楚了：
**能用的只是客户端路径上会被引用到的那些类。**

## 7.3 建议新增（每条：便宜在哪 → 缺口在哪 → 验收判据）

> ★ 2026-10-25：原 7.3a「单文件夹的时间线」按用户决定**删除、不做**（编号不重排，避免旧引用错位）。

### 7.3b 跨槽大文件共享（不止模组）

- **便宜在哪【已核实】**：`Mods.java:954` 已有「把一个槽的模组整套复制到另一个槽」的完整实现，入口现成；
  全仓库**没有一处** `createLink` / 硬链接代码。
- **缺口**：同一个 30 MB 的模组在 3 个槽里就是 3 份；同一张地图被导入两个槽、同一份存档被复制，也是两份。
  游戏开关写在各槽 `settings.bin` 里（`mod-<名>-enabled`），**与文件本身无关** ⇒ 文件共享不破坏"每槽独立启停"。
- **★ 2026-10-21 用户口径**：**不止模组** —— 存档 / 地图 / 蓝图也可以共享存储。
- **判据（关键）**：共享**只认内容哈希（sha256），不认文件名 / 路径 / 所属槽**。
  两个槽里同名但内容不同 = 两个不同的 blob，**绝不共享**；反过来，名字不同但字节相同（同一张图改了名） = 同一个 blob。
- **★ 2026-10-21 用户的担心**：**"存档 / 模组 / 地图不一样的情况会不会出问题"** ——
  按哈希共享就不会：字节不同 = 不同 blob，两个槽各拿各的；只有**逐字节相同**才落到同一份。
  真正要防的是反方向：**共享之后一方修改**（见本节"写时复制"那条）。
- **做法**：对象池按 sha256 存 blob（**`Cas` 已有**，F19 起备份就在用）→ 槽里的文件变成"对 blob 的引用"；
  物理落地用硬链接（`Os.link`，同一分区必然成立），失败回落为拷贝（跨分区 / ROM 不支持）；界面标"共享中"与"独占"。
- **⚠️ 前置：写侧必须都是"原子替换"** —— 直接在原文件上 `write()` 会顺着链接改到别的槽。
  本仓库多数写出走"临时文件 + rename"（rename 换 inode，安全），但**必须逐个写入口核对一遍**；
  不满足的入口只能先断开链接再写（写时复制）。
- **⚠️ 待侦察**：① 游戏扫 `mods/` 会不会因硬链接出现**同一 inode 两条路径**而报"重复副本"（现有的模组体检插件里有这一项）；
  ② `saves/` 里游戏自己的改名 / 覆盖是否也走 rename。
- **验收判据**：① 3 槽共享同一模组，`stat` 显示同一 inode；② 三个槽的启停互不影响；
  ③ 删掉 A 槽该模组后 B/C 仍能加载；④ 模组体检不因共享多报一条；
  ⑤ A 槽改一份共享存档后 B 槽内容**不变**（写时复制那一刀真的断开了）。
- **计划锚点**：`Cas.linkInto(槽, rel, blob)` / `SharedBlobs`
- **成本量级**：3~4 轮（比原估多 1 轮：写入口审计）。**顺手给 4.4b（游戏本体走 CAS）趟路**。

### 7.3c 槽间设置 / 键位搬迁

- **便宜在哪【已核实】**：`SettingsBin` 已有 `read:219` / `encode:307` / `writeAtomic:359` / `sameValues:390` / `diffBytes:408`，
  `settings.bin` 的字节级往返早验过（2.2d）。
- **缺口**：没有跨槽合并。用户开 3 个槽就要配 3 遍键位 / 音量 / 画面。
- **做法**：两槽对同一份 `settings.bin` 做键集合交集 → 只搬"与进度无关"的那批（键位 / 画面 / 音量 / 语言），
  进度相关项（当前版本、上次地图等）**一律不动**；搬前先 `writeAtomic` 备份。
- **⚠️ 待侦察**：白名单得从真实 `settings.bin` 的键名里挑（不是猜），且 `sameValues` 只能证明"相等"，
  不能证明"语义与进度无关" —— 这一条要在文档里写清楚，别把它当判据。
- **验收判据**：① 搬迁后 A 槽进度相关键逐字节不变；② 白名单内键全部到位；③ 反向搬迁结果对称。
- **计划锚点**：`SettingsBin.copyKeys(from, to, keys)`
- **成本量级**：1 轮。

### 7.3d 游玩时长汇总 —— ⛔ **已被 B1 取代（2026-10-22/23 定案，2026-10-26 归档）**

> **本节的旧方案作废**：原来写的是"宿主累加本槽 `saves/*.msav` 的 `playtime`"（锚点 `MsavMeta.totalPlaytime`）。
> 10-22/23 讨论后**明确不采用**（见 `docs/plans/plugin-probes.md` §「游戏时长统计」）：
> `playtime` 是每份存档的累计值，**回档 ⇒ 退回旧值、删档 ⇒ 掉一截、复制/另存 ⇒ 翻倍**，
> 且只在上次保存时更新（上滑清掉丢最后一段）⇒ 求和没有稳定语义。
>
> **现行方案（2026-10-26）**：**已做成官方插件 `plugins/usagestats`** —— 宿主只给机制
> （v29 `Probe.onForeground(boolean)`，v30 `ProbeEnv.version()` / `dataDir()`）；探针自己累计前台毫秒、
> 写**按「槽 + 版本」的账本**（插件自己的 `data/`）；展示在**槽页**（本槽合计 + 按版本分列）与
> **主界面摘要卡**（总时长，插件自述 `playtimeTotal` 声明一个整数）。宿主不写流水、不解析账本。
> `totalPlaytime` 这个锚点**不采用**。


### 7.3e 崩溃后「停用 + 回滚」—— **【不做】回滚部分**

- **2026-10-21 用户否决**：「不建议去回滚（有些时候上次启动没满自动备份时间会丢失存档的）」。
- **机制**：自动备份是**按间隔**触发的（默认 20 分钟）；上次启动没跑满间隔 ⇒ 崩溃前根本**没有**新备份，
  "回到崩溃前"只能回到更早的一份 = **把这段时间的存档覆盖掉**，比崩溃本身更伤。
- **保留的小动作（可选，1 轮）**：崩溃页只给「**停用该模组**」（`applyBool(mod-<名>-enabled=false)` + 先备份），
  **不碰存档**；文案明说"只停用模组，不动存档"。
- **计划锚点**：`CrashFix.disableOnly(...)`

### 7.3f 模组 × 已装版本 兼容矩阵 ✅ 已做（2026-10-25 第 249 轮）

- **便宜在哪【已核实】**：`Hjson` 已在解析模组 `mod.hjson` 的 `minGameVersion`（版本冲突判据 F4 已在用）。
- **缺口**：模组页只回答"这个槽会不会加载"，不回答"换成 160.4 还行不行"——多版本启动器的用户一定会问。
- **★ 2026-10-21 用户问**：「这东西不知道好不好搞（要静态分析代码吗）」—— **不需要静态分析**。
  只读两样：模组 `mod.hjson` 的 `minGameVersion` 声明 + 每个已装版本的 build 号，用 F4 已有的版本比较函数比一下即可。
  真正的不确定性在**声明本身可能写错**，所以每格只能写"按声明：可加载 / 版本过低 / 认不出"。
- **做法**：对每个模组、对每个已装版本给一行结论，只读、不改任何文件。
- **验收判据**：① 与现有的单槽"加载原因"判据同源（同一函数，别写两处）；② 认不出的包进"不确定"桶。
- **计划锚点**：`Mods.compatMatrix(mods, versions)`
- **成本量级**：1~2 轮。

## 7.6 把"漂移"变成断言（三条，都不碰产品逻辑）

文档会漂是因为**完成判据只能靠人记**。这三条都是自检里能钉死的：

1. **锚点失效扫描**：本片每个 `锚点:` 都写成 `文件:符号`；断言"符号能在该文件里搜到"。
   代码改名 ⇒ 自动报"本片过期"，而不是等人发现。
2. **计划锚点冲突**：本片每个 `计划锚点:` 的符号若**已经存在** ⇒ 报"疑似已完成"。
   这正是 7.1 那条（2.6 深链）本该有的防线。
3. **插件 API 版本一致性**：**已落地**（2026-10-23 第 219 轮）—— `PluginApi.DOC_VERSION` 常量 ==
   `PluginHost.API`，自检有一条元断言钉着；注释里的数字不再参与判断（v20 冻结基线 = 20）。

⚠️ 这三条都只读源码 / 文档，不需要真机，适合放在 `SelfTest` 里当"文档卫生"一组。
