# 1.2 自动备份【✅ 已完成（2026-10-01，F5）】

> ✅ **已实现**：`AutoBackup.java`；策略入口在**存档页槽菜单**第 4 项；配置键 `backup_policy`（**每槽独立**）。
> ★★ **本节原方案（"启动某个版本前…比上次备份新"）已被推翻** —— 与桌面版源码不符。
> 核对桌面版启动器的对应实现：`playtime = (time.time() - start) / 60;
> if auto_backup and playtime >= min_playtime: create_backup()` ⇒ 门槛量的是**上一局运行时长**，
> 触发点在**游戏退出之后**。Android 等价实现 = `startVersion()` 记账 → `onResume()` 结算。
> 详见 `FLOWS.md` F5 + `REFERENCE` §25。

桌面版的门槛是「最小备份时间(分钟)」+「最大备份数量」；Android 侧同名同义（默认 20 / 20）。

- 复用 M3 的 `Backup.create` / `Backup.list` / `Backup.delete`，**零新原语**。✅ 已兑现。
- 当前槽被 `:game` 占用时不能备份 ⇒ 结算发生在**游戏退出后**，天然安全。
- 快照是**拷贝**、大槽会耗时 ⇒ 已挪到**后台线程**，且**不在启动路径上**。
- ★ **每槽独立**：`backup_policy` 是对象、以槽名为 key（Android 的槽按版本分配，不是桌面版的"当前分类"）。

# 1.4 运行日志页【已核实机制，可行性高】

**数据源（两侧，互补不重叠）**：

| 来源 | 内容 | 实测 |
|---|---|---|
| `<数据根>/last_log.txt` | **游戏侧**日志（`[I]/[W]/[E]` 前缀，纯文本无颜色码） | ✅ 存在，3071 B |
| `<数据根>/crashes/crash_<毫秒时间戳>.txt` | **游戏侧崩溃报告**（含 `Android API level` / 堆栈 / mod 归因） | ⚠️ 目录尚未出现（至今没崩过）⇒ 源码+dex 确证，**未实测** |
| 我们自己的 `report-launch.txt` 等 | **启动器侧**：六步管线耗时、槽交换、体检结果 | ✅ 已有 |

★ **关键边界**：`last_log.txt` 是 `ClientLauncher.setup()` 里才装的（GL 线程），
**我们的六步管线在它之前**，游戏日志里**看不到**。
所以我们那份和游戏那份**必须并排显示**，只读一个都会缺一半。详见 REFERENCE §14.3。

**已确证的三条语义**（源码级，不是猜）：
1. `writer(false)` ⇒ **截断覆盖**，只留最近一次会话（与桌面版一致，**没有历史轮次**）；
2. 每写一行都 `flush()` ⇒ ★ **硬崩溃 / force-stop / 被 OOM 杀，日志照样在盘上** ⇒ 崩溃诊断可用；
3. 写入的是游戏自己的 `Log.logger` handler ⇒ 我们的 `android.util.Log` **不在里面**。

**可做且低成本的增强**（REFERENCE §14.3）：
- `Log.logger` 是**公开可写静态字段** ⇒ 我们在启动游戏**之前**装自己的 handler，
  就能把游戏日志**加上时间戳**（游戏那份没有）转写进我们的文件，**与我们六步管线的时间线合成一条**。
  游戏随后的 `loadFileLogger()` 会包住我们的 handler，两边都成立。
- 崩溃文件名是**毫秒时间戳** ⇒ 可与我们的墙钟直接对齐，判断"哪次启动崩的"。
- 记住"上次启动"，进主界面时若 `:game` 已死且日志尾部是 `[E]` ⇒ 提示"上次启动可能崩了"。

- ⚠️ **部分 ROM 会滤掉应用自己的 logcat**（探针阶段已记录）⇒ 日志页只能靠**文件**，不能靠 `logcat`。
- ⚠️ **`crashes/` 要能"清空/导出"**：它是用户数据，删之前要确认；但也不能无限堆积。
  清空**已在 F7 实现**（按 `log_max_files` 保留最新、删最旧 + 确认框）；**导出已由 F20 完成**（页首一键导出全部）。
- ⚠️ 补一条**待验证**：`Log` 无时间戳 ⇒ 想显示"哪一步慢"只能靠我们自己的记录，别指望解析游戏日志。

# 1.5.1 深浅色不再只跟随系统 ✅ 已实现（2026-10-01，F15 / REF §31）

**需求**：深浅色要能在设置里手选，不必非得跟随系统。

- **背景**：F1 起主题就只依赖 `values-night/` 资源限定符 ⇒ 换不换深色**由系统 `uiMode` 决定**，
  用户在启动器里**没有选择权**。而"启动器想浅色、系统是深色"是很自然的需求（游戏满屏时尤其）。
- **实测裁定**：framework 只有两条路 —— ① `UiModeManager.setApplicationNightMode()`（API 31+，
  但改的是**系统层面 per-app 夜间模式**、会写系统设置）；② **自己包 `Configuration` 的 `uiMode` 位**。
  **选 ②**（API 17+ 通用、零权限、只影响本 Activity，且 AndroidX 内部也是这么干的）。
- **做法**：新增 `ThemeMode`（三态 + `wrap(Context,int)`）+ `BaseActivity`（在 `attachBaseContext`
  里换 base context，并在 `onResume` 比对"建实例时的模式快照"决定 `recreate()`）。
- ★ **代价真的很低**：`values/` 与 `values-night/` **不用动**（限定符匹配的是当前 Configuration 的
  night 位）⇒ **不需要第二套布局/颜色**，只加了一个设置行。
- ⚠️ 两个必须记住的坑：`attachBaseContext` 是**唯一**来得及的时机；模式判定**必须记快照**
  （包完 context 后 `getResources().getConfiguration().uiMode` 永远等于期望值，不记就判不出"用户改回来了"）。
  细则见 `REFERENCE` §31。

# 1.6 进 / 出口对称：所有"导入"都必须能从槽内发起 ✅ 已实现（2026-10-01，F15 + F15b 收口）

**需求**：导入/导出入口应放在对称的位置。

- **问题**：F6 / F6c 之后，"出"方向（导出存档 `.msav` / 导出整槽 zip）在**槽操作菜单**里，
  但"入"方向（导入 `.msav` / 导入整槽 zip）只在**存档页顶层** ⇒ 用户在槽里想"把这个存档导进来"
  得先退出去，**且两个方向看不见彼此**。
- **判据**：**凡是有"导出"的地方，就近必须有对应的"导入"**。按**介质**成对，不按方向分组：
  槽菜单前四项 = `导入存档(.msav)` / `导出存档` / `导入整槽(zip)` / `导出整槽(zip)`。
- **实现**：把原先"先选槽再选文件"的两个流程各拆成两半（`pickMsavForSlot` / `pickMsavFile`），
  **存档页顶层入口保留**（从顶层发起 ⇒ 先选槽；从槽内发起 ⇒ 跳过选槽、直进 SAF）。
  > ⚠️ **2026-10-01 第二十六轮（F15b）修正**：那条"存档页顶层入口保留"是错的 ——
  > 复查认定**这里 UI 重复**，需要解决。F15 是**只加不减**，造成了同一界面上两组同义入口。
  > ⇒ 存档页那两个入口**已删除**（连带 `pickSlotDialog` + `dialog_pick_slot.xml`），
  > **槽菜单成为唯一导入入口**；存档页顶层只留「新建槽」「数据根体检」两项"无槽语境"的动作。
