## 阶段 4：`.msav` 解析器

### F10 —— `.msav` 解析器（纯 Java，零游戏依赖）

**目标**：读出存档/地图的元数据（名字 / 尺寸 / 版本 / 游玩时长 / 波次 / tag），用于列表展示、备份校验、槽体检。

**已核实**：纯解析器**够用**，不需要反射游戏类。478 个真实样本、**0 失败**、覆盖 v4~v13、平均 432 μs。
（原因：`SaveVersion.getMeta(DataInput)` **只定义一次**、被 `Save1..Save13` 全继承，内容恒为 `readInt()` 长度 + `readStringMap()` ⇒ **元数据布局版本无关**。）

**改动面**：新 `app/src/io/mdt/launcher/MsavMeta.java`（纯 Java + `java.util.zip.InflaterInputStream`）。

**步骤**
1. 打开：`new InflaterInputStream(new FileInputStream(f))` —— ★ **容器是 zlib 不是 gzip**（`SaveIO.getStream()` = `InflaterInputStream`）。
   魔数校验用 zlib 的 `78 01` / `78 9c` / `78 da`（**不要用 gzip 的 `1f 8b`**）。
2. `DataInputStream` 读：`saveVersion(int)` → 按版本分支读 `metaRegionLength(int)` + 元数据区。
   **只读元数据区**，读到就走（**内存开销与文件体积无关**）。
3. `readStringMap()`：`count(int)` + `count×{readUTF key, readUTF value}`。
4. 从 map 里取：`name` / `width` / `height` / `rules` / `wave` / `tick` / `build` / `mods`，以及 `isMap`（有 `width/height` 无 `tick` 之类）。
5. 边界处理：外部文件**不可信** ⇒ 长度字段要上限检查（真实最大 `metaRegionLength` 30487 B，给个宽松上限），
   任何一个字段越界都当"解析失败"而不是抛到崩。

**验收**
- 用探针工程内现成的 478 份样本语料跑一遍：**OK=478 / FAIL=0**（原实验就是这套）。
- 单文件耗时 < 5 ms（最慢样本 4797 μs）。
- 挂 `dev_xxx` 口：`--es dev_msav_meta <path>` 输出元数据文本，便于回归。

**坑**
- ⚠️ 别用 `JSONObject`/`JsonReader` 去解 —— 元数据是**游戏自己的 string map**，不是 JSON。
- ⚠️ 地图体（地形/方块）**随版本变**，本解析器**不读它**。真需要读地图体时，走反射游戏类 + 抛弃式进程（原 NPE 风险只在那条路上成立）。
- ⚠️ 备份校验升级：从"md5 相同"升级为"结构可解析"—— **两者都要保留**，md5 证明"没改过"，解析证明"游戏读得出来"。
- ★ **第 81 轮补：地图的导入与导出都放页面顶部**（定案：导入和导出都放页面顶上）——
  导出**不限本槽**：游戏自带 / 模组自带的图在 APK / 模组包**里面**（`Maps.Item.container + entry`），
  要取出来只能走 `Exporter.writeEntry`（zip 条目流式拷）；本槽的走 `Exporter.writeFile`。
  真机判据 = 导出文件与源 **sha256 逐字节一致**。
- 🔴 **新页面必须补系统 insets**：布局根节点带 `@+id/root`，且 `onCreate` 里
  `Util.applySystemInsets(root)` 之后再 `setContentView`。漏了它（targetSdk ≥ 35 强制 edge-to-edge）
  ⇒ **整页从 y=0 开始画、被状态栏 + 顶栏整块盖住**，而且**全程不报错**：
  症状是"表头 / 第一行凭空消失"，而 `uiautomator dump` 里 view **还在**（bounds 从 `[0,0]` 起）。
  ⚠️ 别改成 `android:fitsSystemWindows="true"`（Util.java 里有定论）。自检 **㉛** 已把 7 个页面布局钉死。
  细则 REF **§57**。

**顺带三个大收益**（做的时候一起接上）
1. 备份列表显示存档名/尺寸/时长，不再是 `20260930-234012`；
2. 备份校验升级；
3. 槽健康检查（F4）。

### F21 —— 地图资源统计（地矿 / 墙矿 / 可采地板 / 加成地板）✅ 已完成（2026-10-03 第 82~83 轮）

**需求**：具体实现地图矿物统计功能（第 82 轮先做了只读可行性，第 83 轮落地）。

**入口**：槽二级页面 → 「地图」→ 点任意一张 ⇒ **独立详情页**（不是弹窗：四段可折叠内容弹窗装不下）。
本槽的图在详情页里还能「删除（挪进中转站）」，删完回列表**自动重新清点**。

**一段一段怎么算**（判据 + 依据）

| 段 | 判据（全部来自游戏字段） | 头号数字 |
|---|---|---|
| 地矿 | 矿层 id 的 `isOre=1` 且 `wallOre=0`；名字照 `OreBlock` 口径 = **掉落物名**；用**地钻**采 | 能采到的格数 |
| 墙矿 | 同上但 `wallOre=1`；名字 = 掉落物名 + `wallore`（「（墙）」）；要用**墙钻** | 总格数（见下） |
| 可采地板 | `isFloor=1` 且 `itemDrop` 非空；副行给「掉落 X」 | 能采到的格数 |
| 加成地板 | `isFloor=1` 且（有属性 / 移速≠1 / 伤害≠0）；名字带属性词（含水/含油/高温…） | 能采到的格数 |

🔴 **四段头号数字的口径必须一致**（2026-10-04 截图暴露：**沙子的数量怎么两个值**）：
同一批格子会**同时**算「可采地板」与「加成地板」（沙地既掉沙又含油），
若一段显示"能采到"、另一段显示"总格数"，用户看到的就是**同名两个数**。
⇒ **每行头号数字一律「能采 X 格」，副行给「共 Y 格」**，摘要给「共 Y 格，其中能采到 X 格」；
唯一例外是「墙矿」段（行名带「（墙）」不会同名，且它本来就长在墙里 ⇒ 用总格数 + 摘要说明
「长在墙里，**需要用墙钻**」）。
★ **两类矿的定名口径**（2026-10-04 定）：**地矿 / 墙矿** ↔ **地钻 / 墙钻**；
别写"普通钻头采不了"。⚠️ 游戏自己的 zh_CN 里没有这几个词（只有机械/气动/激光/爆破/冲击/爆裂钻头…）
—— 这是玩家口径，界面上照这套词写。
★ **出不了预览图就把那块收掉、不留空框**（2026-10-04：没有预览图（比如没版本的情况）
不要放个空框）：`detail_image` 默认 `gone`，拿到位图才显示。

- **"能采到"** = `方块层是 air`（露天）+ `能拆的遮挡`；**`拆不掉的墙`压住的不算**（2026-10-03 定的口径）。
  "能拆" = `synthetic/destructible/breakable/alwaysReplace/unitMoveBreakable` 有任意一个为真。
  旁证：游戏 `Drill.canMine(Tile)` 第一句就是 `if(tile.block().isStatic()) return false`。
- **一格可以同时是可采地板与加成地板**（`sand-floor` 既掉沙又含油）⇒ 两条判据**独立**，不是 `else if`。
- 同名合并：`ore-thorium` 与 `ore-crystal-thorium` 都显示「钍」⇒ **合成一行**，内部名放「技术细节」。

**内容定义表（问"这格到底是什么"，三张表叠起来）**
1. **原版表**：`MapStatsTable`（**自动生成，勿手改**；探针工程内的表生成器 GenTable 从 160.4 的 jar 导出
   447 行 + **153 个方块类的默认值**——模组 JSON 没写的字段取类默认值，不是 false）；
2. **模组**：本槽**已启用**模组的 `content/blocks/**`（有 `type:` ⇒ 新内容 `<前缀>-<文件名>`；
   无 `type:` ⇒ 在旧行上改字段）——**只认 `content/blocks/`**（游戏按 `ContentType.folderName` 扫目录）；
   `type:` 查表是**大小写敏感的精确简单名**（`ClassMap.classes` 的键 = `getSimpleName()`）⇒
   模组写 `powerTurret` / 全限定名的，**游戏自己也认不出**，我们跟着跳过；
3. **地图自带数据补丁**（v12+ 的 patches 区）：`patch` 改字段 / `content` 新增内容（游戏加 `dp-` 前缀）。
   位置判据 = **只可能是第 2 个区（下标 1）** + 解完"刚好读完"。

**译名**（**三个来源 + 两层 bundle**）：
1. ★ **内容文件里写的** `"localizedName": "石英"`（实测 `frost-industry-mod.zip` 整包**没有** `bundles/`，
   中文全写在 `content/items/*.hjson` / `content/blocks/*.hjson` 里；游戏 `ContentParser` 会把它赋给
   `UnlockableContent.localizedName` —— 构造器先按 bundle 取名、JSON 再覆盖）；
2. **bundle**，两层、**层内模组优先**（依据 `Mods` 字节码：对 `Core.bundle` 链**逐层**灌）：
   - 语言层 = 版本 APK 的 `bundle_zh_CN.properties` ⨁ 各模组的 `bundle_zh_CN.properties`（模组后写 ⇒ 覆盖）
   - 基础层 = 版本 APK 的 `bundle.properties` ⨁ 各模组的 `bundle.properties`
   - 查找 = 语言层 → 基础层
   ★ 目录名不只有 `bundles/`：**`*-bundles/` 也要读**（实测 `Neon-vN14.zip` 的
   `fst-bundles/bundle_zh_CN.properties` 里就是原版内容名，由它自己的 Java 代码加载）；
3. 都没有才退回内部名的可读化形式（`Quartz Deposit`）。
★ 矿**没有自己的键** ⇒ 用物品名（`item.<掉落物>.name`），物品名同样按上面顺序找
（为此要读 `content/items/**`，虽然物品不进地图的 content 区）。
★ 模组 JSON 里的内容引用是**短名**（VE 的矿写 `itemDrop: aluminium`），游戏解析时
**先试 `<模组名>-<名字>`、再试原样**（`ContentParser$2` 字节码）⇒ 我们照同一条顺序查。
★ 模组还能用 `name:` **自己指定注册名**（frost-industry：不带前缀）⇒ 两种写法我们都登记成别名。
**属性词游戏里没有译文** ⇒ 只能用 `strings.xml` 里我们自己的七个词。细则 REF **§63 / §64**。

**性能**：统计那一段按 content id **预计算标志 + int[] 计数**，循环里不出现字符串/HashMap
（朴素写法 15.31 ms/张 → 这样写 1.64 ms/张）。真机：60 张图 **平均 2 ms / 最坏 95 ms**（冷启动那张）。
模组表**按槽缓存**（一个包几百个 JSON，每次重解要几秒）。

**dev 口**：`--es dev_mapstats <槽>`（可加 `--es dev_mapstats_file <某个 .msav>`）⇒ 逐图数字 + 耗时，
落 `hub/report-devtool.txt`。

**坑（都不报错那种）**
- 🔴 **子 View 写了 `android:clickable="true"` 会吃掉父 View 的点击**：卡片点不开、毫无报错。
- 🔴 **生成表被 stub 覆盖 = 静默降级**（`TYPES_B64=""` 只是"模组类默认值全取不到"）。
- 给 `GenTable` 的 jar 必须是 **160.4**（官方 160.4 的 `server-release.jar`）——
  `Mindustry-master\desktop\build\libs\Mindustry.jar` 其实是 159.7（446 个方块）。
- 格式 **v2** 的老地图（游戏自带的 `canyon.msav`，2019 年的老文件）现有解码器解不出来 ⇒ 详情页显示「数不出来」（不崩）。
  ⚠️ **2026-10-05 订正**：原文写的"v146 的 `canyon.msav`"是把**格式版本**说成了**游戏版本** ——
  实测那张图在 v146 / v147 / v158 / 159.7 / v160 / master / MindustryX 的包里**是同一份**

## 列表的搜索 / 排序 / 「只看有问题的」（第 122 轮，2026-10-07，细则 REF §83）

地图页顶上加了「**筛选与排序**」行 + 搜索框（模组页同款形状）：

* 搜索匹配 **地图真名 + 文件名/条目名**（游戏自带那批只有条目名，`0.msav` 那种）。
* 排序：**按名称**（默认）/ **有问题的在前** / **按大小（大的在前）**；
  「只看有问题的」= **元数据读不出来**（`Maps.isProblem`，与列表行第二行那句同一个判据）。
* 判据在纯函数 `ListQuery` + `Maps.KEY`，四个列表页共用一份。
* ⚠️ 列表显示的是**筛过的那一份**，而「导出地图…」与"存档 → 地图"的**源图匹配**走的是**全部**
  —— 那是"挑一份"的入口，不该被列表上的搜索框缩窄。
* ⚠️ 空态分两种（一张图都没有 / 筛完一条不剩），只有重建列表那一处同时知道两者
  ⇒ 空态文案在 `rebuildList` 里决定（留在扫描回调里会退化成前一种）。
