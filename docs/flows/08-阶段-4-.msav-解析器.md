## 阶段 4：`.msav` 解析器

### F10 —— `.msav` 解析器（纯 Java，零游戏依赖）

**目标**：读出存档/地图的元数据（名字 / 尺寸 / 版本 / 游玩时长 / 波次 / tag），用于列表展示、备份校验、槽体检。

**已核实**：纯解析器**够用**，不需要反射游戏类。478 个真实样本、**0 失败**、覆盖 v4~v13、平均 432 μs。
（原因：`SaveVersion.getMeta(DataInput)` **只定义一次**、被 `Save1..Save13` 全继承，内容恒为 `readInt()` 长度 + `readStringMap()` ⇒ **元数据布局版本无关**。）

**改动面**：新 `app/src/io/mdt/launcher/MsavMeta.java`（纯 Java + `java.util.zip.InflaterInputStream`）。

**步骤**
1. 打开：`new InflaterInputStream(new FileInputStream(f))` —— ★ **容器是 zlib 不是 gzip**（`SaveIO.getStream()` = `InflaterInputStream`）。
   魔数校验用 zlib 的 `78 01` / `78 9c` / `78 da`（**不要用 gzip 的 `1f 8b`**）。
2. `DataInputStream` 读：`saveVersion(int)` → 按版本分支读 `metaRegionLength(int)` + 元数据区。
   **只读元数据区**，读到就走（**内存开销与文件体积无关**）。
3. `readStringMap()`：`count(int)` + `count×{readUTF key, readUTF value}`。
4. 从 map 里取：`name` / `width` / `height` / `rules` / `wave` / `tick` / `build` / `mods`，以及 `isMap`（有 `width/height` 无 `tick` 之类）。
5. 边界处理：外部文件**不可信** ⇒ 长度字段要上限检查（真实最大 `metaRegionLength` 30487 B，给个宽松上限），
   任何一个字段越界都当"解析失败"而不是抛到崩。

**验收**
- 用探针工程内现成的 478 份样本语料跑一遍：**OK=478 / FAIL=0**（原实验就是这套）。
- 单文件耗时 < 5 ms（最慢样本 4797 μs）。
- 挂 `dev_xxx` 口：`--es dev_msav_meta <path>` 输出元数据文本，便于回归。

**坑**
- ⚠️ 别用 `JSONObject`/`JsonReader` 去解 —— 元数据是**游戏自己的 string map**，不是 JSON。
- ⚠️ 地图体（地形/方块）**随版本变**，本解析器**不读它**。真需要读地图体时，走反射游戏类 + 抛弃式进程（原 NPE 风险只在那条路上成立）。
- ⚠️ 备份校验升级：从"md5 相同"升级为"结构可解析"—— **两者都要保留**，md5 证明"没改过"，解析证明"游戏读得出来"。
- ★ **第 81 轮补：地图的导入与导出都放页面顶部**（定案：导入和导出都放页面顶上）——
  导出**不限本槽**：游戏自带 / 模组自带的图在 APK / 模组包**里面**（`Maps.Item.container + entry`），
  要取出来只能走 `Exporter.writeEntry`（zip 条目流式拷）；本槽的走 `Exporter.writeFile`。
  真机判据 = 导出文件与源 **sha256 逐字节一致**。
- 🔴 **新页面必须补系统 insets**：布局根节点带 `@+id/root`，且 `onCreate` 里
  `Util.applySystemInsets(root)` 之后再 `setContentView`。漏了它（targetSdk ≥ 35 强制 edge-to-edge）
  ⇒ **整页从 y=0 开始画、被状态栏 + 顶栏整块盖住**，而且**全程不报错**：
  症状是"表头 / 第一行凭空消失"，而 `uiautomator dump` 里 view **还在**（bounds 从 `[0,0]` 起）。
  ⚠️ 别改成 `android:fitsSystemWindows="true"`（Util.java 里有定论）。自检 **㉛** 已把 7 个页面布局钉死。
  细则 REF **§57**。

**顺带三个大收益**（做的时候一起接上）
1. 备份列表显示存档名/尺寸/时长，不再是 `20260930-234012`；
2. 备份校验升级；
3. 槽健康检查（F4）。

### ★★ 墙矿的完整口径（2026-10-16：先按用户口述实现，再对齐游戏字节码 + 把"能采"上屏）

**什么算墙矿** —— 逐字照抄游戏 `mindustry.world.Tile#wallDrop()`（v160.4 字节码；墙钻一族
`BeamDrill` 数矿读的就是它）：

```
if(block.solid){
    if(block.itemDrop != null)                      return block.itemDrop;   // ① 方块自己就是墙矿
    else if(overlay.wallOre && !block.synthetic())  return overlay.itemDrop;  // ② 矿层那支墙矿
    else                                            return null;
}
return null;
```

落成**五条**（`①压②`；同一格两层都命中时**按优先级**算，见第 5 条）：

1. **方块自带掉落**（`solid` + `itemDrop` 非空 + 不是矿）= 墙矿，**行名用方块自己的名字**
   （`graphitic-wall` ⇒「石墨墙」）；原版只有它 1 个，模组注册的同类一样算（语料里的
   `exoprosopa-bethinecobalt`）；
2. **矿层 `wallOre` 且方块实心、不是 synthetic** = 墙矿，行名 = 掉落物名 + 「（墙）」；
3. 矿层 `wallOre` 但方块是 air / 建筑 / **玩家墙（synthetic）** ⇒ 按**地矿**算
   —— 用户 2026-10-16：「墙矿放在**非墙体**上实际会被视为**地矿**（但反过来不行）」；
4. 同一格两条都命中（矿层 `ore-wall-x` + 方块层 `graphitic-wall`）⇒ **按底下的墙计**
   —— 游戏里 `block.itemDrop` 优先；
5. ★★ **同一格两层都命中时按优先级算**（2026-10-16 用户：「如果墙矿位置下面的墙本身
   属于类似石墨墙的这种墙，**按底下的墙计**」）：方块层那行照常算一格（能采 / 四周是墙按**它的**邻域判），
   矿层那行**多记一格"按底下的墙算"** —— 墙钻在那格采到的是底下那面墙。
   🔴 **这是优先级问题，不是"被墙压住/遮挡"**（用户 2026-10-16 当场纠正措辞）：
   跟的是游戏 `wallDrop()` 的 `①block.itemDrop 压②矿层 wallOre` ⇒
   界面 / 报告 / 文档里**只说"按底下的墙算"**，不许写「压在…底下 / 被墙盖住 / 遮挡」。
   ⚠️ 与第 4 条那句"一格只算一次"不冲突：**每层各算一次**，两处含义不同
   （方块层 = **那格的资源**；矿层 = **这一格的矿按优先级让给了底下那面墙**）。
   语料 462 张里 **236 格 / 6 图**（`ore-wall-beryllium` / `-graphite` / `-tungsten` 三种，
   例图 `两岸.msav` 46 格、`20802.msav` 84 格）。

**拿不拿得到**（墙矿那一支**不用**露天/可拆/永久那套 —— 那套是说"矿被什么压着"的）：

* **能采** = 上下左右有一个空位（摆得下墙钻）**或**宿主方块**可拆**（拆掉就成了假墙矿 ⇒ 地钻能采）；
* **四周都是墙** = 四邻全是墙 / **出界**，且宿主拆不掉（用户 2026-10-16：「越界肯定算有墙啊」）。
  ⚠️ 这一段的副行措辞**不能**复用「在墙下，拿不到」（墙矿本来就长在墙里，那句自相矛盾）——
  它是另一句话「N 格四周都是墙，挖不到」；
* **按底下的墙算** = 第 5 条那些格 —— 第三句话「M 格底下也是墙矿，按底下的墙算」。
  三种**各说各的**（原因不同，别挤进一个数；`ref/29` 第 45/47 条）：
  前两种是"挖不到"的两种**遮挡**原因，第三种是**优先级**（同一格两层都命中时方块那支优先）。
  行内自洽：`共 Y 格 = 能采 + 四周都是墙 + 按底下的墙算`（自检与审计台都拿这条当元断言）。

### ★★ 优先级链：**方块 &gt; 矿层 &gt; 地板**（2026-10-16 用户定的第三、第四刀）

一格只有**一种**东西能被钻头采到，游戏两段字节码把顺序写死了（都在 `mindustry.world.Tile`）：

```
wallDrop():  if(block.solid && block.itemDrop != null)      return block.itemDrop;    // ① 方块
             else if(overlay.wallOre && !block.synthetic)   return overlay.itemDrop;  // ② 矿层（墙矿）
drop():      if(overlay != air && overlay.itemDrop != null) return overlay.itemDrop;  // ② 矿层
             else                                           return floor.itemDrop;    // ③ 地板
```

⇒ 两条**同族**的"优先级"（都记进 `Row.priority`，界面/报告都说**"按谁算"**，**不**说"被压住"）：

| 冲突 | 谁赢 | 另一个去哪 | 界面那句话 |
|---|---|---|---|
| 方块层自己也是墙矿（石墨墙类） vs 矿层墙矿 | **方块**（按底下的墙算） | 矿层那行多一格 `priority` | 「M 格底下也是墙矿，按底下的墙算」 |
| 可采地板 vs 上面有矿（**地矿 / 真墙矿 / 假墙矿都算**） | **矿层**（按上面的矿算） | 地板那行多一格 `priority`，**不算"能采"** | 「M 格上面有矿，按上面的矿算」 |

* ⚠️ **"总格数照算、能采要剔掉"**：两处都进各自行的 `共 Y 格`，但都不进「能采」
  —— 那格的东西按优先级归了别人；
* 🔴 **只有"这格钻得到"时才谈优先级**（2026-10-16 用户补的）：方块是**拆不掉的墙**（永久遮挡）或
  **认不出**时，钻头根本进不去 ⇒ **可采地板记「在墙下 / 未知」，不记「按上面的矿算」**
  —— 否则会写成"让给了上面的矿"，而上面那份矿自己也拿不到（自相矛盾）。
  语料：**77,851 格**记「在墙下」· **2,418 格**记「未知」（另 445,839 格才是真的"按上面的矿算"）；
* ⚠️ **加成地板不受影响**：属性（含水/含油/高温…）是泵一类读**地板**，与钻头采什么无关；
* 🔴 用户 2026-10-16 纠正过措辞：这是**优先级**问题，**不许**写成「压在…底下 / 被墙盖住 / 遮挡」
  （那套词留给"在墙下 / 四周都是墙"那两种真·遮挡）。
* 语料（575 张可读图，含 App 内置 114 张）：可采地板被矿顶掉 **526,108 格**（地矿 521,310 ·
  真墙矿 4,798 · **假墙矿 0** —— 最后这类语料里恰好没有，靠自检 ⑥c 的 3×3 夹具钉住）；
  墙矿那支 236 格。★ 审计台另有一条 `C19x` 专门数"**本来会被算成能采**的那部分" = **445,839 格** —— 就是这条口径挡下来的数。

### ★★ 「可建造（一般建筑）」的格数（2026-10-17 第 153 轮，用户点单）

用户原话：「**再加一个可建造建筑的格数**（这里建筑按照一般建筑计算，即不能放在墙体 / 部分液体上，
地图原有的建筑可拆掉）」。⇒ 详情页在四段资源之后多一张可折叠卡片「可建造」。

**判据照抄游戏** `mindustry.world.Build#validPlaceIgnoreUnits`（160.4 / 160.7 字节码逐句核过）——
对 **1×1、floating=false、requiresWater=false、placeableLiquid=false** 的一般建筑，逐格两条：

```
地板：  !tile.floor().isDeep()          // 深液体（单位会沉）上放不了 —— **浅水能放**（水泵就摆水里）
        tile.floor().placeableOn        // 原版只有 space / empty 两个地板是 false
方块层：air || block.synthetic()        // = 游戏的 hasBuilding()（update || destructible）⇒ 这是座建筑、能拆
             || block.alwaysReplace      // 石头 / 灌木一类：游戏允许直接压上去
```

* 用户那句「**地图原有的建筑可拆掉**」落地成 **`synthetic`**（＝游戏 `hasBuilding()`，字节码里同一个表达式）；
  天然墙 / 树 / 暗金属四个标志全 0 ⇒ **永远建不了**；
* ⚠️ **只有 `drownTime > 0` 的深液体才挡**（原版 6 种：`deep-water` / `deep-tainted-water` / `tar` /
  `molten-slag` / `arkycite-floor` / `pooled-cryofluid`）。**别拿 `liquidDrop` 当判据** —— 浅水能建。
  为此表里新加两列 `placeableOn` / `isDeep`（生成器 `GenTable` 一并改，**前 18 列逐字节不变**）；
  模组 JSON 的 `drownTime` / `placeableOn` 也照同名字段读。
* **优先级：方块层 > 地板层**（与矿那两处"按谁算"同族）：墙正好压在深液体上 ⇒ 记墙的账。

**六个桶**（界面按这个顺序列；**加起来 == 总格数**，自检有元断言）：

| 桶 | 界面那行 | 含义 |
|---|---|---|
| `free` | 空地 | 方块层是 air、地板允许放 |
| `cleared` | 建筑或石头（拆掉后能建） | 方块层是建筑（`synthetic`）或能直接压上去的东西（`alwaysReplace`） |
| `walled` | 墙和树（拆不掉） | 其余非 air 方块 |
| `deep` + `floorBlocked` | **放不了的地板** | 两桶**合并成一行**（用户 2026-10-17：「这俩合并下吧」）：`floor.isDeep()`（深液体）+ `placeableOn=false`（太空/空）；副行按种类列 `深液体 2,026 格 · 太空地板 536 格`（地板名来自游戏 bundle；这一桶只统计认得出的地板 ⇒ 名字一定拿得到） |
| `unknown` | 认不出 | 地板或方块层没解析到（模组内容）⇒ 不硬猜 |

⚠️ **数据仍是六桶**（深液体与特殊地板分开存，六桶恒等式 `== 总格数` 不变），只是**界面是五行**。
