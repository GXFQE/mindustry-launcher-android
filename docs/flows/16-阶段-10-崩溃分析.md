## F23.2 判据规则（照这个读代码）

| 层 | 判据 | 输入 | 成本 | 代码 |
|---|---|---|---|---|
| **L1** | 报告首句 `The mod 'X' (y) has caused …` 与 `Likely Cause: X (y vZ)` | 报告头部 | 极低 | `judge` 开头 |
| **L1b** | `RuntimeException: Error loading mod <internalName>`（**整条链**里找） | 任一节消息 | 极低 | `findErrorLoadingMod` |
| **L2a** | 栈帧类名落在某个模组 `meta.main` 的**包前缀**下 | 帧 + 模组表 | 低（读一次模组表） | `judge` 的 L2a 段 |
| **L2b/L3** | 帧类名 / **缺失符号**出现在它的 `classes.dex` 里 | 针 + 每个模组一次流式扫描 | 中（几 MB/模组） | `collectNeedles` + `Mods.scanDex` |
| **L4** | 追 `Caused by:` 链 | 报告正文 | 极低（解析时顺带） | `parse` 的异常链循环 |

**针（needle）与权重** —— 判据的核心是一条朴素的直觉：**越不像游戏本体的东西，越有分辨力**。

| 形态 | 权重 | 例 |
|---|---|---|
| 模组自己命名空间的类 | **3** | `stealthpath.StealthPathMod`、`boom.Boom`、`depmod/Dep` |
| 注入进游戏命名空间、但带 `$` 的类 | **2** | `mindustry.logic.SugarCanvas$SugarStatementElem` |
| 长成员名（≥10 字符） | **3** | `definitelyNotAField` |
| 中等成员名（6~9） | **2** | `boostCommand` |
| 纯游戏/系统命名空间的类、短成员名 | **1** | `mindustry.core.Logic`、`state` |

* **门槛 = 2**：权重 ≥ 2 才**点名**；只有 1 分的命中一律降级成"弱线索"（否则每个模组都会被点名
  —— 谁的 dex 里没有几千个游戏类名？）。自检里有一条元断言专门钉这个：给 Neon 一把只装
  `mindustry/logic/LCanvas`（权重 1）的假 dex ⇒ **必须给不出结论**。
* **多命中 ⇒ 并列 + 说明**：两个以上模组命中的是**同一条依据**时，说清"分不出是谁"
  （把别人打包进自己包里的模组就长这样 —— 实测 Neon 一个包里有 logicsystem/stealthpath 等三个模组的内容）。
* **报告里的模组名对不上当前槽**也照样点名（报告是历史事实），只加一句"（这次启动没加载它）"。

## F23.3 措辞：HotSpot ≠ ART（**只照桌面语料写正则在手机上会瞎**）

2026-10-08 用**设备自带的 `dalvikvm`**（同一个 ART；不碰游戏、不碰用户数据）实测四种链接期错误，
逐字原文在 [`../crash-corpus/13-ART-措辞-安卓运行期.md`](../crash-corpus/13-ART-措辞-安卓运行期.md)：

| 错误 | 桌面 HotSpot | 安卓 ART |
|---|---|---|
| `NoSuchFieldError` | `Class a.b.C does not have member field 'int y'` | `No field y of type I in class La/b/C; or its superclasses (…)` |
| `NoSuchMethodError` | `'void a.b.C.m(java.lang.String)'` | `No static method m()V in class La/b/C; or its super classes (…)` |
| `IllegalAccessError` | `class X tried to access private field Y.m (…)` / `Field 'Y.m' is inaccessible to class 'X'` | `Field 'Y.m' is inaccessible to class 'X' (declaration of 'x.Y' appears in …)` ← **两种运行时同款** |
| `NoClassDefFoundError` | `a/b/C`（裸描述符） | `Failed resolution of: La/b/C;` |

⇒ 抽针代码**两套都认**（`FIELD_MSG`/`METHOD_MSG`/`NOCLASS_MSG` + `ART_FIELD`/`ART_METHOD`/`ART_NOCLASS`/`ACCESS_MSG`），
自检里 ART 形态与 HotSpot 形态**各钉一遍**，并有一条"同一根针在两种措辞里抽出来必须一样"的对照。
⚠️ **`of type I` 里的 `I` 是类型描述符、`Failed resolution` 里的 `Failed` 是动词 —— 都不是类名**，
不许进针袋（自检有元断言）。

## F23.4 成本、线程与缓存

* **两段式**：① 解析 + L1/L1b（微秒级）⇒ 有结论**立刻**显示；② 没有才去扫模组表 + dex，
  期间结论行显示"正在核对模组包…"。⇒ "游戏自己写明了归因"这种最常见的情况**感觉不到等待**。
* **一次扫描传全部针**：n 个模组 = n 次流式读（不是 n×k 次）。实测真机 8 份报告共 69 ms（都是启动器自己的报告，**没走到 dex 扫描**）。
* **缓存**键 = `路径|大小|mtime`（来回点 chip 不重扫）；**代次 + `mShownCrash` 双校验**（换页/换 chip 后回来的结果作废）。
* 🔴 **必须用 `Doc.fullText()`**：页面显示那份只有**尾部 400 行**，而报告头（`Version`/`Mods`/`Likely Cause`）
  在**最前面** —— 语料里最长一份 1044 行，用页面的那份就是"永远认不出"。

## F23.5 界面（四种形态 + 三种兜底）
结论行在**崩溃卡 meta 与 chip 之间**（正文之前），`GONE` = 这一份没结论。文案口径三条：
① 只有 L1/L1b 用确定口气（"是「X」引起的"），L2/L3 一律"很可能与「X」有关"；
② **认不出就说不认识** + 给方向（本体 / 环境 / 已删掉的模组）；③ **依据与结论同一行**。

| 形态 | 文案（中文） |
|---|---|
| L1 | 是「X」引起的 —— 游戏自己在报告里写明了归因（Likely Cause） |
| L1b | 是「X」引起的 —— 报告里写着「Error loading mod x」 |
| L2/L3 | 很可能与「X」有关 —— 异常栈里有它的类 …／它的 classes.dex 里有 … |
| 并列 | 报告指向 N 个模组：…（每个各一行依据）+ 分不出是谁的说明 |
| 原版崩 | 不是模组的问题 —— 报告里写着这次没有加载任何模组（Mods: none (vanilla)）。 |
| 认不出 | 认不出是哪个模组 —— 这份报告里没有指向模组的证据。+ 方向 |
| 启动器自己的报告 | 这是启动器自己的崩溃报告（不是游戏），不做模组归因。 |
| 读不出 | 读不出这份报告（文件是空的）。 |

★ **第二批（2026-10-08）：结论"出院"** —— 只在日志页上看得见还不够：
① **进导出文件**（`LogActivity.appendCrashDoc`）：每份崩溃报告前面加一段「启动器对这份报告的判断：」
   （`log_export_verdict`）+ 结论整串 —— 用户报 bug 时发出来的就是这个文件，收件人不必自己重算。
   ⚠️ 拼装点都在**后台线程**（三处导出入口都是），因为"认不出"时 `judgeFull` 会扫 dex；
   被系统回收后重建那条老路原来在 UI 线程拼文本，现在也挪进写文件那个线程了。
② **进模组页摘要卡**（`mods_verdict` + `ModsActivity.refreshCrashVerdict`）：一行「上次崩溃：…」，
   **只在点名成功时显示**（认不出/原版崩/启动器自己的报告都不占位）；进来时两道校验
   （还停在这个槽 + 页面没销毁）。这一页是"为什么它没生效"的入口，"上次崩了可能是谁"是同一类问题的另一半。
③ 三处（页面 / 导出 / 模组页）**共用一个判据入口** `CrashAnalysis.judgeFull(ctx, report, slot)`。
④ 🔴 **真机抓到一个真 bug**：`judgeFull` 原来在便宜层（L1/L1b）命中后**直接返回**、没查模组表

⑤ **dev 口** `--es dev_mods_page <槽>`（直开某槽模组页，与 `dev_maps_page` / `dev_bp_page` 同族）。

★ **第四批（2026-10-08）：真实大模组**（前面只用过 1 KB 探针包）—— 实验槽里放
**Neon-vB16.5.jar**（22.7 MB 包 / `classes.dex` 4.61 MB）+ **stealth-path.zip**，喂两份**真** Neon 报告

① **"注入型"成立**：模组把类注进 `mindustry.logic.*` ⇒ 报告里只剩 `IllegalAccessError: class
   mindustry.logic.SugarCanvas$SugarStatementElem tried to access …` ⇒ **w2 就能点名**（`L3/w2/…`）；
② **成本**：`Mods.scanDex` 改成**逐字节 + 复用窗口**（原来是每块一次 `new String(…,"ISO-8859-1")`

   同进程再点 ~80~120 ms；模组页那一行是**静默后台**算的，不挡操作。

## F23.5.1 ★★「崩了马上说一声」（2026-10-08 用户点单：有没有办法让他崩溃以后立马弹窗提示啊）

**为什么要有**：这一节之前所有东西都是"事后可查" —— 用户得先想到去翻「运行日志」。
崩了那一刻**主动说一声**，才算把 F23 的结论送到用户眼前（与 F23.4 那批"送出日志页"同一个目标）。

**两条路都要**（缺一条就有漏网）：

| 路 | 何时 | 表现 | 判据 |
|---|---|---|---|
| ① 常驻监视 | 本进程还活着（游戏在前台时它也在） | **Toast**（系统浮层，游戏在前台也看得见）+ 有前台页面就直接弹对话框 | 每 700 ms 看**当前槽** `crashes/`；只报**比启动快照新**的那份 |
| ② 回到界面补一次 | 进程被系统杀过 / 用户自己切回来 | 弹**对话框**（结论 +「看运行日志」/「关闭」） | `launchid.dat` 在 **且** 最新报告 ≠ 已提示过的那份 |

**三条纪律**（都写进 `CrashAlert` 的类注释）：
1. **只报新的**：监视线程启动时先快照"当时最新的一份"（`newestName`），之后只报更新的
   —— 否则每次打开应用都会把历史崩溃报一遍（自检有两条元断言钉这个）；
2. **同一份只提示一次**：`Config.crash_alert_last` = `<槽>|<文件名>`（落盘；跨重启有效）；
3. 提示里的结论**只有一份来源**（`CrashAnalysis.text` / `brief`）—— 不许在弹窗里另写一套话术，
   否则会出现"弹窗说 A、日志页说 B"。

**真机实测**（实验槽 `alertlab` + 造崩探针，**不碰用户槽**）：
- 游戏**第 7 秒**自崩，报告 `crash_1791452303321.txt` 落盘；
- ★ **实际先命中的是路②**：游戏进程死的那一刻启动器就回到前台 ⇒ 报告一出现对话框已经在屏上
  （`catchUp` 比 700 ms 轮询更快）：「游戏崩了 / 是「MDT Dep Probe」引起的 —— 报告里写着
  「Error loading mod depuser」」；
- ★ 路①单独逼出来（把报告 `cp` 成一个更新的名字 ⇒ 只有监视线程能看到）⇒ **Toast 与对话框同屏**：
  「游戏崩了：是「MDT Dep Probe」引起的 —— 报告里写着「Error loading mod…」」。
- ⚠️ **验 Toast 的教训**：第一张"对准崩溃瞬间"的截图里没有 Toast，差点据此判"被系统压掉了"；
  logcat 里有 `Toast#…` 的 surface 创建/销毁 + `NotificationService: Toast already killed.
  pkg=io.mdt.launcher` ⇒ **它真的上屏了**。⇒ 瞬时 UI 不能只看截图时机（要么看 logcat，要么把
  时机对准：造文件后 `sleep 1` 再 `screencap`）。
