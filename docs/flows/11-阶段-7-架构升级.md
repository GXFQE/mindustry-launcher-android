## 阶段 7：架构升级

### F0 —— 用 `mindustry.data.dir` 取代「目录改名交换」★ 已完成（2026-10-02）

> ✅ **已落地**（第三十八轮）。细则见 REF **§40**；本节下方保留原计划，
> **以这里的"实际形态"为准**。
>
> · **分流形态**：不是"替换"而是**按【能力】分流** —— `Compat.probe(apk).needsRename()` 为假
>   （dex 里有 `mindustry.data.dir`，即 `build ≥ 147`）⇒ `:game` 只 `System.setProperty(...)`，
>   **一个文件都不搬**；为真（`build ≤ 146` 整段）⇒ 落回**改名交换**。🔴 **`swapTo` 永远不能删。**
>   判据**复用 F18 那次探测**（一次读 APK 回答两个问题），结果用 `EXTRA_LEGACY_SWAP` 透传给 `:game`。
> · **三个路径角色拆开**（原计划的核心）：`Paths.externalRoot`（① `files/`，F0 后只是空壳）
>   ≠ `Paths.slotParent`（② 槽的父目录）≠ `Paths.slotDir`（③ 槽本体，当前槽**恒定**住这儿）。
>   ⚠️ `hub/` 仍挂在 ②（`slotParent()/hub`），**不能**改用 `gameDataRoot`，否则会被塞进槽里。
> · **一次性迁移**：改造前 `files/` **就是**当前槽 ⇒ 升级后首启在 `LauncherApp.onCreate`
>   （早于一切 Activity）+ `GameSlot` 启动前，调**同一份** `Data.reclaimLegacy` 把它收回 `slot-<名>`。
>   判定抽成纯函数 `Data.legacyClaim`（自检可单独证伪）；**失败一定写标记**（`dirOf` 继续指 `files/`，
>   数据一个字节不动）。⚠️ `files/` 必须**存在且为空**（删了游戏会重新复制一遍）。
> · **远古包**：`legacyLendToFiles` 把槽本体 rename 到 `files/` + 写 `mdt-legacy-owner.txt`；
>   `files/` 里的非内容残留用 `stashShell` **挪**到 `<hub>/files-shell/`（**挪不删**，挪不动就放弃本次隔离）。
> · **验收**：自检 **⑬**（171/0 那批）钉住模型 + 三条元断言；真机**迁移 / 注入 / 双版本并行**均已验；
>   自检总数 191/0（含 F4 的 ⑭）。取证：`report-m3.txt` + `hub/report-launch.txt`。

**目标**（原）：M3 的槽模型从"启动前 rename 交换目录"升级为**真隔离**（切换耗时 3~4 ms → ~0，无中间态，可多版本并行）。

**已实测（2026-10-01）**：`:game` 里 `System.setProperty("mindustry.data.dir", <绝对路径>)`
⇒ 游戏把 `last_log.txt`/`settings.bin`/`mods/`/`previews/`/`server_list.json`/`settings_backups/` **全部**写进指定目录；
原数据根 `files/` 的 `settings.bin`、`last_log.txt` **md5 与实验前逐字节相同**；删开关即回落（双向都验过）。
完整证据 + 源码链 + 风险对照表：**`MDT-Android/spike/spike-datadir/RESULT.md`**（含探针源码）。

**改动面**

| 文件 | 做什么 |
|---|---|
| `Paths.java` | ★ 拆开现在被混用的三个角色：新增 `externalRoot(ctx)`（= 现在的 `getExternalFilesDir(null)`，槽的父目录）、<br>把 `gameDataRoot(ctx)` 改成 **`<externalRoot 的父目录>/slot-<当前槽名>`**；槽名读取下沉到本层（或由 `Data` 覆盖，**二选一，别两边各存一份**） |
| `Data.java` | `swapTo()` 的 rename 段**全删**，只留 `rememberSlot()`；`dirOf()` 里"当前槽 = 数据根本体"的特判可以删（新模型下 `slot-<当前名>` **就是**数据根本体，逻辑反而更简单） |
| `GameSlot.java` | ② 那一步从 `Data.swapTo(...)` 换成 `System.setProperty("mindustry.data.dir", dir.getAbsolutePath())`<br>（**选这里而不是 `LauncherApp`**：槽是那一刻才确定的，改动面最小） |
| `Data.healthScan()` | 扫描根从"数据根"变成"槽目录"，**历史残留会留在旧的 `files/`** ⇒ 体检范围要**加一个"旧 `files/`"** |

**步骤**
1. **先做一次性迁移**（向上兼容，不能丢用户存档）：
   老布局是「`files/` 就是当前槽」+ 若干 `slot-<名>/`；新布局要求当前槽也躺在 `slot-<当前名>/`。
   ⇒ `files/` → `slot-<currentSlot>`，**rename 不复制**（同分区瞬时）。
   ⚠️ 三个陷阱：
   ① `files/` 里混着 `files_moved` / `files_moved_103` 这类**游戏自己的标记**，不能当存档带走；
   ② 但**也不能把 `files/` 删掉** —— 游戏会认为"从没搬过"，重新把内部 `files/` 复制一遍（重新污染）；
   ⇒ 迁移后让 `files/` **存在且为空**（或只留标记文件）。
   ③ 迁移必须**幂等**且**失败可回滚**（rename 失败就原地不动、宁可停在旧布局）。
2. 改 `Paths` / `Data` / `GameSlot`（见上表）。
3. **保留 rename 交换作为兜底**：注入后校验一句"游戏真的写到新目录了吗"——
   现成的判定：启动后看 `slot-<名>/last_log.txt` 的 mtime 是否变新。不新 ⇒ 回落到 rename 交换。
   （理由：依赖的是 `ClientLauncher.setup()` 首行那 4 行；MindustryX 的 `0027-H-misc.patch` 同样 patch 了这里 ⇒ 跨分支稳定，但**第三方魔改包仍有风险**。）
4. 核对边角：
   - `Paths.externalHub()` = `<externalRoot 的父目录>/hub` —— **不受影响**，继续可用。
   - `Backup.java` / `Msav.java` / `SavesActivity` 全部走 `Data.dirOf()` ⇒ 改完自动跟随，**不用逐个改**。
   - `slotNames()` 从 `slotParent()`（= `dataRoot.getParentFile()`）列举 ⇒ **必须确认它等于 `externalRoot()`**。

**验收（必须双版本并行实测）**
- 两个游戏版本分配两个槽，**同时**启动、各自读写 ⇒ 互不影响，且 `files/` 保持空壳。
- 老用户数据迁移：拿一份"老布局"的真实数据（迁移前的设备数据快照）走一遍，
  **存档/设置/模组一个不少**，且**第二次启动不会重复迁移**。
- 迁移中途 kill 进程 ⇒ 重启后数据完好（幂等 + 可回滚）。
- `dev_m3_selftest` 全绿（它是"破坏 → 恢复 → md5 逐一相同"的断言，正好覆盖这次改动）。

**收益对照**

| | 现在（改名交换） | 改后（真隔离） |
|---|---|---|
| 切换耗时 | 3~4 ms（与数据量无关） | ~0（只改一个属性） |
| 多版本并行 | ❌ 同时只能一个槽在线；`files/` 被换走期间 HUB 自己也读不到 | ✅ 天然并行 |
| 数据损坏面 | rename 失败要回滚，中途崩溃可能留半交换 | ✅ 不动文件，没有中间态 |
| 对游戏的侵入 | 无 | 依赖 `setup()` 首行那 4 行 |
