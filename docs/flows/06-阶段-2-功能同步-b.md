### F17 —— 版本命名统一（剥 `8-official-` 前缀）✅ 已完成（2026-10-01，第二十八轮）

**触发**：版本号没必要带 `8-official` 那个前缀，全部统一命名规则，「继续上次」也显示版本号。

三个诉求：① 去掉 `8-official-`；② 同一个版本在界面上只有一种叫法；③「继续上次」也带版本号。

**根因**：`versionName` 是 APK 里的**原文**，改不了，只能在显示层处理：

```
io.anuke.mindustry               versionName = 8-official-159.7
com.github.tinylake.mindustryX   versionName = 8-official-2026.09.X37
```
那截前缀（构建序号 + 渠道）对用户没信息量，还**实际有害**：
① 把真版本号挤到行尾，正好落进 ellipsize 裁剪区（**F7 那个"版本号被折叠了"的 bug，诱因就是它太长**）；
② 「继续上次」只有一行，带着它更容易被截断。

|---|---|
| `Versions.java` | 新增 `BUILD_PREFIX` 正则 + `rawVersion()` / `displayVersion()` / `versionTrimmed()` / **`displayName()`**；`title()` = `displayName() + （导入）` |

| `MainActivity.buildTitle()` | `e.versionName` → **`e.displayVersion()`** ⚠️ 见下 |

#### ★★ 关键设计：显示的规范化**只能有一处实现**

抽出 `Entry.displayName()` 作唯一入口，于是 —— **冲突提示也顺带对齐了**（它复用 `title()`）。
若各处自己拼字符串，就得逐个去改，漏一个就又出现"同一个版本两种叫法"。
★ 这与 F15b 那条"UI 上同一件事只留一个入口"是同构的：**规则也要只留一个出口**。

#### 🔴 最容易踩的坑：`buildTitle()` 的 `indexOf` 必须与 `title()` 同源

`buildTitle()` 用 `plain.indexOf(ver)` 找染色区间。若只改 `Versions` 而忘了同步这里：

```
plain = "Mindustry  159.7"      ← title() 已用剥过的短版本号
ver   = "8-official-159.7"      ← 还拿原始 versionName
indexOf → -1 ⇒ 提前 return plain
```
⇒ **染色静默失效**：不崩、不报错、文字也没错，只是版本号不再是弱化色 —— **最难发现的一类回归**。

#### 正则为什么刻意收紧

```java
private static final Pattern BUILD_PREFIX = Pattern.compile("^\\d+-[A-Za-z][A-Za-z0-9]*-");
```
**第一段纯数字 + 第二段以字母开头**，两段各带一个 `-`。
于是 `1-2-3`（次段是 `2`）、`2.1.0-rc-3`（首段不是纯数字）**永远不会被误剥**。
⇒ **宁可漏剥也不能误剥**：剥错了是"版本号显示错"，比"多一个前缀"严重得多。
⚠️ 也**不许硬编码 `8-official`** —— 否则游戏换渠道 / 换序号（`9-beta-`）就悄悄退回老样子。
⇒ 自检 ⑥b 用 `9-beta-160.1` 专门钉住这一点。

|---|---|

⇒ 历史上那些"怪事"**全是同一个机制**：F2c / F3b / **F6c 连改四轮 146177** /

#### F17b —— 导入的版本号也要一并处理（第二十九轮）✅ 已完成

**触发**：导入的版本号也要一并处理。

**根因**：F17 立的纪律「显示的规范化只能有一处实现」**只做对了一半** ——

| `MainActivity.startImport()` | Toast 的 `fentry.optString("version")` → **`Versions.displayVersionOf(...)`**（**本轮唯一的功能改动**） |
| `SelfTest.java` | ⑥b 扩成三段（构造用例 / 裸串入口 / **真机登记数据回归**），**79 → 88 项** |

```java
        fentry.optString("label"),

```

**排查手段（可复用）**：
```bash

```
⇒ **凡是"原始版本串"字面出现的地方，就是该检查的地方**（F17b 前共 6 处，其中 5 处已规范、

#### ★ 纪律的修正：**不是"只能有一个方法"，是"只能有一段实现"**

F17 的表述容易被读成"只要存在一个 `displayName()` 就够了"，于是把方法做成**实例方法**
就觉得收口完成了 —— 但调用方**拿不到实例**时会绕过它。

⇒ 判据改成：**规则本体必须放在"任何需要它的调用方都够得着"的地方**。
   对显示层规范化而言就是**类级静态方法**，实例方法只是门面。
   ⚠️ 可操作规则：**新写显示版本号的代码，先 grep `displayVersionOf`**；
   搜到就复用，搜不到才是缺入口 —— 而不是"这里没有 Entry，就自己取字段"。

⚠️ **反向纪律**：**生产者不许调用它**。`Importer.readVersion()` 拼出的 `8-official-159.7`
是**真实数据**，`config.json` 也必须存原文（详情弹窗的「原始版本名」靠它）⇒
**数据层保真，显示层才规范**。

组内 ≥3 时**每一行都只报同一个对手** ⇒ 用户以为只有两个版本在抢槽。

**改法**：抽成类级纯函数（沿用 F17b 的"实现放任何调用方都够得着的地方"）：

```java
// Versions.java
public static String conflictPeerDesc(String firstName, int total) {
    return "「" + firstName + "」" + (total > 2 ? "等 " + total + " 个版本" : "");
}
```

| 组内数 | 输出 |
|---|---|
| 2 | `⚠ 与「A」共用此槽，存档会互相覆盖` |
| 3 | `⚠ 与「A」等 3 个版本共用此槽，存档会互相覆盖` |

⚠️ `total` 含**自己**（中文"等三人" = 共三人）。
⚠️ **书名号必须由 desc 带、fmt 不带** —— 否则"等 N 个版本"会掉到书名号**外面**。

##### 二、自检报告：结论前置 + 标题恒定显示

**根因**：结论原本是 `L` 的**最后一行**；报告几百行，AlertDialog 一打开只有开头几屏 ⇒
判读"过没过"要**滚 5 屏、截 5 张图**。

**改法（两层）**

1. **报告重排**（`runM3` 收尾，不删明细）：抬头 → **汇总** → 失败项（若有）→ 原有全部明细。
2. **结论进弹窗标题**（AlertDialog 的标题**不随正文滚动**）：
   ```java
   alert(getString(R.string.selftest_result) + " · " + SelfTest.summaryOf(r), r);
   // 标题：M3 自检结果 · 通过 102 项，失败 0 项
   ```
   ⚠️ `summaryOf()` 只为**显示**；**永不据此判断通过与否**（真判据只有 `stat`）。

⇒ **一张截图即可判读**（取证成本从 5 张图降到 1 张）。
⇒ 同一个毛病在 `runHealthReport` 里也存在，一并把"有多少要处理的"提到第一屏。

##### 三、🔴 顺带修正：中文串接多了空格

```xml
<!-- ❌ 原写法（"给插入值加个分隔更清楚"——中文不需要） -->

```

**不崩不报错**，靠"改完文案习惯性 dump 回读"才发现。已改为 `⚠ 与%1$s共用此槽…`。

##### 四、★★ 新纪律：**先修再写断言 ⇒ 断言必须自证有分辨力**

修完空格再补断言，会掉进一个陷阱：**断言永远通过、无法证伪**。
（这是 F17b「断言写宽了把好数据判死」的**镜像**。）

⇒ 补**元断言**：拿"真实写错过的那一行"喂给判据，**要求它必须判死**；

```java
ok(stat, L,  hasCjkSpace("⚠ 与 「A」等 3 个版本 共用此槽…"), "元断言：错误文案会被判死（证明判据有分辨力）");
ok(stat, L, !hasCjkSpace("⚠ 与「A」等 3 个版本共用此槽…"), "元断言：正确文案不被误杀（判据不是恒真）");
```

★ **可迁移规则**：**"先修好、再补断言"时，必须给断言喂一个"已知是坏的输入"** ——
  否则那条断言可能只是恒真的装饰（判据写反 / 永远返回 false），
  **"看着有自检、其实什么都没验"比没有自检更危险**（它给的是虚假信心）。

判据刻意**不用 `contains(" ")`**（会在 fmt 将来真需要空格时误杀），
而是锚定四处**具体紧邻组合**：`与 「` / `」 ` / ` 共` / `版本 等`。

### F7b —— 跨进程配置同步 ★ 继续上次要重启才更新 ✅ 已完成（2026-10-01，第十九轮）

**问题**：继续上次必须把启动器重启才能更新。

**现象**：切到另一个版本玩一局 → 回到启动器 → 点「继续上次」，**仍指向上一局之前的版本**；
必须 force-stop 杀掉启动器再打开，才会变成刚玩的那个。

**根因**（真机复现定案）：`Config` 是**进程内单例**，`load()` 幂等（`mFile != null` 直接 return）
⇒ 每个进程只在启动时读**一次**盘。而 `last_version` 是 `GameSlot` 在 **`:game` 进程**里写的
（`GameSlot:84`，游戏启动成功之后）—— 主进程内存里那份 `mRoot` 毫不知情。
最毒的地方是**它看起来完全正常**：盘上明明是新值，主界面就是旧的，而且这个差值
会随主进程存活时间无限拉长（进程不被杀就永远不刷新）。

| 步骤 | 盘上 `last_version` | 「继续上次」 |
|---|---|---|
| 初始 | `official-159.apk` | official-159 |
| 外部写入 `com.github.tinylake.mindustryX`（等价于 :game 写入） | MindustryX | **official-159** ← 走 2 次 onResume 都不变 |
| force-stop 重开 | MindustryX | MindustryX ✅ |

**修法**：`Config.reload(Context)` + `MainActivity.onResume()` 里**第一句**调用
（在 `rescan()` 与 `AutoBackup.settle()` **之前**）。三条取舍都写进了 `Config.reload` 的注释，别改：

- **不做 mtime / 指纹短路，一律重读**：config.json 只有 1~2 KB，解析代价可忽略；
  而「漏判」的后果**恰好就是本条要修的 bug** —— 省这点 I/O 不值得冒险。
- **读失败保留内存值**（不归档、不清空）：reload 在运行期跑，用户已经在界面上看到了内容，
  「这次不刷新」远好于「把配置清成默认值」。（`load()` 的读失败处理相反：那是启动阶段。）
- **成功则整体替换 `mRoot`**，不逐键合并：盘上才是唯一事实，合并会留下已删键的幽灵。

**纪律（以后会反复用）**：`:game` 进程**只写 `last_version` 这一个键**（全库唯一的跨进程写入点，
已 grep 核实：`GameSlot:84`）。**以后任何新增的「跨进程写键」，读它的那个页面都必须在
`onResume` 里补一次 `reload`** —— 这个坑不会自己消失。

**验收**（dev + 产品版双双）：真实链路 —— 点 MindustryX 启动游戏 → 回启动器，
**主进程 pid 全程不变**（dev 16020 / 产品 18479）而「继续上次」立刻从 official-159 变 MindustryX；
外部写入往返两次同样即时反映；M3 自检 **36 / 36**；启动管线 **40 ms** 六步无回归；浅色 / 横屏正常。

### F20 —— 运行日志一键导出 ✅ 已完成（2026-10-02）

**需求原文**：「加一个一键导出所以日志的功能」。

**问题**：日志页原来每个卡只有一个「复制」（进剪贴板）—— "把日志发给别人看"这件事等于不可用：
三个源要来回切、复制三次、再自己拼起来。

**做法**：页首一行「导出全部日志」（`row_action` 范式），把三个源拼成**一个 txt**，
经 SAF（`ACTION_CREATE_DOCUMENT` + `Exporter.createDoc(name, "text/plain")`）存到用户选的位置
（`Exporter.writeText` —— **UTF-8 不带 BOM**）。

文件结构（`LogActivity` 的导出拼装，文案全在资源里）：

| 段 | 内容 |
|---|---|
| 抬头 | 导出时间 / 应用版本 / 当前槽 / 数据根 / HUB / 设备 / ABI / 页大小（`log_export_head_fmt`，8 个参数） |
| ① | **游戏日志**：当前槽的 `last_log.txt` |
| ② | **启动器日志**：hub 下 6 份 `report-*.txt`，每份前一行 `──── 名称（文件名）────` |
| ③ | **崩溃报告**：数据根 `crashes/` |

**四条不可省的判据**（都写在类注释里，别"顺手简化"）：

1. 🔴 **导出与页面显示是两套读取**：页面只留**尾部 400 行**（`MAX_LINES`；几千行别把界面拖卡），
   单文件超过 512 KB 只读尾部；而导出走 `Doc.fullText()`、**不截断** —— 截断等于悄悄丢掉
   最前面的启动阶段信息（那往往正是要查的那段）。把两者合并成一个方法是"很自然、也很错"的合并。
2. 🔴 **单份文件 8 MB 上限**（`EXPORT_MAX_BYTES`）：三源全文要拼进一个 `StringBuilder`，
   某个文件被写成几百 MB（游戏死循环刷日志）时，无上限就是一次 OOM —— 而 OOM 发生在**导出中途**，
   用户看到的是"闪退"而不是"日志太大"。宁可**明说被截**（`log_export_big_fmt`）。
3. **缺失 / 空文件都显式写出来**：`（缺失）` / `（空文件）`，不许静默跳过 ——
   否则读的人会以为"这个源本来就没有"。
4. **两种"做不了"都要说人话**：一个日志都没有 ⇒ `log_export_empty`；
   系统里没有能"保存文件"的应用 ⇒ `log_export_no_picker`（不静默什么都不发生）。

**为什么要这样**：这份 txt 是给**别人**看的（发 issue / 发群里），它是排障链上唯一的"一次带走全部现场"，
所以它的目标是**完整 + 自解释**，不是"跟界面显示一致"。

**验收**：真机导出到 Download ⇒ 三段齐全、抬头 8 项都在、中文不乱码；
全程零存储权限申请（SAF 只给一个写句柄）。

**步骤**

1. **先定口径**（决定后面所有行为）：判据只能是「**凡是我们没法重造的用户数据都要在**」。
   而"模组把配置放哪儿"**事先不可能枚举**（第三方作者，爱建什么目录建什么目录）
   ⇒ 只能**反过来**枚举"哪些**确定不是**用户数据"。
   排除理由各有实测依据：三项是 HUB 自己被游戏首启抄进数据根的残留；`tmp` 是游戏自认的临时目录；
   ★ `cache` 是**游戏每次启动都会先 `deleteDirectory()` 删掉它**（源码 `Vars.setup()` 坐实）。
2. **备份与导出共用一个口径**：同一条 `Data.contentRoots`。
   理由：两者问的是**同一个问题**；反过来（导出全、备份少）会得到一个**没有任何症状**的坏状态 ——
   用户拿备份恢复完发现地图/蓝图/模组配置没了，**而备份本身"看起来是成功的"**。
3. `Backup.create` 用 `contentRoots` 的清单顺序 ⇒ **排序稳定**（目录在前、名字不区分大小写升序），
   否则 diff 全是噪声。`Cas.BULK_LOCK` 仍覆盖「写对象 → 写清单」整段。
4. **rel 收口到 `Util.relOf`**（原 `Exporter.relOf` 与 `Backup.rel` 两份且内容不一致）。
   🔴 补上 **`f == base`** 与 **「`f` 不在 `base` 之下」** 两条兜底 —— 见"坑"。
5. `contentSkipped` **顶级与任意深度共用同一份**：以前它是 `Exporter` 的私有逻辑，
   备份那条路**没有它** ⇒ `saves/x.msav.part` 会进对象池。
6. `SelfTest.backupAndRestore` 重写：假数据分【A】该进（含 `logic-tool/history/project-1.json`、`previews/p.png`）、
   【B】顶层排除（`config.json` / `cache/junk.bin`）、【C】通用跳过（`*.part` / `.hidden/`）**三类**，
   **正反两侧都断言**；另加**两条结构断言**守卫 rel 形状（见下）。
7. 文案改口径说法（**别写"白名单"这种实现词**，写清后果）：
   「备份槽里的「全部内容」——包括模组自己放的配置文件。只排除：…」。

**坑（本轮新增）**

- 🔴★ **顶层文件的相对路径会算成空串**：`absolute.substring(root.length())` 在 `f == base` 时给 `""`，
  拼出来是 **`"settings.bin/"`（带尾斜杠）** —— 而 `new File(root, "settings.bin/")` 会**丢掉尾斜杠**
  ⇒ **恰好能用**、恢复跑得通、清单看着也对、**没有任何症状**。
  ⇒ 两条兜底：`f == base ⇒ f.getName()`；**`f` 不在 `base` 之下 ⇒ 也返回 `f.getName()`**
  （不加后者，`startsWith` 失败时 `s` 还是**绝对路径**会进清单 ⇒ 恢复时 `new File(dst, rel)`
  **写到槽外面去**）。
  ⇒ **对应的结构断言**（内容断言测不出来）：顶层 `settings.bin` 的 rel 必须**就是** `"settings.bin"`；
  **遍历全清单**，每条 rel 必须**非空 · 相对 · `/` 分隔 · 无尾斜杠 · 无盘符冒号**。
- 🔴★ **`chmod -R 0777` 外部数据根 ⇒ 制造假失败**：`/storage/emulated/0/Android/data/<pkg>/`
  顶层目录带 **setgid**，清掉之后应用**新建**的文件归属 `u0_a298:u0_a298` 而非 `u0_a298:ext_data_rw`
  ⇒ `md5sum` 行**多一列不同的组名** ⇒ `diff` 报 4 个文件"不一样"，**内容其实一个字节没差**。
  ✅ 正确姿势 `umask 000; mkdir -m 2777 -p ...`；⚠️ 对顶层目录 `chmod` 报 `Operation not permitted`
  是**非致命**的（sdcardfs/FUSE 不给改挂载点属性），别当失败去"修"。
- ⚠️ **恢复 = 只覆盖、不删除**（有意）：快照里没有的文件原样留着。
  不能改成"先清空再解包"（不可逆 + "哪些是备份之后加的"判不出来，mtime 会被改）。
  真要整槽替换走「整槽导出 + 导入」（`Data.WIPE_DIRS`，★ `mods` 刻意不在里面）。
  这条**已写进 `restore_confirm_msg_fmt` 文案**，用户看得见。
- ⚠️ **改口径只管新快照**：老快照的清单里**当初就没记** `logic-tool/` 这类条目
  ⇒ 拿老快照恢复**还是会少数据**（不是 bug，是那份清单没有）。
- ⚠️ **测试用的非 ASCII 文件名不能在设备上用 `input text` 打**（中文 IME 会吃成拼音候选）
  ⇒ 用 `run-as`/sh `printf` 写在设备上。
