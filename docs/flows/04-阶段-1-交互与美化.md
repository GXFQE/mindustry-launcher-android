- ⚠️ **ListView 的 item 根节点 `layout_margin` 无效** —— `AbsListView.generateDefaultLayoutParams()` 给的 `AbsListView.LayoutParams` 只有 width/height，**不带 margin**。行间距必须用「外层容器 padding + 内层卡片」两层结构；左右间距交给 ListView 自己的 `paddingStart/End` + `clipToPadding="false"`。

- ⚠️ **`Util.applySystemInsets()` 会覆盖 root 的 padding**（F2c 起**四边**都写 `base + inset`，见 F2c）⇒ 根节点别设 padding，页面内边距交给内部容器与 ListView。
- ⚠️ 验证配色**别靠缩略图肉眼**（本次把"浅紫底 + 靛蓝字"的徽标误看成"深底白字"，差点去改一个本来正确的资源）——**取背景像素定案**。

### F2c —— 横竖屏适配（整页可滚）★「横屏以后底下按钮点不到」

> ✅ **已完成（2026-10-01）**：两页由「顶部固定 + ListView 自滚」改为「整页 ScrollView」；
> `Util.applySystemInsets()` 补上 left / right。产物基线 **95990 B（不变）**；`dev_m3_selftest` 36/36；
> 横屏实拍滚动前 / 滚动后 / 存档页三张（`evidence/f2c-*.png`）。
> 完整根因与证据：`REFERENCE-android-adaptation.md` **§23**。

**现象**：竖屏一切正常；**转到横屏后**版本列表整块消失、最底下那行「存档与备份」被压成一条线看不见，
怎么点都没反应，也没有任何滚动条。

**根因（真机取证，不是推测）**

旧结构是「根 `LinearLayout(vertical)` + 顶部区 `wrap_content` + `ListView` `0dp/weight=1`」，
设计意图是"顶部固定、列表自己滚"。这个结构**只有在高度够用时才成立**：

1. 横屏可用高只有 **376dp**（1224px @520dpi，还要再减 ActionBar 86dp）。
2. 顶部区（状态卡 + 继续上次 + 三行操作卡 + 内边距）需要约 **334dp**，本身就快顶满。
3. `LinearLayout` 分配时，`weight` 子视图在**剩余空间为负**时只能拿到 0 ⇒ `ListView` 高度归零。
4. 更阴的是：**压缩不是一次性发生的，而是沿 `AT_MOST` 逐层往下传递** ——
   最末端那个子视图独自承担全部差额。实测 `row_saves` 被从 204px 压到 **85px**，
   它内部的 `act_title` 只剩 **7px**（文字被裁成一条线，点击热区几乎为零）。

> ★★ **两个必须记住的取证陷阱**（本轮各踩一次）：
> ① **`uiautomator dump` 报的 bounds 是"被父容器裁剪后的可见区"**，不是视图的真实高度。
>    证据：滚动前 `row_saves` 报 131px（= 204 - 超出屏幕的部分），滚动后同一个视图报 **204px**。
>    ⇒ 看到"被压扁"先别下结论，**先滚一下再 dump 一次**才能区分"真被压缩"和"只是被裁掉"。
> ② **完全落在屏幕外的节点根本不上报**。`ver_list` 在滚动前从 UI 树里彻底消失，
>    这不是"视图不存在"，而是"不可见不上报"。
> ③ 判据要选**能证伪**的那个：本例真正的问题是"能不能滚下去"，
>    所以决定性实验是 `input swipe` + 重新 dump，而不是看静态的 bounds。

**修法（XML-only，Java 一行没动）**

| 文件 | 做什么 |
|---|---|
| `app/res/layout/activity_main.xml` | 根 `LinearLayout` → **`ScrollView`**（`fillViewport="true"`，保留 `@+id/root` 与背景）；新增一层内层 `LinearLayout(vertical, wrap_content)`；`ListView` 由 `0dp/weight=1` → **`wrap_content`** |
| `app/res/layout/activity_saves.xml` | 同上（两页结构对称，以后改一个记得改另一个） |
| `Util.java` | `applySystemInsets()`：left / right 也叠加；四个方向的 base 全部先存档（防重复派发时 padding 累积） |

`ListView` 在该结构下**不再自己滚**，滚动条由外层 `ScrollView` 提供。
> ⚠️ **本节下面这句当时的结论是错的，F3b 已推翻**（保留在此只为留下推理痕迹）：
> 曾写"这依赖 API 24+ 的 `AbsListView.onMeasure`（`heightMode=AT_MOST` 时测量全部 child）"——
> 实测 `ScrollView` 给子级的是 **`UNSPECIFIED`**，而那个分支**只按单行估高**。
> 结果就是"能滚，但滚不到底"，列表末尾的条目永远出不来。详见 **F3b** 节。

**验收**
- 横屏下 `input swipe` 能滚到最底：`row_saves` 完整 204px、`ver_list` 出现且三个版本行齐全。
- 点「存档与备份」中心坐标 ⇒ 真的跳进 `SavesActivity`（`mCurrentFocus` 命中）。
- 存档页横屏：三个操作行 204px 完整，`slot_list` 可见。
- ~~竖屏回归：内容 2265px < 视口 2395px，**不产生滚动**，观感与 F2b 一致。~~
  ⚠️ **这条结论是错的，F5b 已实测更正**：竖屏**确实产生滚动**（当时实测 119px），
  只是范围小到"慢拖几乎看不出来"，因此被误读成"不用滚"。别再引用本行。
  F5b 已把竖屏滚动范围抬到 197px（详见 **F5b** 节）。
- `dev_m3_selftest` 仍 36/36。

**坑**
- ⚠️ **`weight` 救不了高度不足**：`layout_weight` 只在"剩余空间为正"时才有分配意义；
  为负时它只会被压到 0，而且**压缩会逐层下传，最深的那个视图独自承受全部损失**。
  凡是"顶部固定 + 列表自滚"的页面，都要先问一句"横屏够不够高"。
- ❌ **`ScrollView` 里放 `ListView` 并给 `wrap_content` 是【不】可用的** ——
  这是本节当时的错误结论，**F3b 已推翻**：能滚，但**滚不到底**
  （`ListView` 只按单行估高，外层滚动范围少算）。列表容器直接用 `LinearLayout` 手工挂载。
- ⚠️ **`uiautomator dump` 的 bounds 是裁剪后的可见区**（见上），别拿它当视图真实尺寸用。
- ⚠️ **横屏时导航栏在窗口右侧**（本机 129px @520dpi，自 x=2571 起）——
  只处理 top / bottom 的 inset 逻辑会让整行内容伸进导航栏底下。四边都要算。
- ⚠️ **insets 会反复派发**（旋转 / 手势条显隐 / 进出全屏）⇒ 必须先存 4 个方向的 base，
  用 `base + inset` 写回；用 `v.getPaddingLeft()` 现读现加会**越加越大**。
- ⚠️ 改横竖屏适配时**两页都要改**（`activity_main` / `activity_saves` 是同构的）。

### F3b —— 列表容器去掉 ListView + 对话框 message/items 冲突 ★「它拖不到最底下啊」

> ✅ **已完成（2026-10-01）**：两页的版本 / 槽列表由 `ListView` 改为 `LinearLayout` 手工挂载；
> 顺带修掉一个**长期潜伏的功能缺陷** —— 两个 `setMessage` + `setItems` 对话框的列表项完全不渲染。
> 产物基线 **91894 B**（F2c 是 95990）；`dev_m3_selftest` 36/36；证据 `evidence/f3b-*.png` 六张。
> 完整根因：`REFERENCE-android-adaptation.md` **§24**。

**现象**：横屏能滚动了，但**滚不到最底下** —— 版本列表只露出第一行，后面几个版本永远看不到。

**根因（AOSP 公式级闭合）**

F2c 把列表容器从 `0dp/weight=1` 改成 `wrap_content` 之后，它从 `ScrollView` 拿到的
高度约束是 **`UNSPECIFIED`**（`ScrollView.onMeasure` 对子级一律用 UNSPECIFIED 量一次）。
而 `ListView.onMeasure` 在 `heightMode == UNSPECIFIED` 分支下**不会去测量全部条目**，
只按「padding + 单个 item 高」估一个整体高度：

```java
if (heightMode == MeasureSpec.UNSPECIFIED) {
    heightSize = mListPadding.top + mListPadding.bottom + childHeight
               + getVerticalFadingEdgeLength() * 2;
}
```

实测数值**逐项对上**：`ver_list` 高度 = **342px** = 39px(`paddingBottom`) + 303px(一行 item)，
而 3 个版本的真实高度应是 3×303 + 39 = **948px**。
⇒ 外层 `ScrollView` 的滚动范围少算了 606px，列表后面的内容**在物理上就滚不出来**。

> ★ 这条**推翻了 F2c 留下的错误结论**（那句"API 24+ 会测量全部 child"是把 `AT_MOST` 的行为
> 安到了 `UNSPECIFIED` 头上）。`ScrollView` 给子级的一律是 `UNSPECIFIED`。

**修法**

| 文件 | 做什么 |
|---|---|
| `activity_main.xml` / `activity_saves.xml` | `ListView` → **`LinearLayout`**（`ver_container` / `slot_container`），高度天然 `wrap_content` |
| `MainActivity` / `SavesActivity` | 删掉 `Adapter` / `setAdapter` / `setEmptyView` / item-click 监听；新增 `rebuildList()` + `bindVersionRow()`，逐个 `inflate` 后 `addView`；整行的单击 / 长按直接挂到行根上；空态改为手工控制 visibility |
| `item_version.xml` | 移除 `descendantFocusability="blocksDescendants"`（它只为 ListView 的 item click 而存在） |

**为什么敢直接放弃 ListView**：条目本来就要求**全展开**（滚动交给外层），数量只有几个到十几个
⇒ `AbsListView` 的回收机制**从来没有真正被用上**。换掉它不损失任何东西，
反而把"嵌套滚动 + AbsListView 测量"这整类不确定性一起删掉了。

**顺带修掉的第二个缺陷（与滚动无关，但同一次复测暴露）**

`slotOps` / `pickMsavTarget` 两个对话框**列表项一个都不渲染** —— 用户点开槽行只看得到
标题、说明和「关闭」，**四个槽操作一个都点不到；`.msav` 导入甚至完全没法用**。

根因：**同一对话框里既 `setMessage(...)` 又 `setItems(...)` 时，list 被吞掉**。
对照实验：`pickSlot()` 用 `setSingleChoiceItems` 且**没有** `setMessage`，列表显示正常。
修法：把说明文字合并进 `setTitle`，`setMessage` 那格空着不用。
