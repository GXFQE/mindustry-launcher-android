**步骤 A：解析器（★ 这条是硬约束）**

**不能选官方 hjson-java 当解析器**：真实 17 个模组元数据的三实现判决 ——
严格 JSON **5/17**、官方 hjson-java 3.0.0 **16/17**（1 个"引号内裸换行"被拒）、
**arc 159.7 与 160.4 都是 17/17**。⇒ 真实数据上**6% 的模组会被误判为不可用**。

- 骨架可用官方 hjson-java（MIT；27 个同名方法里 13 个与 arc 逐字节相同），但必须补：
  ① 引号内允许裸控制字符；② 终止规则的 profile 开关；③ 捕获 `Throwable`（空多行抛 `StringIndexOutOfBoundsException`，深嵌套会栈耗尽）。
- ⚠️ 若用官方库要 **3.1.0 而不是 3.0.0**（3.0.0 带 CVE-2023-39685 / CVE-2023-34620，而**我们解析的是从网上下载的不可信模组**），并重跑对照表。
- ★ **绝不许按后缀选解析器**：`mod.json` / `mod.hjson` / `plugin.json` / `plugin.hjson` **走同一段代码**
  （`Mods.metaFiles` 固定四项、按下标顺序取第一个存在的）。实测反例：好几种叫 `mod.json` 的包内容其实是 HJSON。
- ★ **复刻游戏的解析链，别自己发明**（`Mods.java:1009`）：
  `HJSON 文本 → Jval.read() → .toString(Jformat.plain)（转成标准 JSON 文本） → Json.fromJson(ModMeta.class)`
  ——**游戏从不"把 HJSON 直接解成对象"**，自己解必然在边界样本上分叉。
- `CompatProfile`（`ARC_159` / `ARC_160`）仍做但**优先级可降**：真实数据上两版产物**逐字节相同**，
  真要防的是"**误用官方库**"这条真实路径，不是版本分叉。
- ✅ 可直接复用的回归资产：探针工程内的 HJSON 语法电池 **41 条** + **10 条三实现对照**；
  探针工程内的真实 `mod.json` 语料（17 个真实 meta 原文）= 比合成电池更贴近实战的**真实语料**。

**步骤 B：`settings.bin` 读写（格式已解开，写往返已实测通过）**

```
int32 count
重复 count 次： u2 keyLen + key(modified-UTF-8) | u1 type | value
  type: 0=bool(1B)  1=int(4B)  2=long(8B)  3=float(4B)  4=string(u2+bytes)  5=json(int32+bytes)
```
验证标准：解完 `count` 条必须**恰好消费完整个文件**。真实规模：`502397 B / 5905 键`，decode→encode **逐字节一致**；
改一个键后 arc 自己的 `Settings`（159.7 与 160.4）**都能读回新值**。

- ★ **三条硬约束（源码根据，缺一不可）**：① **改前备份**；② **原子写**（临时文件 + 改名，可复用 `Util.atomicWriteText` 的思路）；
  ③ **写后自检可解码**。
  ⚠️ 原因：`Settings.saveValues()` 的 catch 分支是 **`file.delete()`**（"file is now corrupt, delete it"）
  ⇒ 若 MDT 写出坏文件、游戏随后自己保存出错，**游戏会删掉设置文件**。
- ⚠️ **必须原样保留未知键**（与桌面版 `config.json` 的 `_extras` 同一条教训）：不能"解出认识的键就重建文件"。
- ⚠️ 必须在**游戏未运行时**改写（游戏退出时会整份重写这个文件）⇒ 复用 `Data.gameAlive()` 门禁。

**步骤 C：模组状态与加载门**

| 键 | 类型 | 缺省 | 用途 |
|---|---|---|---|
| `mod-<internalName>-enabled` | bool | **true** | 启用态（**键不存在 ≠ 禁用**） |
| `mod-<internalName>-failed` | bool | false | per-模组崩溃标记 |
| `mod-<internalName>-repo` | string | — | ★ **"检查更新"的数据源**，不用猜仓库地址（真实值 9 条已采到，形式一律是 `<作者>/<仓库>`） |

- `internalName = name.toLowerCase(Locale.ROOT).replace(" ", "-")` ⇒ **英文大小写不敏感**，
  **中文原样保留**（`蓝钢拓展` → `mod-蓝钢拓展-enabled`）⇒ 键名含非 ASCII，读写走 modified-UTF-8（**写往返已实测通过**）。
- ⚠️ **文件名推不出 settings 键**（实测反例：`eb-wilsontomyitems.zip` → `tmi`、`tnmspiroctexoprosa1.zip` → `exoprosopa`）
  ⇒ **必须打开包读 meta**。
- ★ **启停的正解不是改后缀**（改名只对 `.jar`/`.zip` 有效，**对目录形态的模组完全无效**）⇒ 正解就是读写上面那个 settings 键。
- 「为什么这个模组没生效」要按加载门**逐条**报（`Mods.java:1146~1154`）：
  `mainFile.exists() || meta.java` / `!skipModLoading()` / `enabled` / `Version.isAtLeast(minGameVersion)` /
  `minMajor >= minJavaModGameVersion` / 不在黑名单 / `!skipModCode` / `initialize` —— **别只说"未生效"**。
- ⚠️ **静默失败点**：`Mods.java:531 catch(Throwable ignored)` ⇒ 元数据解析失败**无声**跳过。
  ⇒ 「日志里没有该模组」不等于「它解析失败」，要区分是掉在解析、类加载、还是门条件。

**步骤 D：扫描**

- 一级子项保留三类：`.jar` / `.zip` /（目录且 `resolveRoot(dir)` 下有 `mod.json|mod.hjson|plugin.json|plugin.hjson`）。
- `resolveRoot(fi)`：该层只有 1 个条目且是目录 → **下潜一层**（兼容"包里套一层目录"）。
- ⚠️ **冲突点**：两个包解出同一 `internalName` 会**互相覆盖** ⇒ 提前检出并报警。
- ⚠️ **模组在槽内部**（`<数据根>/mods/`）⇒ 天然已按槽隔离，**M3 白送，不用另做隔离**。

### F14 —— 内置模组开发器

**目标**：选模板（新物品 / 新方块 / 新单位）→ 填参数 → 生成 `mod.hjson + scripts/main.js` → 打包 → 放进当前槽 `mods/` → 一键启动验证。

**关键判断：走 JS，不走 Java** —— 这已是**结论**（真机决定性证据：探针脚本打出 `class=$Proxy4`，
即 Rhino JavaAdapter 运行时生成字节码 → `BaseAndroidClassLoader.defineClass()` → `com.android.dx` 翻 dex → `InMemoryDexClassLoader` 加载回来。
这条链断任何一环都打不出那行 ⇒ JS **能注册事件回调、能访问全部游戏内容**）。

**前置**：F13（复用扫描/打包）、F1。

**改动面**：新 `ModWizardActivity` + `res/raw/mdt_mod_template_*.zip` 模板 + 打包工具。

**步骤**
1. 模板硬规则（`Mods.loadScripts()`）：
   - 触发条件 = **`scripts/` 目录存在**，`mod.json` 里**不需要** `hasScripts` 字段；
   - `scripts/` 下只有 1 个 `.js` → 用它；有**多个** → **必须叫 `main.js`**，找不到就 `No main.js found for mod` 并跳过。
   ⇒ **生成器永远输出 `scripts/main.js`，这是最稳的写法。**
2. 模板脚本**每层独立 `try/catch`** —— 脚本报错不致命（被 catch 成 `[E] [<mod>/<script>]: ...` 后继续加载），
   但首层失败会吞掉后续所有证据（**自己踩过**：第一版探针在第一个 `print` 就中断，日志里一条都没有）。
3. 输出通道：`print()` → `<数据根>/last_log.txt`，行首带 `[<mod>/<script>]` 前缀 ⇒ **开发器的"运行结果"就从这里读**（复用 F7）。
4. 写文件位置 = **当前槽的 `mods/`** ⇒ ★ **必须走 `Data.dirOf`，不能硬编码路径**（槽可能会被换走）。
5. 打包：`ZipOutputStream` 打 `mod.hjson + scripts/main.js` → `mods/` 下。**目录形态与 zip 形态走同一分支**（风险低）。

**验收**
- 生成一个"新物品"模组 → 进游戏 → 物品真的出现在物品栏（**端到端，探针只验了机制没验端到端**）。
- 生成"新方块"、"新单位"各一次。
- 故意写错脚本 → 游戏照常进主菜单，且 `last_log.txt` 里能看到我们的 `[E]` 行。

**坑**
- ⚠️ **未实测**：把生成的 mod 打成 zip/jar 后能否照样加载（源码同分支，风险低，但要实跑一次）。
- ⚠️ 不做"应用内 Java 模组编译器"（要 JDK + d8，不现实）；不做 IDE —— **是"模板 + 填空"**。
