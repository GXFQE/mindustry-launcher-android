## F27.1 一句话

**宿主只做机制，不生成补丁。** 一个补丁 = 一份「完整替代类」的 dex（可选再带一个素材包）：
启动时把补丁 dex **插到宿主 dex 之后、游戏 dex 之前**，ClassLoader 先找到谁就是谁 ——
游戏本体（官方 APK）**一个字节不动**，所以不需要重打包、不需要 CAS、不产生第二份游戏。

这是 class replacement（同名完整类顶替），不是字节码注入：补丁类必须**完整**，
只支持"整个方法替换 / 整个类替换"，不支持 Mixin 那种"在方法中间插一段"。
Mixin 的复杂度留在**生成器**（外置工具 / dev-only），宿主永远只认「dex + 可选 assets」。

## F27.2 补丁包格式（对外契约）

```
my-patch.mdp (zip)
├── patch.json
└── targets/<apkSha256>/
    ├── patch.dex          必需：完整替代类
    └── assets.zip         可选：条目必须都在 assets/ 下
```

```json
{
  "schema": 1,
  "id": "mindustryy-160.4",
  "name": "MindustryY",
  "version": "1.0",
  "author": "", "note": "", "tool": "",
  "targets": [
    { "apkSha256": "<64 位小写 hex>", "gameVersion": "160.4",
      "dex": "targets/<sha>/patch.dex",
      "assets": "targets/<sha>/assets.zip" }
  ]
}
```

- **匹配键 = 目标 APK 的 sha256**，不是版本号区间。依据是实测反例：拿 v160 的类去顶
  MindustryX（160.1）⇒ `NoClassDefFoundError: arc.util.OS$$ExternalSyntheticOutline0` 直接崩。
  补丁改的是字节码，合成类 / 内部类每个构建都不同 ⇒ 只能精确匹配。
- 一个包可以带多个 target（同一份改动、不同游戏版本各一份产物）；同一 sha256 写两次 = 拒绝。
- 校验三道（失败码 → 人话在 `PatchText`）：结构（schema / id / name / version / targets）、
  哈希（64 hex）、路径（dex/assets 必须在自己那个 `targets/<sha>/` 下的**单层文件名**，
  整条路径过 `PatchManifest.safeRel`：不许 `..` / 盘符 / 反斜杠 / 前导 `/` / 空段）。
- 上限：单 dex 64 MB、素材 128 MB、整包 256 MB、条目 4096 —— 只是防坏包写满盘。

## F27.3 存储与启用状态

```
app_hub/patches/<id>/<version>/          ← 内部存储（ART 只认内部 + 只读，ref/48）
├── patch.json                           ← 原字节副本（不是重新序列化）
├── <apkSha256>.dex                      ← 只读
└── <apkSha256>.assets.zip               ← 只读（可选）
```

- 外部 hub **只放报告**（`report-patch.txt`），不放可加载物。
- 启用状态在 `config.json` 的 `patch_enabled`，**按「启动项（实例）」存**（第 353 轮起）：
  `{ "<实例键>": ["<id>@<version>", …] }`，实例键 = `Versions.instanceKey` =
  `<版本 key> + NUL + 槽>`（版本 key：已装 = 包名，导入 = `import:<文件名>`）。
  ⚠️ 同一个版本绑多个槽 ⇒ 每一行（启动项）各开各的；`config_version` 从 2 升到 3，
  旧格式（只按版本 key）由 `Config.migratePatchKeys()` 搬到这个版本**主行**的实例键。
- **不做引用计数**：补丁天然是"全局一份 + 版本级启用列表"，不存在多槽副本（与设计草案 §3 的
  设想不同，实现时简化；少一类"数错了就删错文件"的 bug）。
- 删除补丁记录：**启用中拒绝**（先停用），避免下回启动找不到。
  ★ 2026-11-12 第 357 轮起：删除 = **挪进中转站**（`<hub>/patches-trash/`，不再裸删），
  保留份数走**整槽那一档**（默认 3，`Trash.keepFor(Kind.PATCH)`；设置页那一项现在写
  「整个槽 / 游戏版本 / 补丁」）；能从「中转站」放回 `app_hub/patches/<id>/<version>/`，
  放回去是**未启用**状态。用户原话：「游戏补丁中转站保留个数按照哪个算的啊」—— 答案原本是"根本没有中转站"，这轮补上了。
- 首次启用前告知一次（"这会替换游戏代码，可能让游戏崩"），看过记 `patch_warned`。

## F27.4 冲突检测（判据 = dex 里实际的类，不信清单）

清单里的 `classes` 是生成器单方面声明，写错/少写就能让两个补丁改同一个类而"看起来不冲突"
⇒ 宿主直接用 `PatchDex` 读补丁 dex 的 `class_defs`（`type_ids` → `string_ids` → MUTF-8），
素材冲突则枚举 `assets.zip` 条目并**剥掉 `assets/` 前缀**（= AssetManager 里的键）。

三条规则（任一命中 = 拒绝启用，并**点名**对方）：

1. **同一个补丁的另一个版本**已启用（同一 id 两个版本同时生效没有意义）；
2. **两边实际定义的类有交集**（后注入的静默赢 ⇒ 另一个的部分改动失效）；
3. **两边改的素材路径有交集**（addAssetPath 后挂覆盖先挂，同样是静默覆盖）。

只与会**匹配当前 APK** 的 target 比：不适用的补丁本来就不会被注入，拿它拦没道理。

## F27.5 启动接线（Injector / GameSlot）

```
GameSlot.handle
  ├─ Patches.resolve(ctx, apk, 实例键)     ← 键 = 版本 key + NUL + 这一局实际用的槽（第 353 轮起）
  │                                         只在真有启用记录时算 APK 的 sha256（80 MB）
  │    ├─ 记录不存在 / 目标不匹配 / 文件缺失 ⇒ problem（不硬上）
  │    └─ 启动期再查一遍冲突（防御手工改 config）+ 后一条整条跳过
  ├─ plan.patches = [dex, assets?, label]
  └─ Injector.launch
       ├─ ① 量 hostDex = dexElementCount(baseCl)（**注入游戏 dex 之前**）
       ├─ ① 注入游戏 dex（append）
       ├─ ① 每条补丁 insertAt(hostDex + 已插入数)   ← 宿主之后、游戏之前
       ├─ ① 验证 base CL 能解析游戏入口类（**必须放在补丁之后**，否则入口类被原版抢先加载）
       ├─ ② native / ③ 置 loaded / ④ 资产链 = base + assetDeltas + 补丁 assets（后挂覆盖）
       └─ ⑤ startActivity
```

- **失败回退粒度 = 整条补丁**：单条注入失败只跳过它、启动继续（问题写进 `hub/report-patch.txt`）；
  这也符合"补丁坏了不该让游戏完全打不开"的取舍。
- 启动报告 `hub/report-launch.txt` 会写：宿主 dex 条数 / 每条补丁注入到哪个下标、耗时、跳过原因；
  **没有问题时删掉旧的 `report-patch.txt`**（不让过期结论挂在界面上）。
- 耗时（真机）：8.5 MB dex 注入 20 ms、小 dex 1 ms、素材 `addAssetPath` 1 ms。

## F27.6 界面（版本页 → 补丁页）

| 位置 | 内容 |
|---|---|
| 版本页 | 新增一行「补丁」；副标题 = 已启用 N 个（0 个时用静态句"替换这个版本的游戏代码"） |
| 主界面版本行 / 版本页标题卡 | 副标题前缀 **`补丁 N · …`**（有启用补丁时）—— 光写「原端/改端」看不出"这一版其实被补丁改成 fork 了"（第 345 轮用户反馈）；「继续上次」按钮**不带**补丁状态（用户：「要么那个继续上次不显示补丁吧」—— 按钮回到一行短文本） |
| 补丁页（`PatchesActivity`） | 身份卡（版本名 + APK 短哈希 + 已导入几个）/「导入补丁包」/「上次启动：有补丁没应用」卡（点 = 知道了）/ 补丁行 / 空态 |
| 补丁行 | 「名字 版本」+「N 个类 · 状态」；状态四态：已启用 / 未启用 / 不适用这个 APK / 文件缺失 |
| 详情卡（`CardStack`） | **补丁的元信息**（标识 / 作者 / 适用版本 + APK 短哈希 / 类数与素材数 / 体积 / 制作工具 / 导入时间 / 说明）+ 关闭 / 删除 / 启用·停用。**不列替换的类名** —— 使用者要判断的是"这是谁做的、给哪个版本、多大"，不是替生成器审代码（2026-11-10 用户反馈） |

判据收口：状态 = `PatchesActivity.stateOf(record, apkSha, enabled)` 一处；
页面只调用 `Patches`（导入 / 启用 / 停用 / 删除都只有一份实现）。

## F27.8 自检（`SelfTest.patches`，6 层）

1. **dex 解析**：夹具 dex 恰好 2 个类（`PatchProbe` + 匿名内部类）；拿本 APK 的 `classes.dex`
   当神谕（能认出 `Patches` / `PatchManifest` / `PatchesActivity`，认不出游戏类与夹具类）；
   垃圾字节必须解析失败。
2. **清单矩阵**：schema / 哈希 / 路径穿越 / dex 不在自己哈希目录 / 缺 name / 空 targets /
   targets 非数组 —— 每条期望**对得上的码**；`safeRel` 正反矩阵。
3. **导入往返**：真 dex → 内部存储 + 只读 → 扫描读回 → 类/素材键可重新解析 → 重复导入拒绝。
4. **冲突三条 + 反向**：同类冲突；类不相交但素材同路径也冲突；两者都不撞必须**不**冲突。
5. **启动解析**：匹配 → loaded；换 APK → 只报 `no_match`；没启用 → 空。
6. **状态 / 文案 / 跳转 / 素材规矩 / 导入负例**：四态判据、每个错误码都有人话且不印 null、
   版本页 → 补丁页 Intent 的类与 extra 键、素材包必须在 `assets/` 下、坏 zip / 缺条目 /
   坏 dex / schema=2 / 条目 `..` 全部拒绝且不留半条记录。

夹具：`app/assets-dev/patch-fixture/probe.dex`（2.6 KB，**只进 dev 包**）。
真机结果：**1992 / 0**（比第 344 轮的 1941 多 51 条；独立校验 B1/B2 的修复又补了 7 条断言）。

## F27.11 这轮踩到的坑（复查时先看这几条）

1. 🔴 **`adb push <文件> <目录>/` 在本机组合（Windows adb + 这台 ROM）会把目标文件名截成前几个字符**
   （`probe-smoke.mdp` → `pro`）—— 症状是 app 里"文件不存在"而 push 报成功。
   夹具/输入一律**显式给完整目标文件名**：`adb push x.mdp /sdcard/.../x.mdp`。
2. ⚠️ 用 PowerShell `>` 重定向抓设备文件会写成 **UTF-16**（带 BOM）—— 改完推回去会毁 `config.json`。
   抓/回写设备文件用 `adb pull` / `base64` 中转，或 `run-as` 内的 `cp` + `mv`。
3. ⚠️ `dev_m3_selftest` 在**刚启动就触发**时，`⑤ CAS 对象池` 那条断言可能被并发的自动备份干扰
   （40.8 MB → 41.0 MB）。稳妥做法：先正常启动 `MainActivity` 等约 10 s，再发 `--es dev_m3_selftest 1`
   （本轮第二次跑 = 1985 / 0；修完独立校验的 B1/B2 后 = **1992 / 0**）。
4. ⚠️ i18n `SRC-02` 台账随新日志增长：Injector 23 → 32（补丁注入报告行）→ **36**（独立校验 B1/B2
   的修复又加 4 行启动报告）—— 都只进 `report-launch.txt`，与既有 23 条同族。
5. 🔴 **补丁 dex 必须落在内部存储且只读**；放外部 hub 会被 ART 拒绝（`Writable dex file ... is not allowed`
   / SELinux），复制/置只读与 `Importer` 同一套纪律。
6. 🔴 **自己算 DEX 的 Adler-32 时累加器必须用 `long`**：经典实现按 5552 字节一块延迟取模，块内
   累加和最大约 `255*5552*5553/2 ≈ 3.9e9`，用 `int` 会溢出 ⇒ 把**好 dex 判成 checksum 不符**
   （本轮自检实测：自己的 `classes.dex` 被误判；改成 `long` 后全绿）。
7. ⚠️ **安卓的 `ZipOutputStream` 拒绝同名条目**（`ZipException: duplicate entry`）⇒ "同名条目要拒绝"
   这类判据的夹具得在 PC 上造（本轮：`assets-dev/patch-fixture/dup-entry.zip`，dev 包才带）。

## F27.12 独立校验（第 345 轮，队友 `patch-verify`）

> 报告落盘：`.dsh/research/2026-11-10-patch-v1/VERIFY.md`（不入库）。约束：只读源码、不跑构建、不碰设备。

| # | 分项 | 结论 | 关键数字 |
|---|---|---|---|
| ① | dex 类名解析器独立复算（JDK8 单编 `PatchDex` + Python 从零实现） | **PASS** | 三份 dex **类名集合与顺序逐类全等**：2 / 2 / **12162**；大 dex 另做 907 条抽样 bad=0 |
| ② | 静态审查 | **FAIL → 已修** | 1 高危（B1）+ 2 中危（B2/B3）+ 9 低危/nit（B4~B12） |
| ③ | `.mdp` 夹具独立复核（自写 zip/json/dex 检查） | **PASS** | 目标 APK 哈希现场复算命中；2 正例全绿、4 负例各只坏在声明处 |

**B1（高危，已修）**：`Injector.injectPatches` 里 `at = after` 把"合并后总条数"当插入下标 ⇒
第 2 条起补丁被追加到**游戏 dex 之后**、同名类永远被原版覆盖（静默失效）。
真机日志 `补丁[2] … @3` 就是证据。修法：`at = hostDex + 已插入元素数`，并抽成纯函数
`Injector.patchInsertIndex()` 由自检钉住；修后真机复验 = `@1` / `@2`。
**B2/B3（中危，已修）**：`makeDexElements` 把坏 dex 的失败塞 suppressed **不抛** ⇒ 用
`after <= before` 判失败；素材只挂 `applied=true` 的补丁；`dexElementCount` 失败不再回退 0
（否则补丁会被前插到宿主之前，可能顶掉宿主类），改为**跳过全部补丁并记 problem**。
**低危（已修/已处理）**：B4 已启用时先报 `enabled` 再查冲突（不再"点名自己"）· B5 `setText(resId)`
改 `Trans.get` · B6 启用（含冲突检测）挪后台线程 · B7 问题卡加"点一下关掉"提示、删死资源
`patch_page_lead` · B8 预览恰好 12 条时不多打省略号 · B9 外部名字在**解析处**清洗成单行 ·
B10 版本页计数改用 `enabledCount`（跳过孤儿引用）· B11 去掉 `sha256Of` 的 `path|len|mtime` 缓存
（被同长同 mtime 替换时会拿旧哈希去匹配 APK）· B12 拒绝 zip 同名条目 · 另：`PatchDex` 增加
file_size + Adler-32 校验（B2 的根因防线）。

★ 后续（同日用户反馈）：**详情卡改成元信息**（标识 / 作者 / 适用版本 / 数量 / 体积 / 工具 / 导入时间 / 说明，
不列类名）⇒ B8「预览恰好 12 条时多打省略号」随预览列表整体删除而消失（原修法在 `c27705a` 里可查）。

## F27.13 第 353 轮（2026-11-11）：启用状态改成**按启动项（实例）**

> 用户：「游戏补丁的启用状态应该绑定实例吧」。

**为什么**：一个版本可以绑多个槽、每绑一个槽多一行（启动项）。原来按版本 key 存，
给一行开了补丁，同一版本的另一行（另一个槽）也变成「已启用」—— 但用户只想让那个实例生效。

**改法**：
- 键 = `Versions.instanceKey(vkey, slot)`（版本 key + NUL + 槽；与 `Versions.rowKey` 同构）。
  NUL 而不是 `|`：版本 key（导入文件名可变）可能含 `|`，NUL 在 JSON / 包名 / 槽名里都不会出现。
- 全链路换键：`Config` 的 `patchRefs/setPatchRefs/patchRefVkeys/patchRefOwners`（参数文档写明是实例键）·
  `Patches` 的 `enabledRefs/enabledRecords/enable/disable/conflicts/resolve/enabledCount/enabledCounts` ·
  版本页 → 补丁页的 `patchIntent(c, vkey, slot)`（补丁页新增 `EXTRA_SLOT`，头部多一行
  「启动项：槽「X」」）· 主界面行上的 `补丁 N` 徽标按行取 ·
  **启动解析**在 `Data.prepareSlot` 之后取 `Data.currentSlot()` 拼实例键（`slot` extra 可能为空、
  远古包会改道 ⇒ 只有 currentSlot 是这一局真正落地的槽）。
- **迁移**：`CONFIG_VERSION` 2 → 3，`Config.migratePatchKeys()` 把旧键（只有版本 key）搬到主行实例键；
  幂等、没有旧键就不写盘。`Patches.instanceLabel()` 把带 NUL 的键翻成「游戏名 · 槽「X」」，
  用于「删补丁但还被启用」的拒绝文案。
- dev 口：`dev_patch_enable/disable` 支持三段 `vkey|slot|id@version`，也支持
  `--es dev_patch_enable 1 --es dev_patch_key <vkey> --es dev_patch_ref <id@version> [--es dev_patch_slot <槽>]`
  —— 设备 shell 会把 `|` 当管道，中文/带空格的槽名在命令行里很容易被拆坏。

**验收**（2026-11-11 真机，dev 变体）：
- 自检 **2011 / 0**（新增：实例隔离 / 实例键可拆回 / 迁移 / 迁移幂等；补丁页 Intent 多一个槽 extra）。
- 真机：同一版本 `v1607` 的两个启动项（槽「用于测试克隆功能」/「patchlab」）——
  只有前者行显示 `导入 · 备份 1 份 · 补丁 1`，后者只显示 `导入`；
  补丁页头部显示「启动项：槽「用于测试克隆功能」」；从这一行启动游戏 → 补丁生效
  （菜单 `MindustryX 2026.10.10…`），`hub/report-patch.txt` 不存在（没有"没应用"）。
- `config.json` 实测：`config_version = 3`，`patch_enabled` 键为 `import:v1607.apk\u0000用于测试克隆功能`。
- 截图 `evidence/round353/`。

## F27.14 第 357 轮（2026-11-12）：补丁删除进中转站

> 用户：「游戏补丁中转站保留个数按照哪个算的啊」。

- 事实核查：补丁删除原先是**唯一一个裸删的破坏性操作**（`Patches.delete` 直接 `deleteTree`），
  `Trash.Kind` 里也没有补丁 —— 所以根本没有保留份数。
- 改动：`Trash.Kind` 加 `PATCH` + `<hub>/patches-trash/`；`Patches.delete` 改为 `Trash.move` 进去
  （失败时源仍在）；`keepFor(PATCH)` = 整槽那一档（默认 3）；`TrashText.kindLabel` = 「游戏补丁」；
  `Trash.restorePatch` 把目录放回 `app_hub/patches/<id>/<version>`（名字约定 `id@version`，
  按最后一个 '@' 拆；放回去未启用）；中转站动作卡给补丁单独一句说明。
- 验证：自检 2023 / 0（含"删补丁→挪进 patches-trash→认成游戏补丁→放回原位置"一条）；
  真机 UI 往返：补丁页删除 → 中转站显示「游戏补丁 · 14.2 MB」→ 放回去 →
  `dev_patch_status` 记录 1 条、filesOk=true。截图 `evidence/round357/`。
- 存储占用：`patches-trash` 自动进 `Trash.allDirs` ⇒ 存储卡片的中转站段会多一行「游戏补丁」。

## F27.15 第 360 轮（2026-11-12）：崩溃处理与 :game 注入失败保持一致

> 用户：「在包含游戏补丁的情况下游戏崩溃处理方式和 game 进程注入保持一致」。

- 原来的缺口：:game 注入失败有明确处置（**整条跳过 + 写 report-patch.txt**），
  但**游戏运行期崩溃**完全不知道补丁的存在（crash 分析只认模组 / 原版）⇒ 带崩的补丁会一直留着，
  用户每次启动都崩、也不知道该怪谁。
- 现在（同一套处置）：
  - `:game` 注入完写 `hub/report-patch-launch.json`（这一局**实际注入了**谁：slot / 实例键 /
    `applied` 的 ref+label）—— 判据取注入结果，不是 config 的"想启用哪些"；
    ★ 第 365 轮（多开）：**一局一条、按实例键存**（`{v:2, records:{<实例键>:{…}}}`，最多留最近 6 局），
    后启动的实例不再把前一局的记录盖掉；崩溃处理按**崩的那个槽**取它自己那一局；
  - 崩溃处理（`Patches.noteGameCrash`，调用于 `Recovery` 启动自愈、`CrashAlert` 监视/回到界面、
    补丁页 reload）判据三条：① 那次启动真的注入过补丁；② 槽里有**比那次启动更新**的
    **游戏**崩溃报告（`crash_<毫秒>.txt`；`_launcher` 是启动器自己崩的，不算）；
    ③ 补丁在这个实例上还启用着。命中 ⇒ 在这个实例上**自动停用**这些补丁 + 写
    `hub/report-patch-crash.txt`，补丁页的「上次启动的补丁问题」卡会列出来；
  - 用户重新启用 ⇒ 清掉那条旧结论；崩溃弹窗里也补一句「上次启动带着补丁 X 崩了，已自动停用」。
- 为什么是"停用"不是"跳过一次"：注入失败是**持久**的（文件坏了就坏）⇒ 每次启动都跳过；
  崩溃没有持久判据，跳过一次 ⇒ 下次照样崩，变成隔一次崩一次的循环。停用 + 明说 + 可再启用，
  与 `Plugins` 的安全阀（崩溃后自动停用、用户可再开）同一语义。
- 🔴 **真机踩到的坑**：`Recovery.runNow` 在 `LauncherApp.onCreate` 里跑得**比 `Config.load` 早**
  ⇒ 第一次验时配置读成空、判成"用户已经自己停用了"，启动记录被删却什么都没处置。
  修法 = `noteGameCrash` 里先补一次 `Config.get().load(ctx)`（load 幂等）。
- 验证：自检 **2043 / 0**（⑯ 组 19 条：没崩不冤枉 / `_launcher` 不算 / 带崩自动停用 / 幂等 / 重启用清旧结论）；
  真机注入"上一局带补丁 + 下一份游戏崩溃报告"后冷启动 ⇒ `report-patch-crash.txt` 写入、
  启用表清空、`report-recovery.txt` 记 `patch auto-disabled after crash: MindustryX`；
  补丁页显示「上次启动的补丁问题」卡（截图 `evidence/round360/`）。
  ⚠️ 崩溃**弹窗**里那一句只做了资源/自检验证，没有在真机造"带补丁崩"的现场（造崩代价高）。

## F27.17 第 372 轮（2026-11-13）：插件也能读补丁（PluginApi v38）

> 用户：「先给插件加个可以读取当前所有插件及其基本信息的接口，还有读取游戏补丁的接口」。

## F27.18 第 373 轮（2026-11-13）：插件也能**写**补丁（PluginApi v39）

> 用户：「不能碰插件启停，但补丁可以碰（这东西只是个更强的模组而已）」。

- 新增五个写接口（全部异步、回调在 UI 线程）：
  `patchEnable(versionKey, slot, ref, Done)` / `patchDisable(...)` /
  `patchImport(InputStream, Imported)` / `patchDelete(ref, Done)` /
  `patchConflicts(versionKey, slot, ref, Conflicts)`。插件启停（`Plugins.enable/disable/uninstall`）
  **仍不开放** —— 那是宿主的安全锚（信任模型 + 安全阀），补丁没有这一层。
- 宿主实现 = **一层薄壳**（`PluginHost.PContext` 里 `patchOp` / import / delete / conflicts）：
  - 参数闸门：`(版本key, 槽)` 必须是**存在的启动项**（`PluginData.hasLaunchItem`），否则
    `not-found` —— 不让插件在 config 里留一条指向不存在启动项的启用记录；
  - 其余全部复用 `Patches.findByRef` / `enable` / `disable` / `importPackage` / `delete` / `conflicts`：
    实例在跑 `game_alive`、文件缺失 `missing`、不匹配 APK `no_match`、已启用 `enabled`、
    冲突 `conflict`、删除被启用 `in_use`、删 = 挪进中转站、导入先落插件 cache 的临时 zip
    （`MAX_TOTAL + 4 KB` 上限）再走 `importPackage` 的完整校验；
  - `patchConflicts` 与 `enable` 的门禁顺序对齐：**已启用 ⇒ `enabled`**，不许报"它跟自己冲突"。
- 失败码直接沿用 `PatchException` 的码（不另发明一套）；文案仍归插件。
- 验证：自检 **2135 → 2179 / 0**。其中 ⑨ 用"临时绑定一个槽 + 指向真实版本 APK 哈希的补丁包"
  把 **import → 预检 → 启用 → `patches()` 看到 enabled/applies → 再预检=enabled → 停用 →
  删除进 patches-trash** 整条真调回路钉住（反射造真的 `PluginHost$PContext`，异步回调用
  `CountDownLatch` 等主线程）；收尾无条件恢复临时槽绑定与补丁记录。
- 证据 `evidence/round373/`；接口文档 `docs/PLUGIN-API.md`「补丁写（v39）」。
