## F27.1 一句话

**宿主只做机制，不生成补丁。** 一个补丁 = 一份「完整替代类」的 dex（可选再带一个素材包）：
启动时把补丁 dex **插到宿主 dex 之后、游戏 dex 之前**，ClassLoader 先找到谁就是谁 ——
游戏本体（官方 APK）**一个字节不动**，所以不需要重打包、不需要 CAS、不产生第二份游戏。

这是 class replacement（同名完整类顶替），不是字节码注入：补丁类必须**完整**，
只支持"整个方法替换 / 整个类替换"，不支持 Mixin 那种"在方法中间插一段"。
Mixin 的复杂度留在**生成器**（外置工具 / dev-only），宿主永远只认「dex + 可选 assets」。

## F27.2 补丁包格式（对外契约）

```
my-patch.mdp (zip)
├── patch.json
└── targets/<apkSha256>/
    ├── patch.dex          必需：完整替代类
    └── assets.zip         可选：条目必须都在 assets/ 下
```

```json
{
  "schema": 1,
  "id": "mindustryy-160.4",
  "name": "MindustryY",
  "version": "1.0",
  "author": "", "note": "", "tool": "",
  "targets": [
    { "apkSha256": "<64 位小写 hex>", "gameVersion": "160.4",
      "dex": "targets/<sha>/patch.dex",
      "assets": "targets/<sha>/assets.zip" }
  ]
}
```

- **匹配键 = 目标 APK 的 sha256**，不是版本号区间。依据是实测反例：拿 v160 的类去顶
  MindustryX（160.1）⇒ `NoClassDefFoundError: arc.util.OS$$ExternalSyntheticOutline0` 直接崩。
  补丁改的是字节码，合成类 / 内部类每个构建都不同 ⇒ 只能精确匹配。
- 一个包可以带多个 target（同一份改动、不同游戏版本各一份产物）；同一 sha256 写两次 = 拒绝。
- 校验三道（失败码 → 人话在 `PatchText`）：结构（schema / id / name / version / targets）、
  哈希（64 hex）、路径（dex/assets 必须在自己那个 `targets/<sha>/` 下的**单层文件名**，
  整条路径过 `PatchManifest.safeRel`：不许 `..` / 盘符 / 反斜杠 / 前导 `/` / 空段）。
- 上限：单 dex 64 MB、素材 128 MB、整包 256 MB、条目 4096 —— 只是防坏包写满盘。

## F27.3 存储与启用状态

```
app_hub/patches/<id>/<version>/          ← 内部存储（ART 只认内部 + 只读，ref/48）
├── patch.json                           ← 原字节副本（不是重新序列化）
├── <apkSha256>.dex                      ← 只读
└── <apkSha256>.assets.zip               ← 只读（可选）
```

- 外部 hub **只放报告**（`report-patch.txt`），不放可加载物。
- 启用状态在 `config.json` 的 `patch_enabled`，**按「启动项（实例）」存**（第 353 轮起）：
  `{ "<实例键>": ["<id>@<version>", …] }`，实例键 = `Versions.instanceKey` =
  `<版本 key> + NUL + 槽>`（版本 key：已装 = 包名，导入 = `import:<文件名>`）。
  ⚠️ 同一个版本绑多个槽 ⇒ 每一行（启动项）各开各的；`config_version` 从 2 升到 3，
  旧格式（只按版本 key）由 `Config.migratePatchKeys()` 搬到这个版本**主行**的实例键。
- **不做引用计数**：补丁天然是"全局一份 + 版本级启用列表"，不存在多槽副本（与设计草案 §3 的
  设想不同，实现时简化；少一类"数错了就删错文件"的 bug）。
- 删除补丁记录：**启用中拒绝**（先停用），避免下回启动找不到。
  ★ 2026-11-12 第 357 轮起：删除 = **挪进中转站**（`<hub>/patches-trash/`，不再裸删），
  保留份数走**整槽那一档**（默认 3，`Trash.keepFor(Kind.PATCH)`；设置页那一项现在写
  「整个槽 / 游戏版本 / 补丁」）；能从「中转站」放回 `app_hub/patches/<id>/<version>/`，
  放回去是**未启用**状态。用户原话：「游戏补丁中转站保留个数按照哪个算的啊」—— 答案原本是"根本没有中转站"，这轮补上了。
- 首次启用前告知一次（"这会替换游戏代码，可能让游戏崩"），看过记 `patch_warned`。

## F27.4 冲突检测（判据 = dex 里实际的类，不信清单）

清单里的 `classes` 是生成器单方面声明，写错/少写就能让两个补丁改同一个类而"看起来不冲突"
⇒ 宿主直接用 `PatchDex` 读补丁 dex 的 `class_defs`（`type_ids` → `string_ids` → MUTF-8），
素材冲突则枚举 `assets.zip` 条目并**剥掉 `assets/` 前缀**（= AssetManager 里的键）。

三条规则（任一命中 = 拒绝启用，并**点名**对方）：

1. **同一个补丁的另一个版本**已启用（同一 id 两个版本同时生效没有意义）；
2. **两边实际定义的类有交集**（后注入的静默赢 ⇒ 另一个的部分改动失效）；
3. **两边改的素材路径有交集**（addAssetPath 后挂覆盖先挂，同样是静默覆盖）。

只与会**匹配当前 APK** 的 target 比：不适用的补丁本来就不会被注入，拿它拦没道理。

## F27.5 启动接线（Injector / GameSlot）

```
GameSlot.handle
  ├─ Patches.resolve(ctx, apk, 实例键)     ← 键 = 版本 key + NUL + 这一局实际用的槽（第 353 轮起）
  │                                         只在真有启用记录时算 APK 的 sha256（80 MB）
  │    ├─ 记录不存在 / 目标不匹配 / 文件缺失 ⇒ problem（不硬上）
  │    └─ 启动期再查一遍冲突（防御手工改 config）+ 后一条整条跳过
  ├─ plan.patches = [dex, assets?, label]
  └─ Injector.launch
       ├─ ① 量 hostDex = dexElementCount(baseCl)（**注入游戏 dex 之前**）
       ├─ ① 注入游戏 dex（append）
       ├─ ① 每条补丁 insertAt(hostDex + 已插入数)   ← 宿主之后、游戏之前
       ├─ ① 验证 base CL 能解析游戏入口类（**必须放在补丁之后**，否则入口类被原版抢先加载）
       ├─ ② native / ③ 置 loaded / ④ 资产链 = base + assetDeltas + 补丁 assets（后挂覆盖）
       └─ ⑤ startActivity
```

- **失败回退粒度 = 整条补丁**：单条注入失败只跳过它、启动继续（问题写进 `hub/report-patch.txt`）；
  这也符合"补丁坏了不该让游戏完全打不开"的取舍。
- 启动报告 `hub/report-launch.txt` 会写：宿主 dex 条数 / 每条补丁注入到哪个下标、耗时、跳过原因；
  **没有问题时删掉旧的 `report-patch.txt`**（不让过期结论挂在界面上）。
- 耗时（真机）：8.5 MB dex 注入 20 ms、小 dex 1 ms、素材 `addAssetPath` 1 ms。

## F27.6 界面（版本页 → 补丁页）

| 位置 | 内容 |
|---|---|
| 版本页 | 新增一行「补丁」；副标题 = 已启用 N 个（0 个时用静态句"替换这个版本的游戏代码"） |
| 主界面版本行 / 版本页标题卡 | 副标题前缀 **`补丁 N · …`**（有启用补丁时）—— 光写「原端/改端」看不出"这一版其实被补丁改成 fork 了"（第 345 轮用户反馈）；「继续上次」按钮**不带**补丁状态（用户：「要么那个继续上次不显示补丁吧」—— 按钮回到一行短文本） |
| 补丁页（`PatchesActivity`） | 身份卡（版本名 + APK 短哈希 + 已导入几个）/「导入补丁包」/「上次启动：有补丁没应用」卡（点 = 知道了）/ 补丁行 / 空态 |
| 补丁行 | 「名字 版本」+「N 个类 · 状态」；状态四态：已启用 / 未启用 / 不适用这个 APK / 文件缺失 |
| 详情卡（`CardStack`） | **补丁的元信息**（标识 / 作者 / 适用版本 + APK 短哈希 / 类数与素材数 / 体积 / 制作工具 / 导入时间 / 说明）+ 关闭 / 删除 / 启用·停用。**不列替换的类名** —— 使用者要判断的是"这是谁做的、给哪个版本、多大"，不是替生成器审代码（2026-11-10 用户反馈） |

判据收口：状态 = `PatchesActivity.stateOf(record, apkSha, enabled)` 一处；
页面只调用 `Patches`（导入 / 启用 / 停用 / 删除都只有一份实现）。

## F27.8 自检（`SelfTest.patches`，6 层）

1. **dex 解析**：夹具 dex 恰好 2 个类（`PatchProbe` + 匿名内部类）；拿本 APK 的 `classes.dex`
   当神谕（能认出 `Patches` / `PatchManifest` / `PatchesActivity`，认不出游戏类与夹具类）；
   垃圾字节必须解析失败。
2. **清单矩阵**：schema / 哈希 / 路径穿越 / dex 不在自己哈希目录 / 缺 name / 空 targets /
   targets 非数组 —— 每条期望**对得上的码**；`safeRel` 正反矩阵。
3. **导入往返**：真 dex → 内部存储 + 只读 → 扫描读回 → 类/素材键可重新解析 → 重复导入拒绝。
4. **冲突三条 + 反向**：同类冲突；类不相交但素材同路径也冲突；两者都不撞必须**不**冲突。
5. **启动解析**：匹配 → loaded；换 APK → 只报 `no_match`；没启用 → 空。
6. **状态 / 文案 / 跳转 / 素材规矩 / 导入负例**：四态判据、每个错误码都有人话且不印 null、
   版本页 → 补丁页 Intent 的类与 extra 键、素材包必须在 `assets/` 下、坏 zip / 缺条目 /
   坏 dex / schema=2 / 条目 `..` 全部拒绝且不留半条记录。

夹具：`app/assets-dev/patch-fixture/probe.dex`（2.6 KB，**只进 dev 包**）。
真机结果：**1992 / 0**（比第 344 轮的 1941 多 51 条；独立校验 B1/B2 的修复又补了 7 条断言）。

## F27.11 这轮踩到的坑（复查时先看这几条）

1. 🔴 **`adb push <文件> <目录>/` 在本机组合（Windows adb + 这台 ROM）会把目标文件名截成前几个字符**
   （`probe-smoke.mdp` → `pro`）—— 症状是 app 里"文件不存在"而 push 报成功。
   夹具/输入一律**显式给完整目标文件名**：`adb push x.mdp /sdcard/.../x.mdp`。
2. ⚠️ 用 PowerShell `>` 重定向抓设备文件会写成 **UTF-16**（带 BOM）—— 改完推回去会毁 `config.json`。
   抓/回写设备文件用 `adb pull` / `base64` 中转，或 `run-as` 内的 `cp` + `mv`。
3. ⚠️ `dev_m3_selftest` 在**刚启动就触发**时，`⑤ CAS 对象池` 那条断言可能被并发的自动备份干扰
   （40.8 MB → 41.0 MB）。稳妥做法：先正常启动 `MainActivity` 等约 10 s，再发 `--es dev_m3_selftest 1`
   （本轮第二次跑 = 1985 / 0；修完独立校验的 B1/B2 后 = **1992 / 0**）。
4. ⚠️ i18n `SRC-02` 台账随新日志增长：Injector 23 → 32（补丁注入报告行）→ **36**（独立校验 B1/B2
   的修复又加 4 行启动报告）—— 都只进 `report-launch.txt`，与既有 23 条同族。
5. 🔴 **补丁 dex 必须落在内部存储且只读**；放外部 hub 会被 ART 拒绝（`Writable dex file ... is not allowed`
   / SELinux），复制/置只读与 `Importer` 同一套纪律。
6. 🔴 **自己算 DEX 的 Adler-32 时累加器必须用 `long`**：经典实现按 5552 字节一块延迟取模，块内
   累加和最大约 `255*5552*5553/2 ≈ 3.9e9`，用 `int` 会溢出 ⇒ 把**好 dex 判成 checksum 不符**
   （本轮自检实测：自己的 `classes.dex` 被误判；改成 `long` 后全绿）。
7. ⚠️ **安卓的 `ZipOutputStream` 拒绝同名条目**（`ZipException: duplicate entry`）⇒ "同名条目要拒绝"
   这类判据的夹具得在 PC 上造（本轮：`assets-dev/patch-fixture/dup-entry.zip`，dev 包才带）。

## F27.12 独立校验（第 345 轮，队友 `patch-verify`）

> 报告落盘：`.dsh/research/2026-11-10-patch-v1/VERIFY.md`（不入库）。约束：只读源码、不跑构建、不碰设备。

| # | 分项 | 结论 | 关键数字 |
|---|---|---|---|
| ① | dex 类名解析器独立复算（JDK8 单编 `PatchDex` + Python 从零实现） | **PASS** | 三份 dex **类名集合与顺序逐类全等**：2 / 2 / **12162**；大 dex 另做 907 条抽样 bad=0 |
| ② | 静态审查 | **FAIL → 已修** | 1 高危（B1）+ 2 中危（B2/B3）+ 9 低危/nit（B4~B12） |
| ③ | `.mdp` 夹具独立复核（自写 zip/json/dex 检查） | **PASS** | 目标 APK 哈希现场复算命中；2 正例全绿、4 负例各只坏在声明处 |

**B1（高危，已修）**：`Injector.injectPatches` 里 `at = after` 把"合并后总条数"当插入下标 ⇒
第 2 条起补丁被追加到**游戏 dex 之后**、同名类永远被原版覆盖（静默失效）。
真机日志 `补丁[2] … @3` 就是证据。修法：`at = hostDex + 已插入元素数`，并抽成纯函数
`Injector.patchInsertIndex()` 由自检钉住；修后真机复验 = `@1` / `@2`。
**B2/B3（中危，已修）**：`makeDexElements` 把坏 dex 的失败塞 suppressed **不抛** ⇒ 用
`after <= before` 判失败；素材只挂 `applied=true` 的补丁；`dexElementCount` 失败不再回退 0
（否则补丁会被前插到宿主之前，可能顶掉宿主类），改为**跳过全部补丁并记 problem**。
**低危（已修/已处理）**：B4 已启用时先报 `enabled` 再查冲突（不再"点名自己"）· B5 `setText(resId)`
改 `Trans.get` · B6 启用（含冲突检测）挪后台线程 · B7 问题卡加"点一下关掉"提示、删死资源
`patch_page_lead` · B8 预览恰好 12 条时不多打省略号 · B9 外部名字在**解析处**清洗成单行 ·
B10 版本页计数改用 `enabledCount`（跳过孤儿引用）· B11 去掉 `sha256Of` 的 `path|len|mtime` 缓存
（被同长同 mtime 替换时会拿旧哈希去匹配 APK）· B12 拒绝 zip 同名条目 · 另：`PatchDex` 增加
file_size + Adler-32 校验（B2 的根因防线）。

★ 后续（同日用户反馈）：**详情卡改成元信息**（标识 / 作者 / 适用版本 / 数量 / 体积 / 工具 / 导入时间 / 说明，

## F27.13 第 353 轮（2026-11-11）：启用状态改成**按启动项（实例）**

> 用户：「游戏补丁的启用状态应该绑定实例吧」。

**为什么**：一个版本可以绑多个槽、每绑一个槽多一行（启动项）。原来按版本 key 存，
给一行开了补丁，同一版本的另一行（另一个槽）也变成「已启用」—— 但用户只想让那个实例生效。

**改法**：
- 键 = `Versions.instanceKey(vkey, slot)`（版本 key + NUL + 槽；与 `Versions.rowKey` 同构）。
  NUL 而不是 `|`：版本 key（导入文件名可变）可能含 `|`，NUL 在 JSON / 包名 / 槽名里都不会出现。
- 全链路换键：`Config` 的 `patchRefs/setPatchRefs/patchRefVkeys/patchRefOwners`（参数文档写明是实例键）·
  `Patches` 的 `enabledRefs/enabledRecords/enable/disable/conflicts/resolve/enabledCount/enabledCounts` ·
  版本页 → 补丁页的 `patchIntent(c, vkey, slot)`（补丁页新增 `EXTRA_SLOT`，头部多一行
  「启动项：槽「X」」）· 主界面行上的 `补丁 N` 徽标按行取 ·
  **启动解析**在 `Data.prepareSlot` 之后取 `Data.currentSlot()` 拼实例键（`slot` extra 可能为空、
  远古包会改道 ⇒ 只有 currentSlot 是这一局真正落地的槽）。
- **迁移**：`CONFIG_VERSION` 2 → 3，`Config.migratePatchKeys()` 把旧键（只有版本 key）搬到主行实例键；
  幂等、没有旧键就不写盘。`Patches.instanceLabel()` 把带 NUL 的键翻成「游戏名 · 槽「X」」，
  用于「删补丁但还被启用」的拒绝文案。
- dev 口：`dev_patch_enable/disable` 支持三段 `vkey|slot|id@version`，也支持
  `--es dev_patch_enable 1 --es dev_patch_key <vkey> --es dev_patch_ref <id@version> [--es dev_patch_slot <槽>]`
  —— 设备 shell 会把 `|` 当管道，中文/带空格的槽名在命令行里很容易被拆坏。

**验收**（2026-11-11 真机，dev 变体）：
- 自检 **2011 / 0**（新增：实例隔离 / 实例键可拆回 / 迁移 / 迁移幂等；补丁页 Intent 多一个槽 extra）。

## F27.15 第 360 轮（2026-11-12）：崩溃处理与 :game 注入失败保持一致

## F27.19 第 381 轮（2026-11-15）：中转站往返会丢"只读位" —— 补丁整条被 ART 跳过

> 用户：「补丁机制好像又出问题了啊」。现象：补丁在界面上是启用状态，点启动后游戏照旧是原版。

**证据链（真机）**：

| 看哪 | 写了什么 |
|---|---|
| `hub/report-launch.txt` | `补丁数 = 1` · `补丁[1] … 跳过：注入失败 java.lang.reflect.InvocationTargetException` · `补丁注入完成 0/1` |
| `hub/report-patch.txt` | 只有一行 `bad_dex\|MindustryX (原版 + 补丁)` |
| `run-as … ls -la app_hub/patches/mdtx-1607/<ver>/` | `-rw------- … .dex`（**0600 可写**）；对照同机 APK `-r--------`（0400） |

**根因**：补丁库在**内部** `app_hub/patches`（ART 只认内部 + 只读），而所有中转站在**外部**
`<hub>/patches-trash`。`Patches.delete` / `Trash.restorePatch` 都要跨文件系统搬目录 ⇒
`renameTo` 必失败，退化成 `Trash.move → copyTree → Util.copyFile`，**新建出来的文件是 0600**，
只读位在路上丢了。Android 14+ 的 `DexPathList.makeDexElements` 对可写 dex 直接抛
`SecurityException: Writable dex file ... is not allowed`；反射调用又把它包成
`InvocationTargetException`，于是报告里只剩一个没有 cause 的类名。

**为什么第 357 轮上线中转站时没发现**：导入路径（`importPackage`）确实 `setReadOnly` 过，自检也钉着
`!ta.dex.canWrite()`；但"删除 → 放回"这条新路径是复制语义，自检当时用的是只写了 `patch.json` 的
假记录，没带 dex ⇒ 只读位丢失这条分支从未被走过。

**修法（唯一实现 `Patches.seal`）**：

1. `Patches.seal(dir)`：把记录目录里的 dex / assets.zip / patch.json 落成只读（只扫一层、只认载体名）。
2. 三处调用：导入收尾（替掉原来三处分散的 `setReadOnly`）、`Trash.restorePatch` 放回之后、
   `Injector.injectPatches` 注入前（兜最后一道，任何来源进库都能被纠正）。
3. `injectPatches` 的 `catch` 补 `logThrowable`（把 cause 链写进 `report-launch.txt`）——
   否则 `InvocationTargetException` 永远看不出真因。
4. 自检 +3：`seal` 直接置只读 / 中转站往返后 dex 仍只读（夹具带真 dex）/ 两个数的判据。
   `Injector.java` 的中文字面量台账 36 → 38（只进启动报告，同族）。

★ 判据（可复用）：**任何"挪到另一块存储再挪回来"的文件，都要问它靠什么属性生效** ——
dex 靠只读位，复制路径不会替你保留；重启 / 清理 / 备份同理。

## F27.20 第 402 轮（2026-11-20）：补丁 v2 —— **APK 容器**（整包补丁）

> 用户：「我是想让我们的补丁机制可以做到这个程度的修改」→「其实可以全都打成apk（和游戏本体安装包那样），反正这个版本没有发布倒是问题不大」。
> 研究数据：`.dsh/research/2026-11-20-game-as-patch/RESEARCH.md`；方案：`docs/plans/2026-11-20-补丁机制v2-整端替换.md`。

**做法**：补丁包不再要求自定义 `targets/<sha>/…` 布局，而是**一个 APK**（标准布局）+ **根上一个 `patch.json`**：

```
mdtx-b509.patch.apk
├── patch.json            ← 根上（不在 assets/ 下，不进游戏资产）
├── classes.dex / classes2.dex…
├── lib/<abi>/*.so        ← 可选；仅 role=game
└── assets/**             ← 可选；全量或差分
```

清单 `schema: 2`：`id / name / version / role / apkSha256（基座）/ gameVersion / note / tool`；
一个包只对一个基座（不再有 `targets` 数组）。判据实现：
- 识别 `PatchPackage.isApkContainer`：根上有 `classes.dex` **且** 有 `patch.json`（老 `.mdp` 的 dex 在 `targets/` 下 ⇒ 不会被误判）。
- 导入 `PatchPackage.validate`：清单 → 每份 dex（≤8 份、头/Adler-32/至少 1 类；合计 ≤128 MB）→ `assets/`（安全路径）→ `lib/<abi>/<name>.so`（仅 role=game；abi 白名单）→ 整包 ≤256 MB。
- 存储：`app_hub/patches/<id>/<ver>/patch.apk` + `patch.json`（都只读；`seal` 认 `.apk`）。
- 运行时（`Injector`）：`Patch.apk` 非空 ⇒ **整包注入**（`Reflect.injectDex` 直接吃 APK；多 dex 由 ART 展开）、
  `mountAssets` 直接把**补丁 APK** 挂进资产链、`loadNatives` 先在补丁 APK 的 `lib/<abi>/` 里找（补丁优先、基座兜底），
  补丁 native 的落点 tag = `tagOf(版本 tag + "+" + ref)`（不与基座互相覆盖）。
- `TargetFile` 增加 `apk` 分支：类集 / 素材键 / 计数 / native 键全部从 APK 里读；老 v1 记录（单 dex）行为不变。

**真机验收（HONOR ELP-AN00 / Android 16，2026-11-20）**：

- 夹具：`MindustryX-2026.10.10.B509-Android.apk`（79,203,298 B，**2 份 dex**）根上追加 `patch.json`
  （target = 官方 v160.7 的 sha `a298a773…`、`role: game`）⇒ 79,203,658 B。
- 走**正式链路**（`dev_patch_import` → `dev_patch_enable` → `dev_launch_key`），基座 = 官方 v1607：
  `report-launch.txt` 写 `补丁[1] MindustryX 注入 @1 elements 2→3 (80 ms)` / `libarc.so … [补丁 MindustryX]` /
  `资产链 = v1607.apk patch.apk` / 前置段 **119 ms**；截图是 **MindustryX 主界面**（`release build 160.7` + `MindustryX 2026.10.10.B509`、核心数据库 / QQ 群 / 检测更新）。
- 自检 **2353 / 0**（新增 ⑨ 组：整包识别 / 导入只读 / 类与 assets 读取 / native 键 / 启动解析 / 普通补丁带 lib 拒绝 / 清理）。

**边界（v2 仍不做）**：清单 / 包名 / versionName、`resources.arsc`/`res/`、APK 根上的 classpath 资源（`vfxshaders/`）、
删除基座里的素材；普通补丁带 `lib/` 在导入时拒绝（避免"半个 native"）。

## F27.30 整端补丁崩溃回退：演练与两处修复（2026-11-21，第 413 轮）

目的：真机走一遍「整端（`role=game`）补丁崩了 ⇒ 自动停用 ⇒ 回退官方本体」，验证这条安全阀不是纸面上的。

探针：手工造 `crashlab.patch.apk`（1,414 B；根 `patch.json` schema 2、id `crashlab`、`role=game`、`apkSha256` 指向官方 160.7；`classes.dex` 916 B，`mindustry.android.AndroidLauncher extends Activity` 的 `onCreate` 直接抛 `RuntimeException`）。用 `dev_patch_import` 导入、`dev_patch_enable` 启用（**两项都要显式 extra**，见 F27 既有条目）、`dev_launch_key` 拉起。

### 发现 1：整端补丁在游戏自己的崩溃转储初始化前就炸 ⇒ 一个字节都没有

`Patches.noteGameCrash` 只认数据根 `crashes/crash_<毫秒>.txt`（游戏命名），且要求毫秒 ≥ 启动记录。整端补丁换掉入口类，`AndroidLauncher.onCreate` 一进来就抛，此时 Mindustry 的转储还没初始化 ⇒ 没有报告 ⇒ 不提示、不自动停用。

修法（`Crash.java` / `GameSlot.java`）：

- `Crash.installForGame(ctx)`：`:game` 进程里、槽准备完、拉起游戏之前装一个兜底 handler（先写报告再交回旧 handler）。
- `Crash.writeGameFacing(...)`：按**游戏那份命名**写 `crash_<毫秒>.txt`，头部多一行 `备注：来源：启动器兜底（:game 启动期，游戏自己的崩溃转储尚未初始化）`。
- 落点用 `Data.dataRoot(ctx)` ⇒ 远古包（build ≤146，数据根就是 `files/`）也落在实际根上，`noteGameCrash` 读得到。

### 发现 2：`:probe` 进程也在跑启动恢复，把「自动停用」写回启用

`LauncherApp.onCreate` 里整段 F0 迁移 + `Recovery.runNow` 在**每个进程**都跑。`:probe` 里 `Data.gameAlive` 同样为 false ⇒ 它和主进程各持一份 `Config` 内存副本、先后写 `config.json`，把主进程刚写下的「自动停用」又盖回启用（现场：`report-patch-crash.txt` 已有 `crash_disabled_game|Crash Probe|crashlab@1.0`，config 里 crashlab 仍在）。

修法：`LauncherApp` 把这段收进 `startupRecovery()`，只在 `Util.isMainProcess(this)` 时执行；`Config.get().load(this)` 仍对所有进程执行。

### 验证结果（HONOR ELP-AN00 / Android 16）

- 启动 ⇒ `:game` 崩；兜底报告 `files/crashes/crash_1795260797342.txt`（2,196 B，头 `当前槽：crashlab`、`数据根：…/files`、备注为启动器兜底）。
- 冷启主进程 ⇒ `hub/report-recovery.txt`：`patch auto-disabled after crash: Crash Probe`；`config.json` 的 `patch_enabled` 里 crashlab 消失（只剩 patchlab 的 mdtx-1607）⇒ **自动停用落盘**。
- 自检：槽还停在 `crashlab` 时 2409 / 8（8 条全在图集/配色那一组，与本次改动无关）；拨回 `patchlab`、清掉演练留在 `hub/patches-crash.txt` 的结论后 **2417 / 0**。

### 仍未覆盖的缺口：崩溃提示

`CrashAlert` 的监视器在 `MainActivity` 起来时把「最新一份」当快照，`catchUp` 又依赖游戏写的 `launchid.dat`；这次崩在游戏写 `launchid.dat` 之前 ⇒ 安全阀有效，但界面上没有「整端补丁崩了、已回退」的那句话（`crash_alert_last` 没有推进）。要补需要新的判据（例如启动器自己记「这次启动有没有走完」），不在本轮范围。

## F27.21 第 403 轮（2026-11-20）：`role=game` 的产品语义 —— 「整端」

> 承接 F27.20 的"能力已通、语义没做"。这轮只补语义，不动存储/注入格式。

**独占（硬约束，两道门）**
- 启用时（`Patches.enable`）：`C_ENABLED` 之后、冲突检测之前判 role ——
  ① 要启用的**是整端**且这个启动项上已经有别的补丁 ⇒ `C_GAME_LAYER`（detail = 已有的那些名字）；
  ② 要启用的**不是整端**、但已有整端 ⇒ `C_GAME_LAYER`（detail = 整端名）。
- 启动解析时（`Patches.resolve`）：`gameSeen` 记账 —— 整端只在**第一位**（之前没有任何补丁）才加载，
  且整端之后再来的补丁一律跳过并记 `Problem(C_GAME_LAYER)`。两道门都判，是因为启用记录可能被外部改写
  （`config.json` / 插件写口），不能只信启用那一刻。

**界面说法（同一份判据 `PatchManifest.isGame()`，别处不再各自判）**
- 类型词：有整端 ⇒ `version_type_full`（**整端**），压过"有补丁 = 半改端"；
- 主页行副标题：整端写 `patch_badge_game_fmt`（`整端 <名字>`），**不再**写「补丁 N 份」；
- 版本页副标题：`subtitle_patch_game_fmt`（`整端 <名字> · 来源 · 大小 · 备份`）；
- 补丁页行副标题：`patch_row_sub_game_fmt`（`整端 · N 个类 · 状态`）；详情第一行后追加
  `patch_detail_game_note`（"这是一整份游戏本体：会替换代码、素材和 native，并独占这个启动项"）；
- 首次告知：整端用 `patch_warn_game_body`（更强的说法）。⚠️ "只告知一次"的记账是**普通补丁**的，
  整端**每次启用都再告知一次**（整端启用频率极低；不能被"以前启用过小补丁"吞掉）。

**崩溃文案（两句话不能混）**
- 整端崩了 ⇒ `noteGameCrash` 记 `C_CRASH_DISABLED_GAME`（普通补丁仍是 `C_CRASH_DISABLED`），
  补丁页原因与崩溃弹窗都说"**回退到官方本体**"（`patch_err_crash_disabled_game_fmt` /
  `crash_patch_disabled_game_fmt`）；弹窗用 `Patches.crashDisabledWasGame(ctx, slot)` 选句（按 `# slot` 过滤报告）。

**自检（2361 / 0）**：新增 8 条 —— `typeFor`/行名整端、主页与版本页副标题、两个新码有人话、
普通补丁不算整端、整端独占**双向**（各自点名对方）。

## F27.26 第 408 轮（2026-11-21）：native / 属性判据按「实际生效的载体」

整端补丁（`role=game`）会换掉游戏的代码 / native，但第 407 轮为止，三项判据都只读**基座**。
第 408 轮由用户复查发现并修掉：

- **ABI**：`Compat.pickAbi(ZipFile)` 只枚举基座自己的 `lib/`。纯 32 位设备上，基座空壳只带
  `arm64-v8a`、整端补丁带 `armeabi-v7a` ⇒ 导入期就被 `compat_reject_abi` 挡掉，尽管补丁能跑。
- **页对齐**：只读基座那条 so，真正 `System.load` 的却是「补丁优先」那条 ⇒ 验的和用的不是同一个
  文件。16 KB 页设备上 4 KB 对齐的补丁 so 会到启动时才炸；空壳的 9 字节假 so 还会让探测返回 0，
  `alignOk()` 保守放行。
- **属性注入**：`hasProp` 只扫基座 dex。空壳基座恒 false ⇒ 永远走改名交换；更危险的反向是
  「基座 160（有属性）+ 整端补丁里 ≤146 的老游戏（不认属性）」⇒ 判成属性注入，游戏却写默认根，
  跨槽串数据。

现在按什么判：

| 判据 | 现在按什么判 |
|---|---|
| ABI | `Compat.pickAbi(List<ZipFile>)`：基座 ∪ 已应用补丁的 `lib/` 并集（`Injector.loadNatives` 里先打开补丁包再选） |
| 页对齐 | `Compat.maxAlignOf(真正选中的那个 zip, entry)` + `alignBlocks(align, pageSize)`；不合格抛 `launch_err_native_align_fmt`（点名库名 / 对齐 / 页 / 来源） |
| 属性注入 | `GameSlot.needsLegacySlot(apk, it, res)`：补丁的 dex 定义了 `AndroidLauncher` 就看补丁的 `hasProp`，否则看基座 |
| 导入期 / 启动预检 | 只拦「基座没有入口类」（`!cp.hasEntry`）；ABI / 对齐留到 `Injector.loadNatives` |

`Data.slotNameFor(ctx, target)`：`GameSlot` 要在 `prepareSlot` **之前**解析补丁（实例键 = 版本 + 槽），
槽名先按 prepareSlot 的同一套规则算出来（空 = 当前槽 / `shared` 原样 / 不合法 = 当前槽）；
算出真实 `ikey` 后再核对一次，不一致就重新解析。

**验证**：自检新增 6 + 4 条（基座无 ABI 仍 `runnable` / `abiDeferred` / `alignBlocks` 真值表 /
基座 ∪ 补丁并集选 ABI / 补丁 so 对齐读得到 16384 / 基座没有 so ⇒ 0）；真机 **2408 / 0**
（`report-m3-408.txt`：基线 2363 + 第 409~411 轮插件接口用例 + 本轮 10 条）。

## F27.29 第 412 轮补充（2026-11-21）：根 classpath 资源（`vfxshaders/`）实验

**为什么**：F27.20 / 研究阶段一直写着"APK 根上的 classpath 资源换不掉"，而整端补丁（MDTX）恰恰带 29 个
`vfxshaders/*.frag`；空壳基座（653 B，没有根资源）能跑起来这件事本身就和那句结论矛盾 —— **做个实验钉清楚**。

**怎么读这些文件**（源码）：`arc.fx.FxFilter` 的构造器调 `Core.files.classpath("vfxshaders/…")`
（`javap -c` 在 160 桌面 jar 里确认）⇒ 走的是 **classloader 的 `getResourceAsStream`**，不是 `AssetManager`。

**探针**（`.dsh/research/2026-11-20-game-as-patch/resprobe/`，`dalvikvm` 在 mdt35 上跑）：

| 探针 | 做法 | 结果 |
|---|---|---|
| `ResProbe` | `PathClassLoader(base:patch)` 直接读根资源 | stub（缺 29 个）+ b509 ⇒ **读得到**（len 640 …） |
| `ResProbeB` | 按 `Injector` 的做法，把补丁的 dex 元素 append 进基座 `DexPathList` | 见下 |

`ResProbeB` 用一份 919 B 的 `override-root.apk`（只有 `classes.dex` + 改过的 `vfxshaders/zoom.frag`，51 B）：

- 顺序 A（**base 元素在前、patch 在后**）：`zoom.frag -> len=207 first=0xa` ⇒ 基座赢；
- 顺序 B（**patch 元素在前、base 在后** = 我们真实的注入顺序：宿主、补丁…、基座）：
  `zoom.frag -> len=51 first=0x2f` ⇒ **补丁赢**。

**踩到的坑**：拿 b509 的副本改一个条目但**不重签**，在顺序 B 下读根资源会抛
`java.lang.SecurityException: SHA-256 digest error for vfxshaders/zoom.frag` ——
classloader 读根资源走 JarFile 校验 ⇒ **改过条目的补丁 APK 必须重新签名**（`assets/` 走 `AssetManager`，不受这条影响）。

**结论**：

- 根 classpath 资源**能换**：基座缺的由补丁补上；同名条目因为补丁 dex 元素排在基座之前，**补丁覆盖基座**；
- 空壳基座（没有 `vfxshaders/`）能跑 MDTX，根资源就是从补丁 APK 读的 —— 这和 F27.22 的观察对上了；
- 仍然换不掉的只有：清单 / 包名 / versionName、`resources.arsc` / `res/`、以及"删掉基座 assets"（只叠加不删除）。
- 产物侧要求：补丁 APK 必须有效签名（改条目要重签），否则它自己的根资源会在读取时被校验拦下。

**证据**：`resprobe/report.txt`（三种探针的原始输出与夹具说明）。

## F27.31 整端补丁崩溃提示（第 414 轮）

F27.30 留了个洞：**安全阀有效、提示哑**。整端补丁在 `mindustry.android.AndroidLauncher.onCreate`
就崩时，游戏自己的崩溃转储还没初始化 ⇒ 不写 `launchid.dat` ⇒ `CrashAlert.catchUp` 按老判据
（"有没有游戏写的 launchid.dat"）判成"这次是正常退出"，界面上一个字都没有。

### 判据：启动护栏（launcher 自己落的一道闸）

- `GameSlot` 在 `Injector.launch(...)` **之前**调 `CrashAlert.markLaunched(this, slot)`，
  把「毫秒时间戳 + 槽名」原子写进 `hub/launch-guard.txt`（写不进去只记日志，**绝不许挡启动**）。
- `catchUp`：没有 `launchid.dat` 时改看护栏 —— 只有当前槽 `crashes/` 里存在**比护栏时刻更新**的
  报告才提示（`launchedAt` 核对槽名、`crashedSince` 按文件名毫秒判、`reportMs` 两种命名都认）。
  上次正常退出 ⇒ 没有更新的报告 ⇒ 不烦用户。

### 兜底报告要按"游戏崩了"讲

`:game` 里的兜底报告也是管理器写头（首行 `MDT 管理器 —— 崩溃报告`），老的 `judge` 见 `MDT` 开头
就判 `KIND_LAUNCHER` ⇒ 弹窗说「管理器出错了 … 这是管理器自己的崩溃报告（不是游戏）」（真机截图）。

- `Crash.dump(..., note)` 在备注行之后多写一行**语言无关**标记 `!mdt-fallback=game-v1`；
- `CrashAnalysis.Report.fallback` 由这行标记判定（**不许**拿会被翻译的文案当判据 —— 门禁 `SRC-01` 会拒）；
- `judge`：`if (r.launcherOwn && !r.fallback)` 才进 `KIND_LAUNCHER`。

### 迟到的安全阀要补一句

崩溃当时监视循环里 `Patches.noteGameCrash` 可能被 `WriteGate.blockedInstance` 挡住（`:game` 还没收尸）
⇒ 那一刻的弹窗**没有**「已自动停用」；等 `Recovery` 下次启动真停用时，同一份报告已被认领，不会重弹。
`Recovery` 停用成功后就调 `CrashAlert.toastPatchDisabled(...)` 补一句系统浮层
（句子与弹窗共用 `disabledSentence`，整端仍说"回退到官方本体"）。

| 场景 | 结果 |

| 启动整端崩溃补丁 | 对话框标题「游戏崩了」、正文「认不出是哪个模组…」（不再是"管理器出错了"），截图 `dr414.png` |
| 下次启动 Recovery 停用 | `report-recovery.txt` → `patch auto-disabled after crash: Crash Probe`；浮层「整端「Crash Probe」在这次崩溃后已自动停用，游戏会回退到官方本体。」，截图 `toast414.png` |
