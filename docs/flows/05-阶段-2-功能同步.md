### F5 —— 自动备份 ★ 已完成（语义已按桌面版源码修正）

> ✅ **已完成（2026-10-01）**：新建 `AutoBackup.java`，接入 `MainActivity`；策略入口在**存档页槽菜单**第 4 项。
>
> ★★ **本节原「目标」写错了，必须显式更正**。原文是：
> > 「启动某版本前，若当前槽有数据且比上次备份新 ⇒ 自动快照，超上限删最旧。」
>
> **实测核对桌面版启动器的对应实现**：
> ```python
> playtime = (time.time() - start) / 60
> if auto_backup and playtime >= min_playtime:   # 默认 20 分钟
>     create_backup()
> ```
> ⇒ 门槛量的是**上一局游戏的运行时长**，触发点在**游戏退出之后** ——
> **不是**"启动之前"、也**不是**"比上次备份新"那种启发式；
> 而"超上限删最旧"（`trim`）确实存在，只是它发生在**快照之后**。
> 早期 BACKLOG 写的"启动之前备份"是**推断，与源码不符**，本轮实现以源码为准。
>
> **Android 等价实现（启动时记账 → 回到启动器结算）**：
> 1. `startVersion()` 在拉起游戏前调 `AutoBackup.noteStart(key, slot)`，把「这次玩哪个槽 + 开始时刻」写进 `Config.session`；
> 2. 用户退出游戏、`MainActivity.onResume()` 触发 `AutoBackup.settle(this)`：读 session 算
>    `minutes = (now - at) / 60000`，**先清账再判断**（`Config.sessionClear()`，避免每次 `onResume` 重复触发）；
> 3. `enabled && minutes >= minMinutes` ⇒ 起后台线程 `Backup.create` 快照 + `trim()` 裁剪到上限。
>
> **与桌面版对齐**：默认 `auto_backup=True` / `min_playtime=20` / `max_backups=20`（面板默认值照抄）。
> **刻意的偏差**：备份放**后台线程**、失败**不弹 Toast**（后台行为不打断用户；最常见的"失败"是**新槽还没内容**）；
> `runNow()` 把所有异常吃在里面，结果一律写 `hub/report-autobackup.txt`。
>
> **进程互斥**：`beginWork()/endWork()` 计数 + `awaitIdle(ms)`；`startVersion()` 会先 `awaitIdle(8000)`
> 等备份收尾，防「备份读槽」与「游戏写槽」打架。
>
> 实测（证据 `evidence/f5-slot-policy.png`）：端到端跑通（`report-autobackup.txt` 结果=完成、session 已清账、
> 快照 `12 个文件 5.6 KB` label=自动备份）；上限自动清理（跑 4 次、上限 2 ⇒ 只剩最新两份）；
> 策略对话框 = CheckBox + 两个数字框；槽行摘要显示 `自动备份：玩满 7 分钟 · 最多留 9 份`。

**前置**：F3（开关/门槛/上限）。**零新原语**：`Backup.create` / `Backup.list` / `Backup.delete` 全都有。

> 产物基线 **112812 B**；`dev_m3_selftest` 36/36；15 张实拍（`evidence/f5b-*.png`）。
> 完整根因与证据：`REFERENCE-android-adaptation.md` **§26**。

这两件事，本质是**上一批 F3/F5 留下的两个缺口**：

| # | 问题 | 真实缺口 |
|---|---|---|
| ① | 竖屏滚不动 | F2c 只验证了横屏"能不能滚"，**竖屏被默认成"刚好一屏、不用滚"**——这个结论从来没被实测证伪过，而它**是错的** |
| ② | 存档槽设置的 UI 与全站风格脱节 | `promptPolicy()` 是**代码手拼裸控件**（`new EditText` 逐个 `addView`）+ 系统默认对话框 ⇒ 与全站卡片风完全脱节 |

#### ① 竖屏滚动 —— 根因：`ScrollView` 的 `paddingBottom` 只等于导航栏 inset

F2c 给根 `ScrollView` 加 insets 时，`applySystemInsets()` 把**四边**都写成 padding。
竖屏下 `paddingBottom` = 导航栏 inset（≈40px），**恰好把内容顶出视口**，
于是产生了一个"能用、但只有 119px"的滚动范围。三个后果：

1. 滚到底时**末卡贴住导航栏**（间隙 = 0），观感像"被截断"；
2. 119px 在慢拖时几乎察觉不到 ⇒ 用户以为"不能滚"；
3. F2c 的验收写的是"竖屏内容 2265px < 视口 2395px，不产生滚动" —— **与实测矛盾，本节予以更正**
   （实测竖屏确实可滚，只是范围很小；该结论已在下文 F2c 节标注）。

**修法（最小改动）**：不去动 `applySystemInsets()`（它给四边加 padding 是**对的**，
导航栏在横屏时在右侧，去掉 left/right 会重蹈 §23 的覆辙），
而是在三页的内容 `LinearLayout` **末尾各加一个占位 `View`**：

| 文件 | 做什么 |
|---|---|
| `app/res/values/dimens.xml` | 新增 `page_bottom_space = 24dp` |
| `activity_main.xml` / `activity_saves.xml` / `activity_settings.xml` | 内容 `LinearLayout` 的**最后一个子节点**加 `<View layout_height="@dimen/page_bottom_space" />` |

这样做**不改变 insets 语义**，纯 XML，可回退。
> ⚠️ 曾考虑的另一方案（`applySystemInsets` 只写 top/left/right，尾部留白改为给内容节点加 `marginBottom`）
> **被否决**：那会让「末卡贴底」的观感重新出现在**横屏**，且要改一处公共工具 + 三个 layout。

**验收（真机）**
- 竖屏滚动范围：`ver_container` 由只能位移 119px → **197px**（`input swipe 20 2400 20 400 1000` 慢拖）。
- 滚到底：`ver_container [0,1379][1224,2492]`，`ver_conflict` 底 = 2381px，导航栏顶 = 2570px
  ⇒ **间隙 189px**（原来是 0）。
- 慢拖回顶：`status_box [52,344][1172,481]`、`ver_container [0,1576][1224,2689]`，与初始一致（无 padding 累积）。

### F6 —— 存档 / 备份导出到共享存储 ✅ 已完成（2026-10-01，第二十轮）

**目标**：`.msav` 只有"进"没有"出"；Android 11+ 起 `Android/data/<pkg>/` 对文件管理器和 MTP 都不可访问
（本机实测：只能靠 adb 进）⇒ 用户**没有办法**把存档拿出来。

**前置**：无（F10 会让导出列表更好看）。

**改动面**

| 文件 | 做什么 |
|---|---|
| `Msav.java` 或新 `Exporter.java` | 写向：`ContentResolver.openOutputStream(uri)` + 流式拷贝（`Importer` 的反向） |
| `SavesActivity` | 单文件导出：每个 `.msav` 行加"导出"；整槽导出：把快照目录 zip 一份再导出 |
| `AndroidManifest.xml` | 不需要新权限（SAF 走 `ACTION_CREATE_DOCUMENT`） |

**步骤**
1. 单文件导出：`Intent(ACTION_CREATE_DOCUMENT).setType("application/octet-stream").putExtra(EXTRA_TITLE, 存档名 + ".msav")`
   → `startActivityForResult` → 回来 `openOutputStream` 流式写。
2. ⚠️ **文件名要保留非 ASCII**（产品三约束：玩家看到的存档名）。`Msav.safeName` 只用于**落盘到游戏目录**时，
   导出到 SAF 时**用原始名**，否则用户看到一堆拼音。
3. 整槽导出：`Backup.create` 出快照 → 用 `java.util.zip.ZipOutputStream` 打包 → 导出 `zip`。
   顺带解决"换机迁移"。
4. 反过来做"从 zip 导入整槽"（可选，后置）。

**验收**
- 导出的 `.msav` 能被 PC 端 Mindustry 打开（用桌面版实测一次），文件名正确。
- Android 11+ 上不请求任何存储权限就能完成（SAF 的意义就在这）。

**坑**
- ⚠️ 大文件别一次性读进内存（`byte[]`）—— mods 几十 MB，必须流式 + 8KB 缓冲。
- ⚠️ `ACTION_CREATE_DOCUMENT` 在个别 ROM 上返回的 uri 不可写 ⇒ 写失败要 catch 并给出明确提示，别静默。

**实现落地（第二十轮，真机验收）**

> **落地范围**：FLOWS 原步骤 **1（单文件导出）+ 3（整槽 zip）+ 2 的一半（原始名保留）**。
> 步骤 4（从 zip 导入整槽）**当时未做** —— 它要先有"解包回槽目录"的写路径。
> ✅ **已由 F6c 补上**（含导出口径从白名单升级成"全部文件"，见下一节）。
> 入口挂在**槽操作菜单**里，紧跟「恢复备份…」：`导出存档…` / `导出整槽（zip）…`。
> 实现细节与验收见 `REFERENCE-android-adaptation.md` §29；证据 `evidence/f6-*.png`（11 张）。

| 项 | 决定 | 理由 |
|---|---|---|
| 出口 intent | `ACTION_CREATE_DOCUMENT` + `CATEGORY_OPENABLE` + `EXTRA_TITLE` | 唯一**零存储权限**的出口；`EXTRA_TITLE` 是递原始（非 ASCII）文件名的唯一通道 |
| MIME | 单文件 `application/octet-stream`、整槽 `application/zip` | 存档 .msav 本质是 gzip 流，用 gzip 反而会被某些管理器二次解压；octet-stream 最中性 |
| 文件名 | **`f.getName()` 原样**，绝不 `safeName` | 存档名 = 玩家在游戏里看到的名字（见 `Msav.safeName`）。导向 SAF 时安全化等于把玩家存档名改没了 |
| 单文件导出 | `saves/` 列表 → setItems 选一份 | 与 `导入 .msav` 严格对称 |
| 整槽导出 | 「数据根全部内容 − `SLOT_EXCLUDE`」∩ 存在 **∩ 非空**，`ZipOutputStream` 打 zip | 口径与「备份」一致 ⇒ 解包丢回槽目录即可；槽目录里的缓存/日志不进包。<br>⚠️ **F6c 把口径从"备份白名单"改成「数据根全部内容 − 排除项」**（口径对齐/超越原生）；<br>★ **F19 把「备份」也改成同一个口径** ⇒ 现在两边**共用** `Data.contentRoots`，不再是"一个宽一个窄" |
| zip 压缩级 | `Deflater.BEST_SPEED` | mods 几十 MB，用户等着；压缩比不值那几秒 |
| 写入模式 | `openOutputStream(uri, "wt")`，抛则回落默认 | `"w"` 不截断 ⇒ 覆盖时旧内容尾巴会留在新文件后面。真机上系统其实会自动加 `(1)` 序号（见 REF §29.4），但**不能依赖 provider 都这么做** |
| 空目录 | 保留条目（`entry/`） | 否则解包后目录结构消失 |
| 条目名 | 相对基准目录、分隔符统一 `/`，保留非 ASCII | zip 规范；中文存档名不能变下划线 |
| 越界 mtime | 不 `setTime` | `ZipEntry.setTime` 对 1980 前 / 2107 后会抛，坏 mtime 在导入过的文件上真出现过 |
| 进度反馈 | 单文件后台线程 + Toast；整槽 `ProgressDialog` | 单文件几 MB 不值得打断；整槽可能几十 MB 必须给进度 |
| 空槽拦截 | **在打开 SAF 之前**就判 | 放到后面的话用户已经点了"保存"，系统先建出一个 0 字节 zip 我们才报错 |
| 游戏占用 | **只提示不拦截**（"建议先退出游戏"） | 导出是纯只读；对比备份/恢复是写操作必须拦 |

★ **本条顺手修掉两个真机踩出来的坑**：
① `Data.savesDirOf()` 会 `mkdirs` ⇒ "只读地看一眼有没有存档"会把空 `saves/` 造出来，
   进而污染空槽判定（改用 `new File(Data.dirOf(...), "saves")` 只读探测）；
② 槽的 `saves/` 空壳会被算成"有内容" ⇒ 导出一个几百字节的空 zip（判据加"非空"）。

### F16 —— CAS 存档备份（内容寻址对象池）✅ 已完成（2026-10-01，第二十五轮）

> **编号说明**：F16 排在 F15 之后，因为 CAS 是**先被实测改判、再动手**的（BACKLOG 4.5 / REF §32 →
> §33）。`F8`~`F14` 仍是预留计划项，不受影响。

**触发**：先实现 CAS 存储；旧备份的迁移方式定为 —— **自动迁移、不维护长期双格式兼容**。

**为什么值**：桌面端 27 份真实备份实测 **5.1 GB → 328.6 MB（省 93.7%）**；收益来自 `mods`
（占一份备份 74%、跨备份跨槽都不变）与 `saves`（复用率 96.2%）。套 Android 口径 20 份备份
**3.0 GB → 241 MB**。价值不在省空间，在**行为改变**：用户终于敢把保留份数留在 20 而不是被磁盘逼到 3。

---

#### ① 新增 `Cas.java`（对象池本体，模块边界最干净的一个类）

照抄桌面版的 `CASStore`。**它只认「目录 + 字节」，不认清单格式** ——
引用集由调用方（`Backup`）扫完清单后传进来。要抄齐的四个方法 + 两级分片：

```java
Stored put(File src, MessageDigest extra)      // 入库：流式读源文件 + 写 tmp + 按 sha rename
String sha256Of(File f)                        // 只算 sha256，不落盘
void   getTo(String id, File dst, boolean verify)  // 还原：写 .part → 校验 → rename
int    garbageCollect(Set<String> referenced)  // 只删"未引用 且 过了宽限期"的对象
Pool   scan(Set<String> referenced)            // 体检（与 GC 用同一套"可删"判据，否则报告对不上）
```

关键是**布局**：`objects/<sha 前 2 位>/<后 62 位>` ⇒ GC 只要两层 `listFiles`，不用递归；
也不会出现"一个目录三万条目"。`objects/tmp/` 用**名字长度 ≠ 2** 天然躲开两层的分片扫描。

#### ② 三条防误删设计（缺一条就出"对象丢失"，症状极难查）

| 设计 | 挡的是什么 |
|---|---|
| `GC_GRACE_MS = 600_000` | 太新的对象一律不删。锁只管本进程；被强杀留下的半截状态、将来的多进程只能靠年龄兜 |
| `BULK_LOCK`（**静态**，等价桌面版 `RLock`） | 「对象已落盘、清单还没写」的空档里，这些对象在 GC 眼里全是孤儿 ⇒ 不持锁会被整批删掉，**而清单随后照样写成功** ⇒ 备份列表正常、一恢复才报「对象丢失」 |
| 先落对象、最后**原子写**清单 | 清单是唯一"不能删"名单来源，写坏了 = 内容真没了 |

`BULK_LOCK` 用 `synchronized`（Java 监视器天然可重入 = 桌面版 `RLock`：迁移内部还会调 `put`，要能重入）。

#### ③ `Backup.java` 改造

- `create`：`synchronized (Cas.BULK_LOCK)` 区间内逐个 `pool.put(f, null)` 收集 entries → 原子写清单。
- `restore`：v2 走 `pool.getTo(e.hash, to, true)`，**逐项容错**（池不可变 ⇒ 坏一项不影响别的项，
  不再"整份拒绝"，那会让用户一个文件都拿不回来）；v1 分支原样保留当迁移输入。
- 新增：`casBaseDir` / `allReferencedShas`（GC 的唯一"不能删"名单）/ `gcNow` / `scheduleGc`
  （去重 + application context + `MIN_PRIORITY`）/ `poolStats` / `hasLegacy` / `migrateLegacy` / `autoMigrateAsync`。
- ★ **池落点是 `<hub>/cas/`，故意不在 `<hub>/backups/` 里**：否则多出「用户把槽命名成 `objects`
  会撞池」的隐患（`Data.sanitizeSlot` 允许这个名字）。分两棵子树后 `deleteSlotBackups` /
  `renameSlotBackups` 天然碰不到池，零回归。

#### ④ 清单格式与迁移

| 标记 | 形态 |
|---|---|
| `mdt-backup 1` | `files/` 全量拷贝 + `md5  size  rel`（旧） |
| `mdt-backup 2` | 无 `files/`，`sha256  size  rel`，快照目录只剩一个 ~12 KB 的清单 |

`migrateLegacy`（幂等，`static synchronized`）四步**顺序不可颠倒**：
读 v1 清单 → 逐文件 `pool.put(f, md5Digest)`（**一遍 I/O 顺带验旧 md5**，不符则整份跳过）→
**原子写** v2 清单 → **最后**才删 `files/`。
入口：`MainActivity.onCreate` 收尾调 `autoMigrateAsync`（后台线程，不阻塞首屏）。

#### ★ 坑（F16 独有，都踩过）

1. 🔴 **`adb shell touch` 改不了应用外部存储文件的 mtime（跨 UID）**。
   `find … -exec touch -t 202001010000 {} +` 对 9 个对象**全部** `Operation not permitted`
   ⇒ 「把对象拨老，验证过期孤儿被删」在主机侧**做不成**，GC 的删除分支一度无法验证。
   ★ 正解：**在应用进程内** `File.setLastModified()`（文件属主就是应用，没有这个限制）。
   于是把它做成自检用例 —— 删除分支从此**可长期回归**，不再依赖手工拨时间。
2. 🔴 **自检必须能在「脏池」上通过**。池是**跨轮持久**的（这正是它的价值）。
   第一轮报 3 项失败，全部同一根因：测试内容固定 ⇒ 第二次跑时对象已在池里 ⇒
   「首次入库写出 0 B」假失败（**那是 CAS 的正常行为**）；池里 24 MB 历史对象 ⇒
   「池实占 < 逻辑总量」恒假。
   ⇒ **(a) 每轮用带 nonce 的唯一内容；(b) 断言一律用增量**（"造第二份快照前后池占用差 == 0"
   才是去重的真不变量）。**教训：跨轮持久的资源，断言不能用绝对量。**
3. 🔴 **`^= 0x5a` 是对合运算 ⇒ 负例会「静默假阳性」**。上一轮已把**同一个对象**翻过一次，
   本轮再翻同一字节 = 翻回正确内容 ⇒ 恢复反而成功、而「坏对象没被写出去」**照样通过**（它其实没坏）。
   ⇒ **篡改前先自证对象有效**（重算 sha256 与地址比对）。
   顺带确认池的假设：`put()` **只查存在性、不校验内容**（"池内不可变"是前提，不是保证）。
4. ⚠️ **`PoolStats.saved()` 的公式曾经写反**（`1-(logical-actual)/logical` ⇒ 得到占比而非节省率，
   真机 74.4% 报成 25.6%）。⚠️ **小数据自检同样测不出来** ⇒ 改成用**合成数字精确断言公式本身**
   （`SelfTest.savedFormula`）。
5. ⚠️ **断言"报告里必须出现某句话"时，一定要把原文打出来**（`L.add("恢复报告：" + oneLine(r))`）。
   否则失败时只能靠猜 —— 本次为定位这条白走了一段。
6. ⚠️ **外部存储 mtime 不完全可信**（观察到同一 sha 的对象 mtime 会变）。影响可控：
   mtime 只用于"年龄"判据，判错方向只会是"看起来更新" ⇒ GC 少删、不误删。

  现象：屏幕一直黑、`uiautomator dump` 报 `could not get idle state`、`screencap` 全黑，
  **看着完全像"主题把界面搞崩了"**。
  ⇒ dev 口在 `recreate()` 之前**必须 `intent.removeExtra(...)`**。
  （`onNewIntent` 那条路里 `setIntent` 存的就是同一个对象，清一次就够。）
- ★ **dev 报告别用会弹窗的那个口**：连调三次 `reportDev`（每次都 `alert`）⇒ 三层 AlertDialog 的 dim 相乘，
  整屏压成纯黑，和上一条的症状一模一样、**差点互相误判**。
  ⇒ 给"调用后马上 recreate"的口单独备了只落盘的 `writeDevReport`。
- ⚠️ **`GameSlot` 必须关掉 onResume 自查**：它的 onCreate 跑的是六步加载管线
  （dex 注入 / load native / 挂资产链），中途 `recreate()` 会把启动流程打断。
  它只闪一下就被游戏盖住，不值得冒险。
- ⚠️ **设置页改完必须自己 `recreate()`**：改动发生在当前 Activity 内，`onResume` 不会因为"配置变了"而重跑
  （用户会以为没生效，然后再点一次）。其它页面从设置页返回时才走 `onResume` 自查。
- ⚠️ **点坐标前必须 dump 确认前台**。本批验收时 `keyevent 4` 把存档页关掉、回到了主界面，
  本次沿用了**上一屏的坐标**，踩了盲点 —— 正好点中版本列表，**把游戏拉起来了**，只能立刻 `force-stop`。
  副作用：`last_version` 被写成 `io.anuke.mindustry`（原为 `com.github.tinylake.mindustryX`），
  事后按 `evidence/f8-continue-updated.png` 里的旧值改回。
  **盲点坐标的代价可能是"替用户启动一次游戏"** —— 这是本项目第一条"测试动作伤到用户数据"的记录。
- ⚠️ **dev 口要生效，目标 Activity 得在前台**：`am start --es dev_new_slot f8t` 在 MainActivity
  位于后台时，会把 intent 投给它那个实例（`Warning: ... delivered to currently running top-most instance`）
  却**不把界面带到前台**，于是命令"成功"、目录却没建出来。先把启动器带回前台再发。
- ⚠️ **尺寸又同**：本批 dev 与产品版**都是 150344 B**（含"只改注释"那一轮，第 6 次）⇒ 仍然只验行为。

### F15b —— 删掉存档页那两个重复的导入入口 ✅ 已完成（2026-10-01，第二十六轮）

**触发**：存档页顶部操作卡与槽菜单**UI 重复**（附两张截图）⇒ 需要解决。

**重复的精确来源** —— F15 的 ② 是**只加不减**的：为了"进 / 出口对称"，在槽菜单里补了
「导入存档（.msav）」「导入整槽（zip）」，但**原样保留了**存档页那两个入口
（F15 注释里写的理由是"先拿到文件、后想落点的人走那条，两条路各管一种直觉"）。
⇒ 同一个界面上出现**两组语义相同的入口**：

| 存档页顶部 | 槽菜单 | 是否重复 |
|---|---|---|
| 导入 .msav | 导入存档（.msav）… | 🔴 **完全重复** |
| 导入整槽（zip） | 导入整槽（zip）… | 🔴 **完全重复** |
| 新建槽 | —— | 否（造槽本身，不针对某个槽） |
| 数据根体检 | —— | 否（**全局**维护，与槽无关） |

**裁决：删存档页那两条，保留槽菜单**。理由是槽菜单那条**严格更优**：
导入的落点必然是某个槽，从槽进去时目标已知、**少一次"选槽页"**，
而且槽菜单里那条正好和「导出存档 / 导出整槽」按介质成对。
⇒ 存档页顶部操作卡只剩「**无槽语境**」的两项（新建槽 / 数据根体检），语义不再与槽菜单交叉。

**续（同日）—— 槽菜单四条文案的介质标注对称**

删完重复入口后又暴露出一个疑点 —— 「导入存档」有入口，却看不到 `.msav` 导出的标注 ——
因为槽菜单四条里只有三条标了格式，`slot_op_export_save` 写的是**光秃秃的「导出存档…」**。

| 文案键 | 改前 | 改后 |
|---|---|---|
| `slot_op_import_save` | 导入存档（.msav）… | 不变 |
| `slot_op_export_save` | **导出存档…** | **导出存档（.msav）…** |
| `slot_op_import_slot` | 导入整槽（zip）… | 不变 |
| `slot_op_export_slot` | 导出整槽（zip）… | 不变 |

**根因**：F15 补四条时按"介质成对"排了**顺序**，但**没有把标注也做成模板** ——
四个字符串各写各的，漏掉一个没有任何机制能发现（编译过、跑得起来、菜单看着也正常）。

**功能核实（结论：没问题，只缺标注）**：`promptExportSave()` 取的正是 `saves/` 下**原始文件**，
`fs[w].getName()` 直接作 SAF 建议名 ⇒ 导出的**就是** `.msav`，F6 已有真机 md5 佐证。

★ **纪律**：**不对称的文案会让人怀疑功能不对称**。成对出现的入口，文案必须逐字段对齐
（介质 / 省略号 / 语序）—— 一个符号的疏漏就要赔上一轮追问。

**验收**：真机 dump 槽菜单九项，四条标注齐全（`evidence/f15b-slot-menu-symmetric.png`）；
APK 内读回 `slot_op_export_save = "导出存档（.msav）…"`；产物仍 **158459 B**
（**改文案不改体积**，必须读 APK 内容而非看数字）。
