# 版本号与发布规则

> 2026-10-24 定案。以后发版按这里走；**改规则先改这份文档**。
> 本文只管「版本怎么叫、怎么滚、发到哪」；构建命令见 [DEVELOPING.md](DEVELOPING.md#构建)，
> 签名密钥与网络排障在维护者记录里（不入库）。
> ⚠️ 本文**不预设下一版叫什么、什么时候发** —— 那是发布时由维护者拍板的事。

## 0. 先分清几个号

| 号 | 是什么 | 谁定 | 例子 |
|---|---|---|---|
| 启动器版本 `versionName` | 用户看到的版本 | 发布时定 | `0.7.0-preview` |
| `versionCode` | Android 判升级用的整数 | 发布序号 | `7` |
| 插件接口版本 | `PluginHost.API` / `PluginHost.API_MIN` | 接口变更时 | `28`（以 `PluginHost.API` 为准，现查） |
| 游戏版本 | 官方 APK 自己的 `versionName` | 游戏作者 | `8-official-160` |

开发轮次（「第 226 轮」）只是内部记录，**不进版本号**。

## 1. 版本名

格式：`MAJOR.MINOR.PATCH[-preview|-rcN]` —— **三段，`.0` 不省略**。
历史 `0.1` ~ `0.6` 是两段写法，不回改；从下一个版本起按三段写。

| 段 | 管什么 | 例子（示意） |
|---|---|---|
| MAJOR | 破坏兼容：数据要迁移、插件接口基线往上抬、换签名、删功能 | `1.0.0` → `2.0.0` |
| MINOR | 加功能，旧数据与旧插件照常能用 | `0.7.0` → `0.8.0` |
| PATCH | 只修问题：不加功能、不加接口、不改数据格式 | `0.7.0` → `0.7.1` |

### 怎么滚

| 这次发布 | 0.x 阶段 | ≥ 1.0 |
|---|---|---|
| 只修问题 | PATCH+1 | PATCH+1 |
| 加功能（兼容） | MINOR+1，PATCH 归零 | MINOR+1，PATCH 归零 |
| 破坏兼容 | **MINOR+1**，并在发布说明里点名 | MAJOR+1，其余归零 |
| 进 1.0 | 显式决定（见第 2 节），不是滚出来的 | — |

> 0.x 里 MINOR 就是「可能不兼容」的信号；破坏兼容不抬 MAJOR —— 那会把版本顶到 1.0，
> 等于错误地宣告稳定。

### 后缀

| 后缀 | 功能状态 | GitHub | 用途 |
|---|---|---|---|
| `-preview` | 还会加功能 / 改接口 | Pre-release | 0.x 的常态 |
| `-rcN` | 冻结，只修问题（同一个版本依次 `rc1`、`rc2`…） | Pre-release | 进 1.0 前至少一个 |
| 无 | 稳定 | 正式 Release | 1.0 起 |

比较顺序：`-preview` < `-rc1` < `-rc2` < … < 无后缀；数字段按数值比。

**三条硬约束**

1. **一个版本名只对应一个二进制。** 内容变了就 PATCH+1；不许同一个版本名重打一份发出去
   （崩溃报告与校验值会对不上）。
2. **版本号只增不减；发布出去的 tag / release 不删。** 删了会让 `versionCode` 计数回退、
   下载链接断、老用户装不上新包。
3. **0.x 也不随便弄坏用户数据。** 真要破坏，发布说明里点名；能迁移就带迁移。

## 2. 1.0 的门槛

缺一条就继续 0.x：

1. README 里 v1 范围（离线功能集）做完；
2. 插件接口基线冻结：之后只加不删，`API_MIN` 不动；
3. 槽 / 数据格式稳定：跨版本能读，或有迁移；
4. 至少一个 `-rcN` 周期没有 P0，且真机基础功能全过；
5. 同一把签名密钥的升级链验过（`versionCode` 递增、能原地升级）。

## 3. versionCode

`versionCode` 是**发布序号**：从 1 起，每发一个 APK +1，不重用。
已发 6 个（`v0.1-preview` ~ `v0.6-preview`，`vc` 1~6）—— **数字会过期，发版时现查**。

**算法**：`vc = 已有发布 tag 数 + 1`（2026-10-24 时是 6 ⇒ 7），即

```bash
git tag -l 'v*' | wc -l    # 现在是 6 ⇒ 下一个 vc = 7
```

- 只在 `v*` 命名空间给**发布**打 tag；别给文档 / 实验打 —— 会把这个计数带偏。
- 发布 tag 的说明最后一行写 `vc=N`（`git tag -n` 能直接看到）。
  对得上：这个 tag 的 `vc` 应等于**包含它在内**的 `v*` tag 总数（打完 tag 再数一遍）。
  `v0.1`~`v0.6` 当时没写，按顺序对应 1~6。
- 已推送 / 已发布的 tag 不删；只在本地、还没上传过的 tag 可以删（删前确认没发布过资产）。
- 发布出去的包不重打。内容要变 ⇒ PATCH+1（新版本、新 vc）。
- 本地 / 开发构建不参与编号：清单里那个 `1` 只是占位，不代表发布版本。

## 4. 什么时候滚版本

- **只在发布时滚，不按开发轮次滚。** 一次发布可以包含任意多轮。
- 发不发、发哪个号，由维护者在发布时拍板；本文不预设下一版是 preview 还是 rc。
- 一个版本只装一类变化（加功能 **或** 只修问题）；混在一起就没法按第 1 节定号。
- 公开说明里写过的计划（比如「下一版进 rc」）如果没做到，**下一次发布说明要明说计划变了**，
  不能悄悄改。

## 5. 发布物

- **tag**：`v` + 版本名（annotated），说明最后一行 `vc=N`。
- **release 标题**（示例）：
  - preview：`v0.7.0-preview —— 第七个公开预览版（功能未完成）`
  - rc：`v1.0.0-rc1 —— 第一个候选版（功能冻结，只修问题）`
  - 稳定：`v1.0.0 —— 正式版`
- **资产名固定** `mdt-launcher.apk`：不要把版本写进文件名，下载链接才稳定。
- **发布说明以 GitHub 为唯一正文**，仓库里不复制第二份（复制必漂）；
  本地底稿放 `.dsh/release-notes-<版本>.md`。
  - 结构：这是什么 / 这一版（相对上一版）/ 装之前先看 / 文件与校验。
  - 只写用户看得见、做得到的变化；内部词（接口号、路径、白名单…）先 grep 再发；
    **上一版就有的不算新增**。
- preview / rc 勾 `--prerelease`；稳定版不勾。稳定版出来之前 `releases/latest` 是 404 ——
  以后做「检查更新」不能只读 `latest`，要读 releases 列表并按上面的比较顺序排。

## 6. 发版前检查清单

1. 工作树干净，HEAD 就是要发的那个提交；
2. 自检全绿；**真机基础功能过一遍**（启动游戏 / 切槽 / 导入导出这几条）；
   ★ **至少两个 API 段各跑一遍**（2026-10-25 起是硬要求：老系统上真出过"只有用户能复现"的启动崩溃）
   —— 手边没有真机就用模拟器（**本机常备 `system-images;android-26/29/34/35`**，AVD 同号；
   其他版本 `sdkmanager --install "system-images;android-NN;default;x86_64"` 现下，约 3~4 GB 一个），
   判据是「发布签名的那个 APK」能进游戏主菜单，**不是** debug 版能跑；
   2026-10-25 的完整矩阵（API 26~36）见 `.dsh/memory/next/57` 与 `.dsh/evidence/round245/matrix.txt`；
3. `vc` == `git tag -l 'v*' | wc -l` + 1；
4. 发布构建用发布密钥；`apksigner verify --print-certs` 指纹对得上
   （换密钥 = 用户只能卸载重装 = 丢槽）；
5. `aapt2 dump badging` 核对 `versionCode` / `versionName`，且没有 `application-debuggable`；
6. sha256 / 大小 / 指纹**从产物现算**，不手抄；
7. tag → push → `gh release create`（preview / rc 加 `--prerelease`）；
8. 发完在 `next/40` 记一行内部批次（对外历史就是 GitHub Releases）。

## 7. 历史版本怎么算

`v0.1-preview` ~ `v0.6-preview`（2026-10-04 ~ 10-18，`vc` 1~6，全是 Pre-release，
两段式写法）。逐版说明在 GitHub Releases；内部批次与推送记录在 `next/40`。

- **不回改**：tag、release 标题、说明、资产名一律保持原样。改 tag = 删了重打 ⇒ 旧下载链接断、
  已经装了的用户对不上号，也违反「发布出去的 tag 不删」。
- **比较时按 `x.y.0` 读**：`0.6` 当作 `0.6.0`，所以 `0.6` < `0.7.0` 成立；**字符串 / 标签本身仍写 `0.6`**。
  以后做「检查更新」的比较器要按这条归一化，别拿字符串直接比。
- **`vc` 不补**：旧 tag 说明里没有 `vc=N`，不去补（补 = 重打 tag）；`vc` 1~6 继续有效，下一个从 7 起。
- **只对最新一版出补丁**：例如最新是 `0.6`，可以出 `0.6.1-preview`（PATCH+1）；
  更老的线（0.5 及以前）不再回补，修复一律进新版本。
- 旧安装里「关于」页显示 `0.6 (build 6)` 是正常的；升级到新版本后自然变成新号。
